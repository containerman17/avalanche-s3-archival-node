## Principle [BUILT]
Bodies + headers + proposervm extras are the only ground truth. State history, receipts, logs, all indexes are caches rebuildable by re-execution (~5-6k blk/s). Re-executing one block was the universal primitive; after the 2026-07-20 ruling logs/receipts are STORED, and re-execution remains only for traces, createAccessList, and verification.

## Architecture [BUILT]
- Immutable per-epoch files, self-described by filename: `epoch_<startblock>_<blockcount>.epoch`. No catalogue; startup = readdir + read footers. Height->epoch = binary search over the readdir table.
- Epoch boundary rule: FIXED TX COUNT per epoch. An epoch seals at the first block whose cumulative tx count reaches the threshold. Uniform file weight by construction, immune to throughput growth (SAE ~10x). Deterministic and bit-identical: cumulative tx count is chain content.
- Staging during sync is separate and disposable: height-bucketed arrival segments (100k blocks per bucket, `arrival_NNNNN.log` + `index_NNNNN.log` sidecar). The cooker consumes staging forward behind the executor, cuts epochs by tx count, and deletes a staging bucket once all its blocks are cooked. Buckets and epochs do NOT align 1:1; staging exists only on the machine doing the initial sync.
- Epoch sections: bodies (zstd frames of 16 containers + published 512KB dict; measured 2026-07-17 on 112k real containers: 2.24x blended, 34us random-access decode; frame-256 buys +5% for 14x slower access, rejected), headers, proposervm extras, state write-log SST of (account,key,^block)->NEW value rows, EF fp48 tx index, log posting lists (position-agnostic addr/topic -> EF block lists), per-epoch key bloom, stored-logs sections, footer (offsets, version; NO embedded signature: signing is manifest-level so independent syncs stay bit-identical, decided 2026-07-20).
- Tx index: Elias-Fano over sorted 48-bit hash fingerprints + bit-packed block numbers. Verify by decoding the candidate block. No MPHF (EF matches its size, simpler). Validated on 12M real Fuji txs 2026-07-17: 288ns lookups, 0 false positives. EF cost is density-dependent (log2(U/N)+2), so PER-EPOCH sections run ~27-28 bits/tx; duplicate fp48s are real (~2,600 pairs at 1.2B txs), so the lookup API returns a candidate LIST. Atomic txs live in extdata, not the eth tx list, so they are outside this index.
- Compression: per-epoch zstd dict trained AT SEAL TIME on that epoch's raw containers (user directive 2026-07-18, supersedes one-global-dict; the dict ships inside the epoch file so distribution stays self-contained). Trainer is the zstd CLI (pinned v1.5.7) with a start-block-derived `--dictID`: klauspost's `dict.BuildZstdDict` is map-iteration nondeterministic (measured) and would break bit-identical files. Encode/decode is klauspost zstd, SpeedBestCompression.
- Sealing parameters (constants in `state/epoch.go`): PRODUCTION EPOCH_TXS=10,000,000 (user-confirmed 2026-07-20: ~120 epochs of ~4GB for full mainnet, ~10-day seal cadence, hot tail 1-4GB; 100M rejected: 3-month fill, 40GB files; 25,000 was corpus-stress only), frame-16 bodies/headers, 512KB dict target, 64KB SST blocks, bloom 10 bits/key x 7 hashes.
- Epoch format v3 (2026-07-28 user decision): contract code ships INSIDE the epoch as `'c' | hash | zeros` rows in the SST keyspace ('a' < 'c' < 's'), so it rides the existing sparse index and key bloom and needs no new section. An epoch carries the code of every account row it writes (placement rule, see Torrent distribution). Blob rows are not state diffs: verification and the base fold skip them.
- Epoch format v2 (2026-07-20 user ruling), folded into v3: stored-logs sections are MANDATORY, not a flag. Per log-bearing block: addr/topics/data/txIndex records (logIndex positional, txHash+blockHash derived from bodies at read time), frame-16 with a DEDICATED 128KB logs-trained dict (measured better than the container dict). Per tx-bearing block: uvarint gasUsed + status byte (cumulative gas by prefix sum; bloom/contractAddress/effectiveGasPrice derived). eth_getProof stays impossible; getLogs posting lists still provide candidates, the stored sections replace only the response construction.
- NO UPGRADE PATH (user ruling 2026-07-28). v3 is the only format the code can read: `OpenEpoch` refuses a v1 or v2 file by name ("format v2, unsupported: delete the corpus and resync") and there is no re-seal, no section surgery, no migration. The corpus is disposable, so a format change is paid for by a from-scratch sync, not by rewriting files.
- No database anywhere. Hot period = append-only logs + RAM maps; sealing = rewriting those logs into sorted compressed sections. Everything mmap'd; recent blooms pinned, old ones page-cached.
- Historical state read at block N: LRU, then hot RAM map, then per-epoch blooms newest-to-oldest from epoch(N), one SST seek on first hit, then the floor (genesis alloc today).
- getLogs: intersect posting lists -> candidate blocks -> read stored logs sections -> exact filter. Range capped at 10k blocks. No re-execution.
- Tip following: REAL snowman consensus (ported from flatstate), validator set from 2+ cross-checked P-chain RPCs (>=95% stake agreement). Ingest: naked p2p GetAncestors racing peers (deforestationdb-proven), no full node.

## RPC surface [BUILT]
Full parity with a coreth v1.14.2 node across eth, web3, net, txpool, debug, minus the exceptions below. Filters and WS subscribe exist; personal/admin are N/A by design (no keystore, no node-ops surface). Notable entries:
- `debug_getModifiedAccountsByNumber/ByHash` at ANY height straight from the per-block write capture (the differentiator; a normal node needs both boundary states live). Caveats: union-of-writes counts a value rewritten to its original; capture order, not hash order; needs the raw writelogs, so epoch-only nodes get a clean error; range capped at 10k blocks.
- `eth_getProof`: N/A. Historically impossible by construction (no per-block tries). At the tip it is a Firewood limit, not ours: ffi v0.3.1 has no EIP-1186 path proofs (v0.7.0 added `EthGetProof`, bump attempted 2026-07-22).
- `eth_sendRawTransaction` / `sendTransaction` / `fillTransaction` / `resend`: documented errors, no mempool or relay yet.
- `debug_dumpBlock` / `accountRange` / `storageRangeAt`: tip-POSSIBLE (ffi `Revision.Iter` can range-read the frontier) but the replay process holds the exclusive Firewood handle; revisit when the unified node owns one handle.
- `avax_*` atomic tx/UTXO methods: unindexed, out of scope.
- Tolerances vs the public archive RPC: it refuses the whole debug namespace, createAccessList, getProof, and the internal-eth methods (-32601), so those gates are self-consistency or cryptographic rather than A/B.

## Verification without re-execution [BUILT]
Third parties verify downloaded epochs with NO EVM execution: (1) state: stream SST post-image diffs from genesis into a throwaway Firewood, commit per block, root must equal `header.Root` every block; (2) bodies: recompute txRoot per block from verbatim containers; (3) logs/receipts: v2 sections reconstruct full receipts (cumGas prefix sum, bloom from logs) and recompute receiptsRoot; (4) headers: parent-hash chain to a trusted anchor. Estimated 5-10x cheaper than replay (~1 day for full mainnet vs ~9 days); (2)+(3) are embarrassingly parallel.
Two bootstrap modes: plain (download-only, exit when the manifest is complete) and `--verify` (download + PIPELINED sequential verification: a cursor and one throwaway Firewood chase the contiguous prefix as epochs complete out of order). Failure names the epoch and exits nonzero. Slab-parallel verification (self-anchoring constructed frontiers) is a future many-machines option, not built.

## Torrent distribution [BUILT]
Epochs are deterministic and bit-identical across builders, so their sha256 and v1 torrent infohashes are stable facts shipped in a committed manifest (`epochs.manifest` at the repo root, regenerated by `epochdb manifest`). Seeding (`epochdb seed`) is always-on for whatever epochs are local: verify sha256, skip+warn on mismatch, announce on DHT + two public trackers. Leeching happens at startup behind `serve --fetch-epochs` or standalone `bootstrap`: diff manifest vs local, magnet-fetch missing epochs (4 concurrent, `--epoch-timeout` default 5m), sha256-verify, tmp+rename in.

Contiguous-prefix rule after an incomplete fetch: coverage is the contiguous epoch range from genesis (`EpochSet.CoveredEnd`). State, receipt, and log queries above the first gap return a clean "missing epoch epoch_X" error (`RequireCovered`). ASYMMETRY, deliberate: bodies and tx-by-hash above the gap still serve (epoch-local reads) while state correctness requires full descent to genesis. `SealedEnd`/head still reports the highest local epoch.

CODE IN THE EPOCH FILE, format v3 [BUILT 2026-07-28, user decision 2026-07-28]. The gap: contract code is NOT in the epoch format and NOT in the manifest, it lives only in the standalone `code.log` (`state/codestore.go`, read at `state/overlay.go:433`), which the executor writes as a side effect of replaying blocks. So a node bootstrapped purely from torrented epochs holds every block, state value, log, and account code HASH, but not the code, and the first `eth_getCode` or contract-touching `eth_call` fails. Never caught because every gate ran on a box that had built its own corpus and therefore had `code.log` locally.

Decision: code belongs IN the epoch, as `'c' | hash` rows in that epoch's SST keyspace, exactly the trick `state/base.go` already uses ('a' < 'c' < 's' share one sorted keyspace). Code lookup then rides the existing per-epoch bloom and descent with no new machinery, and an epoch file becomes genuinely self-contained, which is what the torrent contract always claimed. `code.log` stays as the hot-tail store for code deployed above the sealed end. Limited-history nodes are unaffected either way (state sync hands over code blobs, and the base file already carries them as 'c' rows).

PLACEMENT RULE, decided by measurement on the real 0-10M corpus (2026-07-28): an epoch carries the code of EVERY account row it writes, not only of the code first deployed inside it. Measured on the 7 production epochs: first-deploying-epoch would cost 288MB of blobs, every-referencing-epoch costs 478MB, i.e. +190MB (+0.6%) on a 32.6GB corpus, 57-87MB per epoch before compression. That price buys the invariant that WHICHEVER epoch answers the account read also carries that account's code, derived from the epoch's own account rows: no earlier epoch and no raw writelog, only code.log for the blob bytes. DETERMINISM: the set is a pure function of the epoch's own post-image rows (chain content), blobs are content-addressed, and `buildSST` sorts them, so map iteration order, wall time and local file layout cannot reach the bytes. Sanity check on the corpus: every code hash referenced by an account row over all 10M blocks is present in code.log, zero misses, and 34,711 of code.log's 35,011 blobs are referenced at all.

AS BUILT: footer version 3, same 16 sections and same layout as v2 (code rows live inside the SST, so nothing new is indexed). Read path is code.log, then epochs newest-to-oldest bloom-gated, then the base file, then the genesis alloc (alloc code is never deployed by a block, so no epoch carries it). There is NO in-place upgrade: the v1 -> v2 append path and the v2 -> v3 section surgery were written, proven on a real production epoch, and then DELETED 2026-07-28 per the no-migration ruling. `OpenEpoch` reads the footer version, refuses anything but v3 by name, and that is the whole of the compatibility story, so `serve` needs no version check of its own. Two absent-file rules relaxed so a torrent-bootstrapped node can start at all: a missing `code.log` and a missing `misc.log` are now empty stores rather than open errors (nothing ever executed there); `OpenHistory` still refuses a dir with no buckets, epochs or base file. `epochdb manifest` regenerates cleanly; every infohash changes, which is expected (a v3 epoch is a different file). Per the 2026-07-28 ruling there is no re-seal of the existing mainnet corpus: data-fresh stays v2 and frozen, and the v3 corpus comes from the from-scratch sync at the end of the work order.

## Entry points, complete tiering

2. Files-as-API for same-machine processes (beats any socket protocol): sealed epochs are immutable mmap-able files (zero coordination); the hot tail is append-only buckets + fixed-record sidecars + the exechead watermark, readers chase sidecar growth. Proven in production: cook/bench/verify ran beside live writers via `OpenReadOnly`. Contract: accepted, durable, ~seconds fresh. NOT single-block files (fs metadata churn, nothing gained). [BUILT, shipping it as a library is PLANNED]
3. HTTP/WS JSON-RPC for remote/standard clients (~30k req/s ceiling is the wire's). [BUILT]
4. gRPC: only if remote high-throughput typed access is ever needed; locally dominated by tier 2. Not built, probably never.

## Single-machine HA via flock [PLANNED]
N identical processes; ONE holds an exclusive flock and is the writer (follower+sealer); all others serve reads from the same files AND wait in a BLOCKING flock() as the failover pool (no polling: the kernel releases the lock on writer death, even kill -9). Takeover = acquire lock, run the proven crash recovery (torn-tail truncation, walk back to the Firewood root, re-execute the gap), continue. Readers never blink. Per-machine only (cross-machine needs real leases). Equal motivation: dev/prod cohabitation on one machine. Block delivery to reader processes must be sub-5ms: split visibility from durability (writer `write()`s per block so bytes are visible via page cache instantly, fsync stays batched), wake slaves via inotify on the sidecar (sub-ms) or a tipbus-style mmap seq counter (~100us, flatstate-measured). The bleeding tail is visible-but-provisional: a writer crash may truncate behind what a slave saw, so the lockfile carries a generation counter and slaves re-validate their last blocks on writer change.

## Limited-history mode [steps 1 and 3 BUILT, step 4 PLANNED] (user decisions 2026-07-28)
Disk-bounded deployment for a validator host that needs current state and fast tip, not deep history: two validators share a 2TB disk with ~600-700GB free, and full-mainnet epochdb is ~590-690GB of epochs plus ~100-150GB of Firewood. Target ~200GB.

THE ONE STRUCTURAL CHANGE: state reads descend epochs newest-to-oldest and fall through to a floor (`History.search`), and that floor is the genesis alloc. That is the only reason coverage must reach genesis. Replace it with a flat live-state base file at block B: every read at N >= B is answered by (raw tail, epochs above B, base file) and nothing below B exists. Deleting epochs WITHOUT swapping the floor is silently wrong, not an error (the descent misses and reports "account does not exist"), so the floor check is the safety property of the whole feature.

Decisions, REWRITTEN 2026-07-29 (the original 07-28 rulings assumed network state sync; superseded by the snapshot design, see "Our own state sync"): the bottom is a SNAPSHOT from the manifest, preimage-keyed, produced by a pruning node. B is the snapshot's boundary (canonical, cumTx in the footer), so sealing above B cuts canonical epochs. Firewood and its per-block root check stay, so ~125GB is a fixed cost and not a lever. Gate: A/B vs the public network RPC at tip.

Base file (`base_<block>`, implementer's call): a new file kind, not an epoch, because hashed keys do not fit the 53-byte preimage row. Reuses the epoch machinery (zstd-framed sorted blocks, sparse index, keybloom, mmap, versioned footer) with key layout `kind(1)|keccak(addr)|keccak(slot)` = 65B, values only (no block numbers, the file IS state at B), a code section carrying every live account's code blob (also the fix for the code.log gap on this path), and the 256 headers below B so eth_call BLOCKHASH works in [B, B+256). The footer records B and the state root, verifiable by rebuilding into a throwaway Firewood and comparing to `header(B).Root`.

Call sites that change: floor check plus base lookup in `History.search` (`state/overlay.go`); `EpochSet` coverage anchors at the floor and `RequireCovered` reports "pruned below block B" (`state/epochread.go`); the delete map only needs epochs above B (the base file is a post-image, so no pre-B deletion or resurrected slot can exist); `OpenHistory` must open with a base file and no buckets; `serveMain`'s block-hash scan starts at the floor, not 0; `rpc/{tx,block,logs}.go` coverage errors become pruned errors, and below-floor tx-by-hash returns a typed pruned error rather than null (a bot silently seeing null for a real tx is the bad failure mode).

Contract: full archive semantics from B forward, nothing below B, B printed at startup. Budget ~165-180GB full mainnet (base ~20 + code ~5 + 0-3 epochs + raw tail ~15 + Firewood ~125). Epochs above B accumulate ~4GB per 10 days, so a fold-down step is eventually needed and is deliberately NOT in this design (a hashed bottom cannot fold). Lazy-attach of old epochs on query stays rejected: fine for epoch-local reads, useless for state, since a tip read can hit a key last written years ago.

AS BUILT (step 1, 2026-07-28, `state/base.go` + `epochdb snapshot` + floor-aware read path): file `base_<block>`, footer-last with magic at both ends, four sections (sst rows `key65|uvarint vlen|value` in ~64KB zstd blocks, 73B sparse index, keybloom identical to the epoch bloom, and one zstd frame of the 256 headers below B decoded at open). Code blobs are ROWS, not a section: kind 'c' | hash | zeros, and since 'a' < 'c' < 's' they share the one sorted keyspace, index and bloom. No zstd dict (65B random-hash keys plus short values are not worth training one). Builder is a k-way heap merge over the already-sorted bucket and epoch cursors, then hashed rows scatter into 768 on-disk prefix buckets sorted one at a time, so RAM stays bounded. Measured on real mainnet at `--at 1000000`: 24.5MB for 586,687 live rows + 559 code blobs (~42 B/row), built in 2m35s, and `--verify` PASSES, the rows rebuild `header(1000000).Root`. So the earlier "base ~20GB" budget line is a FULL-MAINNET estimate: at 10M blocks the base is ~2GB.

Read path as built: `History` gained a floor from `OpenBase`; `search` rejects below-floor with a typed `state.PrunedError` before any descent and consults the base after epochs miss; the genesis-alloc fallthrough survives only when floor == 0; code and the BLOCKHASH headers fall back to the base; `EpochSet` coverage anchors at the floor; the deletes map skips everything below it; `serve` prints `LIMITED HISTORY: floor=N`. RULINGS: an unknown tx hash on a pruned node returns an ERROR, not null (a hash carries no height, so "below the floor" is undecidable, and null would let a bot conclude a real tx never existed); the JSON-RPC code is the generic -32000 that geth-family pruned nodes use, with the floor in the message. The gate is `ab-bench --floor N` with `--local` on the pruned node and `--remote` on a full one (a separate ab-prune command was written and DELETED as a duplicate: the ab-bench family already does local-vs-remote, the floor only adds boundary heights at F/F+1/F+255/F+256 and a below-floor refusal pass).

THE MISS RULE (fixed 2026-07-28 after an adversarial review reproduced silent wrong state): a state row found at or BELOW the floor is a MISS, not an answer, so the descent falls through to the base file, which is the authority for everything at or below B. Per ROW, not per source, because a raw bucket can straddle the floor (the gate run had bucket 49 covering 4,900,000..4,999,999 with floor 4,904,340). Without it, an account SELFDESTRUCTed below the floor read as gone from AccountAt while StorageAt still returned its pre-destruct slot value, since the deletes map deliberately skips below-floor records while the descent did not. Gated on floor > 0, so a full node is byte-identical to before. Same review round fixed: `eth_createAccessList` never checked `statedb.Error()` and so returned a fabricated access list built on all-zero state below the floor; `eth_getRawTransactionByHash` and `debug_getRawTransaction` answered "0x" instead of the pruned error (only two of the four tx-by-hash methods had been wired); `eth_getBlockByNumber` said "container N missing" instead of naming the floor; `BuildBase` silently re-floored a dir that already had a base (now refused: base-merging is the deferred fold-down step); the base header window became [B-256, B] so the file is self-contained at its own floor.

GATE RESULT (2026-07-28, floor F = 4,904,340, the epoch_1 boundary): base_4904340 is 0.37GB for 8.8M live rows (~42 B/row), built in 17m44s, `--verify` PASS rebuilding header(F).Root in 11s. Pruned dir assembled by hardlinking the epochs above F, so it costs 0.37GB of real disk. `ab-bench --floor` 6,016 state probes ZERO mismatches with 80/80 below-floor probes refused; after the fixes all four A/B commands run pruned-vs-full clean (ab-bench, ab-bench-tx, ab-bench-logs, ab-bench-rpc), each with its own below-floor refusal pass. Teeth check: pointing `--local` at the FULL node while claiming a floor fails 46/46 as it must. Non-zero equality at F proven on real values (WAVAX balance, nonce, totalSupply via eth_call, code hash, storage slot 0). Pre-existing tool bug found and fixed in passing: `diffBlockReceipts` reported a mismatch when BOTH sides errored, which fired on raw-tail heights even full-vs-full.

RE-GATE after the fixes (2026-07-28): all four gates clean again (5,008 + 1,198 + 120 + 1,009 probes, zero mismatches, 86 below-floor probes zero answered). Two things that run proved rather than assumed. (1) The miss rule works on real mainnet data, not on absence of data: a node was built with `cp -al` of the FULL corpus plus the base file (the synthetic-floor config, where every below-floor row is physically present), 11,464 accounts deleted below F were scanned, and the 5 with live pre-delete storage all read zero storage and empty code exactly like the full node. (2) The base's code rows really serve: a hardlink tree with an EMPTY code.log answered 500 real sub-floor contracts with non-empty code, byte-identical to the full node. Also found there and fixed: `findTx` walked tx-index candidates with NO floor check, so a node still holding below-floor containers answered `eth_getTransactionByHash`/`getTransactionReceipt` below the floor (5 of 10 refusal probes answered). It was the last floor enforcement that depended on data being absent instead of on a check. Block F is deliberately asymmetric: state AT F answers from the base, the BODY of F does not exist (it lived in the dropped epoch), and the error now says so.

RESOLVED 2026-07-28 by format v3: a missing `code.log` (and a missing `misc.log`) is an empty store, not an open error, since v3 epochs and the base file carry the code. The wrong-data-dir guard stayed where it already was: `OpenHistory` refuses a dir with no buckets, no epochs and no base file.

AS BUILT (step 3, 2026-07-29, `statesync/` + `state/basebuild.go` + `epochdb statesync`): the base file now comes from the network. `epochdb statesync --network mainnet --data <dir>` dials p2p, takes the accepted frontier, walks containers down by parent ID to B-256 (so header(B) is anchored to the frontier by a hash chain, not asserted by an RPC), picks B as the newest 16384-boundary at least 256 below head, then runs the ported loader and writes `base_<B>`. No node runs anywhere and no history is replayed.

PORTED from flatstate's `follower/sync`, per the ruling: the two-phase shape and its reason (phase 1 walks ONLY the account trie and queues storage roots, phase 2 drains the queue; peers serve leaves optimistically from their CURRENT snapshot and diverged ranges fall back to slow trie iteration, so both cost and failure grow with the AGE of B, and flatstate measured the inline account+storage walk starving at 18% coverage after an hour), the 256-segment account walk, the open-ended-request-plus-local-truncation trick (`VerifyRangeProof` cannot verify an EMPTY bounded response, so a bounded request for a range's empty tail retries forever), the giant-storage-trie fan-out, code first-claim, and the whole peer discipline (global in-flight cap, per-peer cap, 3-minute cooldown, random spread instead of PeerTracker.SelectPeer). NOT PORTED: the entire LMDB resume layer (segment bitmap, per-segment and per-sub-range watermarks, 0x09 pending-storage queue rows, single-writer bundle pipeline and its barriers) and the final code sweep that existed to close crash gaps. All of it exists to make a random-access KV store resumable; the base builder is an append-only spill sorted once at the end, with nowhere to read a watermark from and no commit-order invariant to defend. DEBT: a killed run starts over. flatstate's own net stack did not come across either, per the unified-node plan: the loader rides epochdb's `fetch` network, which gained AppRequest/AppResponse (`fetch/apprequest.go`) beside its GetAncestors, so state sync and the header walk that anchors it are one dialed session.

THE ROOT GUARANTEE, precisely. Two independent checks, and the file only reaches disk if both pass. (1) Wire-level: every leaf response is verified by the reused coreth sync client as a merkle RANGE PROOF against the root we asked for, and every code blob against its hash, so no peer can insert a row that is not in the trie of that root, and the client's verified `More` flag plus contiguous `lastKey+1` continuation means a peer cannot silently skip a range either. That is a guarantee about ROWS. (2) File-level, which is the one that matters, because (1) says nothing about whether OUR walk covered the keyspace: `BaseBuilder.Finish` streams the finished row set through `trie.StackTrie` and recomputes every storage root (compared to the root each account row claims) and then the state root (compared to `header(B).Root`), refusing to leave a file behind on mismatch and also refusing an account that claims a storage root whose slots never arrived. So a `base_<B>` on disk is proof-carrying: its rows rebuild `header(B).Root` exactly, and the only remaining trust is that header(B) is the real block B, which comes from the peer-majority accepted frontier plus a verified parent-hash chain down to B (real snowman consensus on the frontier is the obvious upgrade and is not wired here).

CONCURRENCY IS THE ONLY LEVER THAT MATTERS (measured 2026-07-29, both runs on the same pivot minutes apart). A peer takes ~2s to serve one 1024-leaf range, so throughput is purely outstanding-requests, not bandwidth. `--workers 32` (flatstate's default) gave 14k rows/s; `--workers 384 --inflight 1536 --per-peer 6` gave 125-135k rows/s, a 9.5x speedup, with the failure rate staying negligible (771 failed requests over 90.9M accounts). The global in-flight semaphore is what makes this safe to turn up: workers can exceed it freely and simply queue locally, so the cap, not the worker count, is what peers ever see. Do NOT raise inflight to flatstate's measured collapse point (~4000 outstanding degenerated to <20 req/s). 32 workers is the wrong default at 580 connected mainnet peers.

HASHED KEYS ARE NOT A WALL, for the base file OR for the Firewood frontier (settled 2026-07-29 with a runnable proof, `verify/hashedfrontier_test.go`; supersedes the step-1 belief that a hash-keyed file can never be re-verified). Two independent facts. (1) A merkle-patricia root needs hashed keys in ascending order and nothing else, so `trie.StackTrie` recomputes `header(B).Root` from the base file's own rows, in one streaming pass, no Firewood and no preimages: that is what `BaseBuilder.Finish` does, and it also checks every contract's storage root against the root its account row claims. (2) Firewood's key space is ALREADY HASHED. `graft/evm/firewood/base_trie.go` hashes on the way in and stores `keccak(addr)` -> account leaf RLP and `keccak(addr)||keccak(slot)` -> `rlp(trimmed value)`, which is byte-for-byte what a state sync yields and what the base file stores; the preimage-keyed `UpdateAccount(addr, ...)` surface is a convenience layer, and `TrieDB.Firewood` is an exported `*ffi.Database` whose `Propose([]ffi.BatchOp{ffi.Put(hashedKey, val)})` + `Commit` reproduces the canonical MPT root exactly (proven against a stack trie in that test). So a limited-history node builds its Firewood frontier at B directly from the base file's rows, with no preimages, no execution and no replay, and the executor above B keeps its per-block root check unchanged. The frontier does NOT have to come out of the sync in merkle form.

Known gaps from step 1: the base-fold `snapshot --verify` still rides along with the build rather than checking an already-written file (it predates the stack-trie check above, which does work on the file alone); that verify applies every row in ONE Firewood proposal, untested at 43M rows; genesis-alloc STORAGE is unsupported and errors loudly (dead code on both networks today, whose single alloc account has code but no storage); folding cannot range-skip an epoch, since SST rows are key-ordered. Two more from the gate run: "nothing below F exists" is exact for STATE but bucket-granular for BODIES (a raw bucket straddling F still serves bodies below it, and the floor check lives in the descent, not in the file set); and the base's CODE section is still effectively untested, because code.log is a single global file that has to be carried whole, so eth_getCode resolves from it rather than from the base on any node built by folding an existing corpus.

Work order: (1) DONE, floor plumbing against the existing mainnet 10M corpus with a synthetic floor, gated on "a node pruned to floor F answers byte-identically to the full node for every block >= F"; (2) Helicon bump, the long pole and bigger than this feature; (3) port `follower/sync`, writing its output into the base file plus code.log; (4) follow and seal above B on Fuji, A/B gated. Open: does SAE change the state-sync protocol (gates step 3); is a smaller local EPOCH_TXS worth it now that boundaries match nothing.

## Our own state sync: publish a flattened snapshot [PLANNED] (user design 2026-07-29)
Upstream has no C-chain state sync under SAE and will not soon: `vms/saevm/cchain/sync.go` is a stub returning StateSyncEnabled=false with `// TODO(#5513)`, the SAE VM registers only three p2p handlers (warp/acp118, atomic tx gossip, tx gossip), and ava-labs#5513 "Epic: SAE State Sync" is open with "register the server side" still on its list. Verified against both the v1.15.0-fuji tag and master HEAD c5d3c8aa (2026-07-28). So every new Fuji C-chain node today bootstraps by executing from genesis, and porting flatstate's v1.14.2 leaf-sync client is dead work for Fuji.

We route around it: SNAPSHOTS. A pruning node's normal output IS the state-sync artifact, and clients download it instead of syncing state from the network. One sync mode, one rule, no special cases (user rulings 2026-07-29):

- ONE SYNC MODE: every node starts from a snapshot. "Genesis sync" is just starting from snapshot(0), which is the genesis alloc and is HARDCODED IN THE CLIENT (it already ships there: `exec.NetworkGenesis`); no snapshot-zero file exists. A node given a later snapshot downloads it, dumps it into Firewood, and replays the gap to tip; every key not found in local data falls back to the snapshot, which is the descent floor.
- ONE PRODUCTION RULE: at every canonical boundary (cumulative-tx-count, same for everyone), a PRUNING node emits snapshot(K) = snapshot(K-1) folded with the period's own captured writes, and a NON-PRUNING node emits epoch K. Each is a pure function of chain content plus the previous artifact of its kind, hence bit-identical across nodes within its kind. Pruning nodes never seal epochs; archival nodes never emit snapshots. No producer flags, no conversions, no folding epochs into snapshots anywhere, ever.
- ONE PUBLICATION PATH: the operator runs two real nodes, one archival and one pruned, and periodically asks each for its content hashes; the manifest JSON is assembled from those answers ("hey, what's your latest snapshot" -> hash into the JSON). Manifest carries all epochs plus the NEWEST snapshot only, no ladder. Snapshot and epochs alike are fetched BY HASH over torrent; the client pins nothing but the manifest. Plain HTTP/S3 stays an optional mirror.
- ONE ROW FORMAT: the snapshot is PREIMAGE-KEYED with the same 53-byte keys as epochs and buckets, because its producer (the pruning node's own capture) has the preimages. The hash-keyed 65-byte base keyspace existed only for network leaf-sync, which is deleted (below). Firewood load hashes keys on the way in.
- VERIFICATION IS THE LOAD, not a pass: dumping the snapshot into Firewood computes the root as a side effect of the commit, so the check is one free comparison against `header(B).Root` (kept only for a clear early error), and the next executed block re-verifies the inherited state transitively anyway. The StackTrie verify pass and `snapshot --verify` machinery are deleted.
- Cadence does not matter for clients: catching up from B to tip is p2p block fetch plus replay at 3-6k blk/s, so even a 10-day-old snapshot costs a couple of minutes of replay.
- BYTE-IDENTITY REQUIREMENT: all producers cut at the same canonical heights, and a snapshot-synced node cannot compute cumulative tx count from history it does not have, so the SNAPSHOT FOOTER carries cumTx at B. It is the one footer field `header(B).Root` does not cover; a lie there breaks manifest agreement loudly at the node's first boundary.
- Measured basis (2026-07-29): base_200000 loads into a frontier in 1.04s with the root matching the header; 8.8M rows rebuild in 11s; full mainnet extrapolates to about a minute. Rows stored sorted in trie order make the bulk load near-linear despite a 7-9 level trie.

DELETED BY THIS DESIGN (Occam pass, user-confirmed 2026-07-29): the network state-sync port (`statesync/`, `state/basebuild.go`, `fetch/apprequest.go`, the second base-writer and its encoding conflict): snapshots travel by torrent, nobody leaf-syncs, and post-Helicon peers cannot serve leaves anyway; the one-shot fold-epochs `epochdb snapshot` command (a pruning node produces snapshots as its normal output; the manifest asks it, not a tool); the hash-keyed base keyspace; the StackTrie/`--verify` snapshot verification machinery. The mode-matrix legality rules from earlier today collapse too: with genesis = snapshot(0) there is no genesis-vs-snapshot switch and nothing is illegal, the only switches are pruning on/off and which snapshot you start from.

Three deployment personas, one artifact set: (1) FULL ARCHIVAL, download the epochs, do indexing and historical work; (2) TIP-FAST, download the newest snapshot and replay the gap, serving the tip within about the download time; (3) TIP-FAST BUT KEEP EVERYTHING FROM NOW ON, the same snapshot with pruning off, for rerunning algorithm benchmarks against identical data as development proceeds. That third one is exactly the floor node built on 2026-07-28.

Distribution (user ruling 2026-07-29): the snapshot ships in the SAME manifest as the epochs, with its sha256 and infohash, and is fetched BY HASH over torrent exactly like an epoch file. The client pins nothing but the manifest, and the two checks are independent: the infohash proves the bytes are what the manifest names, the root check against header(B).Root proves those bytes are real state. Plain HTTP or S3 (a cheap box in front of S3) stays an optional mirror for anyone who prefers one big object over a swarm. S3-as-truth for epochs (disk as an LRU of byte ranges) remains the recorded v3 archival mode and is a natural fit, since every section in the format is offset-addressed and reads become range GETs.

PARKED, not rejected (2026-07-29): rewriting Firewood in Go. Read-side FFI crossings were already worked around by the capture cache, and replay runs 2,900-6,000 blk/s, so FFI is not obviously the bottleneck; profile before touching it. If we ever did own the merkle store, the measured shape says NOT to bother dropping leaf values (flat state is 2.82GB of a 20.7GB Firewood at 10M blocks, so at most ~14%); the 86% is interior nodes, so the only real lever is storing interior hashes down to a depth cut and recomputing deeper subtrees from flat state on demand, which our trie-order row layout makes cheap. Disk down, per-block CPU up, root checks intact.

## Unified node: flatstate absorbed into epochdb [PLANNED] (user direction 2026-07-20)
Flatstate (fast tip) and epochdb (compact history) merge into ONE codebase: one snowman follower, one post-image capture stream, N sinks behind flags. Two repos maintaining two followers is the wrong option. Single process only if the history/seal sink sits behind async backpressure and can NEVER stall block application (chain pace is the tip invariant); fallback is one binary, two configs, two processes.

Repo strategy: epochdb absorbs flatstate (~7.4k LOC of self-contained leaf packages move; flatstate's `follower/consensus` + `follower/net`, ~2k LOC, are deleted as duplicates). epochdb has 2.4x the surviving code, the newer follower generation, the heavier integrated deps (firewood FFI, torrent), and the paths that must stay stable. go.mod merge is clean (both on avalanchego/coreth/evm v1.14.2 + libevm 1.13.14-0.4.0.rc.2; add PowerDNS/lmdb-go, bump go, bump uint256).

The seam is `capture.Sink`. Unified `capture.Block` carries Height/Hash/Parent/Time, the verbatim proposervm container, the header, post-image Ops (flatstate's richer op set, with `OpAccount` carrying the full `types.StateAccount` because epochdb's SST rows and diff-apply verification need Root/CodeHash), full Logs, per-tx {GasUsed, Status}, and code blobs. Two decorators: `AcceptedOnly` (buffers Block, acts on Finalize: the epoch sink) and `Async` (bounded channel, fail-loud on overflow: the chain-pace guard). Bonus: live Logs/TxMeta capture makes the seal-time `DeriveStored` re-execution unnecessary for newly sealed epochs, but only if the output is byte-identical.

epochdb's ported consensus engine survives as the core (flatstate's live-measured constants baked in, decoupled from libevm via injected Parse, plus the multi-source validator cross-check flatstate lacks). Port back from flatstate: the preferred-tip surface (`Sink.Verified/Head`, preference walking) for the tier-1 API, the executor hook at issue time plus `SeedHeaders` for the BLOCKHASH window, and the store-resume anchor. Keep epochdb's outside-the-engine backfill.

Hard constraint: sim/bots stay separate processes. `corethcore.RegisterExtras` type-asserts the concrete `*state.StateDB` and panics on sim's custom statedb, so simulation can never live inside the unified node process; it reads via tier 2.

Stages: (0) import packages, both binaries still build; (1) one follower, dry-run 24h+ against the live flatstate follower and diff accepted heights/hashes; (2) unified sink, A/B LMDB rows old-vs-new and byte-diff epoch output; (3) first integrated milestone `serve --follow --history --pin-state`, run a week beside the old follower; (4) contracts (flock HA, tail wakeup, pinned-map OOM valve, library door); (5) retire flatstate. ~15-18 agent-days. Top risks: re-adding preferred-tip emission to the ported engine, post-image divergence between the two executors (EIP-6780, multicoin slot normalization), seal bursts vs tail latency in single-process mode, and bit-identity of epochs during the capture switch.

`--pin-state` contract (flatstate discipline, NOT an LRU): lazily populated, pin-forever, plain pointer-free Go maps, presence = knowledge (pinned zeros make negative caching free), no per-read bookkeeping, RAM bound = touched working set <= live state size. OOM valve: near ~98% memory, DROP THE ENTIRE MAP and refill lazily. No partial eviction (it breaks presence=knowledge; a full drop resets it correctly).

## Helicon / ACP-194 SAE [PLANNED] (researched 2026-07-22 at avalanchego v1.15.0-fuji)
SAE is not a coreth change, it is a whole new VM (`vms/saevm`). The C-chain registers `transitionvm.Factory{PreFactory: coreth, PostFactory: saevm/cchain}`, runs coreth until HeliconTime - 10s, then boots the SAE VM on the same database. Coreth actively rejects blocks carrying SAE settled markers, so coreth-as-library can never process post-Helicon blocks.

What changes semantically: `header.Root` of block N is the post-execution state root of the last block SETTLED by N, not N's own state (settlement lag tau = 5s of gas time, a handful of blocks). Headers gain `SettledHeight`, `SettledGasUnix`, `SettledGasNumerator`, `SettledExcess`, plus ACP-283's `MinPriceExponent` and ACP-176's `TargetExponent`. Receipts are computed and stored per block at execution time but committed only at settlement: the settling block's receiptsRoot/bloom cover the CONCATENATED receipts of every block it settles. `header.GasUsed` becomes worst-case charged gas of the block's own body (statically checkable), per-tx gas charging floors at limit/2, and base fee for execution comes from the deterministic gas clock, never `header.BaseFee`. RPC labels shift: pending = last accepted, latest = last executed, safe/finalized = last settled.

Wire format is otherwise unchanged (one RLP block-with-extData, proposervm and GetAncestors untouched), but the new RLP tail fields mean a v1.14.2 decoder CANNOT parse any post-Helicon header, and v1.15 peers drop sub-v1.15 handshakes at activation. Fuji activates 2026-07-29 00:00 JST; mainnet is unscheduled in the tag, expect roughly 3 weeks after the mainnet release lands (Granite precedent), and our mainnet v1.14.2 pin is safe until then.

SAE DELETES C-CHAIN STATE SYNC (measured + read 2026-07-29, decisive for limited-history mode). `vms/saevm/cchain/sync.go` is a stub: `StateSyncEnabled` returns false, every summary getter returns ErrNotFound, `AcceptSummary` returns ErrStateSyncableVMNotImplemented, and the file carries `TODO(#5513): Implement C-Chain state sync`. The SERVING side went with it: `vms/saevm/sae/vm.go` registers exactly one p2p handler, `p2p.TxGossipHandlerID`, and there is no coreth leafs/code/block handler anywhere in saevm. `transitionvm` routes every AppRequest to `vm.current.chain`, which after HeliconTime is the SAE VM, so coreth's legacy even-request-ID sync server stops existing on that chain at activation. `p2p.FirewoodProofHandlerID` is RESERVED in `network/p2p/handler.go` and has zero implementations and zero references in the tag, so the Firewood-proof replacement is planned, not shipped. MEASURED on live Fuji 2026-07-29 09:43 JST: 36 peers connected, the header walk and container parse both fine (v1.15 handshakes and post-Helicon containers decode), then 24,881 leaf requests, 100% AppError, ZERO accounts in 4 minutes. Same binary, same minute, mainnet: 121 failures and 5.5M accounts. Consequence: a limited-history Fuji node cannot be built from the network at all until #5513 lands, and any Fuji plan that assumed state sync needs re-planning. Mainnet is unaffected (coreth peers, HeliconTime unscheduled).

Ranked epochdb work: (1) small and urgent, do not crash at the boundary (park fetch at HeliconTime on Fuji); (2) small, dep bump to v1.15.0-fuji so parsing and handshake work; (3) medium, verifier re-point: keep a ring of computed roots and assert `header.Root == root(SettledHeight)` with marker monotonicity, plus the body statics (`GasUsed == sum tx gas + op gas`, receiptsRoot over the merged settled range); (4) large, execution engine swap for post-Helicon heights to `saexec.Execute` + `vms/saevm/cchain` hooks. Firewood stays, and SAE ships native Firewood support to crib from. Scale note: max block gas becomes R*tau*lambda = 20x target (double the old cap), so EPOCH_TXS assumptions should be sized on charged gas. Risk: SAE Go APIs are explicitly unstable, so pin exact release tags.

## Operations
- Build/run: `go run ./cmd/epochdb <cmd>`. Commands: fetch (`--network mainnet --tip-override N` | `--follow --vdr-sources ...`), exec (`--stop N --state-cache 3 --commit-every 1000`), cook-index, cook-txindex, seal (`--out DIR --epoch-txs N`), manifest, seed, bootstrap (`--verify`), verify, serve (`--port`), ab-bench / ab-bench-tx / ab-bench-rpc / ab-bench-logs / rpc-bench.
- New node today: copy `epochs.manifest` into the data dir, `epochdb bootstrap --data <dir>` (exits 0 when complete), then `epochdb serve --data <dir> --network mainnet`. Live follow needs `fetch --follow` with vdr-sources.
- Memory: replay wants `GOMEMLIMIT=10GiB --state-cache 3 --commit-every 1000` on a 25GB box (the 6GiB default state-cache thrashes in dense eras, incident 2026-07-19). Seal at 10M-tx epochs gathers a whole epoch in RAM (~20GB anon live): run it ALONE with `GOMEMLIMIT=20GiB`, it OOMs beside a replay.
- Long stages MUST be setsid-detached (harness background tasks get reaped; learned twice).
- Multi-process: writers truncate torn tails on open, so NEVER open a live writer's dir with the writing opener. `state.OpenReadOnly` / `fetch.Reader` exist for cohabitation (production-proven). Two cook/seal processes must not share a dir (tmp+rename races).
- `du` lies on WSL2 and page-cache-heavy dirs; footers and manifests are truth.
- ALWAYS pass `--network mainnet`: the default is fuji and the chain-id mismatch fails late.
