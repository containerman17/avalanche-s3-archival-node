## DESIGN FINALIZED 2026-07-31 (user: "all 6 yes")
The six rulings that close the residency and artifact design. Anything elsewhere in this file marked PLANNED or OPEN from the 2026-07-30 planning day is SUPERSEDED by this block; each section gets flipped to as-built as the implementation lands.
1. THE SNAPSHOT AND THE PRUNING NODE ARE DEAD. AS BUILT 2026-07-31, both halves. DELETED (~3,600 lines): the fold producer (`state/fold.go`, `epochdb fold`), the base-file format and every consumer (`state/base.go`, the Executor's `base` field and `startFromBase`, the `base_<B>.cas` marker handling in bootstrap, the base fallbacks in `loadHeader`/`GetHeader`/`CodeByHash`), the floor concept end to end (`History.floor`, `EpochSet.SetFloor`/`Floor`, `PrunedError`, `RequireCovered`'s below-floor refusal, the descent's per-row below-floor miss rule, the rpc pruned errors and the ab-bench `--floor` gates), and the snapshot half of `latest`, which now names one thing. KEPT, because they are about seal and not about pruning: seal's retirement of raw buckets behind the sealed end, and `exec.New`'s CommitEvery-vs-walkback guard. `RequireCovered` still refuses a mid-set coverage HOLE.
BUILT in its place, ~330 lines: `state.MergeFrontier` + `exec.BuildFrontier`, run as `epochdb bootstrap --frontier` (its own step, not part of serve, because it is a full pass over the corpus). The merge is a k-way merge over every epoch's SST section, one cursor per epoch marching the same sorted key space with a single decoded 64KB SST block each, so the working set is bounded by the epoch COUNT and no SST block is ever revisited. Rows are (key53, block) ordered, so the last row at or below H wins per key; tombstones follow the descent's rules exactly (an empty account row is a SELFDESTRUCT and kills every storage row written before it; 'c' code rows are skipped, Firewood holds accounts and storage only). Winners stream into Firewood in 200k-op batches (~20-30MB of pinned cgo ops), and the final root is compared against header(H).Root read out of the epoch's own headers section. On success the build copies the headers of [H-256, H] down into the state layer (BLOCKHASH above H, and the crash walk-back's only way to learn what height Firewood's root belongs to) and parks exechead at H, so `serve` starts executing at H+1 with no further plumbing. Deletes are emitted ONLY for keys the genesis alloc put in the trie: every other key the merge sees IS the trie's content, so a dead one is simply not written.
A POST-SAE FRONTIER VERIFIES AGAINST THE SETTLING HEADER; THE PRE-SAE PATH IS UNCHANGED [RULING 2026-08-01, AS BUILT the same day; supersedes the "post-Helicon H is a HARD ERROR by name" limitation recorded on 07-31]. THE RULE, one line: the merge targets the height the sealed end's header COMMITS TO, and is checked against that header's Root. Below the boundary a header commits to its own post-execution root, so the target is H and the check is `merged == header(H).Root`, byte-for-byte the code that was there. Above it (ACP-194) `header(H).Root` is the post-execution root of the block header(H) SETTLES, so the target is S = settledHeight(header(H)) and the check is `merged at S == header(H).Root`. Same cryptographic strength, one header hop away; no trust-me mode, no second code path for the pre-SAE case. A header that settles itself, the future, or genesis is refused, and so is a merge that does not reproduce the root, exactly like a pre-SAE mismatch.
WHY THE SETTLED HEIGHT AND NOTHING ELSE. The pairing is FORCED, not chosen. (a) It is the only height above the boundary any header names at all: settlement advances in jumps, so most heights are never named, and their roots live nowhere but the executor's own `sae.ring` (which a downloaded node does not have and cannot have). (b) The gas clock, not just the root: executing S+1 needs its PARENT's gas clock, consensus publishes it only at settlement points, and the same four markers that attest the root pin it (`hook.SettledGasTime`, upstream's own reconstruction). So a frontier parked anywhere but a settlement point could not take a single step even with a correct root. That is why the build seeds `ring[S]` with the verified root plus the reconstructed clock and stamps a FRONTIER FLOOR in misc: nothing below S was ever executed here, so a later header settling a height below the floor has no root of ours to present and `checkSettled` skips it instead of hard-stopping (the floor itself IS checked, by this build). The boundary-straddling case falls out for free: when S is at or below the transition block it is a synchronous height whose own header carries root and clock, so nothing is seeded and `postExecutionAt` reads them where it always did.
COST, recorded: the frontier lands a settlement lag (1..10 blocks on live Fuji) below the sealed end, so the follower re-fetches and re-executes those few blocks on the way up. `serve` therefore floors the fetcher at min(sealed end, exec head) instead of the sealed end flat, and the header window the build copies down stops AT the frontier, never above it, or the crash walk-back would start at a height whose container this node never fetched. Blocks below the sealed end that get re-executed are ignored by seal (it cuts from the sealed end + 1) and by the tail overlay (it backfills from the cooked/sealed head + 1).
NOT GATED END TO END YET: the tests are unit-level, on synthetic headers carrying real ACP-194 markers over a real replayed corpus (pre-SAE unchanged, lag 1, lag 3, frontier at the activation boundary, corrupted settled root refused, self-settling header refused). Verification against the real Fuji sealed SAE epochs is PENDING the live node finishing its first seal crunch; nothing here has touched a real post-Helicon epoch.
MEASURED 2026-07-31 on a purpose-built corpus (400 blocks x 500 statedb writes replayed through the real capture + Firewood path, sealed into 100 epochs, 152,755 winning keys, this 16-core box): merge alone 1.54M keys/s, full build (merge + keccak + rlp + Firewood) 374-439k keys/s, i.e. 152,755 keys in 409ms. Working set with 100 open epoch cursors: 71MB of live Go heap mid-merge, of which ~6.4MB is the decoded SST blocks and the rest is the per-epoch zstd decoder state any read path allocates anyway; the merge itself adds one map entry per account ever SELFDESTRUCTed and nothing else. It does not grow with corpus size, which is the property that matters.

3. KERNEL-TIERED RESIDENCY IS THE MODEL. [CACHE HALF SUPERSEDED 2026-08-03 by "THE WINDOWED SHARED CHUNK CACHE" below: sparse files, SEEK_DATA presence, hole punching, CacheBytes and the pin contract are all deleted. The residency MODEL is unchanged, only the tier under it. What follows is kept as the record of what was built and why, unrewritten.] AS BUILT 2026-07-31, both halves (casfs's in its own repo, 56cafda/777915b; epochdb's below), with ONE ruling amended by measurement: the account-delete map STAYS a heap map, see the deletes entry. Nothing on the read path lives on the Go heap: every index structure is a section of a mapped file; the kernel tiers RAM to SSD (safe, a refault); casfs tiers SSD to S3 with ONE SPARSE FILE per artifact (chunks pwritten at true offsets, presence discovered via SEEK_DATA so the kernel's extent metadata is the truth, eviction via FALLOC_FL_PUNCH_HOLE), and PINNED RANGES protect live-mapped resident sections, because punching under a live view silently reads zeros and a zeroed bloom page is a FALSE NEGATIVE, i.e. wrong answers, not slow ones. AS BUILT, ruling 3's epochdb half [2026-07-31, no format change, v6 unchanged; the pin/punch parts of this block were REPLACED on 2026-08-03, see the windowed-cache ruling below]:
- ZERO-COPY ON BOTH PATHS. `dist.Blob` is a mapping either way: the spool file without credentials, casfs `View` (a subslice of a whole-file PROT_READ mapping of the sparse cache file, filled on demand) with them. `Blob.Slice` therefore copies nothing anywhere and `ReaderBlob`, the old credentialed ReadAt path, is deleted. `Blob.Pin/Unpin` are no-ops without credentials.
- THE PIN CONTRACT, which is what makes that safe: an epoch pins its resident sections at open (dict, bodiesIdx, headersIdx, sstIdx, deletes, txbloom, keybloom, logsDict, fullLogsIdx, rcptIdx) and unpins at Close, and EVERY other read pins its range for the duration of the access and releases right after. `Epoch.read` returns (view, release, err) and the release comes immediately after the decode that copies (zstd frames, SST blocks, stored records). The logidx binary search pins each probe on its own, because pinning that section whole would FILL 10-13% of the epoch to answer one lookup: `View` fills every chunk of the range it is given.
- THE HAZARD, restated because it is the whole reason for the shape: a hole punch under a live mapping is silent (no error, no fault, no short read) and the range reads back as zeros. Pinning does NOT refill an already-punched chunk, so a cached view cannot be re-read across an unpinned gap; the read path re-Views inside its pin every time, which is why nothing caches a decoded index any more.
- THE TX INDEX IS A BYTE VIEW. `ef`/`packed` read little-endian u64s straight out of the section bytes (`words.get`, alignment-free), so opening an epoch's tx index is a 16-byte header parse plus five slices whatever the entry count. The build side still materializes in heap and serializes (`efBuild`/`packedBuild`), so epoch bytes are unchanged. The v5 heap LRU (`txHotEpochs`, `touchTxIndex`, `dropTxIndex`) is DELETED: there is nothing left to evict. A candidate walk pins the txidx range for the traversal and unpins after; the txbloom reject is permanently pinned and happens first, so an unknown hash (the pending-tx poll) still touches no Elias-Fano page. The raw staging index reads its own file the same way.
- MEASURED (not modelled) on a purpose-built epoch of 1,000,000 txs + 10,000 block hashes = 1,010,000 entries, txidx section 5.58MB: the old heap decode costs 5,585,816 bytes = 5.53 B/entry; the byte view costs 128 bytes TOTAL, i.e. 0.0001 B/entry, and that 128 is two small structs. At mainnet shape the v5 LRU could hold 4 x ~59MB of decoded index; it now holds nothing at all, so the tx index is 0 heap and 0 open-time cost on every node.
- CLEAN SHUTDOWN IS WIRED. `dist.Store.Close` marks the casfs cache clean and hangs off `state.Store.Close`, which serve, the SDK, exec, cook and the bootstrap/verify/seal commands already call; a process that skips it (kill -9, log.Fatalf) starts with a COLD cache and nothing worse, because the spool and the bucket are untouched. ONE CASFS PER CACHE DIRECTORY is now enforced inside the process by a refcounted shared store: `casfs.New` removes the clean marker and wipes what it cannot vouch for, so a second store over a live cache dir would delete the first one's chunks and leave two LRUs on one byte cap, and `bootstrap --frontier` (artifact store, then a whole state layer over the same dir) hit exactly that. ACROSS PROCESSES NOTHING ENFORCES IT, and that is the one place this constrains us: running a sibling tool against a serving node's data dir costs that node its warm cache (never correctness, never anything durable). A read-only SDK consumer beside serve is the realistic case, and it only pays with credentials configured.
- THE PIN IS PER CHUNK, so a pinned range holds whole 4MB chunks, and a pin OUTRANKS `CacheBytes` (casfs blows through the cap rather than punch a pinned chunk). CONSEQUENCE for operators, recorded: the resident-section budget is now a FLOOR under the chunk cache. At the projected ~7.7GB of mainnet resident sections, an `EPOCHDB_CACHE_BYTES` anywhere near the 8GiB default leaves nothing evictable for bodies and SST blocks, so the cache thrashes on ranged GETs while the cap is nominally respected. Size the cache above the resident budget, not against it.
- TESTS WITH TEETH (`state/pin_test.go`, an in-process fake S3, ~90 lines): an epoch is published, uploaded and its local copy RELEASED, then reopened through casfs with the cache capped at ONE chunk over a multi-chunk artifact, so every read punches holes in whatever it is not reading. Every query (containers, headers, state search, key bloom, tx candidates, log posting lists, stored logs and receipts, a full row walk) must return exactly what the spool-resident epoch returned, and the test FAILS if the fake bucket's ranged-GET count says nothing was ever evicted. Disabling `Pin` makes it fail (the epoch does not even open: the resident sections get punched between reads). Plus an 8-goroutine concurrent walk of the pinned txidx path under -race, and an EF traversal over the byte view compared entry for entry with the pre-change heap decoder, which survives in the test as the oracle and nowhere else.
- THE ACCOUNT-DELETE MAP STAYS A HEAP MAP, and this amends the ruling on measurement. MEASURED over mainnet blocks 1..200,000 (data-v3's cooked buckets, 1,711,514 rows, 767,951 of them account rows): 13,747 account-delete rows and exactly TWO distinct deleted accounts, 0x..01 and 0x..02, the ecrecover and sha256 precompiles emptied by EIP-158 touch-and-delete, at 13,686 and 61 deletions. So the merged map is a couple of dense sorted []uint64 runs at 8 B per row, against the 61 B per row the epochs' own deletes sections spend on the same facts: mapping it would need 7.6x more resident bytes to answer the same question, plus a bloom probe and a binary search per epoch (120 at mainnet) on the StorageAt hot path. The row count is bounded by BLOCK count, not tx count (one post-image row per key per block): 0.069 rows/block measured gives ~6.2M rows and ~50MB at mainnet's 90M blocks, and even a chain that empties a precompile in every single block lands in the low hundreds of MB. Under the ruling's own "a few hundred MB" bar, so it is not built. REVISIT TRIGGER, recorded in `state/overlay.go`: a real corpus showing delete rows approaching one per block AND many distinct accounts.

## RULING 2026-08-03: THE WINDOWED SHARED CHUNK CACHE [BUILT 2026-08-03, casfs 66aba74 + this repo]
SUPERSEDES the cache half of ruling 3 of 2026-07-31 (sparse files, SEEK_DATA presence, hole punching, `CacheBytes`, and the pin contract). Ruling 3's OTHER halves stand unchanged: nothing on the read path is decoded onto the Go heap, the Elias-Fano index is still read in place, the account-delete map is still a heap map, and the epoch format is still v6 with no section moved. Finalized after a two-pass adversarial design review; every rule below is deliberate and several exist because the review killed the obvious alternative.

WHY IT REPLACED BUDGET + PIN + PUNCH. Four things were wrong with the old tier, and only the fourth is a bug rather than a design cost.
(a) A BYTE BUDGET IS A NUMBER NOBODY CAN SET. `CacheBytes` had to be picked ahead of time, per node, against a disk shared with the spool, the raw tail, Firewood and everything else on the box; too high and the node fills the disk, too low and it refuses to use free space that is sitting there. The thing an operator actually knows is "do not fill my disk", which is a WATERMARK, not a budget.
(b) THE PIN CONTRACT WAS CORRECTNESS DEBT SPREAD ACROSS TWO REPOS. A hole punch under a live mapping is silent: no error, no fault, no short read, just zeros, and a zeroed bloom page is a FALSE NEGATIVE, i.e. history the node holds and denies. Every read path in epochdb had to pin the exact range it was about to touch and release it at exactly the right moment, and one missed release leaked residency while one missed pin was a wrong answer. That contract is now DELETED rather than documented harder: casfs evicts by `unlink`, and unlinking a mapped file cannot change what a reader is looking at.
(c) ONE PROCESS PER CACHE DIRECTORY. `New` wiped anything it could not vouch for, so a sibling tool run against a serving node's data dir ate that node's warm cache. The window tree has no in-file index to disagree about, so N processes now share one cache and the worst a race costs is one ENOENT and a refetch.
(d) THE CLEAN MARKER WAS A COLD START WAITING TO HAPPEN. A fill was one `pwrite` with no atomicity, so a `kill -9` meant the whole cache had to be thrown away. Chunk files are renamed into place after an fsync, so a `kill -9` now costs nothing at all and `Close` is no longer load-bearing.

THE LAYOUT. The cache is a shared tree of PLAIN CHUNK FILES, 4MB, named `<artifacthash>.<index>`, at `<data>/cache/<window>/<chain>/<hash>.<index>`. The file name is NOT a content hash of the chunk, deliberately: artifact hash plus index already names immutable bytes uniquely, is derivable by anyone holding the artifact hash without fetching a chunk list first, and leaves ownership of a stray file decidable by looking at its name. The spool and the pointers keep their current semantics and stay OUT of the cache tree.

THE WINDOW IS A HUMAN, SORTABLE NAME AND IT COMES FIRST. A window is the UTC start of a 20-minute bucket, written `2026-08-03T12-40` (Go layout `2006-01-02T15-04`), fixed width in every field so the minute is always 00, 20 or 40. Two properties are load-bearing, not cosmetic. (a) ALPHABETICAL ORDER IS CHRONOLOGICAL ORDER, so the globally oldest cohort is the lexicographically first directory under the cache root and `os.ReadDir`'s own sort hands it over for free. (b) It parses back to the exact instant, and a name that does not re-format to itself is not one of ours, which rejects a stray directory and an off-grid minute with ONE rule. An integer bucket number had neither: an operator could not read it, and hand-trimming meant arithmetic. Never local time.

THE CHAIN IS THE LEVEL UNDER IT. Hash filenames are illegible to a human, so the chain directory is what makes ownership visible: `du -sh cache/*/<chain>` per chain, `rm -r cache/*/<chain>` to wipe exactly one chain, and the one-writer-per-chain invariant enforced by the directory tree instead of by a convention. THE IDENTITY IS THE DATA DIRECTORY'S OWN NAME (`dist.chainKey`), which needs no plumbing at all and is already the right string: in a fleet each chain's dir IS its blockchainID (`resolveServeChain`), the same id `/status` and `/ext/bc/<id>/rpc` use. The chain root hex was the other candidate, since it qualifies the tip pointer, but dist does not have it until `SetLatest`: it comes from a P-chain resolve that happens long after the store is open. Solo, the cache root is already inside that one chain's dir, so the level is pure legibility and the layout is identical either way.

THE WINDOW IS THE LRU. The directory a file sits in IS its recency, so the recency order is written in the filesystem rather than in one process's memory: it survives a restart with no journal, and several processes can share it without agreeing about anything. Each process keeps a `chunk -> window` map in RAM for its own artifacts, rebuilt by ONE NAME-ONLY WALK of its own chain directory in each window at startup (MEASURED on a synthetic 175,000-file tree, ext4 on this box: 118ms, 112ms, 112ms over three passes; the tree took 3.4s to create). An entry that is wrong because a sibling evicted the file is an ordinary miss: ENOENT, drop the entry, fetch, maybe cache.

READS. `open`+`pread` for the query path. TOUCH PROMOTION: a read of a chunk in ANY non-current window renames it into `<current window>/<chain>/`, mkdir on demand, at most one rename per chunk per window. The review killed promote-only-if-two-windows-behind: under pressure everything the worker is about to eat looks equally stale, so that rule stops separating hot from cold exactly when it matters and the cache degrades to FIFO. A rename failure other than ENOENT keeps the old map entry (the file is still where we think it is). In-process singleflight per chunk, so N concurrent misses on one chunk cost ONE ranged GET.

LONG-LIVED MMAPS ARE ALLOWED ONLY FOR THE RESIDENT SET. Chunk files are separate inodes, so a section spanning several of them is not contiguous memory: a resident section is one mapping per chunk, assembled at epoch open and held for the process's life, and `View.Slice` aliases inside a chunk and COPIES ACROSS A BOUNDARY. ACCEPTED COST, recorded rather than hidden: an unlinked-but-mapped chunk keeps its blocks, so a node can hold ghost disk roughly the size of its resident set.

WRITES: ADMISSION CONTROL, NEVER EVICTION. Before a fill is written, `statfs` (f_bavail, ABSOLUTE BYTES, not a percentage of a filesystem casfs does not own) says how much room is left. Over the watermark the chunk is NOT cached: the fetched bytes are served from memory and forgotten. Nothing is ever deleted to make room for a fill. Under the watermark: tmp, FSYNC, rename. The fsync is MANDATORY and is correctness, not tuning: nothing checksums a chunk file on the way back in, so a torn chunk under a correct name is a silent wrong answer, and a half-written bloom page poisons a heap load into exactly the false negatives (b) was about. Default watermark 95% of the filesystem, held internally as a bytes-available floor, configurable (`EPOCHDB_CACHE_MIN_FREE`).

EVICTION: ONE BACKGROUND WORKER, ONE `rm -r`, NO ALLOCATION-TIME EVICTION. Putting the window first collapses this to almost nothing. A loop per process: while the disk is over the watermark, DROP THE OLDEST NON-CURRENT WINDOW ENTIRELY, then wait ~60s for statfs to settle before believing it again; under the watermark, idle on a short poll. There is no per-file victim selection, no cursor, no batched getdents, no rmdir-after-drain and no skipped-entry-while-unlinking caveat, because the names sort chronologically: the first entry of a sorted readdir IS the oldest cohort, and everything in it is at least one window cold by construction. Every chain sharing that window goes with it, which is correct, since they are competing for one disk.

IT NEVER TOUCHES THE CURRENT WINDOW: if only the current window has files it stops and admission control carries the load. That is deliberate and the review proved the alternative strictly worse: a saturated cache should FREEZE FULL, because every evicted-and-immediately-refetched chunk is a GET that bought nothing. Stray `*.tmp` older than ~1h are collected in the sweep.

THE ACCEPTED EDGE, recorded rather than hidden: a cache filled FAST concentrates most of its bytes in few windows, so the first pressure eviction after a bootstrap or a backfill drops a big cohort at once. Deliberate, self-correcting (the next fills spread across new windows), it fires only when the disk is genuinely full, and everything it drops is already at least one window cold. The alternative, per-file selection inside a window, buys a smoother curve for a cursor, a scan and a class of race the whole-window drop does not have.

TTL. `--cache-max-age`, default 30 DAYS (`EPOCHDB_CACHE_MAX_AGE`): the SAME OPERATION, gated on the window name's date instead of on disk fill. Whole window directories older than the max age go BY NAME, with no stat and no per-file work. Safe by construction because a promotion's target is always the CURRENT window, so nothing anyone still reads can be sitting in a directory named thirty days ago.

METRICS. `casfs.Store.Stats()` reports evictions (WINDOWS dropped, not files), admission refusals, free bytes and the watermark, plus VICTIM AGE: the age of the window the worker last deleted from. That last number is THE HONEST HORIZON, i.e. how long a chunk really survives on this node, which is a thing a configured byte cap could never have reported. `/status` carries it per chain (`cacheHorizon`, `cacheEvictions`, `cacheRefusals`, `cacheFreeBytes`, `cacheMinFreeBytes`).

MIGRATION: NONE, by the standing rule. The cache is disposable, so the first run on the new layout deletes the old files wholesale: anything at the top of the cache dir that is not a window directory goes, and `dist.Open` additionally removes the pre-2026-08-03 `<data>/chunkcache` tree on sight, since the directory moved to `<data>/cache` and a stale one is pure wasted disk. ONE DATA FOLDER, and `cache/` is a subfolder of it: solo that is `<data>/cache`, and in a fleet `dist.SetRoot` puts the shared one at `<root>/cache` beside the shared `<root>/cas` spool.

DELETED FROM casfs: the byte-budget accounting and `CacheBytes`, the pin contract (`File.Pin`/`Unpin`), hole punching and `sparse.go` entirely, the per-artifact sparse files, the presence bitmaps and their SEEK_DATA scan, `CacheUsage`, `TouchInterval` and the throttled mtime touch, and the clean-marker cache wipe. `Close` now stops the eviction worker and nothing else.

THE EPOCHDB SIDE, as built.
- BLOOMS (key + tx) ARE LOADED ONCE INTO THE GO HEAP at first epoch touch and NEVER RE-READ (user ruling; epochs are immutable, so there is nothing to re-read). This is the one place the design deliberately spends heap: a filter is exactly the structure where a byte that changed underneath is a wrong answer rather than a slow one, and it is read on every descent forever. Test-enforced by deleting the whole chunk cache AND shutting the bucket down, then probing both filters.
- THE OTHER RESIDENT SECTIONS (dict, sstIdx, headersIdx, bodiesIdx, deletes, logsDict, fullLogsIdx, rcptIdx) keep long-lived views: per-chunk mmaps assembled at epoch open, held for the process's life, with copy-at-boundary for anything that straddles 4MB.
- THE TXIDX VIEW IS LAZY, not opened at epoch open (deviation from the ruling as drafted, recorded here with its reason): mapping it at open would fetch every epoch's Elias-Fano chunks at startup and destroy the v5 property that a pending-tx poll touches no EF page at all. It is mapped once, on the first query that gets past the tx bloom, and held from then on.
- QUERY-PATH SECTION READS (SST binary search, logidx probes, zstd frames, stored records) go through `pread` and COPY. `Epoch.read` returns `[]byte` and there is no release function to forget any more.
- THE STRADDLE INVENTORY, measured against the format rather than assumed. Every fixed-stride structure in the resident set can cross a 4MB boundary, because sections start at arbitrary artifact offsets and none of the strides divide 4MB: sstIdx entries are 69 bytes (`sortedKeySize` 53 + 8 + 8), deletes entries are 61, the stored-logs and receipt index members are 12 with an 8-byte offset table after them, and the framed bodies/headers index is 8-byte words at an unaligned section base. So the boundary case is handled ONCE, generically, inside `View.Slice` (alias when the range is inside one chunk, copy when it is not) rather than open-coded per structure. At 4MB granularity a 69-byte entry straddles one boundary in roughly 60,000, so the copy is noise and the common case allocates nothing.
- THE JOIN/BOOTSTRAP FLOW, THE PUBLISH FLOW AND POINTER SEMANTICS ARE UNCHANGED. `ReadEpochLink` still costs exactly the footer's chunk, which is still test-enforced.
- ONE COST ACCEPTED: object sizes are no longer free at startup. The sparse cache file used to BE the object's length; a plain chunk file is not, so a restart pays one HEAD per artifact it opens. One HEAD per epoch beats an on-disk index that can go stale.

## Principle [BUILT]
Bodies + headers + proposervm extras are the only ground truth. State history, receipts, logs, all indexes are caches rebuildable by re-execution (~5-6k blk/s). Re-executing one block was the universal primitive; after the 2026-07-20 ruling logs/receipts are STORED, and re-execution remains only for traces, createAccessList, and verification.

## Architecture [BUILT]
- Immutable per-epoch artifacts, NAMED BY THEIR OWN HEX SHA256 since 2026-07-30 (see Distribution). The local index is one marker file per epoch, `epoch_<startblock>_<blockcount>.cas`, holding that artifact's hash: startup = readdir the markers + read footers, exactly the old shape, and height->epoch stays a binary search over that table. No catalogue and no manifest; the marker is a local pointer, the hash inside it is self-verifying, and it is written by whoever learned the epoch (seal, or bootstrap walking the hash chain).
- Epoch boundary rule: TX COUNT per epoch, from the doubling schedule `state.EpochTxsAt(index)` (250k doubling to 8M, entry below). An epoch seals at the first block whose cumulative tx count reaches that epoch's threshold. Immune to throughput growth (SAE ~10x). Deterministic and bit-identical: cumulative tx count is chain content and the threshold is a pure function of the epoch index.
- Staging during sync is separate and disposable: height-bucketed arrival segments (100k blocks per bucket, `arrival_NNNNN.log` + `index_NNNNN.log` sidecar). The cooker consumes staging forward behind the executor, cuts epochs by tx count, and deletes a staging bucket once all its blocks are cooked. Buckets and epochs do NOT align 1:1; staging exists only on the machine doing the initial sync. Buckets are height-bounded (not tx-bounded) because blocks arrive out of order, so a file must be addressable by height alone; the constant is local-only tuning, never canonical. Mainnet at 10M blocks measured ~1.2GB per bucket all families combined (writelog ~450MB avg, 1-2GB dense-era). For a much denser chain (subnet EVM later), lower BucketBlocks per deployment: cook RAM scales with per-bucket writelog size (user reviewed 2026-07-29: fine as is).
- Epoch sections: bodies (zstd frames of 16 containers + published 512KB dict; measured 2026-07-17 on 112k real containers: 2.24x blended, 34us random-access decode; frame-256 buys +5% for 14x slower access, rejected), headers, proposervm extras, state write-log SST of (account,key,^block)->NEW value rows, EF fp48 tx index, the per-epoch TX-FINGERPRINT BLOOM in front of it (v5), log posting lists (position-agnostic addr/topic -> EF block lists), per-epoch key bloom, stored-logs sections, footer (offsets, version, and since v4 the PREV-EPOCH HASH; NO embedded signature: nothing in the file depends on who built it, so independent syncs stay bit-identical, decided 2026-07-20).

- SECTION RESIDENCY, the read-path shape since the casfs integration: an epoch's bytes arrive through `dist` (an mmap of the local spool file with no S3 credentials, casfs chunk-cache reads with them), so sections are no longer free slices of a mapping on every node. At open we read the SMALL ones and keep them (dict, both framed indexes, sstIdx, deletes, txbloom, keybloom, logs dict, both stored-section indexes); everything big is read BY RANGE at query time (bodies, headers, sst, logidx, stored logs, stored receipts, and since v5 txidx, which is read behind its bloom and, since ruling 3 landed on 2026-07-31, read AS BYTES with no decode and no LRU). The one searchable big section, logidx, is binary-searched with one small ranged read per probe and its list bounds come from the next table entry's offset (exact, because buildLogidx appends lists in table order). Since ruling 3 both paths are mappings and NOTHING copies: the resident sections are pinned views of the spool file or of casfs's sparse cache file, so the resident set is page cache on every node and a full node's first boot pays for it in ranged GETs. (It used to be heap on a credentialed node, because casfs assembled fresh copies per read.) (This used to say a limited-history node does not, because its bootstrap stopped at the floor; there is no floor since 2026-07-31, so every node opens every epoch.)
- Tx index: Elias-Fano over sorted 48-bit hash fingerprints + bit-packed block numbers. Verify by decoding the candidate block. No MPHF (EF matches its size, simpler). Validated on 12M real Fuji txs 2026-07-17: 288ns lookups, 0 false positives. EF cost is density-dependent (log2(U/N)+2), so PER-EPOCH sections run ~27-28 bits/tx; duplicate fp48s are real (~2,600 pairs at 1.2B txs), so the lookup API returns a candidate LIST. Atomic txs live in extdata, not the eth tx list, so they are outside this index.
- Compression: per-epoch zstd dict trained AT SEAL TIME on that epoch's raw containers (user directive 2026-07-18, supersedes one-global-dict; the dict ships inside the epoch file so distribution stays self-contained). Trainer is the zstd CLI (pinned v1.5.7) with a start-block-derived `--dictID`: klauspost's `dict.BuildZstdDict` is map-iteration nondeterministic (measured) and would break bit-identical files. Encode/decode is klauspost zstd, SpeedBestCompression.
- Sealing parameters (constants in `state/epoch.go`): the EPOCH SIZE SCHEDULE `EpochTxsAt` (see the doubling-schedule entry below; it replaced the flat EPOCH_TXS=10,000,000 of 2026-07-20 and the 25,000 corpus-stress dev value, and there is no size flag any more), frame-16 bodies/headers, 512KB dict target, 64KB SST blocks, bloom 20 bits/key x 14 hashes (RAISED from 10 x 7 on 2026-07-30, see the miss-cost entry below; free to change because Fuji had not sealed yet).
- WHY EPOCHS STAY SMALL, the argument re-derived and re-confirmed 2026-07-30: the UNSEALED tail costs ~1.8GB per million txs on every node (measured: 128GB of ancillary families for 70M txs), and the sealed form is ~4.5x denser. Epoch size therefore sets everyone's raw window: 10M txs bounds it at ~18GB, while the 50-100M-tx epochs proposed that day would make it 90-180GB. Seal itself is cheap and streaming either way (a k-way merge, a few GB of RAM, ~2h of single-threaded zstd CPU per 10M-tx epoch), so nothing pulls the other direction. (The flat 10M this concluded with is SUPERSEDED by the doubling schedule below, which keeps the argument and only changes the ceiling to 8M; the tail bound moves to ~14.5GB.)
- EPOCH SIZE IS A DOUBLING SCHEDULE, NOT A CONSTANT [RULING 2026-07-31, AS BUILT the same day]. `state.EpochTxsAt(i)` is the entire rule: `size(i) = min(8,000,000, 250,000 << i)`, i.e. 250k, 500k, 1M, 2M, 4M, then 8M forever, so the cumulative boundaries are 0.25M, 0.75M, 1.75M, 3.75M, 7.75M, 15.75M, and +8M each after. It is a PURE FUNCTION OF THE EPOCH INDEX, identical for every chain and every VM kind, with no flag and no config: `seal --epoch-txs` is DELETED, `SealEpochs` no longer takes a size, and the index the seal loop feeds the schedule is simply how many epochs are already sealed, so a resumed seal cuts exactly where an uninterrupted one would. This supersedes the flat 10M (ruling 2026-07-28) and closes the OPEN epochTxs pair recorded under the fleet section.
  - WHY THE SMALL START: never sealing is not free, and the cost falls on the node that is running, not on a publisher. A chain that never fills an epoch hoards its whole history in the raw tail, which is HEAP-BACKED and unevictable rather than mapped, is ~4.2x bigger than the sealed form on SSD, has NO S3 offload path (only sealed artifacts are content-addressed and tierable), and answers misses by descending it without a per-epoch bloom. Measured on FIFA 2026-07-31: ~250 B/tx of heap for a tail that never seals. At 250k the first epoch is reachable by a real L1 (FIFA at 972k txs seals two epochs, cumulative 750k, plus a ~222k tail instead of zero), which is the whole point of the small start.
  - WHY THE GIANTS ARE UNAFFECTED: the five small epochs are 7.75M txs, noise against a billion, and everything above them is the flat 8M, so a big chain converges to the proven shape: C-chain at ~1.2B txs cuts ~152 epochs, DFK at ~1B cuts ~130. Miss cost and bloom hot-key duplication scale with the NUMBER of epochs, and ~152 is still the shape the residency numbers were measured against (120 epochs): ~152 bloom probes ~15us per miss, ~0.01 wasted SST reads per miss at the 20-bit bloom, bloom RAM grows from the measured 3.30GB toward ~3.7GB.
  - WHY A PURE FUNCTION OF THE INDEX: node equality is the format's core promise, and every node must cut byte-identical boundaries independently, without a registry, a config file or a conversation. Cumulative tx count is chain content and the epoch index is a count of epochs, so nothing local can reach the boundary. This is exactly why ADAPTIVE thresholds (cut on elapsed time, disk pressure, or observed tx rate) and CONFIGURED thresholds (a per-chain or per-operator knob) were rejected: both let two honest builders of the same chain emit different files.
  - WHY NOT THE FLAT PER-VM-KIND PAIR that was on the table (coreth 10M, subnet-evm 1M): a large L1 is not a small chain. DFK at ~1B txs under a 1M constant would cut ~1000 epochs, i.e. ~6.5x the mainnet epoch count on a chain smaller than mainnet, which is the one number the whole residency design is sized against. One schedule keyed on the index does what the pair was trying to do without the cliff.
  - ACCEPTED COST, stated plainly: the unsealed tip tail can reach 8M txs before a seal. The ceiling was briefly 16M (user amendment 2026-07-31, pure powers of two off the 250k base) and was lowered to 8M the same hour (user ruling 2026-07-31): at L1 density (~1.2 tx/block) a 16M tail is ~100GB of non-offloadable disk and ~4GB of heap, and halving it costs the C-chain only ~77 to ~152 epochs, still inside the proven miss shape. 8M keeps the powers-of-two aesthetic.
  - NO MIGRATION AND NOTHING TO REPACK: the Fuji corpus has not sealed a single epoch yet (seal runs after the replay finishes), and mainnet is untouched, so the schedule simply applies at the first seal. Nothing that exists on disk is affected.
- ONE NODE TYPE (ruling 2026-07-30). There are no archival/pruned/indexer personas and no second binary: "how much history do I keep locally" is a chunk-cache size over the bucket, and the indexes are inside the epoch format. (This line used to offer a floor as the other half of that knob; ruling 1 of 2026-07-31 deleted the floor, so local disk decides only how fast cold history answers, never what a node can answer.) The serving core does decompose into two roles, which is what makes that true: the follower/executor/publisher role, which owns the writable data dir and is the only writer, and a STATELESS IMMUTABLE-HISTORY role, which needs nothing but hashes and a chunk cache. A future `serve --history-only` worker (pin a hash or chunk range, serve reads out of it) therefore falls out of the seal boundary with no architecture change; not built, nothing blocks it.
- Epoch format v6 (2026-07-31): SAME 17 sections as v5, different contents in two of them: txidx and txbloom now cover every BLOCK hash as well as every tx hash, in one fp48 space, each block hash mapped to its own height. That is what deleted the floor-to-head block-hash map; see "Block hashes in the tx index" below.
- Epoch format v5 (2026-07-30): v4 plus one section, the tx-fingerprint bloom (`secTxBloom`, 17 sections now), which is what let the tx index come off the resident set. See the tx-index residency entry below for what was built and what it measures.
- Epoch format v4 (2026-07-30): v3 plus one footer field, sha256 of epoch K-1's whole file, with sha256 of the chain's genesis config as the root (see Distribution). Nothing else moved; the section table just starts 32 bytes later.
- Epoch format v3 (2026-07-28 user decision): contract code ships INSIDE the epoch as `'c' | hash | zeros` rows in the SST keyspace ('a' < 'c' < 's'), so it rides the existing sparse index and key bloom and needs no new section. An epoch carries the code of every account row it writes (placement rule, see Torrent distribution). Blob rows are not state diffs: verification and the base fold skip them.
- Epoch format v2 (2026-07-20 user ruling), folded into v3: stored-logs sections are MANDATORY, not a flag. Per log-bearing block: addr/topics/data/txIndex records (logIndex positional, txHash+blockHash derived from bodies at read time), frame-16 with a DEDICATED 128KB logs-trained dict (measured better than the container dict). Per tx-bearing block: uvarint gasUsed + status byte (cumulative gas by prefix sum; bloom/contractAddress/effectiveGasPrice derived). eth_getProof stays impossible; getLogs posting lists still provide candidates, the stored sections replace only the response construction.
- NO UPGRADE PATH (user ruling 2026-07-28). v6 is the only format the code can read: `OpenEpoch` refuses an older file by name ("format v5, unsupported: delete the corpus and resync"; a v4-or-older file also fails the footer-magic check first, because the section table grew by one entry at v5, and gets the same "delete the corpus and resync" answer), and `OpenEpochSet` refuses a pre-casfs data dir (loose `epoch_*.epoch` files) by name for the same reason and there is no re-seal, no section surgery, no migration. The corpus is disposable, so a format change is paid for by a from-scratch sync, not by rewriting files.
- No database anywhere. Hot period = append-only logs + RAM maps; sealing = rewriting those logs into sorted compressed sections. Everything mmap'd; recent blooms pinned, old ones page-cached.
- Historical state read at block N: LRU, then hot RAM map, then per-epoch blooms newest-to-oldest from epoch(N), one SST seek on first hit, then the floor (genesis alloc today). DESCENT COST, verified 2026-07-30 and the reason no snapshot ladder is needed: ALL mainnet epoch blooms together are a few GB resident, so a full-depth miss walk (which is what every touch of a fresh address costs) is bounded by that RAM for the whole chain and a few hundred bloom probes. Snapshot-less serving is affordable at mainnet scale. See Measured numbers for the derivation.

MISS COST AND THE BLOOM WIDENING (measured 2026-07-30, user-driven). A key nothing ever wrote has NO early exit: `History.search` probes EVERY epoch, and sorted keys are `kind|addr|slot` unhashed so every epoch spans the full key range and no range pruning is possible. Expected WASTED SST block reads per miss = epochCount x per-epoch false-positive rate, and under casfs a wasted block read can be a cold 4MB chunk GET. At the original 10 bits/k=7 that was 0.98 on a 120-epoch mainnet: every unset-slot read (the common case inside any eth_call) paid a real block read. Measured with the exact bloom, 40M probes per setting: 10/7 gives 0.8172% per epoch and 0.98 wasted reads per miss at 1.65GB resident; 16/11 gives 0.0449% and 0.054 at 2.64GB; 20/14 gives 0.0069% and 0.0083 at 3.30GB; 24/17 gives 0.0009% and 0.0011 at 3.96GB. RULING: 20 bits x 14 hashes. 118x fewer wasted reads for 1.65GB more resident bloom and the same 1.65GB spread across the whole published corpus, which is noise against ~500GB of history; probe cost goes 60ns to 99ns, irrelevant beside the block read it avoids. This kills the need for a separate global union filter over all keys ever, which would have cost more RAM for the same effect. Readers already take m and k from the file, so this was a two-constant change.
THE RESIDENT INDEX BUDGET, measured 2026-07-30 and larger than the ~8GB this file used to claim. Section costs from real epoch files (4 epochs of exactly 40,000 txs each; the txidx header's own nTx is the cross-check, and a footer parsed with the v4 layout on a v3 file silently gives right sizes with wrong per-tx figures): txidx 6.35 B/tx, rcptIdx 11.7-12.1 B/block, fullLogsIdx 8.9-10.5 B/block, bodiesIdx and headersIdx 0.51 B/block each, dict 0.016-0.524MB fixed per epoch, keybloom bitsPerKey/8 per distinct key written. Resident sections are 4.7-7.2% of an epoch file. Projected to mainnet (1.2B txs, ~90M blocks, 120 epochs of 750k blocks, EF l=24 blkBits=20, model reproduces the measured epoch to 1%): txidx 7.10GB, keybloom at 20 bits 3.30GB, rcptIdx 1.07GB, fullLogsIdx 0.87GB, bodies+headers idx 0.09GB, TOTAL ~12.4GB plus a few hundred MB of dict/deletes/sstIdx. THE txidx LINE IS HISTORY as of the v5 build below: it is 0 resident now, replaced by 2.40GB of tx bloom, so the same projection is ~7.7GB, of which 5.70GB is mmap-backed bloom (keybloom + txbloom) and ~2GB the remaining indexes. The v6 block-hash fold adds a measured 180MB to the tx bloom at mainnet's ~90M blocks (2.40GB -> 2.58GB) and deletes 7.3-9.1GB of Go heap for the map it replaces.
SO THE TX INDEX, NOT THE STATE BLOOM, IS THE BIGGEST RESIDENT ITEM, at more than 2x the key blooms, and it is the one with NO filter in front of it. fp48 is not the waste and must NOT shrink: an unknown hash false-matches with probability 10M/2^48 per epoch, about 4e-6 across the whole chain, whereas 40 bits would give ~1.1 false candidates per query and each one costs a body read, which is exactly the failure the bloom widening just removed. At 47 bits/tx for a (48-bit fingerprint, 20-bit block) pair the structure is already near its floor. THE ONLY LEVER: put a per-epoch tx-fingerprint bloom in front and make txidx range-read on demand, which trades ~4-5GB of RAM for a ranged read (possibly a cold 4MB chunk) on the hot path of a KNOWN tx lookup. RULED ON AND BUILT the same day, see the next two paragraphs.

AS BUILT: (a) `secTxBloom`, a new epoch section over exactly the fp48s `buildEpochTxidx` encodes (same slice, so the filter and the index it guards cannot disagree), 16 bits/tx with the matching optimal k=11, built with the existing bloom machinery (`bloomBits`/`bloomSet`/`encodeBloom`/`bloomHash`, now taking bits-per-key and k as arguments so the key bloom and this one share one implementation) and read through `bloomView`, a zero-copy slice of the section probed with `binary.LittleEndian.Uint64`: alignment-free, so it is page cache and not Go heap, exactly like keybloom. BLOCK HASHES IN THE TX INDEX [BUILT 2026-07-31, epoch format v6, ruling 2 of the finalization]. THE PROBLEM: serve held the block-hash index as a plain `map[common.Hash]uint64` over EVERY block from floor to head (`fetch.BlockHashes` at startup plus an `AddBlockHash` backfill loop), the single biggest resident item in the process, larger than every bloom and index combined, and missed in the earlier budget. THE FIX is not a second structure: a block hash and a tx hash are both just hashes that resolve to a block number, so block hashes go INTO the tx index and its bloom in the same fp48 space, mapping to the block's OWN height.

AS BUILT: (a) `buildEpochTxidx` prepends one (fp48(keccak(headerRLP)), block) pair per block to the pairs it already builds from the tx hashes, so the EF index, the bloom (built from the same slice) and the sort are unchanged code paths, and `state.BlockHashFromHeaderRLP` is the one definition of a block hash both sides use (it IS `types.Header.Hash()`: keccak of the header's RLP, so no decode). NOT BUILT, deliberately: no separate block-hash bloom or index (the whole point is that one structure serves both kinds), no "kind" bit to disambiguate a collision (verification already does it, and a bit would cost more than the one read it saves), no cook-watermark prune on the ring (a fixed FIFO is smaller code; during a multi-thousand-block/s catch-up the ring can wrap before the next cook and a block-by-hash in that window answers null until the cook lands, on a node that already reports `eth_syncing`), and no verification-side check that an epoch's folded entries are complete (the same argument as the v5 bloom: the fingerprints derive from headers the verifier already checks, and a wrong index can only cost reads or a null, never a wrong block).

PLANNING SESSION 2026-07-30 EVENING, kernel-tiered residency. OPEN DIRECTION, nothing built, nothing committed to. Where it landed: (1) the rule is "nothing on this path lives on the Go heap": every index structure is a section of a mapped file and the KERNEL tiers S3 to SSD to RAM; blooms stay hot because misses themselves touch them, everything else falls out of cache, and on a small box the penalty is a refault instead of an OOM. (2) The meta/data file split was proposed and KILLED same session: it only bought cold-start locality, demand paging gives that for free, and a historical cold start is weeks anyway, so 10GB of index fetch is noise. (3) The concrete mechanism candidate for mmap over casfs: ONE SPARSE FILE per artifact instead of per-chunk files, chunks pwritten at their true offsets, presence discovered at open via SEEK_DATA (the kernel's extent metadata is the truth, no bitmap to persist), eviction via FALLOC_FL_PUNCH_HOLE, whole file mmap'd so Blob.Slice stays zero-copy and contiguous across chunk boundaries. (4) THE TRAP, and it is correctness, not performance: the RAM-to-SSD tier is safe (evicting a file-backed page just refaults), but the SSD-to-S3 tier is NOT, because punching a hole under a LIVE mapped view silently reads back zeros, and a zeroed bloom page produces FALSE NEGATIVES: the descent skips an epoch that has the key and serves an older value as current, or a real tx reads as not-found. Today's unlink eviction cannot do this (an open fd keeps its data). So hole-punch eviction REQUIRES pinning: an epoch open declares its resident-section ranges and casfs never punches pinned ranges. This is the load-bearing detail if the direction is ever built.

WHY ELIAS-FANO, AND THE PERFECT-HASH ALTERNATIVE (considered 2026-07-30, NOT adopted). EF is not a poor choice: it stores an EXACT sorted set of n 48-bit fingerprints in l + ~2 bits each, and the information-theoretic floor for that is log2(u/n) + log2(e) = 26.2 bits at 10M txs per epoch, so the measured 27.4 bits is within about 5% of optimal. The 47.4 bits/tx splits as 27.4 for the fingerprint side and 20.0 for the block number. But exactness is capability we do not need: the fp48 is ITSELF only a lossy proxy for the tx hash, so paying near-optimal cost to store a lossy value exactly is the real inefficiency, which is what a perfect hash would fix. A minimal perfect hash (RecSplit ~1.6 bits/key, BBHash ~3, PTHash ~2-4) maps the epoch's hashes to [0,n) with no collisions, and a 16-bit verification fingerprint per slot rejects non-members at 2^-16 per epoch (about 0.002 false candidates per unknown-hash query chain-wide, versus 4e-6 today). That is 3 + 16 = 19 bits where EF spends 27.4, saving about 18% overall, which is modest ONLY because the 20-bit block payload is incompressible and dominates.
THE REAL PRIZE IS WHAT MPHF ENABLES, not the bits it saves: a slot is computable, so the block array becomes ONE ranged read at a known offset instead of an EF traversal, which makes it viable to keep the block array OFF the resident set. Resident would then be MPHF plus fingerprints, 0.45GB + 2.40GB = 2.85GB against today's 7.10GB, with unknown hashes still rejected entirely in RAM and a known hash costing one small ranged read. NOT ADOPTED, for one reason that outranks 4.25GB: MPHF construction is seed-search based, and epoch byte-identity across independent builders is this project's core promise, so introducing a randomized build step into the one artifact that must be reproducible bit for bit is a hazard on exactly the guarantee we cannot get wrong. Deterministic construction is achievable (fixed seed, ordered iteration) but it must be PROVEN by two independent builders, not assumed. Secondary reason: 7.10GB is not the binding constraint next to Firewood's 130-157GB. REJECTED outright, same session: a plain sorted array of (fp48, block) pairs at 68 bits/tx, which is worse than EF, and shrinking fp48 (see above). IF this is ever adopted it must land BEFORE mainnet seals, like every other format commitment.
MMAP VERSUS HEAP FOR THE RESIDENT SET (checked 2026-07-30; ITS CONCLUSION IS DEAD as of ruling 3 on 2026-07-31, which mapped the EF exactly as the paragraph describes and made the objection below false: casfs now hands out views of one sparse file per artifact, so a credentialed node DOES have a whole-file mapping. Kept for the reasoning. Also SUPERSEDED FOR THE TX INDEX by the v5 build above, which took the whole 7.10GB off the resident set instead of mapping it, and kept the heap decode for the handful of epochs an LRU holds). The two big items differ, and not in the obvious way. The KEY BLOOM is ALREADY mmap-backed on a credentials-free node: `e.bloomBits` is a slice into `e.sec[secKeybloom]`, which `Blob.Slice` returns as a zero-copy view of the mapping, and probes read it with `binary.LittleEndian.Uint64`, which needs no alignment. So that 3.30GB is page cache, evictable and shared, not Go heap. The TX INDEX is the opposite: `readWords` copies the section word by word into `[]uint64` and the section bytes are then dropped, so all 7.10GB is real Go heap, counted by GOMEMLIMIT and never returned to the OS. It COULD be mmap-backed with no format change, no alignment padding and no unsafe, by changing `ef`/`packed` read accessors to index a `[]byte` view with `binary.LittleEndian.Uint64` instead of a `[]uint64` (the build side keeps materializing in heap before serializing). NOT DONE, and the reason is the direction of travel: a node WITH S3 credentials has no whole-file mapping at all, because casfs assembles fresh copies out of its 4MB chunk cache and `Blob.Slice` allocates, so the win is exactly zero on the offloaded configuration this design is moving toward. Revisit only if casfs learns to mmap its chunk files, or if local-file nodes turn out to be the common deployment.
THE SAME MATH IS WHY EPOCHS STAY BIG: miss cost scales with the NUMBER of epochs, not their size, so 1M-tx epochs (1200 of them) would multiply it by 10 at any bloom width. Which is why the schedule's ceiling is 8M and not 1M: at 8M the C-chain cuts ~152 epochs, still the measured shape, and the five sub-8M epochs at the bottom of every chain cost five probes. (This used to say small L1s can seal smaller because `epochTxs` was a parameter of `SealEpochs`; it is not a parameter any more, the schedule gives small chains their small epochs for free.) Tx-by-hash used to have the same shape and no filter at all; since v5 it has one (`WalkCandidates` probes each epoch's tx bloom and stops at the first verified hit), so its miss cost is 120 in-RAM bloom probes rather than 120 index traversals.

## Verification without re-execution [BUILT]
Third parties verify downloaded epochs with NO EVM execution: (1) state: stream SST post-image diffs from genesis into a throwaway Firewood, commit per block, root must equal `header.Root` every block; (2) bodies: recompute txRoot per block from verbatim containers; (3) logs/receipts: v2 sections reconstruct full receipts (cumGas prefix sum, bloom from logs) and recompute receiptsRoot; (4) headers: parent-hash chain to a trusted anchor. Estimated 5-10x cheaper than replay (~1 day for full mainnet vs ~9 days); (2)+(3) are embarrassingly parallel.
BOTH VM KINDS SINCE 2026-08-01, which closes the last recorded coreth-only wart of the subnet-evm scoping: `epochdb verify --chain <blockchainID>` no longer refuses an L1 by name. `verify.New` takes the kind off the descriptor and routes the libevm extras registration and the throwaway's state database through exec's existing `vmBackend` seam, exactly as exec and rpc do; anchorless mode (tests) takes whatever kind the process registered, coreth when none. NOTHING IS SKIPPED on the subnet-evm path: all four checks run, and the SAE refusal is unreachable there by construction (`hasSettledMarkers` is false on every subnet-evm header, M4). Verification does no execution, so the chain's upgrade.json cannot reach it through the config the way it reaches exec; what it reaches is the ANCHOR, and `VerifySet` now checks epoch 1's prev-hash against `c.Root()` before it verifies a byte, so a dir whose upgrade.json is missing or edited fails by name instead of replaying a different chain's history against default upgrades. Gate: `verify/sevmverify` (its own package for the process-global-registration reason `exec/sevmexec` has), a FIFA-shaped mainnet L1 WITH an upgrade.json, two hash-chained epochs off its real genesis, plus the two mutations that prove it can fail (a flipped SST byte, and verifying with the upgrade bytes dropped).
Two bootstrap modes: plain (walk the hash chain, index it, exit) and `--verify` (walk, then verify the whole indexed set in chain order against one throwaway Firewood, which is also what pulls every byte). Failure names the epoch and exits nonzero. The PIPELINED cursor that used to chase the contiguous prefix as parallel downloads completed was deleted with the fetcher on 2026-07-30: casfs moves the bytes now, so there is no out-of-order completion to pipeline against. Slab-parallel verification (self-anchoring constructed frontiers) is a future many-machines option, not built.

## Distribution: S3-first and content-addressed [BUILT 2026-07-30, library + integration]
User ruling 2026-07-29: "normal centralized epoch + latest snapshot publishing works for me." Distribution is one publisher and many read-only consumers, exactly the case where a swarm is a worse HTTP server, so the ENTIRE torrent stack is GONE: `dist/` (471 lines), the anacrolix dependency tree (17 modules out of go.mod, 458 lines out of go.mod+go.sum), `epochdb seed`, DHT/trackers, `serve --fetch-epochs` (redundant once bootstrap is a plain GET pass), and the manifest's infohash column. Object storage is R2/B2-class with zero egress; raw S3 egress would be ~$60 per full archival bootstrap. Epochs stay deterministic and bit-identical across builders, so sha256s remain stable facts anyone can independently reproduce.

RULING 2026-07-30 (supersedes the 07-29 "lazy loading, fuck that" ruling): S3 offloading with lazy chunk loading IS core, 100%. Publishing an epoch means putting it in a bucket, and a node's local disk is a CACHE of that bucket sized by config. This is the only structural addition that came out of the 2026-07-30 design day; every other candidate was parked or rejected, see "Parked and rejected".

THE LIBRARY [BUILT: github.com/containerman17/casfs, its own public repo, deliberately isolated from epochdb because nothing in it is chain-specific]. A content-addressed file store over any S3-compatible bucket.
- WHOLE FILES, NAMED BY HEX SHA256. The name IS the integrity check, so Put is idempotent and any number of nodes can share one bucket with zero coordination and dedupe for free.
- SPOOL-DIRECTORY DURABILITY: the library holds NO state outside the filesystem, and its spool directory IS the registration. A caller atomically renames a hash-named file into the spool, so there is no ack to lose and it is kill-safe by construction; the library scans the spool at startup and on demand, uploads anything not already in the bucket, and verifies the sha256 WHILE uploading (loud failure on a name/content mismatch, no separate pre-verify pass). `Release` confirms the upload and unlinks the spool file.
- ONE READ PATH: reads ALWAYS go through the local chunk cache. Chunks are ~4MB, and SINCE 2026-07-31 an artifact is ONE SPARSE FILE (`cache/<2-hex>/<hash>`) with chunks pwritten at their true offsets, so a consumer can map the whole thing; a miss is filled by pread from the spool file while that file is still local, otherwise by a ranged GET, and that source choice is the ONLY difference between the two states. Chunks are never durability (the spool file or the bucket is), so eviction is FALLOC_FL_PUNCH_HOLE over the chunk's range, which is also why PINS exist (see ruling 3): a punch under a live mapping reads back as zeros. Presence after a restart is the kernel's own extent map, read with SEEK_DATA; there is still no on-disk index and no compaction. Recency is an in-memory LRU seeded from mtime at startup, with touch-on-read throttled (default 1h) so serving does not become an mtime write storm. A 200GB cache at 4MB chunks is 50k files, trivial.
- POINTERS ARE SPOOLED FILES TOO [SINCE 2026-08-02, see the seal ruling]. The one mutable name in the bucket is written locally by `SetPointer` and reconciled by `Sync` after that pass's content, then released; `GetPointer` answers locally while the value is spooled, otherwise reads the bucket and re-materializes it. No casfs write of any kind touches the network.
- REJECTED same day: a Release-time full-chunkification pre-warm (user: cache pollution; ranges that are cold by definition falling through to S3 on demand IS the design). Only organic traffic warms the cache, which also makes the spool-to-bucket transition invisible: whatever was being read is already cached when the spool file goes away.

NODE SIDE: S3 credentials are OPTIONAL. With them, sealed epochs offload to the bucket and deep history lazy-loads on demand, so a ~200GB node serves FULL archive semantics and is merely slower on cold history. Without them, the node holds everything locally and nothing about the read path changes.

MIRRORS FEDERATE TRIVIALLY: the config takes a LIST of backend URLs, and any HTTP endpoint serving the same hashes is interchangeable, an IPFS gateway included. No registry, no coordination, no official mirror; the hash space is the namespace.

NODE INTEGRATION [BUILT 2026-07-30, `dist/` ~430 lines, the only package that knows casfs exists]. One type, `dist.Store`, hangs off the state layer (`state.Store.Cas()`), so one process has exactly one of them and therefore one chunk cache. Producers publish, readers open, and NOTHING above this file has an S3 branch:
- SEAL PUBLISHES BY RENAME. `BuildEpoch` already assembled the whole file in RAM, so it hashes the buffer and writes it straight onto its own spool path (casfs `Put` stays the fallback nobody needs), then writes the local marker and advances `latest`. (The fold did the same for snapshots; both it and the snapshot half of `latest` died 2026-07-31.)
- READS: `dist.Store.Open(hash)` returns a `*Blob` whose `Slice(off, n)` is a zero-copy view of a mapping on BOTH paths since ruling 3 (the spool file without credentials, casfs `View` over the sparse cache file with them), and `Pin`/`Unpin` are the contract that keeps a view honest. `TestEpochThroughRangedReads` reads one epoch both ways, out of a fake bucket after the local copy is released, and compares every section, so the credentialed path was covered before a real bucket existed; since 2026-07-31 it is also covered against a real MinIO (see Debt and rulings).
- CONFIG IS ENVIRONMENT ONLY (no config system, per the standing directive): `EPOCHDB_S3_ENDPOINT` (empty = fully local), `_BUCKET`, `_ACCESS_KEY`, `_SECRET_KEY`, `_PREFIX`, `_REGION`, and, since 2026-08-03, `EPOCHDB_CACHE_MIN_FREE` (bytes of free space the chunk cache stops filling at, default 5% of the filesystem) and `EPOCHDB_CACHE_MAX_AGE` (default 720h). `EPOCHDB_CACHE_BYTES` is DEAD with the byte budget and is ignored. CREDENTIALS ARE TWO ROADS since 2026-08-01 (user ruling): static `_ACCESS_KEY`/`_SECRET_KEY` are the R2 and MinIO path and always win, and UNSET keys mean the AWS SDK's DEFAULT CHAIN (env, shared config, SSO, instance role), which is what makes a temporary-credential deployment work with nothing but an endpoint, a bucket and a region. casfs pulls in `aws-sdk-go-v2`'s `config`/`credentials` for resolution ONLY: the HTTP client and the SigV4 signer stay hand-rolled, credentials are retrieved per request so a refresh lands on the next call, and a session token is signed as a fourth header, `x-amz-security-token` (the signer is pinned against the SDK's own v4 signer, with and without a token). The chain also supplies the region when `_REGION` is empty, before the `auto` fallback, so R2 is untouched. A bucket outside the shell profile's region still needs `_REGION` set, because the chain hands back the profile's. The spool is `<data>/cas`, the chunk cache `<data>/cache/<window>/<chain>/` since 2026-08-03 (it was `<data>/chunks` until 2026-07-31, which collided with the `chunks/<hash>` pointer namespace: casfs deletes everything in its cache dir that is not one of its own files, so a credentialed open ate the local chunk-list pointers; then `<data>/chunkcache` until 2026-08-03, which `dist.Open` now deletes on sight).
- UPLOADS RUN ON A TICKER INSIDE SERVE, `--sync-every` (default 5m): Sync uploads everything spooled that the bucket lacks, then Release unlinks each confirmed local copy. THE TICKER IS THE ONLY THING THAT TALKS TO S3 (ruling 2026-08-02), pointers included, and it uploads them last. Fail-loud, never fatal: a failed upload leaves the artifact durable in the spool and the next tick retries. Without credentials the loop does not start.
- MMAP OF THE SPOOL FILE IS THE NO-CREDENTIALS PATH ONLY, deliberately. With credentials a released artifact must actually free disk, and a live mmap of an unlinked file pins the inode for the life of the serve process, so a credentialed node reads through the chunk cache. That is a mapping too since 2026-07-31 (one sparse file per artifact), which is what let ruling 3 delete the last copies on the read path.

BOOTSTRAP FLOW [BUILT 2026-07-30, snapshot half deleted 2026-07-31]. The bucket carries exactly ONE mutable, non-content-addressed object PER CHAIN: that chain's `latest-<chain root>` pointer (`dist.LatestPointer`, qualified since 2026-08-02, see THE FLEET), naming the newest epoch hash and nothing else (`epoch <hash>`, written locally as well, and since 2026-08-02 written ONLY locally, with the upload left to the sync ticker, so a producer neither blocks on S3 to publish nor asks it anything on restart). `epochdb bootstrap` is then: read `latest` -> walk the epoch footers BACKWARD by prev-hash, writing one marker per epoch, checking contiguity at every step (epoch K-1 must end exactly where epoch K starts) -> stop at the first epoch, checking that its prev-hash equals this network's CHAIN ROOT, and refusing "wrong chain" otherwise. `--frontier` then merges the indexed epochs into a Firewood frontier at the last sealed block (ruling 1), which is the step that replaces downloading a snapshot. NOTHING IS DOWNLOADED EAGERLY: with credentials the reads that follow pull the chunks they touch, and without them the artifacts are already in the spool. `--verify` runs the whole no-execution verification over the indexed set afterwards, which is what actually pulls every byte. THE POINTER IS A HINT, NEVER AN AUTHORITY: all content self-verifies by hash, the chain roots at the chain root, and the first executed block's Firewood root check against consensus-verified headers catches a lying snapshot. S3 is untrusted infrastructure; the only attack it enables is withholding bytes, which is what mirrors answer.

FORMAT COMMITMENTS [BUILT 2026-07-30, before the mainnet seal as required]. There is no reseal (see the no-migration rule), so these were cheap then and impossible later.
- HASH-CHAIN FOOTERS: epoch K's footer embeds sha256(epoch K-1), and a chain's first epoch embeds the CHAIN ROOT, which since 2026-07-31 is `sha256(genesisData || upgradeBytes)` over the chain's on-chain CreateChainTx genesis (rulings 5 and 6 above; `dist.ChainRoot` still reads avalanchego's embedded `CChainGenesis` for the C-chain, because those bytes were verified identical to the on-chain ones). Prev-hash is chain content, so files stay bit-identical across builders, and ONE head hash authenticates all of history. This KILLED the JSON manifest: `Manifest`, `epochdb manifest`, the HTTP fetcher and the pipelined `verify.Cursor` (which existed only to chase an out-of-order fetcher) are deleted, ~370 lines. Seal takes `--network` again for exactly one reason, that root; it still needs no genesis state, no overlay and no EVM.
- THE SNAPSHOT HASH IS NOT IN THE EPOCH FOOTER, and the plan that said it was is wrong (resolved 2026-07-30 while building; moot since 2026-07-31, there are no snapshots). Archival nodes seal and pruning nodes fold, and neither runs the other; an archival builder cannot know the snapshot's bytes, so embedding its hash would make epoch K depend on which kind of node built it and break the byte-identity the whole scheme rests on. The pairing lives in `latest`, which is exactly where the bootstrap flow reads it.
- PER-CHUNK HASH LISTS: one list per artifact, 32 bytes per 4MB chunk (so ~32KB per 4GB epoch, not the ~600KB the plan guessed), published as an ordinary content-addressed artifact and found through the pointer `chunks/<artifact hash>`. NOT referenced from the artifact's own footer, because it cannot be: a list that covers a file's own chunks changes those chunks the moment the file records its hash. Its authority is instead the whole-file sha256 the epoch chain already carries, so a lying list can waste a downloader's bytes but never make it accept wrong ones. NOT WIRED INTO FILLS: verifying a chunk as casfs materializes it needs a hook casfs does not expose, so today the lists are produced, published and independently checkable (`dist.Chunks`, `dist.VerifyChunk`) and nothing consumes them in-process. That hook is the whole remaining piece for peer-to-peer chunk serving, which stays parked.
- NAMING STANDARD: plain hex sha256. Deliberately NOT IPFS CIDs (a CID of any multi-chunk file is a chunker-dependent DAG root, forcing UnixFS on us) and NOT torrent infohashes (a hash of a bencoded dict, piece-length dependent). Everything stays verifiable with stock `sha256sum`; CIDs remain computable later if interop is ever wanted.

THE LOCAL INDEX, and why it is not a manifest in disguise: a data dir carries one marker per known artifact, `epoch_<start>_<count>.cas` (and, until 2026-07-31, `base_<B>.cas`), each holding 64 hex characters. It records only which artifact covers which heights; it has no sizes, no signatures, no ordering authority, and every hash in it is self-verifying. Boot reads markers (readdir, the old shape), bootstrap writes them from the chain walk, and losing one costs a re-bootstrap, not data. The alternative, walking the chain at every boot, would have made a producer's own history depend on a mutable pointer.

Contiguous-prefix rule after an incomplete fetch: coverage is the contiguous epoch range from genesis (`EpochSet.CoveredEnd`). State, receipt, and log queries above the first gap return a clean "missing epoch epoch_X" error (`RequireCovered`). ASYMMETRY, deliberate: bodies and tx-by-hash above the gap still serve (epoch-local reads) while state correctness requires full descent to genesis. `SealedEnd`/head still reports the highest local epoch.

CODE IN THE EPOCH FILE, format v3 [BUILT 2026-07-28, user decision 2026-07-28]. The gap: contract code is NOT in the epoch format and NOT in the manifest, it lives only in the standalone `code.log` (`state/codestore.go`, read at `state/overlay.go:433`), which the executor writes as a side effect of replaying blocks. So a node bootstrapped purely from downloaded epochs holds every block, state value, log, and account code HASH, but not the code, and the first `eth_getCode` or contract-touching `eth_call` fails. Never caught because every gate ran on a box that had built its own corpus and therefore had `code.log` locally.

Decision: code belongs IN the epoch, as `'c' | hash` rows in that epoch's SST keyspace, exactly the trick `state/base.go` already uses ('a' < 'c' < 's' share one sorted keyspace). Code lookup then rides the existing per-epoch bloom and descent with no new machinery, and an epoch file becomes genuinely self-contained, which is what the distribution contract always claimed. `code.log` stays as the hot-tail store for code deployed above the sealed end. Limited-history nodes are unaffected either way: the snapshot carries the blobs as 'c' rows.

PLACEMENT RULE, decided by measurement on the real 0-10M corpus (2026-07-28): an epoch carries the code of EVERY account row it writes, not only of the code first deployed inside it. Measured on the 7 production epochs: first-deploying-epoch would cost 288MB of blobs, every-referencing-epoch costs 478MB, i.e. +190MB (+0.6%) on a 32.6GB corpus, 57-87MB per epoch before compression. That price buys the invariant that WHICHEVER epoch answers the account read also carries that account's code, derived from the epoch's own account rows: no earlier epoch and no raw writelog, only code.log for the blob bytes. DETERMINISM: the set is a pure function of the epoch's own post-image rows (chain content), blobs are content-addressed, and `buildSST` sorts them, so map iteration order, wall time and local file layout cannot reach the bytes. Sanity check on the corpus: every code hash referenced by an account row over all 10M blocks is present in code.log, zero misses, and 34,711 of code.log's 35,011 blobs are referenced at all.

AS BUILT: footer version 3, same 16 sections and same layout as v2 (code rows live inside the SST, so nothing new is indexed). Read path is code.log, then epochs newest-to-oldest bloom-gated, then the genesis alloc (the base-file step in between died with the base file on 2026-07-31) (alloc code is never deployed by a block, so no epoch carries it). There is NO in-place upgrade: the v1 -> v2 append path and the v2 -> v3 section surgery were written, proven on a real production epoch, and then DELETED 2026-07-28 per the no-migration ruling. `OpenEpoch` reads the footer version, refuses anything but v3 by name, and that is the whole of the compatibility story, so `serve` needs no version check of its own. Two absent-file rules relaxed so a download-bootstrapped node can start at all: a missing `code.log` and a missing `misc.log` are now empty stores rather than open errors (nothing ever executed there); `OpenHistory` still refuses a dir with no buckets and no epochs. Every sha256 changed, which was expected (a v3 epoch is a different file). Per the 2026-07-28 ruling there is no re-seal of the existing mainnet corpus: data-fresh stays v2 and frozen, and the v3 corpus comes from the from-scratch sync at the end of the work order.

## Parked and rejected (design day 2026-07-30)
A full day of alternatives was walked. The outcome, in the user's words: the current architecture was defended 100%, and the only addition is S3 offloading. Concretely, what STANDS: epochs cut at EPOCH_TXS=10M, and state reads by descent with per-epoch blooms. (The third item that day, ONE latest snapshot artifact for bootstrap, was killed by ruling 1 on 2026-07-31: bootstrap merges the epochs instead.) What follows is recorded so nobody re-derives it from scratch.

PARKED, viable and deliberately not built: FAT EPOCHS. A snapshot welded to every Nth epoch boundary, with lookups walking the light epochs back to the nearest fat one instead of all the way to genesis. It buys real things: multiple bootstrap entry points, range nodes ("hold epochs 38-42 only"), misses that cost O(1) independent of chain age, and bloom residency bounded by the cadence rather than by chain length. It costs compounding snapshot rent (every fat epoch carries a state-sized payload that grows with the chain) and a cadence constant to pick and defend forever. PARKED because the verified bloom numbers removed its main argument (all mainnet blooms together are ~1.5-1.8GB, so RAM survival was never at risk) and because bootstrap has exactly one entry point today anyway. REVISIT IF: bloom residency or full-depth miss latency actually starts hurting at 5-10x mainnet, or range nodes become a product requirement. The door stays open at zero cost: hash-chain footers plus snapshots stamped with their boundary make turning this on a publishing-cadence decision, not a format change.
RELATED, and this is what ruling 1 actually shipped on 2026-07-31: a node builds its own frontier locally from the epochs it downloaded, so read-path self-sufficiency never depended on a publisher's snapshot cadence at all.

PARKED: peer-to-peer chunk serving between nodes that are already connected for consensus, one RTT to a peer instead of a ranged GET to a bucket. The per-chunk hash lists above are the whole enabling piece; nothing else is needed and nothing is built.

REJECTED, each with the reason:
- EMBEDDING SNAPSHOT BYTES INSIDE EPOCH FILES: a hash reference from the footer gives identical capability, and separate files let several epochs share one snapshot and keep seal and fold independent of each other.
- 50-100M-TX EPOCHS: the unsealed tail costs ~1.8GB per million txs, so this makes every node's raw window 90-180GB. Epoch size is a tax on all consumers, not just on the publisher.
- RESEALING OR INCREMENTALLY UPDATING PUBLISHED EPOCHS: every reseal is a new hash, which breaks the economics of content addressing (every mirror and every cache re-downloads) and makes compression O(n^2) over the life of the chain.
- IPFS AS THE TRANSPORT: cold DHT resolution is seconds against ~30ms for a ranged GET, and private or permissioned chains need access control, which swarms leak by design. IPFS gateways stay usable as ordinary mirrors, since the naming is plain sha256.
- TORRENTS: buried 2026-07-29, stays buried. Webseeds add nothing over HTTP mirrors.
- SHIPPING FIREWOOD'S OWN FILES instead of our snapshot format: the layout is non-deterministic, so two honest producers emit different bytes and nothing is verifiable across builders.
- A SECOND "INDEXER" SOFTWARE CATEGORY beside the node: the epoch format's internal indexes ARE the indexer (tx index, log posting lists, stored logs and receipts). One binary, one artifact set.

## Multi-chain, Avalanche L1s [PLANNED]
One binary and one format, with trust anchored PER CHAIN: the hash chain roots at sha256 of that chain's genesis config, which the client already has, so there is no global registry and no cross-chain authority anywhere. Every chain operator runs their own publisher and their own bucket. A private or permissioned chain uses a private bucket and inherits access control from S3 natively, which is precisely what a swarm cannot offer. Per-chain constants (EPOCH_TXS, bucket URL list, network id) live next to the genesis.
CONSIDERED AND YAGNI: an OR-bound on the epoch cut (seal at N txs OR M blocks) so a nearly idle chain does not take years to fill an epoch. Avalanche chains build blocks on demand, so few txs means few blocks: an idle chain's epoch simply stays small and cheap, and nothing is waiting on it. The tx-count cut alone stays canonical.

THE FLEET [RULING 2026-07-31, user: "worth building, and let's sync FIFA, let's go"]. The goal made explicit: ALL of Avalanche on one ~2-2.5TB NVMe box plus 3-4TB of S3 (C-chain ~250GB local, two or three mid-size L1s, everything else tiny). As ruled:
- ONE PROCESS PER VM KIND, so exactly TWO processes on the box: the C-chain alone (coreth extras) and one fleet process running every subnet-evm chain (libevm extras registration is process-global and panics on re-registration; this constraint shapes the fleet, it does not fight it). Config UX: a list of chainIDs, discovery via platform.getBlockchains, one goroutine set per chain, per-chain state dirs.
- SHARED CASFS ACROSS THE FLEET: content addressing means hashes cannot collide across chains, so one cache dir and one spool serve every chain in the process; pointers namespace as <chainID>/latest; the SSD-tier LRU is global across chains (a dead chain drains to zero, a hot chain takes what it needs, no per-chain budgets). The RAM tier was already shared box-wide via page cache regardless of process count. Per-chain cache floors are a known lever if noisy-neighbor eviction ever demonstrably bites; not built until then.
- FAILURE DOMAIN, accepted: per-chain executors hard-stop individually (a corrupt chain halts alone, the process lives); a panic in shared code takes the fleet down and a restart is cheap (followers catch up in seconds).
- FIREWOOD CACHE CLAMP [AS BUILT 2026-07-31, see the scoping's as-built entry below]: Firewood's node cache holds DECODED nodes (the measured cost it kills is deserialization and traversal, not reads; page cache already backs its file IO), so it cannot be replaced by mmap without an upstream rewrite. It gets explicit space by formula: clamp(3% of the Firewood dir size, 64MB, 4GB); the measured-good C-chain point is 4GB/157GB = 2.5%, so 3% is the calibrated ratio, and the hardcoded 4GB (whose ponytail comment predicted this day) dies.
- THE ANON BUDGET, the memory rule of the box: malloc is unevictable and page cache is not, so under pressure the kernel dumps exactly the mapped index pages we serve from while anon sits untouchable. Therefore NO dynamic memory-watching control loop; a fixed total budget for everything anon (Firewood clamps + exec state caches + Go heaps under GOMEMLIMIT) of ~30-40% of the box, and the majority of RAM stays DELIBERATELY UNALLOCATED because on a serving box the page cache IS the read cache. The tension self-resolves: big exec caches earn their RAM during catch-up (measured 88-89% hit), which is exactly when nobody queries; at tip pace they shrink. The cap exists so one chain's catch-up cannot strangle the others' serving.
- FLOORS/SNAPSHOT LADDERS re-litigated on fleet numbers and DEAD AGAIN, in the user's own arithmetic: a snapshot every few epochs is a terabyte-plus of near-pure waste now that blooms make misses cheap and the SST merge makes bootstrap cheap. Also noted for the record: ~99% of queries are on latest state, which the overlay and recent buckets serve without touching epochs at all.
- BUILD ORDER: (1) the ACP-77 peer-reachability spike against real FIFA validators FIRST, it is the one unknown that changes the plan; (2) subnet-evm support per the scoping's M1-M7, C-chain path unchanged and re-gated [M1-M5, M7, M8 and the clamp ALL DONE 2026-07-31, fetch live-gated on FIFA the same day; `epochdb serve --chain` is complete end to end and its unit gate is green, so the only thing left on this line is a live FIFA serve]; (3) the fleet process [AS BUILT 2026-07-31, below]; FIFA syncs as soon as the code is ready and the box is free of the Fuji pipeline's heavy stages.
- THE FLEET AS BUILT [2026-07-31, `cmd/epochdb/fleet.go` + `startNode` in `cmd/epochdb/follow.go`; THE COMMAND NAME `fleet` DIED 2026-08-03, it is `serve --chains` now, see the serve section's operator-surface ruling; everything below about the mechanism is unchanged]. It is COMPOSITION, not a second node: `serve`'s entire wiring (follower, executor, state layer, history, tail overlay, RPC, cook loop, status loop) was lifted verbatim into `startNode(ctx, nodeConfig, report)` and `serve` now calls it once, `fleet` calls it N times. Net new code is the supervisor and the router. Choices made where the ruling was silent:
  - CLI [SUPERSEDED the same day by the chains-are-IDs ruling below; it was `--chains fifa.json,beam.json`, descriptor paths]: `epochdb fleet --chains C,<blockchainID>,<blockchainID> --data <root> [--network fuji|mainnet]`, plus the same knobs `serve` has (`--port --node --vdr-sources --state-cache --cook-every --per-peer --sync-every --pprof`). `platform.getBlockchains` discovery stays a paper feature until someone wants to host a list they did not choose by hand.
  - LAYOUT: `<root>/<blockchainID>/` per chain (created on demand), `<root>/cas` and `<root>/chunks` shared by all of them via `dist.SetRoot`, which is the whole shared-casfs mechanism (one process-global variable read by `dist.Open`/`dist.Local`, set before any store opens). The SSD-tier LRU is therefore global across chains for free, since it was always one cap per cache dir. ## serve: one process at the tip [BUILT 2026-07-29] (user ruling: restart-based serving "makes the node unusable")
THE OPERATOR SURFACE IS ONE COMMAND, `serve`, AND EVERYTHING ELSE IS AUTOMATIC OR HIDDEN [RULING 2026-08-03, AS BUILT the same day]. Five parts, all of them live:

1. `epochdb serve` IS THE PRODUCT, and it is the only name an operator ever types. It follows, executes, indexes, cooks, seals, publishes, uploads and answers RPC, for one chain or for many, and it recovers by itself. `fleet` IS GONE AS A COMMAND: hosting N chains is `serve --chains C,<blockchainID>,...`; `--chain` stays the single-chain spelling; the two are ONE knob, and a `--chains` with one entry IS `--chain`, same directory and same behaviour. Only two or more chains change anything: solo, `--data` is that chain's directory, which is every corpus that exists and the docker example; multi, each chain gets `<data>/<blockchainID>` and they share one casfs spool and chunk cache at the root (`dist.SetRoot`), one syncLoop, one listener. `--tip-override` keeps both spellings for the same reason: `<chain>=<containerID>[,...]` when several chains make a bare value ambiguous, the bare container ID when there is only one chain to cap. The fleet SUPERVISOR survives untouched (`cmd/epochdb/fleet.go`: the per-chain context, the failure boundary, `/status`); only the command name died, and `serveMain` is now the single entry that fills one `nodeConfig` per `--chains` entry.

2. `serve --verify` VERIFIES WHAT IS ON S3, AND DELIBERATELY NOT THE LOCAL RAW TAIL. It runs the full no-execution engine over this chain's SEALED epochs (`verify.VerifySet`: diff-applied state roots, txRoot, receiptsRoot reconstructed from the stored logs, the header parent-hash chain), subnet-evm included because the verifier takes its VM kind off the descriptor. That is `dev verify` and its log half in one call. WHY THE TAIL IS NOT IN IT: verification of local raw files is meaningless as a feature, because the honest way to verify raw is to re-download and re-execute it, and that is precisely what a from-scratch start already does. The tail is at most one epoch (8M txs), so FROM-SCRATCH REPROCESSING IS THE LOCAL-RAW VERIFICATION STORY, and the sealed epochs, the artifacts other people consume, are the thing that needs a dedicated verifier. SEMANTICS PICKED, the least code that means anything: a STARTUP check, per chain, after `joinChain` (the walk is what names the epochs) and before that chain serves a byte; a failure is an error out of `startNode`, so that chain refuses to start and its siblings never notice. Not a loop, not a cadence, not a subcommand. A cold dir pays the frontier build first and verifies after, because the join is one call and splitting it to save a wasted build on a corrupt corpus is not worth a second code path.

3. THE RESILIENCE CONTRACT: A CHAIN FAILS, NEVER THE PROCESS. From any situation the system either organizes and reprocesses what it has by itself (the join decision tree, the automatic in-process cook and seal, the retry gates: all of that machinery already exists) or REFUSES TO START THAT CHAIN with a reason an operator can read. What that cost on 2026-08-03: every per-chain `log.Fatalf` on the boot path became a per-chain failure state. The descriptor resolve (a P-chain lookup for one L1), the VM-kind mismatch (libevm's extras registry is process-global, so a coreth chain among subnet-evm ones is refused by name), the duplicate `--chains` entry, the unmakeable data directory and `startNode` itself all route through `fleet.fail`, which records the SAME failure state a runtime death records and surfaces it at `/status`; `loadFleetChains`, which killed the whole process for one chain's bad descriptor, is DELETED. With several chains the process never exits for one chain, at boot or at runtime, and not even when ALL of them fail: it stays up precisely so `/status` can say why. With a SINGLE chain it does exit nonzero, because there is nothing left to serve: a start failure exits 1, and a runtime failure flushes the writers first (`stop()` then `closeAll`, so the restart is a clean resume and not a crash walk-back) and then exits 1, which is the restart contract every supervisor already relies on.

4. AN AGGREGATE HEALTH ENDPOINT [PLANNED, not built]. `/status` already reports every chain in the process, each with accepted/executed/cooked and its stop cause if it has one. A rollup over all of them (one overall verdict, the worst chain's state, a lag summary) is what a load balancer or a pager wants, and it comes later.

5. THE STAGES AND THE BENCHES ARE HIDDEN, NOT DELETED. The 7 pipeline stages (fetch, exec, cook-index, cook-txindex, seal, publish, bootstrap), the 2 standalone verifiers (verify, verify-logs) and the 6 dev benches (ab-bench, ab-bench-tx, ab-bench-rpc, ab-bench-logs, rpc-bench, backfill-logs) are gone from usage and from help, and live behind an undocumented `dev` namespace: `epochdb dev seal ...`, `epochdb dev ab-bench ...`. They stay because our own release gates and experiments drive them, and their flag sets are untouched. A top-level invocation of a retired name PRINTS A ONE-LINE POINTER TO `serve` AND EXITS 2, so a stale script fails loudly instead of silently running a stage the node now does for itself; `fleet` does the same and points at `--chains`. `cmd/epochdb/main_test.go` pins both halves: no retired name appears in usage as a word, and every one of the 15 exits 2 with a pointer that names `epochdb dev <stage>`.

`epochdb serve` runs follower + executor + RPC in ONE process; nothing restarts to surface a new block. RULING 2026-07-29: following is not a flag and there is no static mode ("that's how blockchain nodes work"); a `--frozen` read-only serve was proposed and REJECTED same day (Occam: side consumers read through the one serve's RPC port). RULING same day: the read-only Go SDK (open the store from another process/app, read-only) IS core product, part of the MVP, 100% needed [PLANNED]. RULING 2026-07-30 (user): the SDK reads the tip LIVE from a separate process by TAILING the serve process's append-only files, not by embedding the node and not by lagging behind the cook. serve already appends everything needed (raw writelog frames, block-hash index) and the overlay-backfill-from-raw-writelog path at startup is exactly the mechanism: the SDK opens the dir read-only, builds the same uncooked-tail overlay from the frames it tails, refreshes sorted buckets like History.Refresh, and serves the one read path (overlay then descent) at the writer's head. No second read path, no RPC hop, no cook lag.

RULING 2026-07-29 (Firewood is verify-only): "Firewood is just a dumb hash verifying machine." No read path ever touches Firewood; ONE read path everywhere: in-memory uncooked-tail overlay (writes since the last cook, maintained by the executor, pruned at cook) then the descent. This deletes the Firewood.Revision latest path AND unpins CommitEvery (it was 1 only so the served frontier was a committed revision). No exceptions: `eth_getProof` was the one candidate Firewood reader and was ditched same day; Firewood has ZERO readers. [BUILT 2026-07-29] Ownership rule: the serve process is the sole writer and sole server of its data dir. CLI collapsed same day: plain `serve` follows (no --vdr-sources = validator set from the --node URI with a warning), `--tip-override <containerID>` is the bounded-backfill integration mode, and the static pinned-at-open serve plus the sibling-staging cohabitation mode are DELETED.

GOROUTINES AND OWNERSHIP (`cmd/epochdb/follow.go`, ~270 lines; the rest of the work was making pinned values dynamic):
- `fetch.Fetcher` runs `Follow` (real snowman) and is the SOLE writer of staging. Its in-RAM `fetch.Store` IS the executor's `BlockSource`, so an accepted container is executable the instant it is durable, with no reader-sidecar lag. `--tip-override <containerID>` swaps the follower for a bounded backfill walk in the same slot (fixed-corpus builds and integration runs).
- `exec.Executor` runs one goroutine, holds the exclusive Firewood handle (verification only, nothing reads it), and is the sole writer of the state layer AND of the tail overlay, which it feeds through the one choke point every execution path already uses, `Store.AppendWrites`. serve now runs `CommitEvery=64`: the pin to 1 existed only so the served frontier was a committed Firewood revision, and with no Firewood readers it buys nothing. Freshness is unaffected because head, block-hash index and overlay all advance together in `flushBatch`, per block, right after each block's appends land (publishing only at the batch boundary left `latest` naming an older height than the overlay already served, and left 63 of every 64 block hashes out of the index; both were caught by the A/B probe). ROOT VERIFICATION: per block below the boundary, per batch above it, with an automatic per-block bisect on a boundary mismatch. At the tip that distinction disappears, because `Run` closes the open batch the moment staging runs dry, which at chain pace is after every single block: a following node commits and root-verifies per block exactly as before. Batching only ever engages while catching up. After each published block `OnBlock` advances the serving head and the block-hash index ON THE EXECUTOR GOROUTINE, which is what makes `eth_blockNumber` and the served state agree: a 200ms advance ticker (the first build) let them drift by ~70 blocks during catch-up, which the A/B probe caught as real mismatches.
- `rpc.Server` serves N request goroutines throughout. `latest`/`pending` state is the UNCOOKED-TAIL OVERLAY over the descent (`state/tail.go`), and there is no second read path: `Executor.LiveState`, the `readDB` and the whole `Firewood.Revision` frontier read are DELETED. The overlay is a map of 53-byte sorted key -> newest post-image, fed by the executor's own write frames (nothing re-derived), carrying each entry's block so the cook can prune by height; SELFDESTRUCT is tracked per address so a destructed account's storage reads as gone exactly like the descent's delete rule, recreation included. A miss falls through to `AccountAt`/`StorageAt` at the cooked watermark, and the watermark is read AFTER the miss, which is what makes the prune safe (see below). eth_call/getBalance/getCode/getStorageAt/getTransactionCount at latest stay sub-millisecond, now with zero FFI crossings on the read path.
- sync loop [BUILT 2026-07-30]: `dist.Store.Sync` every `--sync-every` (default 5m), which uploads spooled artifacts and releases the local copies. It does not start at all without S3 credentials, and a failure is logged, not fatal (the artifact stays durable in the spool).
- cook loop: `CookIndex` + `CookTxIndex` + `History.Refresh` + `PruneTail`, every `--cook-every` (default 60s) and ONCE AT STARTUP (so the node begins serving with the smallest possible overlay, and so the residue it then backfills from the raw writelog is bounded; a gap wider than two raw buckets is refused at open with "run epochdb cook-index first"). Async and fail-loud: a failure logs `COOK FAILED ... chain unaffected` and the chain keeps moving; the visible consequence is the historical window freezing plus an overlay that keeps growing, both of which the status line prints. THE PRUNE RACE, and why no double buffer is needed: the prune drops entries at or below the watermark Refresh has just published, Refresh publishes that watermark only after the new sorted buckets are readable, and a reader probes the overlay BEFORE loading the watermark. So an entry pruned between a reader's miss and its descent is covered by the watermark that reader then reads: a write is always in at least one of the two layers. Prune rebuilds the map rather than deleting in place, because a Go map never returns its buckets and this one grows to catch-up size.

THE LISTENER BINDS BEFORE THE STARTUP WORK [2026-08-01]. `serveOn` (serve) and fleet's one listener call `net.Listen` first and `http.Serve` on the bound listener once the node is up, because startup (epoch-chain walk, exec open, startup cook, tail overlay) is ~68 minutes on the 57M-block Fuji corpus and binding last made a port collision a FATAL an hour in, twice in one night (9650 then 9651, both already owned); requests arriving before readiness wait in the accept backlog, and the fleet serves `/status` from the moment it binds so the chains can be watched coming up.

STATE READ BANDS, and the one new refusal: `n > executed` is "not executed yet" (error), `n in [head, executed]` is the executed head (overlay then descent), `n < head` is the historical descent alone. The descent now REFUSES anything above the cooked watermark (`History.stateHead`) instead of silently descending past uncooked writes and answering with a pre-gap value: that was the one place where a moving head could have been quietly wrong. Cook cadence is therefore the historical window's lag (60s chosen; measured 1.2-4.6s of work per run at 1000 blk/s catch-up, far less at chain pace).

PINNED-AT-OPEN VALUES MADE DYNAMIC (the whole point of the change): `History.head` (atomic, advanced per executed block) and the new `History.stateHead`; the sorted-bucket mmaps and the account-delete index (`History.Refresh` re-opens only buckets whose `cookedThrough` grew, merging their deletes into a copied map, and unmaps the replaced ones after the write lock drains readers); the block-hash index (locked, grown per block); the raw tx index (`txIndexHolder` swaps the whole `CombinedTxIndex` after each cook; it is heap-only, so the old one is just garbage); and the state layer itself, which in follow mode is the executor's WRITER store rather than a snapshot taken by `OpenReadOnly`. The `EpochSet` was the last pinned-at-open value and stopped being one on 2026-08-01, when sealing moved in-process: `EpochSet.Reload` publishes new epochs into the SAME set every reader already holds (an atomic snapshot swap, epochs shared with the previous snapshot), so nothing is rewired and nothing an in-flight read holds is ever closed.

SHARING THE WRITER STORE forced the concurrency work that had never been needed: `bucketLog.idx`, `codeStore.idx` and `miscStore.m` were read outside their locks, which beside a live appender is a fatal concurrent map access, not a stale read (`state/store_test.go:TestLiveStoreConcurrentReadWrite`, run with -race). `EthDB()` returns a NEW `ethKV` per call, so its own mutex never guarded anything across instances; the locks now live in the stores themselves, where every caller routes through.

RPC LABELS (SAE, closes the "rpc labels" follow-up): `pending` = last accepted, `latest` = last executed, `safe`/`finalized` = last settled (`Executor.SettledHeight()`, which is the executed head below the Helicon boundary, so all three coincide there). `pending` resolves to the last EXECUTED height for state reads (no mempool: pending state is latest state); `eth_getBlockByNumber("pending")` is the exception and returns the last accepted container, which the tail already serves. `eth_syncing` now reports the geth-shaped object whenever accepted runs ahead of executed.

SEALING IS AUTOMATIC AND IN-PROCESS [RULING 2026-08-01, supersedes "seal stays out of the process" below]. No seal command in a cron, no operator sibling, no flag: the serve/fleet process seals itself on the cook cadence (`chainNode.sealOnce` at the end of every cook pass), because a node that produces epochs is what publishing history means, and an epoch nobody runs the sibling for is an epoch that never exists.

WHY IT IS SAFE NOW, when the sibling was not: the objection was never the write, it was the DELETE of raw buckets a live reader still points at. An external sibling unlinks files while the serving process's fds, mmaps and in-RAM bucket index still name them, and there is no way to tell that process first. In one process there is, and the ORDER is the whole mechanism (`state.History.SealTail`): (1) cut the epochs, deleting nothing, so both sources exist; (2) publish them into the live `EpochSet` and fold their account deletes into the descent's delete index, so every sealed height now has a sealed answer; (3) only then unlink the raw buckets, drop our own mapped sorted buckets, our `bucketLog` pairs and the fetcher's staging segments. Step 3 last is what makes the delete a no-op for correctness; step 3 AT ALL is what makes it free disk, because an unlinked file this process still holds open keeps every one of its blocks allocated until the process exits. Nothing races a cook because cook and seal are the same goroutine. The never-create read rule that made the sibling degrade correctly now covers the fetch staging segments too (`fetch.Store.seg` takes a create flag, reads never pass it), so a retired height reads as "not here" everywhere instead of resurrecting an empty arrival log.

COST IS GATED, not cadenced: a seal attempt that finds no boundary still has to scan the whole unsealed tail to know, which at 8M txs an epoch is minutes of CPU and gigabytes of rows to throw away. So `SealTail` keeps the exec head at which the tail is EXTRAPOLATED to reach the boundary (from the tx-per-block rate the last attempt measured, halved, so a chain that doubles its rate still seals on the first tick past the boundary) and below it opens nothing at all. Being late costs a slightly bigger raw tail, being early costs a wasted gather, hence the bias. Seal failures are logged and never fatal, the same contract cook has: a corpus that cannot be sealed keeps serving. THE GATE DATES A MEASUREMENT, NEVER A FAILURE (see the ruling below): only a pass that actually reached the boundary and found the tail short moves it.

SEALING DOES NOT KNOW S3 EXISTS, AND A FAILED SEAL RETRIES ON THE NEXT TICK [RULING 2026-08-02, AS BUILT the same day]. WHY: on the night of 2026-08-01 the Fuji node's SSO token expired, and seal died three times on `casfs: retrieve credentials ... InvalidGrantException` (18:13, 19:21, 20:29 in `fuji-serve.log`) and then went silent for the rest of the night. Two independent defects, both fixed:
- THE WRITE PATH REACHED THE NETWORK. `casfs.SetPointer` was a synchronous signed PUT, and publishing an epoch sets pointers (`chunks/<hash>` per artifact, then `latest`), so an expired credential killed the SEAL, a purely local piece of work. Pointers are now LOCAL FIRST with EXACTLY THE SPOOL SEMANTICS OF CONTENT (casfs, `.pointers/<name>` under the spool): SetPointer writes the value and returns having sent nothing, `Sync` uploads dirty pointers AFTER that pass's content and only when the content went up cleanly, and a confirmed pointer's local file is then released like any artifact. CONTENT BEFORE POINTER IS THE GUARANTEE: a bucket reader following a pointer never lands on an object that is not there yet. A read after release goes to the bucket and writes the value back to the spool (clean, never dirty: re-uploading a value this node did not author could only put a stale pointer over a newer one). WRITES ARE FIRE AND FORGET, READS ARE LOCAL FIRST, AND A READ THAT GENUINELY NEEDS THE BUCKET AND FAILS BUBBLES AN HONEST ERROR. Nothing fabricates a value.
- THE SEAL ALSO READ THE BUCKET, twice over. `setLatestEpoch` read `latest` before writing it, pointlessly (the pointer has exactly one field and the write overwrites it), and `sealEpochs` called `OpenEpochSet` to learn where the last epoch ended, which OPENS EVERY SEALED EPOCH: on a producer whose artifacts are uploaded and released that is a HEAD plus ranged GETs per epoch per pass. Both are gone: the head epoch now comes from the LOCAL MARKERS alone (`state.sealedHead`: one ReadDir plus one 64-byte read, no artifact opened), which also stops re-opening the whole corpus on every tick of a crunch. `state/sealtail_test.go` pins it by sealing one epoch, uploading and releasing it, KILLING the bucket, and sealing the next one.
- CONSEQUENCE, stated because it is the contract: A FULLY OFFLINE NODE (no `EPOCHDB_S3_*`) AND A NODE WHOSE CREDENTIALS EXPIRED BEHAVE IDENTICALLY FOR SEAL. Both seal locally, forever, on the cook cadence; only uploads stall, loudly, on the sync ticker, and everything they produce stays durable in the spool until the bucket comes back.
- A FAILED PASS LEAVES THE RETRY GATE OPEN. The gate was pushed to `execHead + BucketBlocks` on error, i.e. 100,000 blocks of exec progress, which at the tip is a day and a half: that is why three failures were followed by silence rather than a fourth. Only a successful pass dates the gate now. A no-boundary pass keeps the cheap skip exactly as before, so the gather-per-tick cost this was protecting is unchanged for the case it was written for; a permanently unsealable corpus pays a gather per cook tick and says so every time, which is the correct direction: a stall nobody sees is worse than a log nobody likes.

PER EPOCH, NOT PER PASS, AND INTERRUPTIBLE BETWEEN EPOCHS [RULING 2026-08-01 evening, forced by two things the Fuji backlog crunch showed that night]. (1) DISK: the pass cut all 14 epochs before it deleted anything, so ~100G of sealed output sat on top of all 411G of raw at once and a mainnet fetch had to be paused to protect the disk. (2) SHUTDOWN: a SIGINT at 16:03 landed mid-crunch and the node kept sealing for hours, because only the cook ticker looked at the context and nothing between epochs did. So the whole ordering above now runs ONCE PER EPOCH: cut one epoch, publish it, unlink the raw buckets wholly behind it, drop our handles, raise the fetch floor and retire the staging segments (`SealTail`'s per-epoch callback, which is also the seam that keeps `state` from importing `fetch`), then the next epoch. And the cook loop's ctx reaches `SealTail`, which checks it BETWEEN epochs, so a shutdown costs at most the epoch in flight instead of the whole backlog. Cancellation needs no resume machinery: seal always starts at the next unsealed block, so an interrupted crunch and an uninterrupted one produce the same epochs byte for byte, which is what `state/sealtail_test.go` pins by comparing the two hash chains. NOT finer than an epoch: a gather is one indivisible unit of minutes, and dropping a nearly finished one only makes the next pass redo it from the same block. Buckets are 100k blocks and epochs cut on tx count, so most epochs retire zero or a few buckets; the point is that the ones that do are freed DURING the crunch.

`epochdb seal` stays for offline dirs and keeps the all-in-one shape (nobody is reading, so there is nothing to publish to), but it deletes per epoch too: an offline crunch fills the same disk.

THE SEAL'S PEAK MEMORY IS BOUNDED, AND INDEPENDENT OF BLOCKS PER EPOCH [RULING 2026-08-02, AS BUILT the same day]. WHY: three OOM kills in 24h on the 26G box, the last one a BARE `epochdb seal` with no serve and no fetch beside it, at 23.6G anon RSS while gathering epoch 12. The schedule caps TXS (8M) and says nothing about BLOCKS, so the sparse-L1 shape - Fuji's epoch 12 spans ~4-5M blocks for its 8M txs, and an L1 at 1.2 tx/block puts ~6.7M blocks in every 8M-tx epoch - made an epoch's cost per BLOCK, and the old sealer paid it three times over: (1) `gatherEpoch` held the whole epoch (containers, headers, a tx-hash map, receipt and log records, every post-image row) at a measured 2.75 KB PER BLOCK; (2) `BuildEpoch` assembled the sealed artifact in a `bytes.Buffer`, 7.2 GB on epoch 11 plus a doubling copy every time it grew, on top of the section slices it copied from; (3) `zstd.NewWriter` pools one encoder state per GOMAXPROCS and a dict-primed SpeedBestCompression state is ~1.1 GB on 16 cores, so the three encoders a seal makes held 3.37 GB that `EncodeAll` (which compresses in the calling goroutine, one state at a time) never used.

THE RULE, four parts. STREAM THE SECTIONS: `buildEpoch` writes them in file order straight into a file in the spool, hashing as it goes (`epochOut` + `dist.Digest`), and `dist.Store.Adopt` renames it under its own hash; the sealed size no longer appears in the sealer's resident set at all. RE-READ THE RAW RATHER THAN GATHER IT: `scanEpoch` is the only pass that decodes a block body (it fixes the block count and collects the tx and block-hash fingerprints, so nothing keccaks a transaction twice), and the builder pulls each section through a walk over the raw family it needs (`epochSrc`), sequentially, with the LRU-capped handles the readers already had. A family is walked more than once, which is bandwidth, not memory. EXTERNAL-SORT WHAT CANNOT STREAM: post-image rows and the logs-dict samples go through `extSort` (256 MB in RAM, sorted chunks spilled to a scratch dir IN THE DATA DIR, k-way merge back); rows are laid out `key53|block BE|seq BE|value` so byte order IS (key, block, seq) order, and the key bloom, whose size needs the unique-key COUNT, reads back a scratch file of the keys the SST just streamed. ONE ENCODER STATE: every seal-time encoder comes from `newEpochEncoder`, which pins `WithEncoderConcurrency(1)`.

MEASURED, same synthetic sparse corpus (1.2 tx/block, real headers, write frames, code blobs and capture records), sealed by both sealers, VmHWM of the sealing process: 20k blocks 3.13 GB -> 0.24 GB; 100k blocks 3.42 GB -> 0.28 GB; 2M blocks 11.07 GB -> 2.17 GB, i.e. 5534 -> 1084 bytes per block, at the same wall time (17m08s -> 16m57s) and for the same epoch hash. THE LARGEST PER-BLOCK TERM THAT REMAINS IS NOT THE SEAL: `openBucketLogRO` builds a RAM index entry per block per raw family over the whole unsealed tail, measured 182 B/block (364 MB over this 2M corpus), which any process that opens the store pays; the seal's own residue on top is the tx/block-hash fingerprint pairs it keeps to avoid keccaking every transaction twice (16 B each, ~240 MB for an 8M-tx sparse epoch, marked `ponytail:` in buildEpochTxidx). Extrapolated to Fuji's epoch 12 that is ~4 GB where the old path died at 23.6 G.

BYTE-IDENTICAL OUTPUT IS THE HARD CONSTRAINT, since data-fuji already has 11 sealed epochs and epoch 12 must chain onto epoch 11 exactly as the old sealer would have cut it. `state/sealidentity_test.go` keeps the OLD whole-epoch gather verbatim as the reference and requires both paths to produce the same epoch hashes over the same corpus, hash chain included; the three corpora above were sealed by both sealers and produced identical sha256s. Nothing about the format, the schedule (`EpochTxsAt`), the resume rule, the per-epoch publish/retire order or the `onEpoch` callback changed.

COST, stated because it is real: roughly twice the sequential raw reads per epoch (each family is read once per section it feeds, the receipts family three times because the logs dict has to exist before its records are compressed), and temp files whose size is the epoch's write rows plus its stored-logs records. They live in `<data dir>/sealtmp-*` (never /tmp, same filesystem, removed when the build returns) and `sweepSealScratch` removes a killed build's leftovers on the next pass - unconditionally in the data dir, and only for a day-old `epoch-*.tmp` in the spool, which a fleet shares across chains.

THE SEALED END IS A FETCH FLOOR [RULING 2026-08-01, closes the OPEN wart under the FIFA gate]. `Fetcher.SetFloor(sealedEnd)` is a floor for EVERY walk (`walkSpan` takes the max of it and whatever floor its caller passed), so no block at or below the sealed end is walked or requested. Without it a restarted follower re-downloads all of sealed history: walks short-circuit on the STAGING store alone, and seal legitimately deleted the raw those blocks lived in, so the walk drops off the bottom of the retained tail and re-fetches to height 1. The floor is LIVE, not startup-only, because sealing is in-process and the floor rises while the node runs: `startNode` sets it from the sealed epoch set's covered end and `sealOnce` raises it on every cut, next to the staging retirement it already does (`epochdb fetch` sets it once at startup; nothing seals in that process). Mechanically the floor is the same rule that already ended a walk at height 1 - stop when the next block down is at or below the floor - so floor=0 is the old genesis terminator unchanged.

THERE IS NO SEPARATE BOOTSTRAP STORY [RULING 2026-08-03, AS BUILT the same day; supersedes "bootstrap --frontier then serve" as the operator flow]. A node has ONE start sequence, per chain, and `epochdb serve` on an EMPTY data dir with credentials does the whole join by itself (one chain or several, `--chains`). `joinChain` (cmd/epochdb/dist.go), called by `startNode` before anything opens the dir, IS the decision tree:

1. With S3 configured, resolve this chain's `latest` pointer (`dist.Latest` with the chain root; the pointer name is per chain since 22d0b5f, and the read is local-first with a bucket fallback since the casfs pointer rework).
2. NO POINTER anywhere -> a genuinely fresh chain -> start from scratch: fetch from genesis and execute, the path that always existed.
3. POINTER EXISTS -> walk the epoch chain and confirm EVERY linked artifact is available (bucket or local); anything missing or broken -> HARD ERROR, refuse to start. NEVER silently fall back to from-scratch. That is the whole point of the ruling: a typo'd `EPOCHDB_S3_PREFIX` would otherwise make a provider re-replay weeks of history, which is a disaster, not a degraded mode. The error names the artifact that broke the walk and where to look.
4. CHAIN INTACT BUT NO LOCAL EXECUTION STATE -> run the frontier build automatically: the k-way merge of the sealed state sections plus the settled-root verification that `epochdb dev bootstrap --frontier` does by hand (post-SAE path included, efa0e47), then continue into normal follow/serve.
5. CHAIN INTACT AND LOCAL STATE PRESENT -> today's warm start, unchanged.

WHY: one simple story, and no knowledge an operator has to carry. Joining a chain that already has published history is not a different mode of a node, it is what starting a node means; a second command to remember is a second thing to get wrong at 3am, and the failure it produces (a node that quietly re-executes from genesis) is the most expensive one in the system. Hard error over silent re-replay, always.

VALIDATION IS CHEAP AT EVERY START [same ruling, hard constraint]. A WARM dir pays the FILESYSTEM AND NOTHING ELSE (`checkLocalIndex`): the local markers must name the epoch `latest` points at and must cover blocks 1..N with no gap and nothing stranded above one. Zero requests, milliseconds. It is enough because this dir walked the hash chain when it joined and wrote every epoch it has sealed since, so the local index IS the linkage record; a marker that is missing or out of line is NOT fatal, it drops through to the full walk, which rewrites it. A COLD dir pays metadata: one pointer GET, then per epoch a size probe (a HEAD under casfs) plus its ~1KB FOOTER, which is the only place the prev-hash lives (`state.ReadEpochLink`). Neither path rehashes content and neither downloads an artifact to validate it: the bytes come down when the frontier build or a real read wants them. This is what `state.OpenEpoch` was doing wrong in the walk - it pins every resident section, and the key bloom alone is 20 bits per key, so validating a mainnet corpus meant downloading gigabytes of blooms to prove files exist. `state/pin_test.go`'s `TestReadEpochLinkReadsOnlyTheFooter` pins the cost at one chunk over a bucket-only artifact. FULL CONTENT VERIFICATION REMAINS EXCLUSIVELY `serve --verify`'s job (RULING 2026-08-03; `dev verify` is the same engine driven by hand).

PROVIDERS BOOTSTRAP FROM THEIR OWN BUCKET, and that is the only case [same ruling]. Seeding a new box by copying a bucket is the operator's business; no cross-operator or read-only-foreign-bucket support is designed for, so nothing was removed for it and nothing was added. `epochdb dev bootstrap` stays as the MANUAL/OFFLINE form for offline prep, for a box that will never serve, and for `--verify`; starting a node never requires it.

THE EPOCH CHAIN IS WALKED AT EVERY START [RULING 2026-08-01, still true, now with the cheapness constraint above]. Serving a corrupt epoch set silently is the one unforgivable failure, so `startNode` (every chain a serve process hosts) runs the bootstrap walk before it opens anything: `latest` -> footers backward by prev-hash -> the chain root, checking that every linked artifact EXISTS and that epoch K-1 ends exactly where K starts. A break refuses to start. EXISTENCE AND LINKAGE ONLY: no content is rehashed, no section is read, so it stays O(epochs) metadata reads (milliseconds); the full no-execution pass over the corpus is `serve --verify` and stays there. It is literally `bootstrapChain` with a missing `latest` treated as "this dir never sealed", which is also why it self-heals a lost marker.

TIP OVERRIDE IS A PHYSICAL CONTAINER ID, AND ON FLEET IT IS PER CHAIN [RULING 2026-08-01, AS BUILT the same day]. `--tip-override` accepts ONLY a container ID (cb58, or a 0x-hex eth block hash for a pre-ProposerVM block, where the two are the same 32 bytes). WHY: the height form resolved through the ProposerVM activation constant plus the embedded checkpoint table (below the activation, height -> eth block hash via an archive RPC; above it, snap to the nearest checkpoint at or above the height), and a production operator must not depend on that magic to say which block caps a corpus. A numeric value is refused by name and the error says where the IDs are printed: the fetch log's `consensus: accepted height=N container=<ID>` line, and the anchor line an override itself logs. The CLI now asks the CHAIN for the height (`Fetcher.ResolveAnchor` parses the fetched container), so `preForkCeiling`, the RPC height helpers and the synthesized filler anchors are DELETED, and with them the "C-chain only" refusal: an L1 override is just an anchor with no checkpoints below it. The embedded checkpoint table stays for the one thing it is for, seeding parallel backward walks below the override. ON FLEET the flag is `--tip-override <chain>=<containerID>[,<chain>=<containerID>...]`, keyed exactly as `--chains` (`C` or a blockchainID), because one bare value cannot say which of N hosted chains it caps; a chain with no entry keeps following the live tip. fetch and serve host one chain and keep the plain single value.

SUPERSEDED, kept for the evidence (the fold it also covered is deleted). SEAL STAYS OUT OF THE PROCESS (decision 2026-07-31). Against the live APPENDER it is safe: seal only deletes buckets entirely at or below `sealedEnd <= exechead` and the appender only ever writes at `exechead+1` in a higher bucket (the fold additionally waited for `exechead >= B + BucketBlocks`). Against the live READER it was NOT safe, and that is new because the reader is now in the same process: a reader keeps `bucketLog.idx` entries for retired blocks, and `pair()` opened with `O_RDWR|O_CREATE`, so the next read RESURRECTED an empty data file where the retirement had just removed one, turned every later read of that range into an EOF error instead of an epoch fallback, and left a zero-length file for the next cook to trip over. Fixed: the read path never creates, and a missing bucket returns "not here" so the descent falls through to the epochs or the base. With that, running seal as the documented external sibling degrades correctly; it still must not run beside a cook, and with EPOCH_TXS at 10M a boundary is ~10 days away, so nothing is lost by keeping them out of the tip loop.

## Dev/prod cohabitation on one box [half BUILT, half DROPPED 2026-07-29]
The point (user clarification 2026-07-29): develop bots against live captured state, one writer capturing the tip while bot processes start and stop freely against the same files. That half is BUILT and production-proven: read-only openers (`state.OpenReadOnly`, `fetch.Reader`) beside a live writer, files are the API. The flock failover-pool half (standby WRITERS queuing on an exclusive lock for instant takeover on writer death) is DROPPED: bots never write, a crashed writer just restarts, and the machinery bought nothing for a one-box deployment. Block delivery to reader processes must be sub-5ms: split visibility from durability (writer `write()`s per block so bytes are visible via page cache instantly, fsync stays batched), wake slaves via inotify on the sidecar (sub-ms) or a tipbus-style mmap seq counter (~100us, flatstate-measured). The bleeding tail is visible-but-provisional: a writer crash may truncate behind what a slave saw, so the lockfile carries a generation counter and slaves re-validate their last blocks on writer change.

## Limited-history mode [DELETED 2026-07-31, ruling 1: there is no floor, no base file and no pruning mode. The whole section is kept as the record of what was built, measured and proven, because the tombstone and miss rules it pins are now the merge's rules. Nothing below it is live code.]
Disk-bounded deployment for a validator host that needs current state and fast tip, not deep history: two validators share a 2TB disk with ~600-700GB free, and full-mainnet epochdb is ~590-690GB of epochs plus ~130-157GB of Firewood. Target ~200GB.

THE ONE STRUCTURAL CHANGE: state reads descend epochs newest-to-oldest and fall through to a floor (`History.search`), and that floor is the genesis alloc. That is the only reason coverage must reach genesis. Replace it with a flat live-state base file at block B: every read at N >= B is answered by (raw tail, epochs above B, base file) and nothing below B exists. Deleting epochs WITHOUT swapping the floor is silently wrong, not an error (the descent misses and reports "account does not exist"), so the floor check is the safety property of the whole feature.

Decisions, REWRITTEN 2026-07-29 (the original 07-28 rulings assumed network state sync; superseded by the snapshot design, see "Our own state sync"): the bottom is a PUBLISHED SNAPSHOT (named by `latest`), preimage-keyed, produced by a pruning node. B is the snapshot's boundary (canonical, cumTx in the footer), so sealing above B cuts canonical epochs. Firewood and its per-block root check stay, so ~130-157GB is a fixed cost and not a lever. Gate: A/B vs the public network RPC at tip.

Base file (`base_<block>`): a new file kind, not an epoch, because its rows are live state with no block numbers (the file IS state at B). Reuses the epoch machinery (zstd-framed sorted blocks, sparse index, keybloom, mmap, versioned footer) with the SAME 53-byte preimage keyspace as an epoch SST, code blobs as `'c' | hash | zeros` rows in it, and the headers of [B-256, B] so eth_call BLOCKHASH works in [B, B+256). The footer records B, the state root and cumTx at B.

Call sites that change: floor check plus base lookup in `History.search` (`state/overlay.go`); `EpochSet` coverage anchors at the floor and `RequireCovered` reports "pruned below block B" (`state/epochread.go`); the delete map only needs epochs above B (the base file is a post-image, so no pre-B deletion or resurrected slot can exist); `OpenHistory` must open with a base file and no buckets; `serveMain`'s block-hash scan starts at the floor, not 0; `rpc/{tx,block,logs}.go` coverage errors become pruned errors, and below-floor tx-by-hash returns a typed pruned error rather than null (a bot silently seeing null for a real tx is the bad failure mode).

Contract: full archive semantics from B forward, nothing below B, B printed at startup. Budget ~175-205GB full mainnet (base ~20 + code ~5 + 0-3 epochs + raw tail ~18 + Firewood ~130-157), plus whatever chunk cache is configured when S3 credentials are present. AS BUILT (format v2, 2026-07-29, `state/base.go` + floor-aware read path; content-addressed since 2026-07-30, so the file is named by its sha256 and `base_<B>.cas` is the local index marker): footer-last with magic at both ends, four sections (sst rows `key53|uvarint vlen|value` in ~64KB zstd blocks, 61B sparse index, keybloom identical to the epoch bloom, and one zstd frame of the headers in [B-256, B] decoded at open). Footer: magic, version, B, hdrFrom, cumTx, state root, 4x(offset,len), magic = 132 bytes. Code blobs are ROWS, not a section: kind 'c' | hash | zeros, and since 'a' < 'c' < 's' they share the one sorted keyspace, index and bloom. No zstd dict (short values are not worth training one). NO UPGRADE PATH, same policy as epochs: a v1 file is refused by name ("format v1, unsupported"), and it could not be migrated anyway since it stored hashes and threw the preimages away.

THE ROOT GUARANTEE, precisely. Two independent checks, and the file only reaches disk if both pass. (1) Wire-level: every leaf response is verified by the reused coreth sync client as a merkle RANGE PROOF against the root we asked for, and every code blob against its hash, so no peer can insert a row that is not in the trie of that root, and the client's verified `More` flag plus contiguous `lastKey+1` continuation means a peer cannot silently skip a range either. That is a guarantee about ROWS. (2) File-level, which is the one that matters, because (1) says nothing about whether OUR walk covered the keyspace: `BaseBuilder.Finish` streams the finished row set through `trie.StackTrie` and recomputes every storage root (compared to the root each account row claims) and then the state root (compared to `header(B).Root`), refusing to leave a file behind on mismatch and also refusing an account that claims a storage root whose slots never arrived. So a `base_<B>` on disk is proof-carrying: its rows rebuild `header(B).Root` exactly, and the only remaining trust is that header(B) is the real block B, which comes from the peer-majority accepted frontier plus a verified parent-hash chain down to B (real snowman consensus on the frontier is the obvious upgrade and is not wired here).

CONCURRENCY IS THE ONLY LEVER THAT MATTERS (measured 2026-07-29, both runs on the same pivot minutes apart). A peer takes ~2s to serve one 1024-leaf range, so throughput is purely outstanding-requests, not bandwidth. `--workers 32` (flatstate's default) gave 14k rows/s; `--workers 384 --inflight 1536 --per-peer 6` gave 125-135k rows/s, a 9.5x speedup, with the failure rate staying negligible (771 failed requests over 90.9M accounts). The global in-flight semaphore is what makes this safe to turn up: workers can exceed it freely and simply queue locally, so the cap, not the worker count, is what peers ever see. Do NOT raise inflight to flatstate's measured collapse point (~4000 outstanding degenerated to <20 req/s). 32 workers is the wrong default at 580 connected mainnet peers.

HASHED KEYS ARE NOT A WALL, for the base file OR for the Firewood frontier (settled 2026-07-29 with a runnable proof, `verify/hashedfrontier_test.go`; supersedes the step-1 belief that a hash-keyed file can never be re-verified). Two independent facts. (1) A merkle-patricia root needs hashed keys in ascending order and nothing else, so `trie.StackTrie` recomputes `header(B).Root` from the base file's own rows, in one streaming pass, no Firewood and no preimages: that is what `BaseBuilder.Finish` does, and it also checks every contract's storage root against the root its account row claims. (2) Firewood's key space is ALREADY HASHED. `graft/evm/firewood/base_trie.go` hashes on the way in and stores `keccak(addr)` -> account leaf RLP and `keccak(addr)||keccak(slot)` -> `rlp(trimmed value)`, which is byte-for-byte what a state sync yields and what the base file stores; the preimage-keyed `UpdateAccount(addr, ...)` surface is a convenience layer, and `TrieDB.Firewood` is an exported `*ffi.Database` whose `Propose([]ffi.BatchOp{ffi.Put(hashedKey, val)})` + `Commit` reproduces the canonical MPT root exactly (proven against a stack trie in that test). So a limited-history node builds its Firewood frontier at B directly from the base file's rows, with no preimages, no execution and no replay, and the executor above B keeps its per-block root check unchanged. The frontier does NOT have to come out of the sync in merkle form.

Known gaps: genesis-alloc STORAGE was unsupported in the deleted folder and will need handling in the fold producer (dead code on both networks today, whose single alloc account has code but no storage). Two more from the gate run: "nothing below F exists" is exact for STATE but bucket-granular for BODIES (a raw bucket straddling F still serves bodies below it, and the floor check lives in the descent, not in the file set); and the base's CODE section is still effectively untested, because code.log is a single global file that has to be carried whole, so eth_getCode resolves from it rather than from the base on any node built by folding an existing corpus.

We route around it: SNAPSHOTS. A pruning node's normal output IS the state-sync artifact, and clients download it instead of syncing state from the network. One sync mode, one rule, no special cases (user rulings 2026-07-29):

- ONE SYNC MODE: every node starts from a snapshot. "Genesis sync" is just starting from snapshot(0), which is the genesis alloc and is HARDCODED IN THE CLIENT (it already ships there: `exec.NetworkGenesis`); no snapshot-zero file exists. The first pruned node on a network executes from genesis ONCE, ever; every later client starts from a published snapshot. THE TRUST ANCHOR IS THE GENESIS CONFIG (ruling 2026-07-30, supersedes the 07-29 source-committed snapshot hash): the hash chain roots at sha256 of the chain's genesis config, which the client already ships, so no per-network snapshot constant has to be committed or bumped when a newer snapshot is published. A downloaded snapshot needs no pinned hash of its own either: loading it into Firewood computes its root, and the first executed block's root check against consensus-verified headers rejects a lying one. A node given a later snapshot downloads it, dumps it into Firewood, and replays the gap to tip; every key not found in local data falls back to the snapshot, which is the descent floor.
- ONE PRODUCTION RULE: at every canonical boundary (cumulative-tx-count, same for everyone), a PRUNING node emits snapshot(K) = snapshot(K-1) folded with the period's own captured writes, and a NON-PRUNING node emits epoch K. Each is a pure function of chain content plus the previous artifact of its kind, hence bit-identical across nodes within its kind. Pruning nodes never seal epochs; archival nodes never emit snapshots. No producer flags, no conversions, no folding epochs into snapshots anywhere, ever.
- ONE PUBLICATION PATH: the operator runs two real nodes, one archival and one pruned, and both simply rename their finished artifacts into the casfs spool, which uploads them. Publication carries the NEWEST snapshot only, no ladder. The only mutable thing anywhere is the `latest` pointer, whose two halves each producer advances independently as it publishes (seal sets the epoch half, fold the snapshot half).
- ONE ROW FORMAT [BUILT 2026-07-29, base format v2]: the snapshot is PREIMAGE-KEYED with the same 53-byte keys as epochs and buckets, because its producer (the pruning node's own capture) has the preimages. The hash-keyed 65-byte base keyspace existed only for network leaf-sync, which is deleted (below). Firewood load hashes keys on the way OUT, in `Base.WalkRows`, so an account or storage read costs no keccak at all and only the once-per-node bulk load pays for hashing.
- VERIFICATION IS THE LOAD, not a pass: dumping the snapshot into Firewood computes the root as a side effect of the commit, so the check is one free comparison against `header(B).Root` (kept only for a clear early error), and the next executed block re-verifies the inherited state transitively anyway. The StackTrie verify pass and `snapshot --verify` machinery are deleted. Same ruling applied to the FOLD's pre-publish gate (built 2026-07-29, DELETED same day, user: "extra validation of already-validated data no one asked for"): the producer executed every block root-verified and every client's load re-checks the root, so the throwaway-Firewood gate (which transiently doubled the merkle store on the disk-bounded node) is gone; a bad snapshot is impossible to publish silently because every client refuses it at load. - Cadence does not matter for clients: catching up from B to tip is p2p block fetch plus replay at 3-6k blk/s, so even a 10-day-old snapshot costs a couple of minutes of replay.
- BYTE-IDENTITY REQUIREMENT [BUILT]: all producers cut at the same canonical heights, and a snapshot-synced node cannot compute cumulative tx count from history it does not have, so the SNAPSHOT FOOTER carries cumTx at B (`Base.CumTx()`). - Measured basis (2026-07-29): base_200000 loads into a frontier in 1.04s with the root matching the header; 8.8M rows rebuild in 11s; full mainnet extrapolates to about a minute. Rows stored sorted in trie order make the bulk load near-linear despite a 7-9 level trie.

## Helicon / ACP-194 SAE [PLANNED] (researched 2026-07-22 at avalanchego v1.15.0-fuji)
SAE is not a coreth change, it is a whole new VM (`vms/saevm`). The C-chain registers `transitionvm.Factory{PreFactory: coreth, PostFactory: saevm/cchain}`, runs coreth until HeliconTime - 10s, then boots the SAE VM on the same database. Coreth actively rejects blocks carrying SAE settled markers, so coreth-as-library can never process post-Helicon blocks.

What changes semantically: `header.Root` of block N is the post-execution state root of the last block SETTLED by N, not N's own state (settlement lag tau = 5s of gas time, a handful of blocks). Headers gain `SettledHeight`, `SettledGasUnix`, `SettledGasNumerator`, `SettledExcess`, plus ACP-283's `MinPriceExponent` and ACP-176's `TargetExponent`. Receipts are computed and stored per block at execution time but committed only at settlement: the settling block's receiptsRoot/bloom cover the CONCATENATED receipts of every block it settles. `header.GasUsed` becomes worst-case charged gas of the block's own body (statically checkable), per-tx gas charging floors at limit/2, and base fee for execution comes from the deterministic gas clock, never `header.BaseFee`. RPC labels shift: pending = last accepted, latest = last executed, safe/finalized = last settled.

Wire format is otherwise unchanged (one RLP block-with-extData, proposervm and GetAncestors untouched), but the new RLP tail fields mean a v1.14.2 decoder CANNOT parse any post-Helicon header, and v1.15 peers drop sub-v1.15 handshakes at activation. Fuji activates 2026-07-29 00:00 JST; mainnet is unscheduled in the tag, expect roughly 3 weeks after the mainnet release lands (Granite precedent), and our mainnet v1.14.2 pin is safe until then.

SAE DELETES C-CHAIN STATE SYNC (measured + read 2026-07-29, decisive for limited-history mode). `vms/saevm/cchain/sync.go` is a stub: `StateSyncEnabled` returns false, every summary getter returns ErrNotFound, `AcceptSummary` returns ErrStateSyncableVMNotImplemented, and the file carries `TODO(#5513): Implement C-Chain state sync`. The SERVING side went with it: `vms/saevm/sae/vm.go` registers exactly one p2p handler, `p2p.TxGossipHandlerID`, and there is no coreth leafs/code/block handler anywhere in saevm. `transitionvm` routes every AppRequest to `vm.current.chain`, which after HeliconTime is the SAE VM, so coreth's legacy even-request-ID sync server stops existing on that chain at activation. `p2p.FirewoodProofHandlerID` is RESERVED in `network/p2p/handler.go` and has zero implementations and zero references in the tag, so the Firewood-proof replacement is planned, not shipped. MEASURED on live Fuji 2026-07-29 09:43 JST: 36 peers connected, the header walk and container parse both fine (v1.15 handshakes and post-Helicon containers decode), then 24,881 leaf requests, 100% AppError, ZERO accounts in 4 minutes. Same binary, same minute, mainnet: 121 failures and 5.5M accounts. Consequence: a limited-history Fuji node cannot be built from the network at all until #5513 lands, and any Fuji plan that assumed state sync needs re-planning. Mainnet is unaffected (coreth peers, HeliconTime unscheduled).

Ranked epochdb work: (1) small and urgent, do not crash at the boundary (park fetch at HeliconTime on Fuji); (2) small, dep bump to v1.15.0-fuji so parsing and handshake work; (3) medium, verifier re-point: keep a ring of computed roots and assert `header.Root == root(SettledHeight)` with marker monotonicity, plus the body statics (`GasUsed == sum tx gas + op gas`, receiptsRoot over the merged settled range); (4) large, execution engine swap for post-Helicon heights to `saexec.Execute` + `vms/saevm/cchain` hooks. Firewood stays, and SAE ships native Firewood support to crib from. Scale note: max block gas becomes R*tau*lambda = 20x target (double the old cap), so EPOCH_TXS assumptions should be sized on charged gas. Risk: SAE Go APIs are explicitly unstable, so pin exact release tags.

## Operations
- Build/run: `go run ./cmd/epochdb serve`, and for an operator that is the whole list (RULING 2026-08-03): `serve [--data <dir>] [--network mainnet] [--chain C|<blockchainID>] [--chains C,<id>,...] [--port] [--vdr-sources ...] [--verify] [--tip-override <containerID>|<chain>=<containerID>,...] [--node --state-cache --cook-every --per-peer --sync-every --walks --pprof]`, following by default.
- OUR OWN STAGES, hidden but alive, for gates and experiments only: `go run ./cmd/epochdb dev <stage>` where stage is fetch (`--network mainnet --tip-override <containerID>` | `--follow --vdr-sources ...`), exec (`--stop N --state-cache 3 --commit-every 1000`), cook-index, cook-txindex, seal (`--network mainnet --out DIR`), publish, bootstrap (`--network mainnet [--frontier] [--verify]`), verify, verify-logs, backfill-logs, ab-bench / ab-bench-tx / ab-bench-rpc / ab-bench-logs / rpc-bench. Flags unchanged. A top-level `epochdb seal` (or any other retired name, or `fleet`) prints a pointer to serve and exits 2.
- SEAL ALWAYS DELETES fully sealed raw buckets (2026-07-29: `--delete-raw` was the only sane setting, so the flag is gone). The serve process seals ITSELF (ruling 2026-08-01) and is the only thing allowed to: never run `epochdb dev seal` beside a live fetch or exec, they own those files. Buckets are 100k blocks and epochs cut on tx count, so the bucket straddling the sealed end survives and still overlaps the newest epoch: the delete-map and tx-index dedup stay necessary.
- New node today: export the `EPOCHDB_S3_*` variables for the publisher's bucket (or a mirror) and run `epochdb serve --data <dir> --network mainnet`. That is all of it: the empty dir reads `latest`, walks the hash chain, writes the local index, merges every epoch's SST section into a Firewood frontier at the last sealed block, parks the exec head there and starts executing at H+1 (`joinChain`, RULING 2026-08-03). Add `--verify` to re-verify every sealed epoch first, which downloads everything and refuses to start that chain on a mismatch. With no credentials the same command works entirely off the local spool.
- PUBLISHING: seal drops epochs into `<data>/cas` and advances `latest`; the serve process's `--sync-every` ticker uploads and releases them. Nothing else talks to S3, and epochs are immutable, so nothing in the bucket is ever superseded.
- Memory: replay wants `GOMEMLIMIT=10GiB --state-cache 3 --commit-every 1000` on a 25GB box (the 6GiB default state-cache thrashes in dense eras, incident 2026-07-19). Seal at 10M-tx epochs gathers a whole epoch in RAM (~20GB anon live): run it ALONE with `GOMEMLIMIT=20GiB`, it OOMs beside a replay.
- Long stages MUST be setsid-detached (harness background tasks get reaped; learned twice).
- Multi-process: writers truncate torn tails on open, so NEVER open a live writer's dir with the writing opener. `state.OpenReadOnly` / `fetch.Reader` exist for cohabitation (production-proven). Two cook/seal processes must not share a dir (tmp+rename races).
- `du` lies on WSL2 and page-cache-heavy dirs; footers and artifact hashes are truth.
- `epochdb serve` is the node: follower + executor + RPC in one process, no restarts, following by default (`--vdr-sources <2+ P-chain RPCs>` cross-checks the validator set, otherwise the --node URI with a warning); `--tip-override <containerID>` runs a bounded backfill in the same slot instead. `--chains` hosts several chains in that one process, each at `/ext/bc/<blockchainID>/rpc`, with `/status` over all of them and a per-chain failure boundary. It OWNS every data dir it touches (state writer + Firewood), so nothing else may write there, and no `dev` stage (seal, cook, `bootstrap --frontier`) may run beside it.
- ALWAYS pass `--network mainnet`: the default is fuji and the chain-id mismatch fails late.
- PACKAGING: per-commit images ARE the release channel (ruling 2026-08-01, tagged releases never get cut). Every push to main runs `go vet` + `go test ./...` then builds the root Dockerfile and pushes `ghcr.io/containerman17/epochdb` as `latest` and `sha-<shortsha>`; there are no tagged releases and no Docker Hub. cgo is mandatory (firewood ships a prebuilt glibc `libfirewood_ffi.a`), so the runtime layer is `distroless/cc-debian13`, matching the golang:1.26 builder's Debian 13: `distroless/static` cannot link it and `distroless/base` is missing `libgcc_s.so.1`.
