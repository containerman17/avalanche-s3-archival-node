# epochdb design

## Principle
Bodies + headers + proposervm extras are the only ground truth. State history, receipts, logs, all indexes are caches rebuildable by re-execution (~5-6k blk/s). Re-executing one block is the universal primitive: receipts, traces, and getLogs results are computed on demand, never stored.

## Target architecture (v2, after measurement)
- Immutable per-epoch files, self-described by filename: epoch_<startblock>_<blockcount>.epoch. No catalogue; startup = readdir + read footers. Height->epoch = binary search over the readdir table.
- Epoch boundary rule: FIXED TX COUNT per epoch (single constant, default 10M txs; tune before format freeze). An epoch seals at the first block whose cumulative tx count reaches the threshold. Uniform file weight by construction, immune to throughput growth (SAE ~10x). Deterministic and bit-identical: cumulative tx count is chain content.
- Staging during sync is separate and disposable: height-bucketed arrival segments (100k blocks per bucket, arrival_NNNNN.log + index_NNNNN.log sidecar). The cooker consumes staging forward behind the executor, cuts epochs by tx count, and deletes a staging bucket once all its blocks are cooked. Buckets and epochs do NOT align 1:1; nobody cares, staging exists only on the machine doing the one-time initial sync. Everyone else bootstraps from sealed epoch files over torrent/S3.
- Epoch file sections: bodies (zstd frames of 16 containers + published 512KB dict; measured 2026-07-17 on 112k real containers: 2.24x blended, ~71GB full-Fuji bodies vs 229GB raw, 34µs random-access decode; frame-256 buys only +5% for 14x slower access, rejected), headers, proposervm extras, state write-log SST of (account,key,^block)->NEW value rows, EF fp48 tx index, log posting lists (position-agnostic addr/topic -> EF block lists), per-epoch key bloom, footer (offsets, version; NO embedded signature: signing is manifest-level, external, so independent syncs stay bit-identical: decided 2026-07-20).
- Tx index: Elias-Fano over sorted 48-bit hash fingerprints + bit-packed block numbers on disk. Verify by decoding candidate block. No MPHF (EF matches its size, simpler). Validated on 12M real Fuji txs 2026-07-17: 288ns lookups, 0 false positives, mainnet projects to 46.9 bits/tx = 7.0GB. Caveats from measurement: EF cost is density-dependent (log2(U/N)+2), so PER-EPOCH sections run ~27-28 bits/tx, budget ~4.2GB fp RAM for mainnet, not 3.0GB monolithic; duplicate fp48s are real (~2,600 pairs at 1.2B txs), lookup API must return a candidate LIST; atomic txs live in extdata, not the eth tx list, so they are outside this index (fine for eth_getTransactionByHash, flag if avax atomic lookup is ever in scope).
- Compression: per-epoch zstd dict trained AT SEAL TIME on that epoch's raw containers (user directive 2026-07-18, supersedes the earlier one-global-dict plan; the dict ships inside the epoch file so distribution stays self-contained). Trainer is the zstd CLI (pinned v1.5.7) with a start-block-derived --dictID: klauspost's dict.BuildZstdDict is map-iteration nondeterministic (measured) and would break bit-identical files. Encode/decode is klauspost zstd, SpeedBestCompression.
- Sealing v1 hardcoded parameters (constants in state/epoch.go, all pre-freeze tunables): EPOCH_TXS=25,000 for the iteration corpus; PRODUCTION EPOCH_TXS=10,000,000 (user-confirmed 2026-07-20: ~120 epochs of ~4GB for full mainnet, ~10-day seal cadence, hot tail 1-4GB; 100M rejected: 3-month fill, 40GB files), frame-16 bodies/headers, 512KB dict target, 64KB SST blocks, bloom 10 bits/key x 7 hashes. Measured on the corpus: 3.1-4.2x whole-epoch compression vs raw equivalents.
- Epoch format v2 (2026-07-20 user decision): optional STORED-LOGS sections kill candidate re-execution for getLogs/receipts. Per log-bearing block: addr/topics/data/txIndex records (logIndex positional, txHash+blockHash derived from bodies at read time), frame-16 compressed with a DEDICATED 128KB logs-trained dict (measured better than the container dict; dict bytes count toward the cost); per tx-bearing block: uvarint gasUsed + status byte (cumulative gas by prefix sum; bloom/contractAddress/effectiveGasPrice derived). UNCONDITIONAL as of the 2026-07-20 user ruling: the flag is dead, the sections are mandatory parts of the format, v1 epochs are unsupported at open, and the getLogs/receipts re-execution path is deleted (re-execution remains for traces/createAccessList/verification only). `epochdb seal` upgrades v1 epochs in place. eth_getProof stays impossible; getLogs posting lists still provide candidates, the stored sections replace only the response construction.
- No database anywhere. Hot period = append-only logs + RAM maps; sealing an epoch = rewriting those logs into sorted compressed sections. Everything mmap'd; recent blooms pinned, old ones page-cached.
- LRU value cache key->(lastWriteBlock,value), ~1M entries, absorbs tip-heavy eth_call traffic.
- Historical state read at block N: LRU, then hot RAM map, then per-epoch blooms newest-to-oldest from epoch(N), one SST seek on first hit.
- getLogs: intersect posting lists -> candidate blocks -> read stored logs sections -> exact filter. Range capped at 10k blocks. No re-execution.
- Tip following: lag N blocks behind accepted tips from 2-3 cross-checked public RPCs. No consensus, no P-chain.
- Ingest: naked p2p GetAncestors racing peers (deforestationdb-proven), no full node.
- eth_getProof over history: impossible by construction (no tries), documented as unsupported.

## v1 scope (this build)
Measurement build on Fuji. NO sealing, NO compression, NO EF, NO blooms. Append-only files + RAM maps. Deliverables: p2p fetch of full Fuji history, forward replay with per-block state root verification (Firewood frontier), write capture to append-only writelog + code-by-hash store, historical overlay serving eth_call / eth_getBalance / eth_getStorageAt / eth_getCode at any block, A/B bench vs public Fuji archive RPC.
v1 must produce the unknown numbers: body compression ratio with a trained dict (offline experiment), total write-log size, unique (epoch,key) bloom pair count.

## Unified node direction (user decision 2026-07-20, IMPORTANT)
Flatstate (fast tip) and epochdb (compact history) merge into ONE codebase: one snowman follower, one post-image capture stream, N sinks behind flags (both projects are post-image; capture.Sink is the merge point; flatstate's LMDB tip store and the epoch sealer are sibling sinks). Two repos maintaining two followers is the wrong option. Single process only if the history/seal sink sits behind async backpressure and can NEVER stall block application (chain pace is the tip invariant); fallback: one binary, two configs, two processes.

Config surface:
- --history: archive yes/no (epoch sealing + historical RPC vs tip-only).
- stored logs + receipt fields: UNCONDITIONAL (user decision 2026-07-20: no flag, ~+18% is fine, 620 vs 800GB changes no machine class). getLogs/receipts NEVER re-execute; v1 epochs (no logs sections) are an unsupported format at open. Re-execution remains only for traces/createAccessList and verification.
- --pin-state: latest-state acceleration contract: PINNED MAP (flatstate discipline) vs bounded cache (epochdb style).
- Entry points: HTTP/WS RPC is the default door; the in-process Go API is a FIRST-CLASS second door (not EVM-only: in-process indexers get wire-free speed against the same store).

Pinned map contract (NOT an LRU, deliberately): lazily populated, pin-forever, plain pointer-free Go maps, presence = knowledge (pinned zeros make negative caching free), no per-read bookkeeping. RAM bound = touched working set <= live state size.
OOM valve (user decision): if the process nears out-of-memory (~98% used), DROP THE ENTIRE MAP and let it refill lazily. No restart, no monitoring machinery, no partial eviction (partial eviction breaks presence=knowledge; a full drop resets it correctly: empty map = know nothing = every read falls through to the authoritative store).

## Torrent distribution of sealed epochs (2026-07-20, user directive)
Epochs are deterministic and bit-identical across builders, so their sha256 and v1 torrent infohashes are stable facts shipped in a committed manifest (docs/epochs.manifest, regenerated by `epochdb manifest`). Seeding (`epochdb seed`) is always-on for whatever epochs are local: verify sha256, skip+warn on mismatch, announce on DHT + two public trackers. Leeching happens only at startup behind `serve --fetch-epochs`: diff manifest vs local, magnet-fetch missing epochs (4 concurrent, per-epoch `--epoch-timeout`, default 5m), sha256-verify, tmp+rename in.

Contiguous-prefix rule after an incomplete fetch: coverage is the contiguous epoch range from genesis (`EpochSet.CoveredEnd`). State, receipt, and log queries above the first gap return a clean "missing epoch epoch_X" error (`RequireCovered`, enforced in the state descent, the stored-receipt path, and getLogs). ASYMMETRY, deliberate: bodies and tx-by-hash lookups above the gap still serve — they are epoch-local reads — while state correctness requires full descent to genesis, so anything state-derived refuses. `SealedEnd`/head still reports the highest local epoch so the epoch-local reads resolve.

## Entry points, complete tiering (user discussion 2026-07-20)
1. In-process Go API: preferred/instant/revocable tip included (the unfinalized 2-3 preference layers exist ONLY here; unfinalized never persists). For bots and anything wanting the bleeding edge.
2. Files-as-API for same-machine processes (the third door, beats any socket protocol): sealed epochs are immutable mmap-able files (zero coordination); the hot tail is append-only buckets + fixed-record sidecars + the exechead watermark, readers chase sidecar growth (proven in production: cook/bench/verify ran beside live writers via OpenReadOnly). Contract: accepted, durable, ~seconds fresh. Ship the reader as a library. NOT single-block files (fs metadata churn, nothing gained).
3. HTTP/WS JSON-RPC for remote/standard clients (~30k req/s ceiling is the wire's, fine for its audience).
4. gRPC: only if remote high-throughput typed access is ever needed; locally dominated by tier 2. Not built.

## Single-machine HA via flock (user idea 2026-07-20)
N identical processes; ONE holds an exclusive flock on a lockfile and is the writer (follower+sealer); all others serve reads from the same files AND wait in a BLOCKING flock() as the failover pool (no polling: the kernel releases the lock on writer death, even kill -9, waking a standby instantly). Takeover = acquire lock, run the proven crash-recovery (torn-tail truncation, walk-back to Firewood root, re-execute gap), continue. Readers never blink. Limits: per-machine only (cross-machine needs real leases, not built); takeover costs one recovery walk-back (~seconds). Firewood's own file lock already enforces single-writer at the store level (observed in production).

Addendum (same discussion): the lock model's equal motivation is dev/prod cohabitation on one machine (prod holds the write lock, dev instances read the same corpus without contention). Block delivery to reader processes ("slaves") must be sub-5ms: achieved by splitting visibility from durability: writer write()s per block (bytes visible to all processes instantly via page cache), fsync stays batched (durability only); slave wakeup via inotify on the sidecar (sub-ms) or a tipbus-style mmap seq counter (~100us, flatstate-measured); dumb 1ms stat polling also meets the bound. Contract clause: the bleeding tail is visible-but-provisional; a writer crash may truncate a torn tail behind what a slave saw, so the lockfile carries a generation counter and slaves re-validate their last blocks on writer change.

## Verification without re-execution (user design 2026-07-20)
Third parties verify downloaded epochs with NO EVM execution: (1) state: stream SST post-image diffs from genesis into a throwaway Firewood, commit per block, root must equal header.Root every block (any bad diff breaks the chain forever after); (2) bodies: recompute txRoot per block from verbatim containers; (3) logs/receipts: v2 sections (logs + per-tx gasUsed + status) reconstruct full receipts (cumGas prefix sum, bloom from logs): recompute receiptsRoot vs header; (4) headers: parent-hash chain to a trusted anchor (checkpoint or snowman tip). Estimated 5-10x cheaper than replay (~day for full mainnet vs ~9 days); (2)+(3) embarrassingly parallel. To build: `epochdb verify` command: the post-bootstrap trust ritual.

Verification DX (user design 2026-07-20): two bootstrap modes. (1) plain: download-only, exit when manifest complete. (2) --verify: download + PIPELINED sequential verification: a cursor + one throwaway Firewood chase the contiguous prefix as epochs complete out of order (epoch 1 done -> verify 1; epoch 4 arrives -> nothing; epoch 2 arrives -> verify 2,3,4; verify 5 -> exit 0). Per-epoch verification = diff-apply state roots + txRoot + reconstructed receiptsRoot per block. Failure names the epoch and exits nonzero. Slab-parallel verification (self-anchoring constructed frontiers: first root check validates the inherited past) recorded as a future many-machines/impatient option, not v1.
