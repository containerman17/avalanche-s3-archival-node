## Principles and standing rules [DONE]

- BODIES + HEADERS + PROPOSERVM EXTRAS ARE THE ONLY GROUND TRUTH. State history, receipts, logs and every index are caches rebuildable by re-execution. Logs and receipts are STORED rather than re-derived (user ruling 2026-07-20), so re-execution remains only for traces, createAccessList and verification.
- NO MIGRATIONS, NO COMPAT SHIMS (STANDING RULE, user ruling 2026-07-29, verbatim): we are in active development, so DATA IS DESTROYED AND REBUILT AGAIN AND AGAIN whenever a change wants it (an adequate gate before a multi-hour rebuild is fine, implementer judges). NEVER write a compatibility shim, migration, upgrade path, or backwards-compatibility anything, for any file format or store, UNTIL THE USER EXPLICITLY SAYS someone else has adopted this node in production. Until that day, the only "migration" is delete and resync.
- THERE IS NO RE-SEAL TASK AND NO UPGRADE CODE (user ruling 2026-07-28). The corpus is disposable: when the format is final, a chain gets synced from scratch, not upgraded. So no format change ever owes a migration, an older file is refused at open by name, and nothing rewrites it. Iterate on cheap chains, not on the expensive one.
- BYTE-IDENTITY ACROSS INDEPENDENT BUILDERS IS THE CORE PROMISE. Every artifact is a pure function of chain content, so two honest builders of the same chain emit the same bytes. This is why adaptive or configured epoch boundaries, randomized index construction, and embedded signatures are all rejected.
- NO EXTRA VALIDATION OF ALREADY-VALIDATED DATA (user ruling 2026-07-29, verbatim: "extra validation of already-validated data no one asked for"). A producer executed every block root-verified and every consumer re-checks the root it loads, so a second gate in between is deleted rather than kept "for safety".
- NO DATABASE ANYWHERE. Hot period is append-only logs plus RAM maps; sealing rewrites those logs into sorted compressed sections. Everything is mmap'd or pread; the kernel tiers RAM to SSD and casfs tiers SSD to S3.
- FIREWOOD IS VERIFY-ONLY WITH ZERO READERS (user ruling 2026-07-29, verbatim: "Firewood is just a dumb hash verifying machine"). No read path ever touches Firewood. This is what permanently deletes `eth_getProof`, `debug_dumpBlock`, `debug_accountRange` and `debug_storageRangeAt`, and what unpins `CommitEvery`.
- ONE CHAIN PER PROCESS (user ruling 2026-08-04). Several chains on a box are several processes, one container each.
- ONE NODE TYPE. No archival/pruned/indexer personas, no second binary, no floor (user ruling 2026-07-30): "how much history do I keep locally" is a chunk-cache size over the bucket, and the indexes are inside the epoch format. Local disk decides only how FAST cold history answers, never WHAT a node can answer.
- SEAL ALWAYS DELETES fully sealed raw buckets (user ruling 2026-07-29: `--delete-raw` was the only sane setting, so the flag does not exist).
- MAINNET IS UNTOUCHABLE until Fuji is finished and PROVEN working past SAE (user ruling 2026-07-29). Only then: sync mainnet from scratch on the final format, upload, and update `latest`, which the user does by hand.
- AGENT POLICY (user ruling 2026-07-29): subagents on this project run OPUS, always, explicitly pinned per dispatch; never fable.

## Chain identity [DONE]

A CHAIN IS NAMED BY ITS BLOCKCHAIN ID, NOT BY A FILE (user ruling 2026-07-31). Descriptor JSONs are gone from the CLI. The grammar is one shape everywhere: `--chain C|<blockchainID>`, defaulting to `C`, alongside `--network fuji|mainnet`.
- WHY IT WORKS AT ALL: everything a descriptor file carried is ON-CHAIN. The blockchainID IS its CreateChainTx's txID, so one `platform.getTx` returns the verbatim `genesisData` AND the `subnetID`, and the txID is the string the operator already typed. `C` needs no call: avalanchego's embedded config is the C-chain's canonical genesis, byte-identical to the same tx's genesisData. vmKind is not a question either: `C` is coreth and everything else is subnet-evm, because a custom vmID means nothing (a real L1 ships stock subnet-evm under its own plugin ID) and a wrong guess cannot be silent (the data dir's vmkind stamp refuses it, and the first executed header fails to decode).
- THE CACHE IS A CACHE, NOT A REGISTRY: the first resolution writes `<chain data dir>/chain.json` and every later start reads it with no network call. Delete it and the next start refetches. The cached values WIN over `--network`, exactly as the vmkind stamp wins over the flag: one data dir, one chain, and the cache is what the dir was built with. A cache naming another chain is refused rather than adopted.
- THE DATA-DIR MODE STAMP, day one, per the no-migration rule: `state.Store.BindVMKind(kind)` writes `epochdb.vmkind` into misc.log on first open and refuses the other kind forever after ("data dir was built by coreth, refusing to open it as subnetevm: delete the corpus and resync"). It lives in misc because misc is already the replayed append-only KV every store has.

THE CHAIN ROOT IS THE TRUST ANCHOR, and its byte-exact definition is a format commitment (user ruling 5 of 2026-07-31, AMENDED 2026-08-05 to drop upgradeBytes): `root = sha256(genesisData)`.
- `genesisData` is the P-chain CreateChainTx `genesisData` field VERBATIM, for the tx whose txID IS the blockchainID. NO separator, NO length prefix, NO normalization or re-encoding. THE ANCHOR IS THEREFORE PURELY ON-CHAIN DATA: anyone with a P-chain endpoint and nothing else reproduces it, which is a genuine strengthening over hashing an off-chain file alongside it, and it is immune to the whitespace and key-order sensitivity of hashing a JSON string someone re-serialized.
- UPGRADE BYTES ARE NOT IN IT (amendment of 2026-08-05, and the user's reasoning is the ruling): correctness is enforced by the STATE ROOT, not by the anchor. A semantically wrong upgrade.json diverges at its activation height and the executor hard-stops, so a corpus built with the wrong file CANNOT EXIST. A file that differs only in FORMATTING produces byte-identical execution, so hashing it verbatim manufactured a divergence where there is none, and made the anchor depend on an off-chain file we often cannot obtain (11 of our L1s run configs reconstructed from `eth_getChainConfig`). The residual case, two operators with different FUTURE-dated upgrades producing identical corpora today, resolves itself loudly when the timestamp arrives.
- THE DECISIVE FACT IS UPSTREAM, and it is why the earlier ruling was wrong rather than merely expensive: subnet-evm's `Genesis.toBlock` (`core/genesis.go:314`) calls ONLY `ApplyPrecompileActivations`. STATE upgrades run through `ApplyUpgrades`, called from `core/state_processor.go:84`, `miner/worker.go:232` and the tracer, every one of which takes a PARENT timestamp. Upgrades therefore apply INSIDE A BLOCK and never to genesis; upstream says it outright at `core/state_processor_ext.go:25`: "In block processing and building, [ApplyUpgrades] is called instead which also applies state upgrades". Genesis state, and the genesis block hash, are a pure function of `genesisData`.
- UPGRADE.JSON IS OTHERWISE UNCHANGED: still read verbatim at every start, never cached, never re-serialized, still `<data>/upgrade.json`, still mandatory to REPLAY a chain that ships one, and a missing or wrong one still fails loudly, just at its activation height instead of at the anchor.
- THE C-CHAIN FOLLOWS THE SAME RULE with no fallback and no network call: `platform.getTx` serves it on both networks, and those bytes are BYTE-IDENTICAL to avalanchego's embedded `cfg.CChainGenesis` (sha256 b666bb656e443e80968ab52843ae53244005ee5759e15fbc6c0bb4b73fba3c1a on mainnet, ee55f14ef1ecb457457dd06760d06e8db709314578876b5acac6b8c3f56f4b3a on Fuji). Both hashes are pinned by test, so a drift between avalanchego's copy and the chain fails.
- upgrade.json IS THE ONE THING NOT ON-CHAIN, so it takes avalanchego's own convention: `<chain data dir>/upgrade.json`, read verbatim on EVERY start (never cached, never re-serialized) and fed to the executor. It is NOT hashed into the root, see the amendment above. Nothing else is a chain-level input, which is why there is no config file left.
- THE L1 DOOR, and deliberately nothing more: `dist.GenesisData(ctx, apiURL, blockchainID)` POSTs `platform.getTx` against `<apiURL>/ext/bc/P` and returns raw genesis bytes, blockchainID in, canonical bytes out. No L1 network plumbing beyond it, no client abstraction, no caching.

MULTI-CHAIN, AVALANCHE L1s: one binary and one format, with trust anchored PER CHAIN, so there is no global registry and no cross-chain authority anywhere. Every chain operator runs their own publisher and their own bucket. A private or permissioned chain uses a private bucket and inherits access control from S3 natively, which is precisely what a swarm cannot offer.

## Epoch format [DONE]

An epoch is an IMMUTABLE artifact NAMED BY ITS OWN HEX SHA256. The local index is one marker file per epoch, `epoch_<startblock>_<blockcount>.cas`, holding that artifact's hash: startup is readdir the markers plus read footers, and height->epoch is a binary search over that table. No catalogue and no manifest; the marker is a local pointer, the hash inside it is self-verifying, and it is written by whoever learned the epoch (seal, or the join walk).

SECTIONS (17, format v6): bodies (zstd frames of 16 containers plus a published 512KB dict), headers, proposervm extras, the state write-log SST of `(account,key,^block)->NEW value` rows, the Elias-Fano fp48 tx index, the tx-fingerprint bloom in front of it, log posting lists (position-agnostic addr/topic -> EF block lists), the key bloom, stored-logs sections, stored-receipt sections, and the footer (offsets, version, prev-epoch hash).
- NO EMBEDDED SIGNATURE: nothing in the file may depend on WHO built it, or independent syncs stop being bit-identical.
- CODE SHIPS INSIDE THE EPOCH (user decision 2026-07-28) as `'c' | hash | zeros` rows in the SST keyspace ('a' < 'c' < 's'), so it rides the existing sparse index and key bloom and needs no new section. The gap it closed: a node bootstrapped purely from downloaded epochs held every block, state value, log and code HASH but not the code, so the first `eth_getCode` or contract-touching `eth_call` failed. PLACEMENT RULE, decided by measurement rather than by taste: an epoch carries the code of EVERY account row it writes, not only of code first deployed inside it. First-deploying-epoch costs 288MB of blobs, every-referencing-epoch costs 478MB, i.e. +190MB (+0.6%) on a 32.6GB corpus. That price buys the invariant that WHICHEVER epoch answers the account read also carries that account's code. Determinism: the set is a pure function of the epoch's own post-image rows, blobs are content-addressed, and the SST build sorts them, so map iteration order and local file layout cannot reach the bytes. `code.log` stays as the hot-tail store for code deployed above the sealed end.
- STORED LOGS AND RECEIPTS ARE MANDATORY, NOT A FLAG (user ruling 2026-07-20). Per log-bearing block: addr/topics/data/txIndex records (logIndex positional, txHash and blockHash derived from bodies at read time), frame-16 with a DEDICATED 128KB logs-trained dict, which measured ~2.5 points better than the container dict. Per tx-bearing block: uvarint gasUsed plus a status byte (cumulative gas by prefix sum; bloom, contractAddress and effectiveGasPrice derived).
- BLOCK HASHES LIVE IN THE TX INDEX (user ruling 2026-07-30, verbatim: "instead of 1.2 billion there is 1.3 billion, who cares"). A block hash and a tx hash are both just hashes that resolve to a block number, so block hashes go INTO the tx index and its bloom in the same fp48 space, mapped to the block's OWN height, rather than into a second structure. What it deleted: a floor-to-head `map[common.Hash]uint64` that was the single biggest resident item in the process, measured 80.6-100.5 B/entry, i.e. 4.6-5.8GB of Go heap at 57.4M blocks and 7.3-9.1GB at mainnet's ~90M. What it costs, measured on an epoch of 200,000 blocks and 2,000,000 txs: txidx +9.79% (5.78 B per block hash, in a section that is lazy, not resident), txbloom +10.00% (exactly 2.00 B per block hash of mmap-backed page cache), i.e. +180MB of evictable bloom and +520MB of on-disk index at mainnet against 7.3-9.1GB of heap deleted. What survives on the heap is BOUNDED: a 128Ki-entry FIFO ring of hashes accepted since the last cook, 12.6MB, flat forever, over a day of cook outage at chain pace.
- COMPRESSION: a per-epoch zstd dict trained AT SEAL TIME on that epoch's own raw containers (user directive 2026-07-18, superseding one global dict), shipped inside the epoch so distribution stays self-contained. The trainer is the zstd CLI (pinned v1.5.7) with a start-block-derived `--dictID`, because klauspost's `dict.BuildZstdDict` is map-iteration nondeterministic and would break bit-identical files. Encode/decode is klauspost zstd, SpeedBestCompression, with one encoder state per seal. The trainer's exact version is a hard system requirement, see below.
- BODY FRAMING is 16 containers per frame: 2.24x blended compression at 34us random-access decode. Frame-256 buys +5% compression for 14x slower access, rejected.
- THE zstd CLI AT AN EXACT PINNED VERSION IS A HARD SYSTEM REQUIREMENT [DONE]. The version is `state/epoch.go`'s `ZstdPinnedVersion` (currently 1.5.7), written in that one place and read from there by the Dockerfile so image and binary cannot drift. `serve` checks it at STARTUP and REFUSES TO START on a missing zstd, an unparseable `--version`, or any other version, naming the version required, the version found, and the two ways to satisfy it: install exactly that version, or run the published `ghcr.io/containerman17/epochdb` image, which ships a static copy. User ruling 2026-08-05, verbatim: *"you can absolutely check the zstd version in the binary, and in case if it's different from what you expect to have in the Docker image or whatever, you can just crash immediately. It's okay. We can afford this requirement. We can afford saying, hey, you got to either install what we want you to install, and system requirements is exact pinned version, or use our Docker images. And Docker images should be like 99% the way."* WHY IT EXISTS: the dictionary is trained at seal time BY THAT CLI, the distroless image shipped without the binary, training failed, and the code wrote the epoch dict-less after logging one line, so the same mainnet epoch sealed on two machines produced two different artifacts (`c9313ad0ae1b` at 4.62x on a host with zstd, `757c94419930` at 3.72x in a container without it). Byte-identity across independent builders is the promise the whole format rests on, and an optional binary silently deciding it is the exact failure the promise exists to prevent, so the dict-less fallback is DELETED rather than made configurable: there is no supported way to produce a differently-shaped epoch, and no env var to ask for one. The single remaining dict-less case is a corpus below the trainer's own sample floor (7), checked in Go rather than read off zstd's exit code, so it stays a property of the INPUT and every builder skips the same corpora. For an operator it is one line: same zstd version everywhere, or the node does not run.
- NO UPGRADE PATH (user ruling 2026-07-28). v6 is the only format the code can read: an older epoch is refused BY NAME ("format v5, unsupported: delete the corpus and resync") and a pre-content-addressed data dir the same way. A format change is paid for by a from-scratch sync, not by rewriting files.

STAGING DURING SYNC is separate and disposable: height-bucketed arrival segments (100k blocks per bucket, `arrival_NNNNN.log` plus an `index_NNNNN.log` sidecar), plus the capture families `writelog`, `headers`, `logs` and `rcpt`, all on the same bucketing and the same fsync group, with a missing file meaning an empty store. The cooker consumes staging forward behind the executor and deletes a bucket once all its blocks are cooked. Buckets are HEIGHT-bounded, not tx-bounded, because blocks arrive out of order and a file must be addressable by height alone; the constant is local-only tuning and never canonical. Buckets and epochs do NOT align 1:1. Mainnet at 10M blocks measured ~1.2GB per bucket across all families; for a much denser chain, lower BucketBlocks per deployment, because cook RAM scales with per-bucket writelog size (user reviewed 2026-07-29: fine as is).

RECEIPTS AND FULL LOGS ARE CAPTURED LIVE INTO THE TAIL (user ruling 2026-07-29: a node must serve recent receipts, blocks, txs and logs like a normal node). Receipts used to exist ONLY in sealed epoch sections, so the unsealed tail served zero receipts. A bucketed tail family `rcpt_NNNNN.log` plus its index holds one record per tx-bearing block, `uvarint len(logsRec) | logsRec | rcptRec`, both halves being the EPOCH stored-section encodings VERBATIM, so seal COPIES BYTES and there is no re-execution stage inside seal at all (seal needs no genesis, no overlay and no EVM). NO-RECORDS RULE: seal REFUSES a tx-bearing block that has no captured record ("resync it, there is no backfill"), and a backfill-by-re-execution crutch is deliberately absent because corpora are disposable. Cost: 211 B/block, 8.5% of all raw tail bytes, purely tail disk, since sealed epochs are byte-identical either way. SAE-proof by construction: receipts are per-block deterministic at execution regardless of when a header settles them.

## Epoch size: the doubling schedule [DONE]

`state.EpochTxsAt(i)` is the entire rule: `size(i) = min(8,000,000, 250,000 << i)`, i.e. 250k, 500k, 1M, 2M, 4M, then 8M forever, so cumulative boundaries are 0.25M, 0.75M, 1.75M, 3.75M, 7.75M, 15.75M and +8M each after (user ruling 2026-07-31, replacing a flat 10M and rejecting a per-VM-kind pair). An epoch seals at the first block whose cumulative tx count reaches that epoch's threshold. There is no size flag and no config.

- WHY A PURE FUNCTION OF THE EPOCH INDEX: node equality is the format's core promise, and every node must cut byte-identical boundaries independently, without a registry, a config file or a conversation. Cumulative tx count is chain content and the epoch index is a count of epochs, so nothing local can reach the boundary. This is exactly why ADAPTIVE thresholds (cut on elapsed time, disk pressure or observed tx rate) and CONFIGURED thresholds (a per-chain or per-operator knob) were rejected: both let two honest builders of the same chain emit different files. The index the seal loop feeds the schedule is simply how many epochs are already sealed, so a resumed seal cuts exactly where an uninterrupted one would.
- WHY THE SMALL START: never sealing is not free, and the cost falls on the node that is running, not on a publisher. A chain that never fills an epoch hoards its whole history in the raw tail, which is HEAP-BACKED and unevictable rather than mapped, is ~4.2x bigger than the sealed form on SSD, has NO S3 offload path (only sealed artifacts are content-addressed and tierable), and answers misses by descending it with no per-epoch bloom. Measured: ~250 B/tx of heap for a tail that never seals. At 250k the first epoch is reachable by a real L1, which is the whole point of the small start.
- WHY THE GIANTS ARE UNAFFECTED: the five small epochs total 7.75M txs, noise against a billion, and everything above them is the flat 8M, so a big chain converges to the proven shape (C-chain at ~1.2B txs cuts ~152 epochs, DFK at ~1B cuts ~130). Miss cost and bloom hot-key duplication scale with the NUMBER of epochs, and ~152 is still the shape the residency numbers were measured against (120 epochs): ~152 bloom probes at ~15us per miss, ~0.01 wasted SST reads per miss at the 20-bit bloom, bloom RAM from 3.30GB toward ~3.7GB.
- WHY NOT THE PER-VM-KIND PAIR that was on the table (coreth 10M, subnet-evm 1M): a large L1 is not a small chain. DFK at ~1B txs under a 1M constant would cut ~1000 epochs, ~6.5x the mainnet epoch count on a chain SMALLER than mainnet, which is the one number the whole residency design is sized against. One schedule keyed on the index does what the pair was trying to do without the cliff.
- WHY THE CEILING IS 8M: the ceiling was briefly 16M (user amendment 2026-07-31, pure powers of two off the 250k base) and the user lowered it to 8M the same hour, because at L1 density (~1.2 tx/block) a 16M tail is ~100GB of non-offloadable disk and ~4GB of heap, while halving it costs the C-chain only ~77 to ~152 epochs, still inside the proven miss shape. 8M keeps the powers-of-two aesthetic. Downward, 1M-tx epochs would multiply miss cost by 10 at any bloom width, because miss cost scales with epoch COUNT, not epoch size.
- WHY EPOCHS STAY SMALL ANYWAY, the other side of the same argument: the UNSEALED tail costs ~1.8GB per million txs on every node and the sealed form is ~4.5x denser, so epoch size sets everyone's raw window (8M bounds it at ~14.5GB, while the 50-100M-tx epochs once proposed would make it 90-180GB). Seal itself is cheap and streaming either way, so nothing pulls the other direction. Epoch size is a tax on all consumers, not just on the publisher.
- ACCEPTED COST, stated plainly: the unsealed tip tail can reach 8M txs before a seal.
- CONSIDERED AND YAGNI: an OR-bound on the cut (seal at N txs OR M blocks) so a nearly idle chain does not take years to fill an epoch. Avalanche chains build blocks on demand, so few txs means few blocks: an idle chain's epoch simply stays small and cheap, and nothing is waiting on it. The tx-count cut alone stays canonical.

## The read path [DONE]

STATE AT BLOCK N: the uncooked-tail overlay, then the hot RAM map, then per-epoch key blooms newest-to-oldest from epoch(N), one SST seek on the first hit, then THE GENESIS TRIE STATE. There is no floor and no snapshot ladder: every node opens every epoch, and coverage must reach genesis.

THE DESCENT'S BOTTOM IS WHAT GENESIS MATERIALISED, NOT THE `alloc`, and the two are the same thing only on the C-chain. On subnet-evm `Genesis.Commit` also runs `ApplyPrecompileActivations`, so a precompile enabled at genesis has an account (nonce 1, code `0x01`) and its configured storage in the trie while the `alloc` may list nothing but EOAs; an `initialMint` credits addresses that are in no alloc either. Reading the alloc there answers `eth_getCode`/`eth_getStorageAt`/`eth_getBalance` for such an address with "account does not exist" at every height below its first captured write. So `exec.Genesis` carries `TrieAlloc`, computed once at open by running the VM's own activation code against a throwaway in-memory statedb that holds the activations ALONE (its cost is the precompile count, never the alloc size), and that is the map every floor in `state/overlay.go` reads. It is the same blind spot, one path along, as the alloc-gated tombstone under THE FRONTIER BUILD.

CODE BY HASH: `code.log`, then the epochs newest-to-oldest (bloom-gated, one 'c' row), then the genesis trie state (which is where a precompile's `0x01` body comes from). ONE FUNCTION, `state.Store.Code`, and there is no second code path: the RPC descent, the SEALER (which must copy a referenced blob into the epoch it is cutting) and THE EXECUTOR (through its rawdb, `state/ethdb.go`) all call it. That the executor is on it is not a detail: a node that joined from a bucket replayed nothing, so its `code.log` is EMPTY, and the epochs' 'c' rows are the only code it has to execute the first block past its merged frontier with.

MISS COST, and it is the model the whole residency design is sized against. A key nothing ever wrote has NO early exit: the search probes EVERY epoch, and sorted keys are `kind|addr|slot` UNHASHED, so every epoch spans the full key range and no range pruning is possible. Expected WASTED SST block reads per miss = epochCount x per-epoch false-positive rate, and under casfs a wasted block read can be a cold 4MB chunk GET.

THE BLOOM IS 20 BITS PER KEY x 14 HASHES (user-driven ruling 2026-07-30). Measured with the exact bloom, 40M probes per setting, on a 120-epoch mainnet:

| bits/k | per-epoch FP rate | wasted reads per miss | resident |
|---|---|---|---|
| 10 / 7 | 0.8172% | 0.98 | 1.65GB |
| 16 / 11 | 0.0449% | 0.054 | 2.64GB |
| **20 / 14** | **0.0069%** | **0.0083** | **3.30GB** |
| 24 / 17 | 0.0009% | 0.0011 | 3.96GB |

At the original 10/7 EVERY unset-slot read (the common case inside any eth_call) paid a real block read. 20/14 buys 118x fewer wasted reads for 1.65GB more resident bloom and the same 1.65GB spread across the whole published corpus, which is noise against ~500GB of history; probe cost goes 60ns to 99ns, irrelevant beside the block read it avoids. This also kills the need for a separate global union filter over all keys ever, which would have cost more RAM for the same effect. Readers take m and k from the file.

THE DESCENT IS AFFORDABLE AT MAINNET SCALE, which is why no snapshot ladder is needed: all mainnet epoch blooms together are a few GB resident, so a full-depth miss walk (what every touch of a fresh address costs) is bounded by that RAM for the whole chain plus a few hundred bloom probes.

SECTION RESIDENCY. An epoch's bytes arrive through `dist`, so sections are not free slices of one mapping.
- BLOOMS (key + tx) ARE LOADED ONCE INTO THE GO HEAP at first epoch touch and NEVER RE-READ (user ruling: epochs are immutable, so there is nothing to re-read). This is the one place the design deliberately spends heap: a filter is exactly the structure where a byte that changed underneath is a WRONG ANSWER rather than a slow one, and it is read on every descent forever.
- THE OTHER RESIDENT SECTIONS (dict, sstIdx, headersIdx, bodiesIdx, deletes, logsDict, fullLogsIdx, rcptIdx) keep long-lived views: per-chunk mmaps assembled at epoch open and held for the process's life.
- THE TX INDEX VIEW IS LAZY, mapped on the first query that gets past the tx bloom and held from then on. Mapping it at epoch open would fetch every epoch's Elias-Fano chunks at startup and destroy the property that a pending-tx poll touches no EF page at all.
- QUERY-PATH SECTION READS (SST binary search, logidx probes, zstd frames, stored records) go through `pread` and COPY. The one searchable big section, logidx, is binary-searched with one small ranged read per probe, and its list bounds come from the next table entry's offset, which is exact because lists are appended in table order.
- THE STRADDLE RULE is generic, not per structure: every fixed-stride structure in the resident set can cross a 4MB chunk boundary, because sections start at arbitrary artifact offsets and no stride divides 4MB (sstIdx entries 69 bytes, deletes 61, stored-logs and receipt index members 12, framed indexes 8-byte words at an unaligned base). So `View.Slice` aliases when the range is inside one chunk and COPIES when it is not, once, for everything. At 4MB granularity a 69-byte entry straddles roughly one boundary in 60,000, so the copy is noise and the common case allocates nothing.

THE RESIDENT INDEX BUDGET at mainnet shape (1.2B txs, ~90M blocks, 120 epochs): ~7.7GB, of which 5.70GB is mmap-backed bloom (keybloom 3.30GB at 20 bits, txbloom 2.40GB, +180MB for the folded block hashes) and ~2GB the remaining indexes (rcptIdx 1.07GB, fullLogsIdx 0.87GB, bodies+headers idx 0.09GB, plus a few hundred MB of dict, deletes and sstIdx). Resident sections are 4.7-7.2% of an epoch file.

THE ACCOUNT-DELETE MAP STAYS A HEAP MAP, on measurement rather than on principle, and this is the one place the kernel-tiering rule is deliberately not applied. Measured over mainnet blocks 1..200,000 (1,711,514 cooked rows, 767,951 of them account rows): 13,747 account-delete rows and exactly TWO distinct deleted accounts, 0x..01 and 0x..02, the ecrecover and sha256 precompiles emptied by EIP-158 touch-and-delete, at 13,686 and 61 deletions. So the merged map is a couple of dense sorted `[]uint64` runs at 8 B per row, against the 61 B per row the epochs' own deletes sections spend on the same facts: mapping it would need 7.6x more resident bytes to answer the same question, plus a bloom probe and a binary search per epoch (120 at mainnet) on the StorageAt hot path. The row count is bounded by BLOCK count, not tx count (one post-image row per key per block): 0.069 rows/block measured gives ~6.2M rows and ~50MB at mainnet's 90M blocks, and even a chain that empties a precompile in every single block lands in the low hundreds of MB. REVISIT TRIGGER, recorded at `state/overlay.go`: a real corpus showing delete rows approaching one per block AND many distinct accounts.

getLogs: intersect posting lists, take candidate blocks, read the stored-logs sections, exact filter. Range capped at 10k blocks. No re-execution. The `blockHash` filter form is the same path over one resolved height (see the RPC surface section).
- DISK EMERGENCY LEVERS, recorded and deliberately NOT pulled because getLogs is a primary workload on this node: (1) delete the posting lists and range-scan the stored-logs section instead (block-ordered and contiguous, so a 10k-block query is one ~5-10MB sequential read plus ~600 frame decodes, 20-40ms CPU, near-zero IOPS), saving ~10-13% of every epoch; (2) delete the stored logs and receipt sections and bring back re-execution for getLogs and receipts, saving another ~20% but making every log or receipt read cost ~ms per candidate block, which is the wrong trade for a log-heavy serving node. Together ~30% of the corpus if disk ever truly forces it.

CONTIGUOUS-PREFIX RULE: coverage is the contiguous epoch range from genesis. State, receipt and log queries above the first gap return a clean "missing epoch epoch_X" error. ASYMMETRY, deliberate: bodies and tx-by-hash above the gap still serve (epoch-local reads) while state correctness requires full descent to genesis.

## The tx index [DONE]

Elias-Fano over sorted 48-bit hash fingerprints plus bit-packed block numbers, verified by decoding the candidate block. No MPHF (EF matches its size and is simpler). Lookups are 288ns; EF cost is density-dependent (log2(U/N)+2), so per-epoch sections run ~27-28 bits/tx. Duplicate fp48s are real (~2,600 pairs at 1.2B txs), so the lookup API returns a candidate LIST. Atomic txs live in extdata, not the eth tx list, so they are outside this index.

SEPARATE REJECT FROM LOOKUP, which is what took 7.10GB off the resident set. The user's complaint that drove it stands as the motivation: 7GB resident for history coverage is waste. The clincher is the query pattern, which had been weighted as exotic and is actually the hot path: `eth_getTransactionByHash` for a tx the caller JUST SENT and that is still in the mempool is an UNKNOWN hash, so it misses everywhere and walks every epoch. Every wallet polling its own pending transaction does this, so a node that only ever serves the tip, with no historical use case at all, would otherwise pay the full history-wide residency.
- `secTxBloom` covers exactly the fp48s the tx index encodes (the same slice, so the filter and the index it guards cannot disagree), at 16 bits/tx with the matching optimal k=11, read as a zero-copy view probed with `binary.LittleEndian.Uint64`, alignment-free, so it is page cache and not Go heap. Deterministic by construction (OR-accumulated bits, no seed search). Measured: 2.00 B/tx exactly, with a per-epoch false-positive rate of 0.046%, i.e. ~0.055 wasted index loads per pending-tx poll across 120 epochs.
- THE INDEX IS READ IN PLACE, never decoded onto the heap: the EF and packed readers index the section bytes directly, so opening an epoch's tx index is a 16-byte header parse plus five slices whatever the entry count (measured 128 bytes total against 5.53 B/entry for the old heap decode). The build side still materializes in heap and serializes, so epoch bytes are unchanged.
- `WalkCandidates(hash, fn)` is the traversal: raw tail first, then epochs newest to oldest, deduped, stopping at the first candidate `fn` verifies. The container read and the full-hash compare live inside that callback, so the walk and the verification interleave with the verification logic in one place. Block-by-hash resolves through the same shape with a header compare, so a fingerprint collision between a block hash and a tx hash costs one header read and nothing else.
- fp48 IS NOT THE WASTE AND MUST NOT SHRINK: an unknown hash false-matches with probability 10M/2^48 per epoch, about 4e-6 across the whole chain, whereas 40 bits would give ~1.1 false candidates per query and each one costs a body read, which is exactly the failure the bloom widening removed.
- NOT BUILT, deliberately: no verification-side check of either the bloom or the folded block hashes (the fingerprints derive from bodies and headers the verifier already checks, and a wrong filter can only cost reads or a null, never a wrong answer), no "kind" bit to disambiguate a collision (verification already does it, and a bit would cost more than the one read it saves).

WHY ELIAS-FANO, AND THE PERFECT-HASH ALTERNATIVE (considered 2026-07-30, NOT adopted, and the analysis is kept because it carries the revisit condition). EF is not a poor choice: it stores an EXACT sorted set of n 48-bit fingerprints in l + ~2 bits each, and the information-theoretic floor for that is log2(u/n) + log2(e) = 26.2 bits at 10M txs per epoch, so the measured 27.4 bits is within about 5% of optimal. The 47.4 bits/tx splits as 27.4 for the fingerprint side and 20.0 for the block number. But exactness is capability we do not need: the fp48 is ITSELF only a lossy proxy for the tx hash, so paying near-optimal cost to store a lossy value exactly is the real inefficiency, which is what a perfect hash would fix. A minimal perfect hash (RecSplit ~1.6 bits/key, BBHash ~3, PTHash ~2-4) maps the epoch's hashes to [0,n) with no collisions, and a 16-bit verification fingerprint per slot rejects non-members at 2^-16 per epoch (about 0.002 false candidates per unknown-hash query chain-wide, against 4e-6 today). That is 3 + 16 = 19 bits where EF spends 27.4, saving about 18% overall, which is modest ONLY because the 20-bit block payload is incompressible and dominates. THE REAL PRIZE IS WHAT MPHF ENABLES, not the bits it saves: a slot is computable, so the block array becomes ONE ranged read at a known offset instead of an EF traversal. NOT ADOPTED, for one reason that outranks the RAM: MPHF construction is seed-search based, and epoch byte-identity across independent builders is this project's core promise, so introducing a randomized build step into the one artifact that must be reproducible bit for bit is a hazard on exactly the guarantee we cannot get wrong. Deterministic construction is achievable (fixed seed, ordered iteration) but it must be PROVEN by two independent builders, not assumed. Secondary reason: the tx index is no longer resident at all, so MPHF was solving the wrong half. REJECTED outright in the same session: a plain sorted array of (fp48, block) pairs at 68 bits/tx, which is worse than EF. IF this is ever adopted it must land BEFORE mainnet seals, like every other format commitment.

## The windowed shared chunk cache [DONE]

The cache is a shared tree of PLAIN CHUNK FILES, 4MB, at `<cache root>/<window>/<chain>/<artifacthash>.<index>`. It replaced a byte budget plus a pin contract plus hole-punch eviction, and the four reasons ARE the design (only the fourth is a bug rather than a design cost):
- (a) A BYTE BUDGET IS A NUMBER NOBODY CAN SET. It had to be picked ahead of time, per node, against a disk shared with the spool, the raw tail, Firewood and everything else on the box; too high and the node fills the disk, too low and it refuses to use free space that is sitting there. The thing an operator actually knows is "do not fill my disk", which is a WATERMARK, not a budget.
- (b) THE PIN CONTRACT WAS CORRECTNESS DEBT SPREAD ACROSS TWO REPOS. A hole punch under a live mapping is silent: no error, no fault, no short read, just zeros, and a zeroed bloom page is a FALSE NEGATIVE, i.e. history the node holds and denies. Every read path had to pin the exact range it was about to touch and release it at exactly the right moment; one missed release leaked residency, one missed pin was a wrong answer. That contract is DELETED rather than documented harder: eviction is `unlink`, and unlinking a mapped file cannot change what a reader is looking at.
- (c) ONE PROCESS PER CACHE DIRECTORY. The old store wiped anything it could not vouch for, so a sibling tool run against a serving node's data dir ate that node's warm cache. The window tree has no in-file index to disagree about, so N processes share one cache and the worst a race costs is one ENOENT and a refetch.
- (d) THE CLEAN MARKER WAS A COLD START WAITING TO HAPPEN. A fill was one `pwrite` with no atomicity, so a `kill -9` meant throwing the whole cache away. Chunk files are renamed into place after an fsync, so a `kill -9` costs nothing and `Close` is no longer load-bearing.

THE FILE NAME IS NOT A CONTENT HASH OF THE CHUNK, deliberately: artifact hash plus index already names immutable bytes uniquely, is derivable by anyone holding the artifact hash without fetching a chunk list first, and leaves ownership of a stray file decidable by looking at its name. The spool and the pointers keep their own semantics and stay OUT of the cache tree.

THE WINDOW IS A HUMAN, SORTABLE NAME AND IT COMES FIRST: the UTC start of a 20-minute bucket, written `2026-08-03T12-40` (Go layout `2006-01-02T15-04`), fixed width in every field so the minute is always 00, 20 or 40. Two properties are load-bearing, not cosmetic. (a) ALPHABETICAL ORDER IS CHRONOLOGICAL ORDER, so the globally oldest cohort is the lexicographically first directory under the cache root and `os.ReadDir`'s own sort hands it over for free. (b) It parses back to the exact instant, and a name that does not re-format to itself is not one of ours, which rejects a stray directory and an off-grid minute with ONE rule. An integer bucket number had neither: an operator could not read it, and hand-trimming meant arithmetic. Never local time.

THE CHAIN IS THE LEVEL UNDER IT, because hash filenames are illegible to a human and the chain directory is what makes ownership visible: `du -sh cache/*/<chain>` per chain, `rm -r cache/*/<chain>` to wipe exactly one chain, and the one-writer-per-chain invariant enforced by the directory tree instead of by a convention. THE IDENTITY IS THE DATA DIRECTORY'S OWN NAME, which needs no plumbing and is already the right string: a chain's dir is the one thing an operator names it by. The chain root hex was the other candidate, since it qualifies the tip pointer, but `dist` does not have it until the tip is published.

THE WINDOW IS THE LRU. The directory a file sits in IS its recency, so recency order is written in the filesystem rather than in one process's memory: it survives a restart with no journal, and several processes share it without agreeing about anything. Each process keeps a `chunk -> window` map in RAM for its own artifacts, rebuilt by ONE NAME-ONLY WALK of its own chain directory in each window at startup (measured 112-118ms over a 175,000-file ext4 tree, which is what makes a walk cheaper than a journal). An entry that is wrong because a sibling evicted the file is an ordinary miss: ENOENT, drop the entry, fetch, maybe cache.

READS are `open`+`pread`. TOUCH PROMOTION: a read of a chunk in ANY non-current window renames it into `<current window>/<chain>/`, mkdir on demand, at most one rename per chunk per window. The adversarial review killed promote-only-if-two-windows-behind: under pressure everything the worker is about to eat looks equally stale, so that rule stops separating hot from cold exactly when it matters and the cache degrades to FIFO. A rename failure other than ENOENT keeps the old map entry, since the file is still where we think it is. In-process singleflight per chunk, so N concurrent misses on one chunk cost ONE ranged GET.

LONG-LIVED MMAPS ARE ALLOWED ONLY FOR THE RESIDENT SET. Chunk files are separate inodes, so a section spanning several is not contiguous memory: a resident section is one mapping per chunk, assembled at epoch open and held for the process's life, with copy-at-boundary. ACCEPTED COST, recorded rather than hidden: an unlinked-but-mapped chunk keeps its blocks, so a node can hold ghost disk roughly the size of its resident set.

A RANGED GET IS CHECKED BEFORE IT BECOMES A CHUNK (2026-08-05). Nothing on the read path hashes a chunk back, and a chunk file is named `<artifacthash>.<index>`, so bytes that arrived from the wrong place would be served as verified content forever. The answer's `Content-Range` must therefore parse, its START must equal the offset that was requested, and its TOTAL must equal the size this store derived the chunk layout from; anything else is an error and is never cached. Per-chunk digests exist (`dist` publishes a list and `dist.VerifyChunk` checks one) but nothing on this path calls them: wiring that in needs a casfs hook and is not built.

WRITES ARE ADMISSION CONTROL, NEVER EVICTION. Before a fill, `statfs` (f_bavail, ABSOLUTE BYTES, not a percentage of a filesystem casfs does not own) says how much room is left. A STATFS THAT FAILS IS NOT "NO ROOM": the disk is unknown, so the fill is skipped and, crucially, the worker does nothing at all (read as "not roomy" it dropped one window per settle delay until a flapping mount had deleted the whole cache). Over the watermark the chunk is NOT cached: the fetched bytes are served from memory and forgotten. Nothing is ever deleted to make room for a fill. Under the watermark: tmp, FSYNC, rename. The fsync is MANDATORY and is correctness, not tuning: nothing checksums a chunk file on the way back in, so a torn chunk under a correct name is a silent wrong answer, and a half-written bloom page poisons a load into exactly the false negatives (b) was about. Default watermark 95% full (5% free), held internally as a bytes-available floor, configurable.

EVICTION IS ONE BACKGROUND WORKER, ONE WHOLE WINDOW AT A TIME, NO ALLOCATION-TIME EVICTION. While the disk is over the watermark, DROP THE OLDEST NON-CURRENT WINDOW ENTIRELY, then wait ~60s for statfs to settle before believing it again; under the watermark, idle on a short poll. Putting the window first collapses this to almost nothing: no per-file victim selection, no cursor, no batched getdents, no rmdir-after-drain and no skipped-entry-while-unlinking caveat, because the names sort chronologically, so the first entry of a sorted readdir IS the oldest cohort and everything in it is at least one window cold by construction. Every chain sharing that window goes with it, which is correct, since they are competing for one disk.
- IT NEVER TOUCHES THE CURRENT WINDOW: if only the current window has files it stops and admission control carries the load. The review proved the alternative strictly worse: a saturated cache should FREEZE FULL, because every evicted-and-immediately-refetched chunk is a GET that bought nothing.
- THE ACCEPTED EDGE, recorded rather than hidden: a cache filled FAST concentrates most of its bytes in few windows, so the first pressure eviction after a bootstrap or a backfill drops a big cohort at once. Deliberate, self-correcting (the next fills spread across new windows), it fires only when the disk is genuinely full, and everything it drops is already at least one window cold. The alternative, per-file selection inside a window, buys a smoother curve for a cursor, a scan and a class of race the whole-window drop does not have.
- Stray `*.tmp` older than ~1h are collected in the sweep.

TTL: `EPOCHDB_CACHE_MAX_AGE` (a Go duration, default 720h, i.e. 30 DAYS) is the SAME OPERATION gated on the window name's date instead of on disk fill. It is an environment variable and NOT a flag, like every other cache knob: the cache is configured by `dist` out of the environment, not by `serve`'s flag set. Whole window directories older than the max age go BY NAME, with no stat and no per-file work. Safe by construction, because a promotion's target is always the CURRENT window, so nothing anyone still reads sits in a directory named thirty days ago.

METRICS report evictions (WINDOWS dropped, not files), admission refusals, FILL, EVICT AND CACHED-READ ERRORS with the last error's text (a read-only cache dir, no inodes or an fsync EIO makes a node an S3 passthrough, and so does a cached chunk that will not read or map: that read correctly falls through to the network and returns right bytes, which is exactly why an EIO storm or a process at vm.max_map_count is otherwise indistinguishable from a cold cache), free bytes (-1, never 0, when statfs itself failed), the watermark, and VICTIM AGE, the age of the window the worker last deleted from. That last number is THE HONEST HORIZON, i.e. how long a chunk really survives on this node, which a configured byte cap could never have reported. `/status` carries it.

ONE COST ACCEPTED: object sizes are no longer free at startup. A sparse cache file used to BE the object's length; a plain chunk file is not, so a restart pays one HEAD per artifact it opens. One HEAD per epoch beats an on-disk index that can go stale.

CONTAINERS SHARING A CACHE bind-mount the same host directory and MUST AGREE ON UID; a container that writes as a different user leaves files its siblings cannot evict. Same-uid is the whole requirement: no lock, no manifest, no handshake. Many processes racing to delete the same oldest window is harmless by the same ENOENT tolerance: there is no recursive-delete syscall, so every one of them walks and unlinks individual files, a loser's unlink fails with ENOENT and is ignored, and the racing storms simply parallelize the work.

## Seal [DONE]

SEALING IS AUTOMATIC AND IN-PROCESS (user ruling 2026-08-01). No seal command in a cron, no operator sibling, no flag: the serve process seals itself at the end of every cook pass, because a node that produces epochs is what publishing history means, and an epoch nobody runs the sibling for is an epoch that never exists.

WHY IT IS SAFE IN-PROCESS WHEN A SIBLING WAS NOT: the objection was never the write, it was the DELETE of raw buckets a live reader still points at. An external sibling unlinks files while the serving process's fds, mmaps and in-RAM bucket index still name them, and there is no way to tell that process first. In one process there is, and THE ORDER IS THE WHOLE MECHANISM:
1. CUT the epoch, deleting nothing, so both sources exist.
2. PUBLISH it into the live epoch set and fold its account deletes into the descent's delete index, so every sealed height now has a sealed answer. The publish is an atomic snapshot swap into the SAME set every reader already holds, sharing epochs with the previous snapshot, so nothing is rewired and nothing an in-flight read holds is ever closed.
3. ONLY THEN unlink the raw buckets, drop our own mapped sorted buckets, our bucket-log pairs and the fetcher's staging segments.
Step 3 LAST is what makes the delete a no-op for correctness; step 3 AT ALL is what makes it free disk, because an unlinked file this process still holds open keeps every one of its blocks allocated until the process exits. Nothing races a cook because cook and seal are the same goroutine. THE READ PATH NEVER CREATES: a retired height reads as "not here" everywhere instead of resurrecting an empty arrival log, which is the bug an earlier `O_RDWR|O_CREATE` read path had (it turned every later read of that range into an EOF error instead of an epoch fallback, and left a zero-length file for the next cook to trip over).

PER EPOCH, NOT PER PASS, AND INTERRUPTIBLE BETWEEN EPOCHS (ruling 2026-08-01, forced by two things a real backlog crunch showed). (1) DISK: a whole-pass cut put all the sealed output on top of all the raw at once, ~100G on top of 411G, and a concurrent fetch had to be paused to protect the disk. (2) SHUTDOWN: a SIGINT mid-crunch kept sealing for hours, because only the cook ticker looked at the context and nothing between epochs did. So the ordering above runs ONCE PER EPOCH: cut one, publish it, unlink the raw buckets wholly behind it, drop our handles, raise the fetch floor, retire the staging segments, then the next epoch. The cook loop's context reaches the seal, which checks it BETWEEN epochs, so a shutdown costs at most the epoch in flight. Cancellation needs no resume machinery: seal always starts at the next unsealed block, so an interrupted crunch and an uninterrupted one produce the same epochs byte for byte. NOT finer than an epoch: a gather is one indivisible unit of minutes, and dropping a nearly finished one only makes the next pass redo it from the same block. `epochdb dev seal` keeps the all-in-one shape for offline dirs (nobody is reading, so there is nothing to publish to) but deletes per epoch too, because an offline crunch fills the same disk.

COST IS GATED, NOT CADENCED: a seal attempt that finds no boundary still has to scan the whole unsealed tail to know, which at 8M txs an epoch is minutes of CPU and gigabytes of rows to throw away. So the sealer keeps the exec head at which the tail is EXTRAPOLATED to reach the boundary (from the tx-per-block rate the last attempt measured, HALVED, so a chain that doubles its rate still seals on the first tick past the boundary) and below it opens nothing at all. Being late costs a slightly bigger raw tail, being early costs a wasted gather, hence the bias. THE GATE DATES A MEASUREMENT, NEVER A FAILURE: only a pass that actually reached the boundary and found the tail short may move it. Pushing the gate forward on error once turned three failures into a night of silence, and a permanently unsealable corpus paying a gather per cook tick and saying so every time is the correct direction, because a stall nobody sees is worse than a log nobody likes. Seal failures are logged and never fatal, the same contract cook has.

THE SEAL'S CEILING IS ITS READABLE HEAD, NOT THE EXEC HEAD (ruling 2026-08-05). A seal opens the corpus read-only and works from that snapshot, so its ambition must be bounded by what the snapshot can serve: a pass either cuts an epoch or declines through the tail-stays-raw path that dates the gate, and it never gathers an epoch's worth of blocks only to trip over a height it was never able to read. That is enforced at the source: A READ-ONLY OPEN TAKES THE EXEC HEAD BEFORE IT SCANS, never after. The writer appends every family of a block before the watermark names it, so a watermark read at t is served in full by scans that run after t; read last, it was dated after seconds of RAM-index rebuild over millions of raw blocks, during which a catching-up executor lands thousands more, and the snapshot then carried a head it could not serve. Cost of the rule: a cut can land one cook tick later, i.e. a raw tail bigger by the blocks executed during one open, which is nothing against a wasted gather per tick.

SEALING DOES NOT KNOW S3 EXISTS (ruling 2026-08-02, after an expired SSO token killed three seals and then silence). Two rules:
- THE WRITE PATH DOES NOT REACH THE NETWORK. Publishing an epoch sets pointers, so a synchronous signed PUT there made an expired credential kill a purely local piece of work. Pointers are LOCAL FIRST with exactly the spool semantics of content: set writes the value and returns having sent nothing, and the sync ticker uploads.
- THE SEAL DOES NOT READ THE BUCKET EITHER. The head epoch comes from the LOCAL MARKERS alone (one ReadDir plus one 64-byte read, no artifact opened), instead of opening the whole epoch set, which on a producer whose artifacts are uploaded and released is a HEAD plus ranged GETs per epoch per pass.
- CONSEQUENCE, stated because it is the contract: A FULLY OFFLINE NODE AND A NODE WHOSE CREDENTIALS EXPIRED BEHAVE IDENTICALLY FOR SEAL. Both seal locally, forever, on the cook cadence; only uploads stall, loudly, on the sync ticker, and everything they produce stays durable in the spool until the bucket comes back.

THE SEAL'S PEAK MEMORY IS BOUNDED AND INDEPENDENT OF BLOCKS PER EPOCH (ruling 2026-08-02, forced by OOM kills). The schedule caps TXS and says nothing about BLOCKS, so the sparse-L1 shape (an L1 at 1.2 tx/block puts ~6.7M blocks in every 8M-tx epoch) made an epoch's cost per BLOCK, and a gathering sealer paid it three times over: it held the whole epoch in RAM at ~2.75 KB per block, it assembled the artifact in a growing buffer, and zstd pooled one ~1.1GB encoder state per core that a single-threaded `EncodeAll` never used. THE RULE, four parts:
- STREAM THE SECTIONS: write them in file order straight into a file in the spool, hashing as it goes, then rename it under its own hash. The sealed size never appears in the sealer's resident set.
- RE-READ THE RAW RATHER THAN GATHER IT: one pass decodes block bodies (fixing the block count and collecting the tx and block-hash fingerprints, so nothing keccaks a transaction twice), and the builder pulls each section through a sequential walk over the raw family it needs. A family is walked more than once, which is bandwidth, not memory.
- EXTERNAL-SORT WHAT CANNOT STREAM: post-image rows and the logs-dict samples spill to a scratch dir IN THE DATA DIR (never /tmp, same filesystem) and merge back. Rows are laid out `key53|block BE|seq BE|value` so byte order IS (key, block, seq) order, and the key bloom, whose size needs the unique-key COUNT, reads back a scratch file of the keys the SST just streamed.
- ONE ENCODER STATE per seal.
Result: ~1084 bytes per block of peak RSS at the same wall time and the SAME EPOCH HASH. The largest per-block term that remains is NOT the seal: opening a bucket log read-only builds a RAM index entry per block per raw family over the whole unsealed tail, ~182 B/block, which any process that opens the store pays. COST, stated because it is real: roughly twice the sequential raw reads per epoch (the receipts family three times, because the logs dict has to exist before its records are compressed), and temp files whose size is the epoch's write rows plus its stored-logs records, removed when the build returns and swept if a build was killed.

THE SCRATCH SWEEP IS UNCONDITIONAL AND RUNS AT STARTUP (user ruling 2026-08-06, verbatim: "if we do not share the spool between the chains, then sweeping on the start makes sense, because if you're starting, who needs this?"). A killed build leaves an `epoch-*.tmp` in the spool that NOTHING will ever collect: it never got its hash name, so the sync ticker cannot see it and no later pass looks for it. The 24-hour age guard that used to protect those files was fleet-era reasoning, from when one spool held many chains' builds and a stray `.tmp` could be a sibling's work in progress; one process owns the dir now and the lock above makes that provable, so every `epoch-*.tmp` the running process did not itself open is dead whatever its mtime. The sweep therefore runs on the SERVE PATH AT STARTUP (in the join, before the frontier build) as well as before each seal, and skips exactly the files this process has open, because reclaiming the disk matters most at the moment a container restarts, which is precisely when the box is short of it: the outages of 2026-08-05 left 19.9 GB of abandoned scratch across seven chains, on a box that was out of both disk and memory. BYTE-IDENTICAL OUTPUT IS THE HARD CONSTRAINT and is pinned by a test that keeps the old gathering path as the reference oracle.

## Distribution and casfs [DONE]

Distribution is ONE PUBLISHER AND MANY READ-ONLY CONSUMERS, exactly the case where a swarm is a worse HTTP server (user ruling 2026-07-29: "normal centralized epoch + latest snapshot publishing works for me", which is what buried the torrent stack). Object storage is R2/B2-class with zero egress; raw S3 egress would be ~$60 per full archival bootstrap. Epochs are deterministic and bit-identical across builders, so their names remain stable facts anyone can independently reproduce, and since the naming standard became the chunk hash list that is testable more sharply: same content implies the same list implies the same name.

S3 OFFLOADING WITH LAZY CHUNK LOADING IS CORE, 100% (user ruling 2026-07-30, superseding the previous day's "lazy loading, fuck that"): publishing an epoch means putting it in a bucket, and a node's local disk is a CACHE of that bucket.

THE LIBRARY (github.com/containerman17/casfs, its own public repo, deliberately isolated from epochdb because nothing in it is chain-specific):
- WHOLE FILES, NAMED BY SHA256 OF THEIR OWN PER-CHUNK HASH LIST. The name IS the integrity check AT CHUNK GRANULARITY, so Put is idempotent and any number of nodes can share one bucket with zero coordination and dedupe for free. See FORMAT COMMITMENTS below for the layout; the tail casfs stores past the content is its metadata and is invisible above `dist`.
- SPOOL-DIRECTORY DURABILITY: the library holds NO state outside the filesystem, and its spool directory IS the registration. A caller atomically renames a correctly named, sealed file into the spool, so there is no ack to lose and it is kill-safe by construction; the library scans the spool at startup and on demand and uploads anything the bucket lacks. Each upload makes ONE sequential pass over the file first, computing both the object digest SigV4 signs and the hash list the name commits to, so a name that lies is refused before a byte goes out and a FAILED upload is never reported as corruption. `Release` confirms the upload and unlinks the spool file.
- EVERY CHUNK IS VERIFIED ON FILL against `list[i]`, before it is cached or served, and a mismatch is a loud error naming the artifact and the chunk index. A cache HIT is not re-verified: the file was verified when it was filled and landed by fsync+rename, and re-hashing 4MB on every hot read buys nothing. First open of an artifact costs a HEAD plus ONE ranged read that carries the metadata tail AND the last content chunk together, which a footer-last format was going to fetch anyway; the hash list then stays resident at 32 bytes per 4MB (76KB for a 9.5 GB epoch, ~5MB for all of mainnet).
- A COLD CHUNK IS FETCHED AS PARALLEL SUB-RANGES, NOT ONE SERIAL RANGED GET [DONE, 2026-08-05]. The design input is S3's own latency shape: time to first byte is ~20 ms whatever the range's size, and one connection then moves 93-109 MB/s. A serial 4MB chunk is therefore ~20 + ~43 = ~63 ms, while four 1MB sub-ranges together are ~20 + ~11 = ~31 ms, on the same bucket, for free, and it is what AWS's own performance design patterns recommend. THE SPLIT IS TRANSPORT ONLY: the sub-ranges tile the chunk exactly, with no gap and no overlap, and the assembled bytes are verified against `list[i]` before admission exactly as before, so byte-identity and the integrity claim are untouched. Every sub-range is checked against the `Content-Range` it comes back with, not merely the first, and one that fails, arrives short or arrives from the wrong offset fails THE WHOLE CHUNK rather than leaving a hole in it; there is no retry ladder, because a failed fill is already a miss to the caller. THE COUNT IS DERIVED (`ceil(chunk / 1MB)`), so a short last chunk stays ONE request and the tail read is still the single ranged GET that carries the last content chunk with it. THE CONCURRENCY BOUND IS THE STORE'S, one semaphore across every in-flight sub-request rather than a per-chunk limit, because a joining node misses on many chunks at once and 4 requests each would multiply into a storm the NIC cannot absorb (~12 Gbit is ~125-375 misses/s at 4MB). Default 16, i.e. ~1.6 GB/s at ~100 MB/s per connection; `EPOCHDB_FETCH_CONCURRENCY` overrides it, because the right number is a property of the box rather than of the format.
- MULTIPART ABOVE 5 GiB, IN 128 MiB PARTS. A single PUT is refused outright above 5 GiB, which is where an 8.85GB epoch sat: smaller artifacts uploaded fine and that one could never finish, so the `latest` pointer never moved and no consumer could join the chain. Each part is buffered whole, because SigV4 commits to its sha256 before the body goes out, so peak memory is one part whatever the object is. A completion is PARSED rather than trusted, because S3 answers CompleteMultipartUpload with an Error body under a 200 OK. Anything that fails after initiate aborts the upload best-effort, so a bucket is not left paying for orphaned parts. Multipart and single PUT send the same bytes and produce the same name, because the name is a function of the content and never of how it went up.
- POINTERS ARE SPOOLED FILES TOO, AND THE SPOOL COPY IS WRITTEN WHETHER OR NOT THERE ARE CREDENTIALS. The mutable names are written locally and reconciled by the sync pass AFTER that pass's content, then released. Publishing used to depend on there being a casfs at the MOMENT OF THE WRITE, and the only caller is inside the seal loop: a dir that sealed everything offline and was restarted with keys uploaded its artifacts and no pointer, and the pointer then waited for the NEXT seal, which is weeks on a slow chain. casfs rebuilds its dirty set in its constructor by scanning the spool's pointer directory, so a value left there while offline goes up on the first sync after the keys arrive (`casfs.WriteSpoolPointer` is that write without a store), under the same ordering and with nothing re-sealed. CONTENT BEFORE POINTER IS THE GUARANTEE: a bucket reader following a pointer never lands on an object that is not there yet. A read answers locally while the value is spooled, otherwise reads the bucket and re-materializes it CLEAN, never dirty, because re-uploading a value this node did not author could only put a stale pointer over a newer one. WRITES ARE FIRE AND FORGET, READS ARE LOCAL FIRST, AND A READ THAT GENUINELY NEEDS THE BUCKET AND FAILS BUBBLES AN HONEST ERROR. Nothing fabricates a value.
- REJECTED: a Release-time full-chunkification pre-warm (user: cache pollution; ranges that are cold by definition falling through to S3 on demand IS the design). Only organic traffic warms the cache, which also makes the spool-to-bucket transition invisible: whatever was being read is already cached when the spool file goes away.

NODE SIDE: S3 CREDENTIALS ARE OPTIONAL. With them, sealed epochs offload and deep history lazy-loads on demand, so a ~200GB node serves FULL archive semantics and is merely slower on cold history. Without them the node holds everything locally and nothing about the read path changes. MIRRORS FEDERATE TRIVIALLY: the config takes a LIST of backend URLs, and any HTTP endpoint serving the same hashes is interchangeable, an IPFS gateway included. No registry, no coordination, no official mirror; the hash space is the namespace.

NODE INTEGRATION: one type, `dist.Store`, hangs off the state layer, so one process has exactly one of them, and NOTHING above `dist` has an S3 branch.
- SEAL PUBLISHES BY RENAME onto its own spool path, then writes the local marker and advances `latest`.
- A READ returns a `Blob` whose `Slice` is a view of a mapping without credentials (the spool file) and a chunk-cache read with them. MMAP OF THE SPOOL FILE IS THE NO-CREDENTIALS PATH ONLY, deliberately: with credentials a released artifact must actually free disk, and a live mmap of an unlinked file pins the inode for the life of the process.
- CONFIG IS ENVIRONMENT ONLY, per the standing no-config-system directive: `EPOCHDB_S3_ENDPOINT` (empty = fully local), `_BUCKET`, `_ACCESS_KEY`, `_SECRET_KEY`, `_PREFIX`, `_REGION`, plus `EPOCHDB_CACHE_MIN_FREE`, `EPOCHDB_CACHE_MAX_AGE`, `EPOCHDB_CACHE_DIR`, `EPOCHDB_FETCH_CONCURRENCY` and `EPOCHDB_MAX_STAGING`.
- CREDENTIALS ARE TWO ROADS (user ruling 2026-08-01): static `_ACCESS_KEY`/`_SECRET_KEY` are the R2 and MinIO path and always win, and UNSET keys mean the AWS SDK's DEFAULT CHAIN (env, shared config, SSO, instance role), which is what makes a temporary-credential deployment work with nothing but an endpoint, a bucket and a region. casfs pulls in the AWS SDK's config/credentials packages for RESOLUTION ONLY: the HTTP client and the SigV4 signer stay hand-rolled, credentials are retrieved per request so a refresh lands on the next call, and a session token is signed as a fourth header, `x-amz-security-token`. The chain also supplies the region when `_REGION` is empty, before the `auto` fallback, so R2 is untouched; a bucket outside the shell profile's region still needs `_REGION` set.
- LAYOUT: the SPOOL is PER CHAIN at `<data>/cas`, because it holds one chain's not-yet-uploaded artifacts next to the markers that name them. The CHUNK CACHE is `<EPOCHDB_CACHE_DIR or <data>/cache>/<window>/<chain>/` and is THE ONE THING SEVERAL CHAIN PROCESSES SHARE.
- UPLOADS RUN ON A TICKER INSIDE SERVE, `--sync-every` (default 5m): upload everything spooled that the bucket lacks, then unlink each confirmed local copy. THE TICKER IS THE ONLY THING THAT TALKS TO S3, pointers included, and it uploads them last. Fail-loud, never fatal: a failed upload leaves the artifact durable in the spool and the next tick retries. Without credentials the loop does not start.

FORMAT COMMITMENTS. There is no reseal, so these were cheap once and are impossible later.
- HASH-CHAIN FOOTERS: epoch K's footer embeds epoch K-1's NAME (see the naming standard below), and a chain's first epoch embeds the CHAIN ROOT, `sha256(genesisData)`. Prev-hash is chain content, so files stay bit-identical across builders, and ONE HEAD HASH AUTHENTICATES ALL OF HISTORY. This is what makes a JSON manifest unnecessary: there is no catalogue to publish, fetch, verify or keep in sync.
- THE SNAPSHOT HASH IS NOT IN THE EPOCH FOOTER, and cannot be: an epoch's bytes must never depend on WHICH KIND of node built it, or byte-identity across builders breaks.
- NAMING STANDARD, and it is CHUNK-GRANULAR SELF-AUTHENTICATION [DONE, 2026-08-05]. A stored artifact is `[content: L][hash list: 32*N][trailer: 16]`, where `N = ceil(L / 4MB)`, chunk `i` is `content[4MB*i : min(4MB*(i+1), L))`, `list[i]` is sha256 of chunk `i`, and the trailer is `u64 LE` of `L` followed by the magic `CASFSv1\n`, magic last. THE NAME IS `sha256(hash list)`.
  - THE USER SPECIFIED THE SCHEME HIMSELF (2026-08-05, verbatim): hash every 4MB chunk, put those hashes in one chunk, and make the hash of that the file name. He ruled AGAINST padding the last chunk ("it wastes ~2MB per artifact, which is 3% on the 68MB epochs most of our chains produce, and casfs already handles a short final chunk today") and AGAINST one object per chunk. Two levels, no binary tree, no proofs.
  - ONE SMALL TAIL READ IS ALL IT COSTS, because `L + 32*ceil(L/4MB) + 16` is strictly increasing in `L`: a single stored size admits exactly one `L`, so a reader derives the tail's length from the object size, fetches it in one ranged GET, checks `sha256(list) == name`, and every chunk then verifies POSITIONALLY against `list[i]`.
  - THE CEILING IS 131072 CHUNKS = 512 GB, and anything larger is REFUSED rather than paid for with a second level. The largest epoch this project produces is 9.5 GB.
  - THE TAIL IS CASFS'S METADATA AND IS INVISIBLE TO CONSUMERS: `Size()` is `L`, every range lives in `[0, L)`, and nothing above `dist` ever sees the list or the trailer. THE EPOCH FORMAT IS UNCHANGED by any of this (same sections, same schedule, same boundaries, same contents), but because the epoch footer is LAST, both readers now seek from the LOGICAL LENGTH casfs reports rather than from the end of the file on disk: the credentialed casfs read and the no-credentials spool mmap alike.
  - Deliberately NOT IPFS CIDs and NOT torrent infohashes, and the reason changed: it is no longer that a chunker-dependent name is unacceptable (ours is one now, at a pinned 4MB), it is that a CID forces UnixFS's DAG encoding and an infohash forces bencode plus a piece length, i.e. someone else's container in exchange for interop nobody has asked for. Ours is 16 bytes of trailer and a flat list.
  - THE COST, stated plainly: a name is no longer reproducible with stock `sha256sum`, which the old plain-sha256 rule bought. It is reproducible with four lines of any language (`split -b4M`, sha256 each piece, concatenate, sha256), and the trade is that an artifact is now verifiable INCREMENTALLY instead of only after the last byte lands.

THE LOCAL INDEX, and why it is not a manifest in disguise: a data dir carries one marker per known artifact, each holding 64 hex characters. It records only which artifact covers which heights; it has no sizes, no signatures, no ordering authority, and every hash in it is self-verifying. Boot reads markers, the join walk writes them, and losing one costs a re-bootstrap, not data. Walking the chain at every boot instead would make a producer's own history depend on a mutable pointer.

THE POINTER IS A HINT, NEVER AN AUTHORITY. The bucket carries exactly ONE mutable, non-content-addressed object per chain: `latest-<chain root>`, naming the newest epoch hash and nothing else. It is qualified by the CHAIN ROOT rather than the blockchainID because `dist` already has the root on both sides with no new plumbing (the producer to link epoch 1's footer, the consumer to refuse the wrong chain). An unqualified `latest` let chains publishing into one prefix overwrite each other's tips. The name is not the check: a tip published under another chain's pointer name is still caught by the footer walk. All content self-verifies by hash, the chain roots at the chain root, and the first executed block's root check against consensus-verified headers catches a lying tip. S3 IS UNTRUSTED INFRASTRUCTURE; THE ONLY ATTACK IT ENABLES IS WITHHOLDING BYTES, which is what mirrors answer, and since 2026-08-05 that is TRUE rather than aspirational: the name is sha256 of the artifact's own chunk hash list, so the bucket cannot substitute a chunk, cannot answer with a different object of the same size (what a misconfigured prefix produces), and cannot serve a truncated or edited list, because every 4MB range is hashed against the list before it is cached or served. Before that the name was sha256 of the whole file and NOTHING ON THE READ PATH EVER REHASHED IT, so a wrong chunk became a wrong state answer rather than a load failure.

## Joining a chain [DONE]

THERE IS NO SEPARATE BOOTSTRAP STORY (ruling 2026-08-03). A node has ONE start sequence, and `epochdb serve` on an EMPTY data dir with credentials does the whole join by itself. The decision tree:
1. With S3 configured, resolve this chain's `latest` pointer, local-first with a bucket fallback.
2. NO POINTER anywhere AND NOTHING PUBLISHED UNDER THE PREFIX -> a genuinely fresh chain -> start from scratch: fetch from genesis and execute, the path that always existed. NO POINTER OVER A PREFIX THAT ALREADY HOLDS OBJECTS IS A HARD ERROR, because that is the same disaster as case 3 reached by a different door: content is named by hash and says nothing about which chain it belongs to, but a prefix with content in it is a prefix somebody has published to, so a missing pointer over one is a broken or mis-typed publish and never a fresh chain. THE EMPTY PREFIX STAYS FRICTIONLESS, one list request capped at a single key, no flag and no variable: being the first publisher is the normal way a chain begins. Three cases skip the probe: no credentials (there is no bucket to be wrong about), a dir whose exec head is above 0 (its own history is the evidence, and a producer that has not sealed its first epoch yet restarts for days), and `EPOCHDB_NEW_CHAIN=1`, the deliberate "a new chain into a prefix other chains already publish into", which is legal because pointers are qualified by chain root and which nothing else can tell from the failure. A list that FAILS is a refusal too (it needs `s3:ListBucket`): "cannot tell" resolves the same way everything else here does.
3. POINTER EXISTS -> walk the epoch chain backward by prev-hash and confirm EVERY linked artifact is available (bucket or local), checking contiguity at every step (epoch K-1 must end exactly where K starts) and that the first epoch's prev-hash equals this chain's ROOT, refusing "wrong chain" otherwise. Anything missing or broken is a HARD ERROR that refuses to start and names the artifact that broke the walk. NEVER silently fall back to from-scratch.
4. CHAIN INTACT BUT NO LOCAL EXECUTION STATE -> run the frontier build automatically, then continue into normal follow/serve.
5. CHAIN INTACT AND LOCAL STATE PRESENT -> warm start.

WHY: one simple story, and no knowledge an operator has to carry. Joining a chain that already has published history is not a different mode of a node, it is what starting a node means; a second command to remember is a second thing to get wrong at 3am, and the failure it produces (a node that quietly re-executes from genesis) is the most expensive one in the system. A typo'd `EPOCHDB_S3_PREFIX` would otherwise make a provider re-replay weeks of history, which is a disaster, not a degraded mode. HARD ERROR OVER SILENT RE-REPLAY, ALWAYS.

VALIDATION IS CHEAP AT EVERY START (same ruling, hard constraint). A WARM dir pays THE FILESYSTEM AND NOTHING ELSE: the local markers must name the epoch `latest` points at and must cover blocks 1..N with no gap and nothing stranded above one. Zero requests, milliseconds. It is enough because this dir walked the hash chain when it joined and wrote every epoch it has sealed since, so the local index IS the linkage record; a marker that is missing or out of line is NOT fatal, it drops through to the full walk, which rewrites it. A COLD dir pays metadata: one pointer GET, then per epoch a size probe (a HEAD under casfs) plus ONE ranged read that carries casfs's metadata tail and the epoch's last content chunk together, which is where the ~1KB FOOTER lives and the only place the prev-hash lives. Neither path rehashes content and neither downloads an artifact to validate it: the bytes come down when the frontier build or a real read wants them. Opening an epoch properly must NOT be used for this, because it loads every resident section and the key bloom alone is 20 bits per key, so validating a mainnet corpus that way means downloading gigabytes of blooms to prove files exist. The footer-only cost is pinned by test at one chunk over a bucket-only artifact.

THE EPOCH CHAIN IS WALKED AT EVERY START (ruling 2026-08-01), because serving a corrupt epoch set silently is the one unforgivable failure. EXISTENCE AND LINKAGE ONLY: no content is rehashed and no section is read, so it stays O(epochs) metadata reads. The full no-execution pass over the corpus is `serve --verify` and stays there.

THE FRONTIER BUILD is what replaces downloading a snapshot: a k-way merge over every epoch's SST section, one cursor per epoch marching the same sorted key space with a single decoded 64KB SST block each, so the MERGE's own working set is bounded by the epoch COUNT and no SST block is ever revisited (measured 71MB of live Go heap at 100 open cursors, flat in corpus size; the open epochs' resident blooms sit next to it, as they do for every serving node). Rows are (key53, block) ordered, so the last row at or below the target wins per key; tombstones follow the descent's rules exactly (an empty account row is a SELFDESTRUCT and kills every storage row written before it; 'c' code rows are skipped, since Firewood holds accounts and storage only). Winners stream into Firewood in 200k-op batches. On success the build copies the headers of [H-256, H] down into the state layer (BLOCKHASH above H, and the crash walk-back's only way to learn what height Firewood's root belongs to) and parks the exec head at H, so serving starts executing at H+1 with no further plumbing. Deletes are emitted UNCONDITIONALLY, and an account destructed at or below the target gets its PrefixDelete even when a later row recreates it. The merge does not stream onto an empty trie, it streams onto THE VM'S OWN COMMITTED GENESIS, and on subnet-evm that holds more than the alloc: `Genesis.Commit` runs `ApplyPrecompileActivations`, so every precompile enabled at genesis has an account and its configured storage there, and an upgrade.json that DISABLES one deletes it with `statedb.SelfDestruct`. Restricting tombstones to alloc keys dropped exactly that delete and merged a wrong root on the first Beam join (2026-08-05). Deleting an absent key is a no-op, and account keys sort before storage keys, so every PrefixDelete is queued before the first storage Put.

THE BUILD OPENS FIREWOOD WITH NO HISTORY TO KEEP, and that is a memory requirement rather than a tuning choice, because the merge's OTHER working set is Firewood's. Firewood retains its in-memory revisions (128 while serving, 64 of them unpersisted), so a build that commits one revision per batch retains every batch: growth linear in BATCH COUNT, i.e. in corpus size, measured at 470MB per 200k-op batch, which is what OOM-killed the first join of the published Fuji corpus at 63.9GB of anonymous memory. A build therefore opens Firewood with 2 revisions, which persists every batch; nothing reads a historical revision during a build, and a build that dies is wiped rather than resumed. The per-batch cost then FALLS as the trie grows instead of accumulating (measured over 8 batches of 100k ops: 1483MB retained at the serving profile, 688MB at the build's, with the second half of the batches costing less than the first). Pinned by test.

A TORN BUILD HEALS ITSELF. The merge writes Firewood as it streams, so a process killed mid-merge leaves a partial frontier under an exec head of 0, and every later start then dies in `exec.New` with "head=0 but firewood root X != genesis Y", which is a permanent crash loop out of state that is derived and disposable. Exec head 0 with a non-empty Firewood cannot be an executed history, so it IS torn by construction: the join wipes Firewood, the copied header window and the seeded ring, and rebuilds from the epochs. That signature is the whole detector, so there is no build-in-progress marker to keep consistent, and a dir with an exec head above 0 is never wiped.

THE MERGE TARGETS THE HEIGHT THE SEALED END'S HEADER COMMITS TO, and is checked against that header's Root (ruling 2026-08-01). Below the SAE boundary a header commits to its own post-execution root, so the target is H and the check is `merged == header(H).Root`. Above it (ACP-194) `header(H).Root` is the post-execution root of the block header(H) SETTLES, so the target is S = settledHeight(header(H)) and the check is `merged at S == header(H).Root`. Same cryptographic strength, one header hop away; no trust-me mode, no second code path for the pre-SAE case. A header that settles itself, the future, or genesis is refused, and so is a merge that does not reproduce the root.
- WHY THE SETTLED HEIGHT AND NOTHING ELSE, and the pairing is FORCED rather than chosen. (a) It is the only height above the boundary any header names at all: settlement advances in jumps, so most heights are never named, and their roots live nowhere but the executor's own ring, which a downloaded node does not have and cannot have. (b) The gas clock, not just the root: executing S+1 needs its PARENT's gas clock, consensus publishes it only at settlement points, and the same four markers that attest the root pin it. So a frontier parked anywhere but a settlement point could not take a single step even with a correct root.
- Therefore the build seeds `ring[S]` with the verified root plus the reconstructed clock and stamps a FRONTIER FLOOR: nothing below S was ever executed here, so a later header settling a height below the floor has no root of ours to present and the settled-root check skips it instead of hard-stopping. The floor itself IS checked. The boundary-straddling case falls out for free: when S is at or below the transition block it is a synchronous height whose own header carries root and clock.
- COST, recorded: the frontier lands a settlement lag (1..10 blocks in practice) below the sealed end, so the follower re-fetches and re-executes those few blocks on the way up. `serve` therefore floors the fetcher at min(sealed end, exec head) instead of the sealed end flat, and the header window the build copies down stops AT the frontier, never above it, or the crash walk-back would start at a height whose container this node never fetched. Blocks below the sealed end that get re-executed are ignored by seal (it cuts from the sealed end + 1) and by the tail overlay (it backfills from the cooked/sealed head + 1).

PROVIDERS BOOTSTRAP FROM THEIR OWN BUCKET, and that is the only case. Seeding a new box by copying a bucket is the operator's business; no cross-operator or read-only-foreign-bucket support is designed for. `epochdb dev bootstrap` stays as the MANUAL/OFFLINE form, for offline prep, for a box that will never serve, and for `--verify`; starting a node never requires it.

## serve: one process, one chain [DONE]

`epochdb serve` runs follower, executor and RPC in ONE process; nothing restarts to surface a new block (user ruling 2026-07-29: restart-based serving "makes the node unusable"). Following is not a flag and there is no static mode (user ruling 2026-07-29: "that's how blockchain nodes work"); a `--frozen` read-only serve was proposed and REJECTED the same day, because side consumers read through the one serve's RPC port. The serve process is the SOLE writer and sole server of its data dir.

SOLE WRITER IS ENFORCED, NOT CONVENTIONAL (ruling 2026-08-06, the user's condition on the unconditional scratch sweep below: "if we make sure that this is not possible"). A writing process takes `flock(LOCK_EX|LOCK_NB)` on `<data dir>/.epochdb.lock` and holds it for its whole life; the kernel drops it when the process dies, so a `kill -9` leaves nothing stale to clean up. A second writer FAILS AT STARTUP naming the directory and the fact that another epochdb process holds it: it does not wait and does not proceed, because a second writer has nothing to wait for. Two writers on one dir both append to the raw families, both truncate a torn tail at open and both want Firewood's exclusive handle, so what was silent corruption in exchange for a typo is now one legible refusal. WHO TAKES IT: `serve`, and every `dev` stage that writes the dir (`fetch`, `exec`, `cook-index`, `cook-txindex`, `seal`, `bootstrap`, `publish`, `backfill-logs`), which is the same warning this document already carried about dev stages beside a live chain, with teeth. WHO MUST NOT AND DOES NOT: read-only openers. `state.OpenReadOnly`, the SDK and `dev probe` read a live chain's dir beside its writer on purpose, that capability is production-proven, and no lock reaches it.

THE OPERATOR SURFACE IS ONE COMMAND, AND EVERYTHING ELSE IS AUTOMATIC OR HIDDEN (ruling 2026-08-03). Five parts:
1. `epochdb serve` IS THE PRODUCT, and it is the only name an operator ever types. It follows, executes, indexes, cooks, seals, publishes, uploads and answers RPC, and it recovers by itself.
2. `serve --verify` VERIFIES WHAT IS ON S3, AND DELIBERATELY NOT THE LOCAL RAW TAIL. It runs the full no-execution engine over this chain's SEALED epochs. WHY THE TAIL IS NOT IN IT: verification of local raw files is meaningless as a feature, because the honest way to verify raw is to re-download and re-execute it, and that is precisely what a from-scratch start already does. The tail is at most one epoch, so FROM-SCRATCH REPROCESSING IS THE LOCAL-RAW VERIFICATION STORY, and the sealed epochs, the artifacts other people consume, are the thing that needs a dedicated verifier. SEMANTICS PICKED, the least code that means anything: a STARTUP check after the join walk (the walk is what names the epochs) and before the node serves a byte; a failure exits nonzero. Not a loop, not a cadence, not a subcommand.
3. THE RESILIENCE CONTRACT: from any situation the system either organizes and reprocesses what it has by itself (the join decision tree, the automatic in-process cook and seal, the retry gates) or REFUSES TO START with a reason an operator can read. A start failure exits 1; a runtime failure flushes the writers FIRST (so the restart is a clean resume and not a crash walk-back) and then exits 1, which is the restart contract every supervisor already relies on. No library package has an `os.Exit` or a `log.Fatal`.
4. `/status` REPORTS THIS PROCESS'S ONE CHAIN: chain, serving, accepted/executed/cooked and the chunk cache's own account of itself, as one JSON object. IT REPORTS THE MODE'S OWN NUMBERS AND NEVER ANOTHER MODE'S: `accepted` is the follower's accepted head and exists only when following, while a `--tip-override` backfill has no follower and reports `target`/`stored` instead, the ceiling its walk was given and the containers staged toward it, so `exec_lag` on both the status line and this endpoint is always distance to a height the run will actually reach. Answered from the bind (`serving:false` until the chain is up) so an operator can watch a cold start instead of guessing. AN AGGREGATE HEALTH ENDPOINT IS NOT OURS: a rollup over the chains of a box is a rollup over CONTAINERS, which is exactly what a load balancer, a pager or a Prometheus scrape already does for every other service on the box; building a second one inside a node that can only ever see itself would be a worse version of what the orchestrator has.
5. THE STAGES AND THE BENCHES ARE HIDDEN, NOT DELETED. The pipeline stages, the standalone verifiers and the dev benches live behind an undocumented `dev` namespace with their flag sets untouched, because our own release gates and experiments drive them. A top-level invocation of a retired name PRINTS A ONE-LINE POINTER TO `serve` AND EXITS 2, so a stale script fails loudly instead of silently running a stage the node now does for itself.

ONE PROCESS = ONE CHAIN (user ruling 2026-08-04), and it is a consequence rather than a reversal: THE FLEET WAS THE CACHE'S CHAPERONE. Everything a multi-chain process uniquely bought was one shared elastic LRU across chains, and one process was the only way to have one while the cache had per-process bookkeeping. The windowed cache works IDENTICALLY across processes with zero coordination, because no process has to agree with any other about what is cached, so that reason is gone and what was left of the supervisor is pure supervision code we do not have to own. What the split buys, item by item:
- THE VM-KIND REGISTRATION CONSTRAINT DISSOLVES. libevm's extras registry is process-global and panics on re-registration, which is the constraint that would otherwise force coreth and subnet-evm into separate processes and shape everything around it. One chain per process never binds anything: the C-chain and any L1 are the same command with a different `--chain`.
- PER-CHAIN FAILURE ISOLATION BECOMES THE OS'S JOB. It was a supervisor, a per-chain context, a partial flush that deliberately left mmaps open so a stopped chain could answer frozen data, and a `/status` field to explain it. A process boundary does all of that better and for free.
- TESTNET/MAINNET MIXING IS TRIVIAL, because the network is a per-process flag.
- OPERATORS RUN ONE CONTAINER PER CHAIN, which is how containers work anyway: one image, one command, one restart policy, one set of logs, one port per chain.

THE LISTENER BINDS BEFORE THE STARTUP WORK, because startup (epoch-chain walk, exec open, startup cook, tail overlay) can be over an hour on a large corpus and binding last made a port collision a FATAL an hour in. Requests arriving before readiness wait in the accept backlog, and `/status` answers from the moment it binds.

GOROUTINES AND OWNERSHIP:
- THE FETCHER runs real snowman consensus (ported from flatstate, validator set from 2+ cross-checked P-chain RPCs at >=95% stake agreement) and is the SOLE writer of staging. Its in-RAM store IS the executor's block source, so an accepted container is executable the instant it is durable, with no reader-sidecar lag. Ingest is naked p2p GetAncestors racing peers, no full node. `--tip-override <containerID>` swaps the follower for a bounded backfill walk in the same slot.
- THE EXECUTOR runs one goroutine, holds the exclusive Firewood handle and is the sole writer of the state layer AND of the tail overlay, which it feeds through the one choke point every execution path already uses. `CommitEvery=64`: the old pin to 1 existed only so the served frontier was a committed Firewood revision, and with no Firewood readers it buys nothing, while costing 1,226 against 2,256 blk/s during catch-up (1.84x). Freshness is unaffected because head, block-hash ring and overlay all advance together PER BLOCK, right after each block's appends land, and root verification is per block below the SAE boundary, per batch above it, with an automatic per-block bisect on a boundary mismatch. At the tip the distinction disappears, because the executor closes the open batch the moment staging runs dry, which at chain pace is after every single block, so a following node commits and root-verifies per block. THE ORDERING RULE, written down at the flush: publish head and block hash PER BLOCK (publishing only at the batch boundary left `latest` naming an older height than the overlay already served, and left 63 of every 64 block hashes out of the index), and append to the state layer BEFORE committing Firewood (the other order left Firewood one batch ahead of the highest header after a `kill -9`, and the node refused to start).
- THE RPC SERVER serves N request goroutines. `latest`/`pending` state is the UNCOOKED-TAIL OVERLAY over the descent, and there is no second read path. The overlay is a map of 53-byte sorted key -> newest post-image, fed by the executor's own write frames (nothing re-derived), carrying each entry's block so the cook can prune by height; SELFDESTRUCT is tracked per address so a destructed account's storage reads as gone exactly like the descent's delete rule, recreation included. A miss falls through to the descent at the cooked watermark, and the watermark is read AFTER the miss, which is what makes the prune safe.
- THE SYNC LOOP uploads spooled artifacts every `--sync-every`. It does not start without credentials, and a failure is logged, not fatal.
- THE COOK LOOP runs the index cooks, the history refresh, the tail prune and the seal attempt every `--cook-every` (default 60s) and ONCE AT STARTUP, so the node begins serving with the smallest possible overlay and the residue it backfills from the raw writelog is bounded (a gap wider than two raw buckets is refused at open). Async and fail-loud: a failure logs and the chain keeps moving; the visible consequence is the historical window freezing plus an overlay that keeps growing, both of which the status line prints. THE PRUNE RACE NEEDS NO DOUBLE BUFFER: the prune drops entries at or below the watermark the refresh has just published, the refresh publishes that watermark only after the new sorted buckets are readable, and a reader probes the overlay BEFORE loading the watermark, so a write is always in at least one of the two layers. The prune REBUILDS the map rather than deleting in place, because a Go map never returns its buckets and this one grows to catch-up size.

STATE READ BANDS, and the one refusal that keeps them honest: `n > executed` is "not executed yet" (error), `n in [head, executed]` is the executed head (overlay then descent), `n < head` is the historical descent alone. The descent REFUSES anything above the cooked watermark instead of silently descending past uncooked writes and answering with a pre-gap value: that was the one place where a moving head could have been quietly wrong. Cook cadence is therefore the historical window's lag (60s chosen; at chain pace the window is a handful of blocks wide).

NOTHING IS PINNED AT OPEN: the head, the cooked watermark, the sorted-bucket mmaps, the account-delete index, the raw tx index and the epoch set all move under live readers, by atomic swap or by re-open-then-unmap-after-readers-drain. SHARING THE WRITER STORE forced the concurrency work that had never been needed: reading an index map outside its lock beside a live appender is a fatal concurrent map access, not a stale read, so the locks live in the stores themselves, where every caller routes through.

RPC LABELS (SAE-aware): `pending` = last accepted, `latest` = last executed, `safe`/`finalized` = last settled (which is the executed head below the Helicon boundary and on every subnet-evm chain, so all three coincide there). `pending` resolves to the last EXECUTED height for state reads, because with no mempool pending state IS latest state; `eth_getBlockByNumber("pending")` is the exception and returns the last accepted container, which the tail already serves. `eth_syncing` reports the geth-shaped object whenever the height the node is SYNCING TOWARD runs ahead of executed, and that goal is a SEPARATE number from the labels: a label may only name a height whose container this node holds, a goal may sit far above one. Following, both are the accepted head. Under `--tip-override` there is no follower, so `pending` and the block-number ceiling stay at the executed head while `highestBlock` is the walk's ceiling; nothing anywhere reports the staging store's head, which is whatever an earlier run left in the dir.

THE SEALED END IS A FETCH FLOOR. A floor on EVERY walk means no block at or below the sealed end is walked or requested. Without it a restarted follower re-downloads all of sealed history: walks short-circuit on the STAGING store alone, and seal legitimately deleted the raw those blocks lived in, so the walk drops off the bottom of the retained tail and re-fetches to height 1. The floor is LIVE, not startup-only, because sealing is in-process and the floor rises while the node runs. Mechanically it is the same rule that already ended a walk at height 1, so floor=0 is the old genesis terminator unchanged. Dependency direction: `state` imports `fetch`, so the floor is PUSHED IN from the command layer and the fetcher still knows nothing about epochs.

RETAINED STAGING IS A FETCH CEILING [DONE], the floor's symmetric twin and the gate on every giant chain. THERE IS NO OTHER BACKPRESSURE BETWEEN FETCHING AND EXECUTION: fetch runs ~1,650 blk/s against the executor's ~105 on mainnet, 15:1, and sealing only retires raw BEHIND the executed point. Unbounded, a mainnet run to the live tip finishes all 91.7M blocks in ~15 hours with execution ~5M blocks in, leaving ~86M blocks of raw staged at once: at the ~28 KB/block of epoch 9 (15,798 MB of raw for 564,413 blocks; early blocks are nearer 2.4 KB) that is 1 to 2 TB against 1.5 TB free, before the writelog, logs and receipt families that ride alongside. It fills the disk and wedges the chain in about a day, and the same shape holds for DFK (1.055B txs, ~410 GB just to stage) and Bnry (>1B txs).
- WHAT IS MEASURED IS RETAINED STAGING, NOT FETCHED-MINUS-EXECUTED, because sealing is what actually returns the space and it lags execution by up to a whole epoch. The quantity is the on-disk size of the arrival and index segments the seal has not yet retired, kept incrementally (append adds, retire subtracts a whole bucket) so the check the walk does before every block is one atomic load. ARRIVAL IS THE ONLY RAW FAMILY THAT CAN RUN AWAY, which is why bounding it bounds the disk: writelog/headers/logs/rcpt are the EXECUTOR's output and only ever span exec head minus sealed end, which the seal holds inside an epoch.
- IT PAUSES, IT DOES NOT FAIL. Exceeding the bound is normal operation on a big chain. Walks stall at the top of the walk loop, log ONCE per pause rather than per block (16 concurrent walks stalling on the same ceiling would otherwise be the whole log), and resume by themselves when the cook loop's seal drains the staging. A node that has stopped fetching and keeps executing, sealing and serving RPC is healthy, and `/status` says so with `fetchPaused` beside `stagingBytes`/`stagingCeilingBytes`, the status line with `staging=X/YGB FETCH-PAUSED`.
- THE DEFAULT IS A QUARTER OF FREE SPACE, measured once at open, following the chunk cache's precedent that a byte budget nobody can set is the wrong instrument. Safe on a small disk because it is a fraction OF that disk, invisible on a big one (1.5 TB free gives a 375 GB ceiling, tens of hours of executor runway, against the single epoch a node at the tip retains). A live statfs is deliberately NOT used: the number it gives shrinks as our own staging grows, so the bound would tighten against itself, and the rest of the disk is the chunk cache's own live watermark to defend. `EPOCHDB_MAX_STAGING` overrides it in bytes and 0 disables it, an environment knob like the other operational ones rather than a flag; an unreadable filesystem fails OPEN (unbounded, logged), because an unreadable disk is not a full one.
- THE TIP FOLLOWER IS EXEMPT BY CONSTRUCTION, not by tuning: consensus acceptance appends through its own path and never reaches the walk's check, so a node at the tip is never throttled even while a backfill walk beside it is paused. The bound is about catch-up.
- NO DEADLOCK AND NO SPIN: the pause holds no lock, waits on nothing of ours, and is a select on the context and a 5s timer, so a stopped or wedged executor costs one idle goroutine and a SIGINT returns immediately. The seal and cook loops are other goroutines and are exactly what frees the space, so a paused walk is never in their way. KNOWN CEILING: a bound smaller than one epoch's staging would stall the walk before an epoch can be completed and nothing would ever drain it; at a quarter of free space that needs a disk with a few tens of GB left, where the node has already lost.

TIP OVERRIDE IS A PHYSICAL CONTAINER ID (ruling 2026-08-01): cb58, or a 0x-hex eth block hash for a pre-ProposerVM block, where the two are the same 32 bytes. WHY: the height form resolved through the ProposerVM activation constant plus an embedded checkpoint table, and a production operator must not depend on that magic to say which block caps a corpus. A numeric value is refused by name and the error says where the IDs are printed. The CLI asks the CHAIN for the height by parsing the fetched container. The embedded checkpoint table stays for the one thing it is for, seeding parallel backward walks below the override, and checkpoint resolution SKIPS anything at or below the fetcher's floor before it touches the store: resolving a checkpoint means READING ITS CONTAINER, and seal retires the raw behind the sealed end, so a node that sealed and then backfilled with an override was otherwise unstartable. Those checkpoints are not needed at all, since their spans are durable and no walk descends there. A checkpoint above the floor whose container is genuinely missing still fails loudly.

## Verification without re-execution [DONE]

Third parties verify downloaded epochs with NO EVM execution: (1) STATE: stream SST post-image diffs from genesis into a throwaway Firewood, commit per block, root must equal `header.Root` every block; (2) BODIES: recompute txRoot per block from verbatim containers; (3) LOGS/RECEIPTS: the stored sections reconstruct full receipts (cumulative gas by prefix sum, bloom from logs) and recompute receiptsRoot; (4) HEADERS: parent-hash chain to a trusted anchor. Estimated 5-10x cheaper than replay (~1 day for full mainnet against ~9 days); (2) and (3) are embarrassingly parallel.

A CHECK THAT CANNOT RUN IS A FAILURE, NEVER A PASS [DONE]. Completeness is part of the verification contract, not an implementation detail: both halves COUNT the blocks they actually checked and must account for every block in the epoch, the framed walkers refuse to skip a block whose frame holds fewer payloads than its block group, and the PASS line reports the number the verifier EARNED rather than the block count the epoch claims. Without that, a truncated or zero-length body frame simply advanced to the next frame: the container-hash, txRoot and reconstructed-receiptsRoot checks never ran for those blocks, and the run reported `PASS: N blocks`. The state half only survived by accident (its parent-hash chain and its no-diffs-means-no-root-change rule notice a skipped header at the next epoch boundary); the body half had no continuity to fall over at all. The ANCHOR is mandatory for the same reason: a set is verified against a resolved chain root or not at all, since an anchorless verifier adopts whatever ParentHash the data claims and would pass any internally consistent forgery.

BOTH VM KINDS, with nothing skipped on the subnet-evm path. The verifier takes its kind off the descriptor and routes the libevm extras registration and the throwaway's state database through the same seam exec and rpc use. Epoch 1's prev-hash is checked against the chain root BEFORE a byte is verified, so a corpus belonging to a DIFFERENT CHAIN fails by name up front instead of somewhere in the middle. Since the 2026-08-05 amendment that check no longer says anything about upgrade.json, and is not meant to: upgrades apply inside blocks, so a wrong one diverges at its activation height where the state-root check hard-stops on it.

Two bootstrap modes: plain (walk the hash chain, index it, exit) and `--verify` (walk, then verify the whole indexed set in chain order against one throwaway Firewood, which is also what pulls every byte). Failure names the epoch and exits nonzero.

## RPC surface [DONE]

Full parity with a coreth node across eth, web3, net, txpool and debug, minus the refusal classes below (user ruling 2026-08-01: "whatever API methods are not implemented, implement them"). The audit enumerated every method on coreth's registered API services and diffed it against the dispatch table; subnet-evm registers the same set. Filters exist and WS subscriptions FIRE; personal/admin are N/A by design, since there is no keystore and no node-ops surface.

SERVED (78 methods): `eth_` chainId, blockNumber, syncing, accounts, coinbase/etherbase, getBalance, getTransactionCount, getCode, getStorageAt, call, callDetailed, estimateGas, createAccessList, gasPrice, maxPriorityFeePerGas, baseFee, feeHistory, suggestPriceOptions, getChainConfig, getBlockBy{Number,Hash}, getHeaderBy{Number,Hash}, getBlockTransactionCountBy{Number,Hash}, getTransactionBy{Hash,BlockNumberAndIndex,BlockHashAndIndex}, getTransactionReceipt, getBlockReceipts, getRawTransactionBy{Hash,BlockNumberAndIndex,BlockHashAndIndex}, getLogs, getUncle{Count,}By*, pendingTransactions, new{,Block,PendingTransaction}Filter, getFilter{Changes,Logs}, uninstallFilter, subscribe/unsubscribe; `debug_` traceTransaction, traceBlockBy{Number,Hash}, traceCall, getRaw{Block,Header,Transaction,Receipts}, getModifiedAccountsBy{Number,Hash}, getBadBlocks, printBlock, getAccessibleState, chainConfig; `net_` version/listening/peerCount; `web3_` clientVersion/sha3; `txpool_` status/content/contentFrom/inspect (empty shapes, no pool).

Notable rules:
- `debug_getModifiedAccountsByNumber/ByHash` AT ANY HEIGHT straight from the per-block write capture, which is THE DIFFERENTIATOR: a normal node needs both boundary states live. Caveats: union-of-writes counts a value rewritten to its original; capture order, not hash order; it needs the raw writelogs, so epoch-only ranges get a clean error; range capped at 10k blocks.
- OVERRIDE OBJECTS on `eth_call`, `eth_estimateGas` and `debug_traceCall` are honoured. Parsing them NOWHERE was worse than an error, because it looks like it worked: it silently breaks a simulate-with-fake-balance flow. The structs are reproduced field-for-field from coreth's internal package (not importable), including geth's `**hexutil.Big` balance so an explicit JSON `null` is distinguishable from an absent key, and the untagged BlockOverrides field names that encoding/json matches case-insensitively. The state override ends in `Finalise(false)` exactly as geth's does, so the overrides behave as a transaction that landed just before the call.
- THE `BlockNumberOrHash` OBJECT FORM IS HANDLED ONCE, in the shared block-number resolver, so no method can forget it. `requireCanonical` is a no-op here and that is correct: every height this node serves is canonical, there is no side chain to confuse it with.
- JSON-RPC BATCHING IS SERVED, with the spec's semantics, because batching is on by default or one flag away in most tooling (ethers providers, web3.py, indexers) and an array body used to be a hard `-32700`, which is a parse failure where the caller expected results. N requests in, N responses out, each carrying ITS OWN id (order is not promised and a client must match on id); a NOTIFICATION (no id) runs and produces no entry, including when it fails, since there is no id to answer to; a batch of nothing but notifications returns an EMPTY 200, which is geth's answer and keeps a client that treats non-200 as a transport failure working; an empty array is `-32600`; one malformed element is one error object beside its siblings' answers, never a failure of the whole batch. ELEMENTS RUN SEQUENTIALLY IN ONE GOROUTINE, exactly as a single request is served, so the head may move between elements (as on any node) and no element sees state torn across itself; no parallelism was added, because the observable behaviour would change and the handlers already share a History. TWO CAPS, both `-32600` BY NAME rather than a silent truncation (1000 answers to a 1500-request batch is undetectable at the caller): 1000 requests per batch and a 10MiB body, which are geth's own defaults, so ethers' default of 100 fits with room. The body cap is enforced on the bytes BEFORE anything is parsed, since the point is to bound the work, and one byte over the limit is enough to know.
- `eth_getLogs` TAKES THE `blockHash` FILTER FORM: logs of exactly that block, mutually exclusive with `fromBlock`/`toBlock` (an explicit JSON null is not a bound, matching geth's decoder), with the address and topic filters applying exactly as on the range form and the 10k-block cap irrelevant by construction. It is plumbing, not new capability: `HeightByHash` already resolves a hash through the fp48 candidate walk with a header compare, and the query is then the ordinary one-block range. AN UNKNOWN HASH IS AN ERROR NAMING IT, never `[]`, because an empty array says the block exists and has no matching logs, which is a different answer. A STORED filter (`eth_newFilter`) still refuses `blockHash` and says where to send it, since a filter is a moving range and a single fixed block has no incremental meaning.
- WEBSOCKET SUBSCRIPTIONS FIRE. Acknowledging with an id and then staying silent forever is the failure mode a wallet or indexer cannot detect. newHeads, logs and newAcceptedTransactions are driven by the SERVING head advancing, which is the same source the filter API polls and the only head whose blocks, logs and receipts this node can answer for. newPendingTransactions installs and never fires, and that is CORRECT rather than a gap: no mempool means nothing is ever pending. `ponytail:` the driver is a 250ms poll of the head, one goroutine per CONNECTION (not per subscription), with a 128-block-per-tick catch-up bound; swap for a broadcast off the accept path if sub-100ms head latency is ever needed.
- BLOCK MARSHALLING GOES THROUGH EACH VM'S OWN `HeaderExtra.PostRPCMarshal` rather than a hand-copied field subset, plus the Cancun trio (`blobGasUsed`, `excessBlobGas`, `parentBeaconBlockRoot`) guarded exactly as libevm guards them. A hand-copied subset silently dropped later-fork fields and made every `eth_getBlockBy*` differ from a reference node. `blockExtraData` stays hand-written because it comes from the block BODY; on subnet-evm `extDataHash`, `blockExtraData` and `extDataGasUsed` are OMITTED rather than emitted empty, because an empty extDataHash reads as a real zero hash to a client.
- THE FORWARD-LOOKING FEE ANSWERS ARE REAL NUMBERS, on both kinds. `eth_maxPriorityFeePerGas` is the sampled price MINUS the current base fee, floored at zero; returning the whole price (which it used to) makes a wallet bid roughly the base fee again as a priority fee and pay it. `eth_feeHistory`'s trailing `baseFeePerGas` entry describes the block after the range, and ON AN ARCHIVE MOST OF THOSE BLOCKS ARE NOT UNBUILT: below the head it is read off block `newest+1`'s own header, exact rather than estimated, which is also what avalanchego's own saevm estimator does. Only a range ending at the head is projected, through the `rpcVM.nextBaseFee` seam, by each VM's OWN exported estimator (coreth's and subnet-evm's `customheader.EstimateNextBaseFee`, and above the Helicon boundary upstream's `gastime`) rather than by reimplemented arithmetic. `eth_suggestPriceOptions` takes both inputs from those two answers, so coreth's doubled base fee is now the doubled PROJECTION and its estimate is now the TIP, which removes the deviation that file used to record.
- THE PROJECTION'S ONE ASSUMPTION, stated because a caller cannot see it: the unbuilt block is assumed to follow the head IMMEDIATELY, i.e. at the head's own timestamp. A validator would use its wall clock; a read server answering for a corpus whose head may be years old cannot, because elapsed time decays the fee state and would produce a confident number about a chain that stopped. Elapsed time only ever LOWERS the next base fee, so the assumption makes the entry an upper bound, which is the safe direction for the `maxFeePerGas` a caller builds from it.
- ABOVE THE HELICON BOUNDARY EVERY BASE FEE IS DERIVED, NOT READ, and that is one mechanism serving the whole fee surface rather than a special case in the projection. A stored post-Helicon header carries NO base fee at all, so `header.BaseFee` is absent both for the projection and for every backward-looking read; both now go through the ACP-194 gas clock reconstructed from epoch content (see SAE below). The projection is the same walk one block further on, advanced to the head's own timestamp, so the assumption above and its upper-bound direction are unchanged.
- RE-EXECUTION MUST NOT SWALLOW STATEDB READ ERRORS. geth's `getDeleteStateObject` calls `setError` and hands back an EMPTY account rather than returning the error, so re-execution above the cooked watermark ran against zeroed state; the mild half is a nonsense message, the dangerous half is that a block whose txs happen to survive zeroed state would have returned WRONG receipts with no error at all. Re-execution returns the statedb error in preference to the tx error and checks it once more after the loop, so every consumer gets the same clean cook-lag refusal `eth_call` gives.
- NULL MEANS "NOT ON THIS CHAIN", NEVER "I COULD NOT READ IT" (2026-08-05 audit). Four read-path swallows made a failure indistinguishable from an authoritative answer and are now errors. (1) A tx index that never loaded walked zero candidates, so ONE corrupt `txidx_*.idx` bucket made `eth_getTransactionByHash`, `eth_getTransactionReceipt` and `eth_getBlockByHash` answer null and `eth_getRawTransactionByHash` answer `"0x"` for EVERY hash on the chain, on a node reporting `serving:true`; both holders (serve and the SDK) now report why instead. (2) A candidate height whose container cannot be read (a missing epoch, raw retired below a gap) was reported as "unknown tx", which also SKIPPED the receipt path's coverage refusal, since that only runs once a tx has been found. (3) A sender that does not recover reported `from` and `contractAddress` as a well-formed but entirely wrong address, so an unrecoverable signature is now a refusal ON EVERY PATH THAT MARSHALS ONE: the block paths (`eth_getBlockBy*` with fullTx, `eth_getTransactionByBlock*AndIndex`, `eth_getBlockReceipts`) would otherwise have emitted the refusal as JSON `null` inside an otherwise complete answer, which a client can tell from neither a protocol quirk nor an absent field. A `newAcceptedTransactions` subscription with fullTx ENDS THE CONNECTION there for the same reason, since a notification stream has no way to carry an error and skipping the transaction would drop one it promised. (4) The TRACERS join the re-execution rule above: they take the parent state through the SAME band selection `eth_call` uses and check `statedb.Error()` per tx, so `debug_traceBlockByNumber("latest")` and a trace of a tx in the uncooked tail give the cook-lag refusal instead of a complete, plausible, entirely fictional trace over zeroed accounts. A header read failure no longer collapses into a nil header either: nil is BLOCKHASH `0x0` inside the EVM and appears in NO `statedb.Error()`, so every executing path carries a per-request capturing chain context and surfaces the read error.

THE REFUSAL CLASSES, and why each exists. A refusal is a NAMED -32000/-32601 with a message that says why, never a bare "method not found" that leaves the caller unable to tell a missing feature from a typo:
1. NO TRIES: `eth_getProof`, `debug_dumpBlock`, `debug_accountRange`, `debug_storageRangeAt`, `debug_intermediateRoots`. epochdb stores no per-block merkle tries, and Firewood, the only thing that could range-read or prove, is verify-only with zero readers (user ruling 2026-07-29, superseding a same-day build-it ruling: `eth_getProof` was buildable at the tip via the ffi, and was ditched precisely because it would have been Firewood's only reader). GENUINELY UNIMPLEMENTABLE, not deferred: there is no data structure to derive these from and adding one is a different node.
2. NO PREIMAGE TABLE: `debug_preimage`. The state key space is already hashed, so there is no preimage-to-key table to look a hash up in.
3. NO MEMPOOL / NO KEYSTORE / NO MINER / NO NODE-OPS SURFACE, i.e. components a read-only archival node does not have and will not grow: the four tx-submission methods, `eth_sign`/`eth_signTransaction` (no keys, and signing has no honest answer without them), and the whole `personal_`/`miner_`/`admin_`/`les_`/`clique_`/`ethash_` namespaces, which refuse BY NAMESPACE with a message naming the class.
4. NO RETAINED BAD BLOCKS: `debug_traceBadBlock`, consistent with `debug_getBadBlocks` returning `[]`, because replay is root-verified block by block and a bad block HALTS the executor instead of being kept for inspection.
5. WIRE SHAPE WE WILL NOT HALF-MATCH: `debug_traceChain`, which geth streams over a notification channel, unbounded, for a whole range. Refused with a pointer to `debug_traceBlockByNumber`, which is the same work per block in a shape clients already parse. Judgment call, not an impossibility: it is buildable on the subscription notifier that now exists.
`avax_*` atomic tx and UTXO methods are unindexed and out of scope.

TOLERANCES VS A PUBLIC ARCHIVE RPC: it refuses the whole debug namespace, createAccessList, getProof and the internal-eth methods, so those gates are self-consistency or cryptographic rather than A/B.

THE READ SERVER EXECUTES, which is why it needs its own per-VM seam: eth_call, eth_estimateGas, eth_createAccessList, every debug tracer, `debug_getRawReceipts` and eth_feeHistory's reward percentiles all run the EVM, and on a subnet-evm chain calling coreth's core package directly is not a wrong answer, it is a SEGFAULT inside `ApplyMessage`. The rpc seam is FOUR execution entry points plus the fee answers (`applyUpgrades`, `blockContext`, `applyTx`, `applyMsg`, `minGasPrice`, `nextBaseFee`, `baseFees`, `baseFeeOf`), a SECOND interface rather than an export of exec's, because the two want different things: exec runs whole blocks off a descriptor, rpc runs single messages under a tracer with no descriptor in hand. Everything else stays shared, since block context, tx context, EVM config, receipts, chain config and statedb are libevm types both VMs build on. The kind comes from the process-global libevm registration, so there is no second answer for a server to hold and no constructor argument to thread. `applyUpgrades` takes the parent timestamp as a VALUE, not a pointer, so no caller can express the bug where a nil parent reads as "never forked" and re-activates every already-active precompile on every block. THE SEAM CARRIES THE FEE ANSWERS, all genuinely per-VM. `minGasPrice` is the FLOOR the oracle falls back to with no transactions to sample: 470 gwei is a C-chain protocol constant, while an L1's floor is its own genesis `feeConfig.minBaseFee`. `nextBaseFee` is the projection above. subnet-evm's fee WINDOW in `header.Extra` used to be deliberately never parsed, on the reasoning that it exists only to derive the NEXT block's base fee and nothing needed one; THAT REASON EXPIRED when `eth_feeHistory`'s trailing entry had to be a fee instead of a zero, so the window is parsed now, by subnet-evm's own estimator rather than by a hand-rolled read of the layout. Below the Helicon boundary the base fee OF a block is still `header.BaseFee`, straight off the header; above it there is none to read and `baseFees`/`baseFeeOf` derive it from the gas clock. EVERY EXECUTING READ PATH STAMPS THAT DERIVED FEE ONTO ITS OWN HEADER COPY BEFORE BUILDING A BLOCK CONTEXT, exactly as `saexec.Execute` does, because `vm.Config{NoBaseFee: true}` disables the fee CHECKS and not the BASEFEE opcode: a contract reading `block.basefee` otherwise answers zero to every `eth_call`, `eth_estimateGas`, `eth_createAccessList` and tracer run above the boundary, and the caller cannot tell. The header copy is the only thing mutated (a fresh RLP decode, or `blk.Header()`), so nothing stored or hashed is touched, and a caller's `blockOverrides.baseFee` still wins because it applies to the context afterwards. ONE UPSTREAM RULE SITS ON TOP AND IS NOT OURS TO FIX: with `NoBaseFee` set and a ZERO gas price, `vm.NewEVM` zeroes `blockCtx.BaseFee` itself to keep geth's `basefee <= feecap` invariant, so a priceless call sees zero at every height, above or below the boundary, exactly as a real node answers it. What WAS ours is that `runCall` dropped the caller's `gasPrice` entirely, which pinned `eth_estimateGas` and `debug_traceCall` to that branch no matter what was asked; it reads it now, like `ethCall` always did. BaseFee is also the ONLY block-context field a stored post-Helicon header leaves stale: coinbase, difficulty, number, time, gas limit, extra and excess blob gas are all written by `BuildHeader` and travel on the wire.

## Execution: the VM seam, SAE, and fetch on L1s [DONE]

ONE INTERFACE WITH TWO PER-KIND STRUCTS, no build tags, both linked always. The exec seam is five methods, exactly the symbols that differ: `genesis`, `newStateDatabase`, `runEVM`, `transitionTimestamp`, `hasSettledMarkers`. Build tags were rejected because ONE binary must serve both kinds and `--chain` picks the kind at runtime; a second package was rejected because everything else in exec is already chain-agnostic. One type-level adapter shadows `Engine()`, because a coreth chain context wants a coreth consensus engine and that is the whole reason the two APIs cannot be one call.
- HARD CONSTRAINT, and it is fine: coreth and subnet-evm header RLP are mutually exclusive (coreth has a mandatory ExtDataHash field where subnet-evm goes straight to the optional BaseFee), and libevm's extras registry is process-global and PANICS on re-registration. Both modules link into one binary but only one can register per process, which one-chain-per-process makes free.
- REGISTRATION is a mutex-guarded one-shot switch, idempotent for the same kind and a HARD PANIC on the other. The subnet-evm set lives in its own package because package fetch's own tests register coreth and `go test` runs one process per package. It inlines subnet-evm's three registration calls rather than importing the whole VM plugin for three function calls.
- THE GENESIS TYPE IS VM-NEUTRAL, and `snow.Context` derivation is descriptor-driven: NetworkID, ChainID, SubnetID and CChainID for any chain, AVAXAssetID for coreth only. Every field is an execution input, so an L1 gets its OWN blockchainID and subnetID, which is what the Warp precompile reads.
- THE PRECOMPILE REGISTRY IMPORT IS LOAD-BEARING: subnet-evm's `extras.Precompiles.UnmarshalJSON` keeps only the config keys it finds in the registered-modules registry, and that registry is populated by init functions. Without the import, a genesis carrying a genesis-time precompile config unmarshals to ZERO precompiles with NO error, and every state root from genesis onward is wrong.
- THE FIREWOOD CACHE CLAMP: Firewood's node cache holds DECODED nodes (the cost it kills is deserialization and traversal, not reads; page cache already backs its file IO), so it cannot be replaced by mmap without an upstream rewrite. IT IS SIZED AGAINST THE CONTAINER, NOT THE DIRECTORY: an eighth of this container's own `memory.max`, floored at 64MB, which is the SAME rule and the same eighth as the exec state cache below. A CACHE PAYS FOR THE WORKING SET, AND DIRECTORY SIZE MEASURES HISTORY; the two diverge exactly during catch-up, when the dir is still small but every SLOAD walks the whole live trie at random, so the old `clamp(3% of dir, 64MB, 4GB)` under-provisioned precisely when the chain worked hardest and, being measured once at open, could not correct itself without a restart (mainnet-c at 11.07M: a 6.5GB dir bought 194MB, Firewood reached 52% of exec wall clock, 19k reads/s at 77% utilisation, 262 -> 48 mgas/s over three hours, 13GiB of 34GiB unused). The eighth composes with GOMEMLIMIT's 7/10: 82.5% of the ceiling is written down and the ~17.5% residue covers Firewood's in-memory revisions, zstd state, stacks and the page cache. It scales DOWN too, which is the point given this is unevictable anon: the same rule on the 24GiB ceiling that OOM-killed this container yields 3GB, not 4. Firewood fills the number lazily as a limit, so an idle chain in a big container never pays for its share. The 3%-of-dir formula survives ONLY where there is no cgroup to read, still capped at 4GB, because an unknown ceiling is not a licence. `EPOCHDB_FIREWOOD_CACHE` (bytes) overrides both, and a value that is not a byte count or is below the 64MB floor refuses to start.
- THE ANON BUDGET, the memory rule of a serving box: malloc is unevictable and page cache is not, so under pressure the kernel dumps exactly the mapped index pages we serve from while anon sits untouchable. Therefore NO dynamic memory-watching control loop: a fixed total budget for everything anon (Firewood clamps + exec state caches + Go heaps under GOMEMLIMIT) of ~30-40% of the box, and the majority of RAM stays DELIBERATELY UNALLOCATED, because on a serving box the page cache IS the read cache. The tension self-resolves: big exec caches earn their RAM during catch-up (measured 88-89% hit), which is exactly when nobody queries; at tip pace they shrink. The budget is a BOX number and needs a box-level instrument to hold it, which is the slice in The fleet memory budget; this rule is what sizes each process inside it.

SAE (Helicon / ACP-194). SAE is not a coreth change, it is a whole new VM: the C-chain runs coreth until HeliconTime - 10s, then boots the SAE VM on the same database, and coreth actively rejects blocks carrying SAE settled markers, so coreth-as-library can never process post-Helicon blocks. What changes semantically: `header.Root` of block N is the post-execution state root of the last block SETTLED by N, not N's own state; headers gain SettledHeight, SettledGasUnix, SettledGasNumerator and SettledExcess plus ACP-283's MinPriceExponent and ACP-176's TargetExponent; receipts are computed per block at execution but committed only at settlement, so the settling block's receiptsRoot and bloom cover the CONCATENATED receipts of every block it settles; `header.GasUsed` becomes worst-case charged gas of the block's own body (statically checkable); per-tx gas charging floors at limit/2; and the base fee for execution comes from the deterministic gas clock, never `header.BaseFee`.
- A block is SAE iff its PARENT's timestamp >= HeliconTime-10s, cross-checked against the settlement markers, and disagreement is a HARD ERROR.
- The cchain hooks are forked into this repo because they are unexported upstream. The fork drops metrics, warp and shared-memory apply, and HARDENS the gas-target parse fallback into a hard stop, because it changes the base fee. No chain-config duality is needed (the SAE params package is constants only) and the ceil(limit/2) charged-gas floor rides coreth's own rules for free.
- The gas clock and our per-height post-execution roots persist in a ring of 8192 crc'd slots fsynced with the exec head. It holds EVERY SAE height, because settlement skips most of them, and crash walk-back matches OUR OWN roots, not header roots. The ring is the EXECUTOR's copy, not the only copy: a reader reconstructs the same clock from headers and stored receipts (see the base fee above), but the executor already holds it from execution and would otherwise be reading back records of a block it is still executing.
- VERIFIER: per block, GasUsed == sum(tx limits) + op gas; per settling header, `ring[SettledHeight] == header.Root` plus the markers' gas clock must equal ours; monotonic markers; hard stop, no bisect, since there is one Firewood proposal per SAE block. HONEST WEAKENING, recorded: a frame reaches disk at most one settlement lag (1-5 blocks, mean 2.6) before its root is attested.
- SUBNET-EVM NEUTRALIZATION IS STRUCTURAL, not a runtime flag: the subnet-evm backend reports the transition as never scheduled and its headers as carrying no settlement markers (both true at the pinned version), so the SAE code is unreachable on that path without a single kind check inside any of it.
- WHY OUR OWN JOIN PATH EXISTS AT ALL: upstream has NO C-chain state sync under SAE and will not soon. The sync file is a stub, the SAE VM registers exactly one p2p handler, every AppRequest routes to the SAE VM after activation so coreth's legacy sync server stops existing on that chain, and the Firewood-proof handler ID is RESERVED with zero implementations. Measured on a live post-activation network: 24,881 leaf requests, 100% AppError, ZERO accounts in 4 minutes, while the same binary on a pre-activation network got 5.5M accounts in the same minute. So a downloadable frontier is not an optimization, it is the only way in.
- THE POST-HELICON BASE FEE IS DERIVED FROM EPOCH CONTENT, WITH NO STORED STATE AND NO FORMAT CHANGE. A stored post-Helicon header carries NO base fee: the SAE builder constructs its header BEFORE execution and `saexec` writes the executed fee onto a COPY it takes for the run. Read straight off the header, every fee above the boundary is zero, which is a confidently wrong number on `eth_baseFee`, on each per-block `baseFeePerGas` in `eth_feeHistory`, on `eth_getBlockBy*`, on `eth_maxPriorityFeePerGas`, and on the `effectiveGasPrice` derived onto every receipt and transaction. IT DOES NOT HAVE TO BE STORED, because the fee is a DETERMINISTIC GAS CLOCK whose every input is already in the corpus: consensus republishes the clock at settlement points through the four markers EVERY post-Helicon header carries, so header N alone yields the clock as of the height N settles (1 to 5 blocks back), and between settlement points the clock advances only by block time and by the gas each block's execution consumed. So the read path takes the settlement point at the bottom of the range and replays upstream `gastime`'s own BeforeBlock/AfterBlock forward, which is `saexec.Execute`'s order exactly. THE ONE INPUT THAT IS NOT A HEADER FIELD is that consumed gas, because under SAE `header.GasUsed` is the WORST CASE: the real per-transaction gas is the stored receipt-fields section, and the end-of-block op gas is recovered by SUBTRACTION from the worst-case identity the executor verifies on every SAE block, `GasUsed == sum(tx limits) + op gas`, which is why the read server needs no atomic-transaction parse and no AVAX asset ID. It lives behind the `rpcVM` seam (`baseFees` for a range, `baseFeeOf` for one header), because reading coreth header extras on a subnet-evm process is a panic, not a wrong answer, and subnet-evm headers can never carry markers anyway. A range asks in ONE walk, so it costs the range plus the settlement lag rather than the range times it. Re-execution (`debug_getRawReceipts`, `eth_feeHistory` reward percentiles) substitutes the derived fee onto its header copy exactly as `saexec` does, or a dynamic-fee sender is charged its whole fee cap. Verified against Fuji's public C-chain RPC at nine post-boundary heights including the first SAE block, and the clock walk reproduces the later headers' own markers bit for bit.
- RISK: SAE Go APIs are explicitly unstable, so pin exact release tags.

FETCH ON A NON-PRIMARY SUBNET (ACP-77), every piece load-bearing: TrackedSubnets is the L1's subnetID and NEVER the primary ID (avalanchego returns errTrackingPrimaryNetwork); the subnet's validators go into the validators manager AFTER the network is constructed, which is what makes it pull their signed IPs out of ordinary PeerList gossip and dial them; a public node's `info.peers` stays the gossip entry point, and ZERO of those peers matching the subnet is the normal case, not an error; the peer pool holds the subnet's validators, because no one else can answer for the chain; every request keys on the subnetID; and the dial budget is 90s rather than 30s, because an L1's validators connect 10-15s after the primary peers do.
- THE 95% CROSS-CHECK IS SUBNET-AWARE, and this is a correction rather than a knob: ACP-77 weights are the STATIC registration weights, and the continuous fee drains a separate balance field that never moves `weight`. So an L1 has no delegation churn for the 5% band to absorb, and the band is mis-calibrated anyway, since one large validator can be 38% of total weight, so one registration can blow past 5% while a large validator vanishing cannot be told from a lying source. A non-primary subnet requires EXACT agreement between sources; the primary network keeps 95%.
- THE SYNC ENTRY: avalanchego ships checkpoints for the primary network only, so for a non-primary subnet the accepted frontier IS the anchor. The walk terminator is "height 1" for every chain: no chain serves genesis over GetAncestors and block 1's parent IS genesis, so this is exact on the C-chain and is the only terminator available on an L1, whose genesis is not in avalanchego at all.
- THE BOOTSTRAP ANCHOR TALLY COUNTS SAMPLE DRAWS, NOT DISTINCT NODES. Validator sampling is a WEIGHTED sample WITH REPLACEMENT of K draws, so on a small stake-skewed L1 the draws collapse onto a handful of nodes (25 validators with 5 holding 78.5% of the weight give a mean 8.7 DISTINCT nodes out of a K=20 sample, and P(>=15 distinct) = 1e-4). Tallying one vote per node therefore sits in the anchor phase forever while chits arrive. Each chit is credited with that node's DRAW COUNT, which is what every live poll already does. The primary network hid this: ~600 near-uniform validators make 20 draws ~20 distinct nodes, so the two tallies coincide there.
- Also settled by the scoping: a subnet-evm chain's historical re-execution needs no validator set and no P-chain height (warp predicate results are read out of `header.Extra` rather than verified in the tx), and epochdb never calls `engine.Finalize`, so none of subnet-evm's fee-window or state-dependent FeeConfig machinery is on the execution path.

## Sizing inputs

The numbers the design is sized against. Anything not load-bearing for a decision lives in the devlogs.

- MAINNET SCALE (authoritative over any earlier estimate). Basis: a baseline census of 90,588,836 accounts plus ~800M storage slots live at mainnet block 90.5M, an i7ie storage report's 175GB of flat state history, and the row format in ava-labs/avalanchego#5624. Derived: ~0.95-1.1B DISTINCT state keys ever written; ~1.6-1.8B total writes; ~1.5-1.7 writes per key over the life of the chain.
- BLOOM RESIDENCY: all mainnet epoch blooms together are ~1.5-1.8GB at 10 bits per DISTINCT key per epoch, 3.30GB at the ruled 20 bits. Distinct, not per write: the bloom covers distinct keys, because the SST writer appends a key only when its value changes.
- RESIDENT INDEX BUDGET at mainnet: ~7.7GB total (see the read path).
- TAIL DENSITY: the unsealed tail costs ~1.8GB per million txs (128GB of ancillary families for 70M txs measured); the sealed form is ~4.5x denser. At the 8M ceiling the raw tail is bounded at ~14.5GB.
- SEALED SIZES: 409-592 B/tx by era (dense eras cheaper per tx); stored logs add +18.5%, receipt fields +1.2%; whole-epoch compression 3.1-4.2x; full mainnet (1.2B txs) projects to 0.59-0.69TB.
- STATE VS TRIE SPLIT at 10M blocks: live state = 1.79M accounts + 41.5M slots = 0.63GB of values, 2.82GB of keys+values; Firewood 20.7GB, i.e. 86.4% merkle overhead. Light-verify (no Firewood) would save ~140GB at full mainnet, and the frontier rebuilds from SSTs in minutes.
- FULL-MAINNET BUDGET: local = Firewood 130-157GB + ~14.5GB unsealed tail + ~7.7GB warm indexes + whatever chunk cache is configured; bucket = ~500-690GB of epoch history.
- SEAL PEAK: ~1084 bytes per block, independent of epoch tx count. Opening a bucket log read-only costs ~182 B/block on top, which every process that opens the store pays.
- FLEET ANON AT 22 CHAINS on the 61.78GiB box, the input the fleet budget is sized against, per chain: Firewood's cgo node cache and the exec state cache, an eighth of the container ceiling EACH (so 384MB each at 3g, and 4.25GiB of node cache in the 34g mainnet-c container), the unsealed tail's per-block index at ~182 B/block (~1.2GB for a sparse L1 sitting at the 8M-tx epoch ceiling, and small L1s are NOT free in this term), the epoch blooms on the Go heap (20 bits per distinct key plus 2.00 B/tx, so a few GB for a big published corpus and noise for a young L1), plus the tail overlay during catch-up and a Go runtime baseline. Sum ~30-35GiB, which is why the fleet's target is 44G and not 55G. THE ONE EVENT THAT DWARFS ALL OF IT is a frontier build, 21.54GiB peak on a six-epoch corpus, which is gated to one at a time per box rather than budgeted.
- COOK WRITE AMPLIFICATION, accepted (user 2026-07-31: "that's fine"): the 60s cook rewrites the CURRENT bucket's sorted file wholesale, which at C-chain tip pace is ~100-150GB/day of SSD writes, a decade inside a 2TB NVMe's endurance, and a few MB/day for a small L1. The fix if a measured reason ever appears is append-sorted deltas merged at read, LSM-style; deliberately unbuilt.

## The fleet memory budget [DONE]

A BOX HAS ONE MEMORY BUDGET AND IT IS NOT THE SUM OF THE CONTAINERS' (ruling 2026-08-05, forced by two outages of the Tokyo box in one day). The first was one process: a frontier build inherited the serving Firewood profile and was global-OOM-killed at 63.9GB of anon on a 61GB box, fixed in code by the build's own profile. The second was the SUM: 22 chains, load 8.14, every container under its own `mem_limit`, zero container OOM kills, and the box still starved to the point where sshd accepted TCP and could not send a banner. A per-container ceiling bounds a member and says nothing about the fleet; deliberately oversubscribed ceilings (~130GB of them on 61GB) are the right call for isolation and are not a budget. THE OPERATIONAL REQUIREMENT is not "no chain dies", it is SSHD ALWAYS RUNS: the operator must be able to get in and stop things.

THREE PARTS, one per level, and no memory-accounting system anywhere (the ANON BUDGET rule already forbids a dynamic control loop, and a budget nobody can set correctly is worse than none):

- THE BOX: a systemd slice (`ops/epochdb.slice`, applied by the operator, referenced by docker's `cgroup-parent` so no future container can be forgotten) holds every chain container. `MemoryHigh` is the fleet's working-set target and is the whole mechanism: past it the kernel reclaims the SLICE's own clean file pages, the chunk cache and epoch mappings first, and throttles the slice's allocations, so the fleet DEGRADES BY SLOWING DOWN. `MemoryMax` is the backstop and its value is whose failure it is: one container dies inside the slice instead of the box entering global reclaim. Everything outside the slice, sshd included, is never squeezed by the fleet. Sized off the box and not off the chain count: high ~= 70% of RAM, max ~= 85%, which on the 61.78GiB box is 44G and 52G. `CPUWeight=50` is the same requirement against the other resource, and binds only under contention.
- THE BIGGEST EVENT: a frontier build is the one memory event sized by CORPUS rather than by tip pace (measured 21.54GiB peak on a six-epoch Fuji corpus even with the build's 2-revision profile), so N of them at once is N times that whatever the ceilings say, and a stop/start that wipes the instance store makes every chain join at once. A CROSS-PROCESS QUEUE, not a budget: `flock` on one of `EPOCHDB_HEAVY_SLOTS` slot files (default 1) in the shared chunk-cache dir, which is the one directory a fleet already agrees on. The kernel drops the lock when a process dies, so a killed build frees its slot with no cleanup path to get wrong; a waiting chain has already bound its RPC port, so its requests wait in the accept backlog exactly as they do during the build itself. A box whose chains do not share a cache dir gets a per-dir gate that never blocks, which is correct there.
- THE MEMBER: a chain process derives its own grants from the ONE ceiling the operator already wrote, its container's `memory.max`. GOMEMLIMIT becomes 7/10 of it, so a Go heap approaching the ceiling collects harder instead of being cgroup-killed, and 7/10 because a third of the container is invisible to the Go runtime (Firewood's decoded-node cache is cgo, and the mappings and zstd state are outside the heap, which is exactly what bit the first outage). The exec state cache takes 1/8 of it, and SO DOES FIREWOOD'S NODE CACHE (ruling 2026-08-06), for the same reason either stopped being a constant: a per-chain grant written as a number is multiplied by the chain count, and 1GiB per chain is 22GiB of the box. Two eighths plus seven tenths is 82.5% declared, and the residue is what covers the terms nobody sizes. An explicit GOMEMLIMIT wins, `EPOCHDB_FIREWOOD_CACHE` wins over the node cache's eighth, and an unknown ceiling (no cgroup, "max") leaves every default alone.

WHAT THE OPERATOR WATCHES, and it is four files and one command: `memory.current` against `memory.high` for the fleet total, `memory.events` where a rising `high` means the budget is holding and any `oom_kill` means it is too tight for what is running, `memory.pressure`'s `some avg60` for the throttle band, and `free -g` whose `available` is the sshd reserve and must never approach zero. In the logs, `heavy gate:` lines say which chains are queued behind a build, and each process prints its derived GOMEMLIMIT and state-cache size at start.

## Operations [DONE]

- BUILD/RUN: `go run ./cmd/epochdb serve`, and for an operator that is the whole list: `serve [--data <dir>] [--network mainnet] [--chain C|<blockchainID>] [--port] [--vdr-sources ...] [--verify] [--tip-override <containerID>] [--node --state-cache --cook-every --per-peer --sync-every --walks --pprof]`, following by default, ONE CHAIN PER PROCESS. `EPOCHDB_CACHE_DIR` is what several of them share on a box, and containers sharing it must run as the same uid.
- ALWAYS PASS `--network mainnet`: the default is fuji and the chain-id mismatch fails late.
- A NEW NODE: export the `EPOCHDB_S3_*` variables for the publisher's bucket (or a mirror) and run `epochdb serve --data <dir> --network mainnet`. The empty dir reads `latest`, walks the hash chain, writes the local index, merges every epoch's SST section into a Firewood frontier at the last sealed block, parks the exec head there and starts executing at H+1. Add `--verify` to re-verify every sealed epoch first, which downloads everything and refuses to start on a mismatch. With no credentials the same command works entirely off the local spool.
- PUBLISHING: seal drops epochs into `<data>/cas` and advances `latest`; the `--sync-every` ticker uploads and releases them. Nothing else talks to S3, and epochs are immutable, so nothing in the bucket is ever superseded.
- OUR OWN STAGES, hidden but alive, for gates and experiments only: `go run ./cmd/epochdb dev <stage>` where stage is fetch, exec, cook-index, cook-txindex, seal, publish, bootstrap (`[--frontier] [--verify]`), verify, verify-logs, backfill-logs, ab-bench, ab-bench-tx, ab-bench-rpc, ab-bench-logs, rpc-bench. A top-level invocation of any retired name prints a pointer to `serve` and exits 2.
- OWNERSHIP: `serve` OWNS every data dir it touches (state writer plus Firewood), so nothing else may write there and no `dev` stage may run beside it. Writers truncate torn tails on open, so NEVER open a live writer's dir with the writing opener; the read-only openers exist for cohabitation.
- MEMORY, A FLEET BOX: see The fleet memory budget, whose short form is one slice with `MemoryHigh`, `EPOCHDB_HEAVY_SLOTS=1`, and every other number derived from each container's own `mem_limit`.
- MEMORY, ONE HEAVY REPLAY: replay wants `GOMEMLIMIT=10GiB --state-cache 3 --commit-every 1000` on a 25GB box, because the 6GiB default state cache thrashes in dense eras. Two heavy execs on one small box cost the incumbent ~50% and renice/ionice recover nothing (memory and IO contention, not CPU), so one heavy exec at a time on a small box.
- Long stages MUST be setsid-detached: harness background tasks get reaped, learned twice.
- `du` lies on WSL2 and page-cache-heavy dirs; footers and artifact hashes are truth.
- PACKAGING: per-commit images ARE the release channel (user ruling 2026-08-01; tagged releases never get cut). Every push to main runs `go vet` plus `go test ./...`, then builds the root Dockerfile and pushes `ghcr.io/containerman17/epochdb` as `latest` and `sha-<shortsha>`; there is no Docker Hub. cgo is mandatory (firewood ships a prebuilt glibc static lib), so the runtime layer is `distroless/cc-debian13`, matching the golang:1.26 builder's Debian 13: `distroless/static` cannot link it and `distroless/base` is missing `libgcc_s.so.1`. THE IMAGE ALSO CARRIES THE PINNED zstd CLI, built statically in the builder stage from the checksummed v1.5.7 release tarball and copied to `/usr/local/bin/zstd`, because the sealer shells out to it for every epoch dictionary and distroless has no package manager to add it later. THE VERSION IS WRITTEN IN ONE PLACE ONLY: the Dockerfile seds it out of `state/epoch.go`'s `ZstdPinnedVersion` rather than repeating it, so the image and the binary cannot drift into a container that refuses to start. Bumping the pin therefore needs a new `ZSTD_SHA256` build arg too, and a stale checksum fails the build instead of shipping.
- NEVER MINT CLOUD CREDENTIALS FOR A TEST. Any real-AWS run MUST REUSE credentials that already exist: creating an IAM user, key, role or policy for a test is forbidden, it tripped corporate security monitoring.
- MAINNET ON THE FINAL FORMAT, published from scratch: **IN PROGRESS**, hard-gated behind Fuji past SAE.

- GUARANTEE: epoch bodies store VERBATIM proposervm-wrapped containers. Never switch to extras-reconstruction without an atomic-fidelity plan.
- STILL UNEXERCISED on the S3 path: R2 with the default credential chain, throttling, and cold ranged-GET latency at scale.
- Old local corpora predate the current format and are unopenable by design, so the corpus-backed rpc tests fail with the format refusal until a current corpus exists. Expected, not a regression.
