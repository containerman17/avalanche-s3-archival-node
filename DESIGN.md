## Principles and standing rules [DONE]

- BODIES + HEADERS + PROPOSERVM EXTRAS ARE THE ONLY GROUND TRUTH. Re-execution rebuilds everything else. We STORE logs and receipts rather than re-derive them (user ruling 2026-07-20).
- TRACES ARE STORED, AND CAPTURE FAILURE IS DEATH (user ruling 2026-08-12, reinstating frames the same day they were cut, after the saexec assessment was corrected: its hardcoded `vm.Config{}` is a not-wired-yet simplification, not an architectural switch, and the passthrough is a small upstream PR). Capture at execution is measured FREE on wall clock; in storage v0 frames are one more STREAMED chain-section family, no groups, no index sections, no sort. THE FAIL-STOP IS THE DESIGN, WRITTEN IN ADVANCE (user, verbatim: "We can just die... we're going to reach the Fuji C-chain block at a certain height, and we're going to die. And this is okay."): a block whose trace cannot be captured KILLS THE PROCESS immediately, and the error message names the block, the transaction, THE CONDITION IT ACTUALLY OBSERVED and this section, so the death at Fuji C-chain's Helicon activation height surprises nobody. THE MESSAGE MUST NEVER ASSERT A CAUSE IT DID NOT CHECK: it named the saexec seam unconditionally until 2026-08-14, when the unbalanced enter/exit guard fired on mainnet C block 5,456,905, a chain that cannot take the SAE path in this dep set, and the wrong cause cost a full step of the diagnosis. L1s and pre-Helicon capture fine today; the upstream seam PR unblocks the rest. Frames can never be backfilled by IO, which is exactly why they are captured from day one. THE DOUBLE-ANNOUNCEMENT IS FIXED UPSTREAM AND OUR WORKAROUND IS DELETED (2026-08-15): libevm's precompile environment used to fire CaptureEnter for a call, hand the same call to `evm.Call` which fired CaptureEnter again, and close its own announcement with CaptureEnd rather than CaptureExit, which halted mainnet C at block 5,456,905 on coreth's NativeAssetCall. libevm PR #303 (`db6d70f2748e`, merged 2026-08-03 by an independent contributor whose reproduction names the same block and transaction) lets `evm.Call` emit the balanced pair, so `exec/frames.go` no longer folds anything and the guard fires for every unpaired shape without exception. Proven in production: the deployed binary re-executed that exact transaction through the precompile environment and returned a balanced tree with one announcement per call at every depth. NOTE the shape is RARE, not routine: mainnet C holds exactly two such transactions, at blocks 5,456,905 and 16,159,611, and all occurrences are top-level calls.
- STORED TRACES ARE UNVERIFIED DATA AND MUST BE TREATED AS SUCH (user ruling 2026-08-15). No consensus hash commits to trace content: bodies, receipts, logs and state all recompute against roots the chain itself signed, but frames recompute against nothing, so a reader TRUSTS them rather than verifies them. This is not theoretical, it is measured: a libevm double-announcement produced broken frame stacks for eleven days and no root ever objected. CONSEQUENCES, binding. (1) NEVER USE TRACE DATA WHERE BEING WRONG COSTS MONEY, wallet balances above all: balances and transfers come from state and from logs, which are verified; frames are for exploration, search and debugging. (2) A CALLER WHO NEEDS A TRUSTWORTHY TRACE MUST BE ABLE TO ASK FOR A FRESH ONE: every trace-serving method takes an option to RECOMPUTE by re-executing the transaction against verified state at its height instead of reading the stored frames, which costs milliseconds and is the honest answer when correctness matters more than latency. The stored frames stay the default because whole-history scans are what they exist for. (3) Frames remain captured always and capture failure remains death (below); an unverifiable record is still worth far more complete than partial.
- ALL DATA MUST ALWAYS BE SAFE (user ruling 2026-08-09). Nothing that exists is deleted or overwritten until its replacement is written, fsynced and verified. Derived state that cannot be built consistently refuses queries loudly; it never serves a hole.
- VERIFICATION IS THE ACCEPTANCE TEST, NOT BYTE-IDENTITY (user ruling 2026-08-15, verbatim: "it's not about reproducibility, it's about verification, and if verify doesn't produce any errors, I don't think we have a problem, even if bytes would differ"). A corpus that passes layer 1 is correct, whoever built it and at whatever dependency version. THE REASON THIS IS SAFE is that execution cannot diverge silently: the executor checks the state root against the header on EVERY block and hard-stops, and verify independently recomputes txRoot, receiptsRoot and logsBloom from stored bytes, so a semantic change dies loudly at the first affected block instead of producing a subtly wrong corpus. THE ONE SURFACE CONSENSUS HASHES DO NOT COVER IS CALL FRAMES: no hash commits to trace content, which is exactly why a libevm double-announcement bug produced broken frame stacks for eleven days without any root objecting, so frames are compared as evidence when a dependency changes, never assumed.
- BYTE-IDENTITY WITHIN A VERSION IS STILL FREE AND STILL DOES WORK. Every artifact is a pure function of chain content at a pinned dependency set, which is what lets a consumer recompute a merged run locally and check its hash instead of downloading it, and it rejects adaptive boundaries, configured thresholds, randomized construction and embedded signatures, everywhere and forever. It is NOT a gate ACROSS version boundaries. AI-NATIVE COROLLARY (user, 2026-08-12: "no human will ever read the code"): reproducibility is the debugging story; within a version, "corrupt or correct" collapses to recompute-and-diff, which an agent can run unattended.
- NO DATABASE ANYWHERE. The hot window is RAM maps; everything durable is immutable SSTable runs plus the append-only window log. Pebble is linked as a LIBRARY for its sstable reader/writer and block cache; no live key-value store runs anywhere.
- FIREWOOD IS VERIFY-ONLY WITH ZERO READERS (user ruling 2026-07-29: "Firewood is just a dumb hash verifying machine"). No read path touches it. `eth_getProof` and state-range debug methods stay deleted.
- ONE CHAIN PER PROCESS (user ruling 2026-08-04). One node type, no personas (2026-07-30): local disk decides only how FAST cold history answers, never WHAT a node can answer.
- NO EXTRA VALIDATION OF ALREADY-VALIDATED DATA (user ruling 2026-07-29).
- AGENT POLICY (user ruling 2026-07-29): subagents on this project run OPUS, pinned per dispatch, never fable.

## Chain identity [DONE]

A CHAIN IS NAMED BY ITS BLOCKCHAIN ID (user ruling 2026-07-31): `--chain C|<blockchainID>` beside `--network fuji|mainnet`. Everything a descriptor carried is ON-CHAIN: the blockchainID is its CreateChainTx txID, one `platform.getTx` returns `genesisData` and `subnetID`. `C` is coreth; everything else is subnet-evm. The data dir's vmkind stamp refuses the other kind forever. First resolution of a blockchainID caches to `<data>/chain.json`; the cache wins over the network flag, and a cache naming another chain is refused. THE DEFAULT `--chain C` IS CORETH AND NEVER READS THE CACHE, so every command against an L1 data dir names its blockchainID.

THE CHAIN ROOT IS THE TRUST ANCHOR: `root = sha256(genesisData)`, the P-chain bytes VERBATIM (user rulings 2026-07-31, 2026-08-05). UPGRADE BYTES ARE NOT IN IT: upgrades apply inside blocks, never to genesis, so a wrong upgrade.json diverges at its activation height and hard-stops; a corpus built with a wrong one cannot exist. upgrade.json is the ONE off-chain input: `<data>/upgrade.json`, read verbatim every start, never cached. The C-chain genesis bytes are byte-identical to avalanchego's embedded copy; a test pins both network hashes.

MULTI-CHAIN: one binary, one format, trust anchored per chain. Every operator runs their own publisher and bucket; a private chain inherits S3 access control natively.

## Storage v0: a deterministic LSM of SSTables [DONE]

THE WHOLE ENGINE IN FOUR RULES. (1) A RUN is one immutable file: a chain SST section, a state SST section, a lookup SST section, a footer with section offsets and the hash link. Runs are named by their TxNum range. (2) The MEMTABLE covers the unflushed window and serves it. (3) FLUSH every 500,000 txs or 50,000 blocks, whichever first, aligned to a block boundary (user ruling 2026-08-12). (4) ONE merge level: the L0 runs since the last terminal MERGE into one TERMINAL 8M-tx run at the tx boundary known in advance, and terminals never merge again (user ruling 2026-08-13; 8M is the measured practical floor: ~190 mainnet runs, probe and false-positive costs in the noise, terminal artifacts ~5-10GB). Everything below is elaboration.

BOTH TRIGGERS COUNT SLOTS, NOT TRANSACTIONS, since every block owns a boundary slot: a 500,000-slot run holds 500,000 minus its own block count in transactions, and the 8M terminal boundary likewise. At mainnet C's ~16 txs/block that is ~6% fewer transactions per run and per terminal, i.e. ~200 terminals over the chain instead of ~190, and nothing else moves: the boundaries stay a pure function of chain content, which is the only thing determinism asks. A sparse chain is unaffected in practice because it flushes on the block trigger anyway.

THE BOUNDARY IS 8M TRANSACTIONS AND THE FAN-IN IS WHAT THAT COMES TO: 8M / 500k = SIXTEEN L0 runs on a chain dense enough to flush by transactions, which is every chain that will ever earn a terminal (`MergeFanIn = TerminalTxs / FlushTxs`, derived, not configured). TxNum is the trigger rather than the run count because TxNum is THE dimension and because the two disagree exactly where it matters: a sparse chain flushes on the 50,000-BLOCK trigger instead, so numine's 1.07M txs make TWENTY L0 runs, and a count-triggered merge would cut it a tiny terminal out of a chain that has not earned one. The span is therefore every L0 since the last terminal (sixteen on a dense chain), which also keeps the terminals tiling the chain from TxNum 0 with no gap: that is what lets the published manifest list terminals ALONE and still walk back to the chain root.

THE BUCKET IS WRITE-ONCE AND FOREVER (user ruling 2026-08-13: "we write to S3 once and forever, no trash there, all data there is final"). ONLY TERMINAL RUNS UPLOAD. L0 runs and the window never leave the machine, so nothing in the bucket is ever superseded, and no delete, recycle, or garbage-collection concept exists in code or bucket. THE GATE IS A DIRECTORY AND NOT A POLICY: `dist.Sync` uploads the SPOOL, an L0 run is adopted into `<data>/runs` instead, and reads try that directory first, so there is no flag anywhere that could be set wrong. A run carries its level and tx range in its name everywhere a name is a string: `l0-<fromTx>-<toTx>-<hash>` for the local file, `run-t-<fromTx>-<toTx>.tmp` while a terminal is being built, and both fields per run in the manifest. A bucket object's key stays the bare hash, because casfs names an object by the hash its content commits to and that IS the integrity check; the manifest is where a bucket's contents are read by range and level. The published pointer advances once per terminal run and references only bucket-resident objects, so a bucket consumer always sees a complete final set while the local live manifest runs ahead of it. A chain that has not yet earned a terminal run publishes NOTHING (no pointer, no manifest object, an empty prefix) and is joined over p2p, which is minutes for anything that small (numine, 1.07M txs, full clean sync in 8m38s); a mainnet joiner lands at the last 8M boundary and re-executes at most ~1.7h, against ~18h for a status-quo pruned state-synced node, and arrives with a full archive. **DONE**, proven by test: two builders produce byte-identical terminals under identical names, the gate never uploads an L0 (locally and over the MinIO wire), the published manifest never names an absent object, a consumer joins cleanly while the producer is ahead, a corpus under the boundary publishes nothing, and no code anywhere can send a bucket a DELETE.

THE ONE DIMENSION IS TxNum (Erigon's pattern, adopted 2026-08-12): a global monotone transaction number. The logical clock (flush and merge triggers), the run names, the keys and the indexes are all the same integer. A run named [from, to) covers exactly the slots from..to-1, so the manifest range check alone routes a lookup with no bloom and no search.

EVERY BLOCK OWNS A BOUNDARY SLOT, which is the rest of Erigon's pattern and was deferred until a defect forced it (user ruling 2026-08-14). A block whose `blk/` row says (first, count) occupies the slots **[first, first+count]**: its transactions take first..first+count-1, and **first+count is its boundary slot**, which no transaction owns and which carries the state the block wrote OUTSIDE any transaction. The next block starts at first+count+1. Worked example: block 100 with 3 txs starts at 40 and takes 40,41,42 for its transactions and 43 for its boundary; block 101 has NO transactions, so it takes 44, which is its boundary and its only slot; block 102 also has none and takes 45; block 103 with 2 txs takes 46,47 and 48. WHY IT EXISTS, exactly: a block with zero transactions still changes state (on coreth an atomic import or export moves balances in a block that carries no EVM transaction), and without a slot of its own such a block wrote its rows at a TxNum the reader excluded, while the NEXT such block reused the same TxNum and replaced them. That corpus stored wrong historical state and no verification layer could see it; it is reachable on mainnet C, which is why the run was blocked on this. The cost is that the tx-keyed families (`tx/`, `rcpt/`, `itx/`) are dense PER BLOCK rather than over the whole run: every slot but the boundary ones has a row. Nothing routes on that density; the range check is what routes.

THE VERSION STAMP IS NOW 1 (the ENGINE is still called storage v0 in this document, as opposed to the epoch-era V1 corpora; the stamp inside a manifest and a run footer is a different number and it moved). It changed because the same TxNum names a different thing in an old artifact. There is NO migration, NO compatibility reader and NO conversion, per the standing clean-slate ruling: the stamp exists so the five already-published v0 prefixes are REFUSED BY NAME at open and at join instead of being read with the new semantics and quietly answering the wrong state. Every chain re-syncs, which was the plan for all of them anyway.

KEY SCHEMA, chain section (height/TxNum-ordered, arrives sorted, streams to disk during execution, big compression blocks, NO bloom: existence is answered by the run name before any file opens):
- `hdr/<height>` -> header RLP verbatim; `pvm/<height>` -> the proposervm wrapper bytes verbatim (a couple hundred bytes per block, and the difference between an archive and almost-an-archive); `blk/<height>` -> the block's first TxNum and its tx count, which together name its slots [first, first+count] and therefore its boundary slot.
- `tx/<txnum>` -> tx RLP verbatim; `rcpt/<txnum>` -> receipt + full logs, epoch encoding carried over. VALUE GRANULARITY RULE: the value of a row is the smallest unit ever served alone; a whole block is a contiguous key range, one sequential scan. NO CONTAINER DUPLICATION (user ruling 2026-08-12: "no data duplication, you can assemble it, it's pretty damn fast"): proposervm extras stored beside the header, containers reassembled on demand; stored bytes stay the exact consensus RLP so header hashes and tx roots recompute from what we store.
KEY SCHEMA, state section (keys sort by account/slot, not by txnum, so this section is sorted at flush like lookup, and it MERGES; prefix bloom at 20 bits/key excluding the txnum suffix):
- `itx/<txnum>` -> the tx's call frames in enter order with depth (kind, from, to/created, value, gas, gasUsed, input, output, error; the top-level frame is the tx itself and is excluded). Arrives in txnum order, streams like everything else in this section. Determinism notes carried from the V1 capture work: DELEGATECALL frames carry the parent's value (excluded by read-time transfer filters, never by capture); SELFDESTRUCT has no hook at this pin; frames follow execution exactly, so a config that would change them diverges the state root first.

- `state/<account>/<slot>/<txnum>` -> post-tx value, PER-TX granularity (user ruling 2026-08-12: downgrade to per-block is a pure lossy transform consumers can run themselves). A slot's key range IS its time series: one contiguous scan yields every value it ever had, including intra-block ticks, which is where DeFi opportunities live and die. Cleared storage is a ZERO-VALUE ROW at its txnum; the EVM defines cleared as zero, so no tombstone mechanism exists (user ruling 2026-08-12). Account rows and code rows (`'c'` rows, invariant kept from V1: whichever run answers an account read also carries its code) live in the same family. Keys stay UNHASHED `kind|addr|slot`: clustering per contract is what read-through caching feeds on (user, 2026-08-11: DeFi happens in ~8,000 contracts; the cache converges on their regions), and SST prefix compression makes the shared prefix nearly free.

KEY SCHEMA, lookup section (arrives unsorted, sorted in memory at flush inside the bounded window, small blocks, blooms):
- `txh/<txhash>` -> txnum and `blkh/<blockhash>` -> height. Whole-key bloom; a hash lives in exactly one run, so nearly every probe is a miss, the bloom's best case. The block-hash row is DERIVED, never carried in: a block hash is keccak256 of the header RLP, which is stored verbatim, so nothing in the executor knows this family exists.
- `addr/<address>/<txnum>` -> role bits (sender, recipient, created, log emitter, frame participant). Populated from execution outputs, no ECDSA recovery at flush (the EVM already recovered the sender).
- `topic/<value>/<txnum>` and `logaddr/<address>/<txnum>` -> posting rows for getLogs, tx-granular (the V1 block-granular lists measured 5.1x read amplification; TxNum granularity is the fix).
- Prefix blooms via Pebble's `Comparer.Split`: the TxNum suffix stays OUT of the bloom (the CockroachDB MVCC pattern), so "does this address/key exist in this run" answers regardless of position. BLOOM POLICY: only families whose queries can miss; hot topics waste their bits by always hitting, accepted, unknowable at write time.

COMPRESSION AND BLOCK SIZE ARE PER-SECTION FORMAT CONSTANTS, MEASURED THEN PINNED (user direction 2026-08-12). THE CODEC IS ZSTD AT LEVEL 9 IN ALL THREE SECTIONS. Block sizes: chain 128KB, state 32KB, lookup 8KB. EVERY SECTION IS A POINT-READ SECTION, chain included: `hdr/`, `blk/`, `tx/` and `rcpt/` are separate Gets landing in different blocks, there is no block cache by design, and one row read decompresses ONE WHOLE BLOCK, so each size is the smallest that still compresses well for that family. Chain takes the largest of the three because its rows are large and its scans long, and 128KB rather than 512KB because the bigger block costs 2.6x the latency of a warm `eth_getTransactionByHash`-shaped read (~173us against ~67us) and buys back only ~3% of corpus bytes; latency on a hot query shape wins. The index block is twice the data block and never below 64KB, because an index that outgrows one block turns into a two-level index and that is a property of the block size, not a free choice. Level 9 is where the size curve flattens; 19 buys a couple of percent for several times the write clock. CGO IS IN THE PINNED SET: pebble reaches zstd through `github.com/DataDog/zstd` under cgo and through `klauspost/compress/zstd` without it, the two write DIFFERENT BYTES from the same rows, and klauspost collapses levels onto four speed classes, so a `-tags pebblegozstd` build is refused at compile time. A custom profile must be based on `sstable.ZstdCompression` and never on the Good/Fast/Balanced presets: those put MinLZ in OtherBlocks, MinLZ needs a newer table format than we write, and pebble then SILENTLY replaces the whole profile with snappy. Three sections is the count because there are three tuning profiles, not a byte-layout limit: prefixes are free and more sections cost one footer entry each, and a family's own section buys nothing else, because an SST section is key-sorted and every family already occupies one contiguous range of blocks inside it.

DETERMINISM PINS: Pebble's `TableFormat` (Pebblev2), writer options, comparer, per-section profiles and cgo pinned exactly; nothing carries a wall clock (pebble writes a zero creation time, and the run footer holds no timestamp at all). ONE SSTABLE IMPLEMENTATION READS AND WRITES RUNS, `cockroachdb/pebble/v2`, and its version is pinned like a format constant. libevm's own ethdb wrapper still links pebble v1, which is a DIFFERENT MODULE PATH and never touches a run, so a pebble bump here is ours alone. Same sorted rows in = identical bytes out. Proven at unit level (the same blocks through the writer twice produce byte-identical run files and the same casfs name, and re-flushing the same staging range reproduces the same run) and on the corpus (two independent numine builds, 6 runs, byte-identical under identical casfs names). THE PINNED zstd CLI REQUIREMENT DIES WITH THE DICT TRAINING: block compression is the library's, pinned by module version.

MERGES ARE DETERMINISTIC AND OPTIONAL TO CONSUME: a merge is a pure function of its input runs, so a consumer holding the small runs computes the merged run locally, byte-identical, and checks the hash: compaction without re-download. Chain sections never merge above the flush level in spirit (their ranges never overlap; a merged run's chain section is pure concatenation); merging exists for the lookup and state families, whose keys overlap across runs. Mainnet settles around 190 terminal runs plus at most sixteen L0 runs live at any instant, instead of thousands.

THE SPAN IS THE NEWEST RUNS, AND THAT IS FORCED: a run's footer names the PREVIOUS run, so the live set is a prev-linked list, and replacing a span in the middle of a linked list orphans its successor. The newest span has no successor, so merging there keeps the list intact at every instant, which is exactly what the join walk reads. A merged run's prev is the run before the span, i.e. the previous terminal or the chain root, which keeps that too a pure function of chain content and makes the terminals a prev-linked list of their own: the one the published manifest lists. A MERGE THAT DID NOT FINISH RUNS BEFORE THE NEXT RUN IS CUT (fix 2026-08-14): the span is every L0 since the last terminal, so a crash between the boundary and the manifest swap would otherwise hand the retry a SEVENTEENTH run, and every terminal boundary after it would land at a different TxNum than another builder's. The retry is therefore the first thing a flush does. RUNS MUST ALSO TILE: a manifest whose runs overlap is refused at open, because the point read walks the runs newest-first and the sequential iterator walks them oldest-first, so an overlap is two readers disagreeing rather than a corpus that limps. RETIREMENT IS PUBLISH-BEFORE-DELETE: the merged run is written, fsynced, reopened and row-counted against what went in, then the manifest swaps, then and only then the inputs' copies are unlinked. They only ever existed locally, so that unlink is the whole story and there is nothing in any bucket to reconcile; a consumer that wants to recompute a merge re-executes the range rather than re-downloading inputs that were never published.

THE MANIFEST is the existing two-level casfs structure (user ruling 2026-08-12: "this is just a list of hashes... something we already implemented"): a run's name is sha256 of its chunk-hash list; the manifest lists live runs by tx range and name; each run's footer embeds the previous run's name and the first embeds the CHAIN ROOT. One head hash still authenticates all of history. The manifest is ITSELF a published artifact, and the chain's one mutable pointer names it, so a joiner reads one pointer and one small object to learn the whole live set. The pointer stays a hint, never an authority; S3 stays untrusted (the name commits to every 4MB range), and the joiner re-derives everything it matters about from the footers. The only thing taken on trust from the manifest is each run's merge LEVEL, which is scheduling bookkeeping and cannot move a byte of any run.

FETCH ASCENDS AND STAGING DOES NOT EXIST (user rulings 2026-08-13; this replaced the descending walk and the height-bucketed arrival segments wholesale). **DONE**, proven on numine and thegrotto. The forward-walk primitive is in the consensus protocol itself: PullQuery carries `RequestedHeight` and a peer's Chits answers with `GetBlockIDAtHeight(requestedHeight)` for any height below its last accepted (verified in avalanchego v1.15.0-fuji, snow/engine/snowman/engine.go), so a height resolves to a container ID without a checkpoint, an anchor or a walk. The fetcher resolves heights across validators, fetches containers, and VERIFIES FORWARD: every block's parent hash must equal the previous block's hash, anchored at the genesis block, so a lying peer is caught by the very next link and its span is discarded and re-asked elsewhere. THE WINDOW RULE is the entire flow control, one line, deliberately not a concept (the "simulated tip" framing was considered and rejected: only one tip exists anywhere): fetch target = min(real tip, executed + 100,000 blocks), refill when the gap ahead falls under 50,000. Fetched-not-executed containers live in a bounded RAM queue, never on disk: the durable copy of an unexecuted block is the network. DEPENDENCY, stated plainly: peers must serve deep history, which default avalanchego does (pruning drops state, never block bodies) and V1's own 43.6M-block mainnet fetch proved. THE CONSENSUS FOLLOWER OWNS THE REAL TIP ZONE UNCHANGED, and the handover needs no state of its own: the queue takes a container only if it is the next height AND its parent hash links, so every accepted container is offered to it and simply dropped while the window is still climbing through history, and taken the moment the window arrives under it. DELETED WITH DESCENT: the arrival-bucket format and fsync group, recovery scanning of staging, span/floor bookkeeping, the disk-unbounded staging directive, the ~0.6-0.7TB mainnet staging headroom (now ~160MB of RAM at numine's block size), the embedded-checkpoint seeding, and the O(chain) by-height and by-ID maps, whose bookkeeping is now O(window).

TWO AMENDMENTS FOUND WHILE BUILDING IT. (1) ONE POLL SEEDS A SPAN, NOT A BLOCK. Going forward, a container ID can only come from a poll, so a literal Get-per-height costs two round trips per block: ~2M messages on numine and ~184M on mainnet C, against the ~1,300 GetAncestors an ~800-container batch needs for the same history. The window is therefore cut into 4,096-block spans, ONE PullQuery resolves each span's top height, and the span's containers arrive in GetAncestors batches, which is the protocol's own bulk primitive and arrives newest-first. Nothing about that reaches the executor: the queue re-orders spans and DELIVERS STRICTLY ASCENDING, every batch is checked link by link as it is consumed (each container must be the one the previous one named), and every block still has to link at the queue. A PRUNED PEER IS DETECTED FOR FREE: its Chits fall back to its last accepted ID, and the container it serves says what height it is, so the candidate is dropped and the next one tried. (2) CRASH RECOVERY RESTARTS THE FETCH A WALK-BACK BUDGET BELOW THE STATE LAYER'S HEAD, not at the last flushed run boundary: a run is cut inside the executor's batch loop, BEFORE that batch's Firewood commit, so a crash can leave Firewood below the flushed floor, and the reconcile then wants containers below it. `exec.WalkBackBudget` is the one number both the reconcile and the fetch read (8,192 blocks at CommitEvery=64, i.e. seconds of re-fetching), and the re-fetched run is hash-anchored on the stored header of the block below it.

MEASURED ON NUMINE 2026-08-13, fresh dir, full clean p2p sync from genesis: 1,038,920 blocks / 1,069,181 txs, 8m38s from process start to tip (8m18s from the first block), verification layer 1 PASS over the whole chain. That is against a descent-era 12m fetch plus 7m20s execution run SEQUENTIALLY, and the overlap lands where the rule predicts: at the slower of the two, which is now execution. Peak RAM queue 157.9MB, i.e. the 100,000-block window at numine's ~1.5KB containers, ~34s of executor runway at the measured block rate. thegrotto (a second mainnet L1, 148,037 blocks / 231,131 txs) synced and passed layer 1 the same way, with a kill -9 mid-sync: the restart re-fetched forward from head-8,192 and resumed without touching anything below it.

THE UNFLUSHED WINDOW IS DURABLE (amendment 2026-08-12, found while building it): Firewood cannot be rolled back, so a restart that found the state layer 50,000 blocks behind Firewood could neither rewind Firewood to the flush boundary nor re-execute forward from it. The window therefore streams into one append-only log beside the runs, fsynced on the executor's own cadence and replayed back into RAM at open, cut at the last COMPLETE block. That is not a WAL in the redo sense (nothing replays it into a database; it IS the memtable's backing file) and it is what keeps the state layer at or ahead of Firewood, which is the invariant the reconcile walk-back has always needed. THE WALK-BACK RE-EXECUTES, IT NEVER RE-APPENDS: a block's chain rows are written EXACTLY ONCE, so `memtable.add` skips any block below the window's next height, and an EMPTY window's next height is the last sealed run's end rather than nothing at all. Guarding only a started window was a real defect, found by layer 1 in production (apertum, 2026-08-13): a crash whose state layer stopped exactly on a flush boundary left the window empty over an already-sealed run, the walk-back re-appended those blocks at fresh TxNums, and every tx row from the boundary onward was out of step with its blk row.

## The read path [DONE]

ONE DESCENT FOR EVERYTHING: memtable, then live runs newest-to-oldest, bloom-gated, first hit wins. State at block N seeks `state/<key>/` at the largest txnum at or below N's end (or below tx k for mid-block reads). The descent's bottom is what genesis MATERIALISED, not the alloc (subnet-evm activations included; `exec.Genesis` carries `TrieAlloc`). Code by hash: THE CODE CACHE, then memtable, then bloom-gated `'c'` rows, then genesis: ONE function, all callers.

THE CONTRACT-CODE CACHE IS THE SECOND TIER IN FRONT OF THE DESCENT, AND IT NEEDS NO CONSISTENCY MACHINERY AT ALL (user ruling 2026-08-13: contract code is a cache candidate and may be a bit slower than the flat state cache, being roughly 20x less used). BYTECODE IS IMMUTABLE BY HASH, so unlike state there is no height to carry, no fill to race and nothing to invalidate: one hash names one blob at every height forever. It is therefore a plain bounded LRU keyed by code hash, checked before the descent in `DB.Code` and filled from a run hit, so `eth_call` at the tip stops paying a descent plus a 32KB zstd decode per contract it touches, and a proxy call stops paying it twice. Only a run hit fills it: a window hit is already RAM. THE BUDGET is `EPOCHDB_CODE_CACHE` bytes, defaulting to A TENTH of the flat cache's budget, because code is the far smaller working set (a contract's blob, not its whole state region) and is spent out of the same heap grant, not a new claim on the box.

THE JUMPDEST BITMAP IS THE SAME CACHE ONE LAYER UP, AND IT IS BLOCKED ON A LIBEVM SEAM (measured 2026-08-17). A jump-analysis bitmap is A PURE FUNCTION OF BYTECODE, so by the rule above it caches exactly like code does: keyed by code hash, no height, no fill to race, nothing to invalidate. libevm builds it in the `Contract` object and shares it only inside ONE top-level call, so the next transaction touching the same contract builds it again, and a historical replay that hits the same few thousand DeFi contracts millions of times pays for it every time. The mainnet C rebuild's CPU profile puts `opJumpi -> validJumpdest -> isCode -> codeBitmap` at 7.2% of process CPU and about 24% of EVM compute, roughly 70us per transaction; measured here on the twelve most-called mainnet C contracts (mean 12.0KB of code) ONE analysis is 19.0us against 0.39us for a cache hit, so the profile is naming about four contract loads per transaction, which is what a router plus a pair plus two tokens costs.

THERE IS NO SEAM TO FILL IT FROM HERE, AND THAT IS THE FINDING, NOT THE CACHE. `Contract.jumpdests` is unexported and `NewContract` is called by coreth's and subnet-evm's own `state_transition.go` with a `vm.AccountRef`, so nothing this repo constructs is on the path; `vm.Hooks` is at-most-once and both graft VMs already claim it inside their `RegisterExtras`; and a `vm.Config` field would not reach the C-chain replay that pays the cost anyway, because `saexec.Execute` hardcodes `vm.Config{}`, WHICH IS THE SAME HOLE the tracer passthrough already owes upstream. THE FIX IS UPSTREAM AND IT IS SMALL: a `vm.JumpDestCache` interface plus a process-wide `vm.RegisterJumpDestCache` in libevm's own `register.AtMostOnce` idiom, consulted in `Contract.isCode` before the analysis runs and offered the result after, nil and inert for everyone who registers nothing. go-ethereum's own line already carries the same idea as `EVM.SetJumpDestCache`, so this is a backport to the v1.13.15 fork rather than a new idea, and process-wide rather than per-EVM is what saexec forces and what the content addressing allows, since a code hash means the same bitmap on every chain in the process. OUR HALF IS THE CODE CACHE'S TWIN: `EPOCHDB_JUMPDEST_CACHE` bytes, defaulting to AN EIGHTH of the code cache's budget because libevm's bitmap is `len(code)/8+5` bytes, so an eighth holds the analyses of the contracts the code cache holds the code of. CORRECTNESS IS THE WHOLE GATE, because a wrong bitmap makes an invalid jump look valid and diverges a state root: the test is BYTE-IDENTITY of a served analysis against a freshly computed one, plus unchanged output, gas and error, over every code blob in a corpus and over PUSH data holding `0x5b`, a truncated PUSH at the end of code, empty code, code at the 24576-byte limit and one byte past it. THE FLAT LATEST-STATE CACHE IS IN FRONT OF THE DESCENT AT THE HEAD, AND ONLY AT THE HEAD (user ruling 2026-08-13: "the flat state, the latest cache, should be part of the design, 100%"). It is the in-memory current state DESIGN's fast path always named: account/slot -> the latest stored row, a Go map maintained by the executor as blocks land, serving `CallAt` at the tip and `eth_call latest` without touching the memtable, any SST or the descent. A miss falls through to the normal path and populates it, so it warms with no special path and a read-only corpus warms it exactly as a live node does. EXACT CONSISTENCY WITH THE HEAD IS TWO RULES AND NOTHING ELSE. (1) The cache carries THE HEIGHT IT IS THE LATEST STATE OF, moved by exactly one thing: applying a block's own state rows under the cache's write lock inside `WriteBlock`, the same critical path that publishes the block; a read is served only when the height it asks for is the height the cache holds, checked under the same lock as the lookup, so a block landing mid-read cannot hand a reader another block's value, and a read at any historical height never touches it in either direction. (2) A fill from a miss is accepted only if the height has not moved since the descent read that produced it, and a block that is not the cache's height plus one (a walk-back replay, a gap) DROPS THE CACHE WHOLE rather than arguing: where consistency cannot be argued cheaply at a boundary, the cache refuses that boundary and falls through. A DROPPED ENTRY IS ONLY A CACHE MISS, because the descent underneath is always the truth, which is what makes the byte budget safe to enforce bluntly. THE BUDGET is `EPOCHDB_FLAT_CACHE` bytes, defaulting to an eighth of the container's own `memory.max` (the same eighth the exec state cache and the Firewood node cache take, one arithmetic for every anon grant) and to 1GB where no ceiling is written down; it is a Go map, so it is spent out of the heap GOMEMLIMIT already reserved rather than being a fourth claim on the box. Eviction is two generations, hot in front of cold, rotating when hot fills half the budget: a Go map has no eviction and keeping an LRU list costs a per-entry write on the READ path, which is the lock this whole round removed.

READS DO NOT TAKE A WRITE LOCK ANYWHERE, and that is what made the fast path scale. The window log is append-only, so every byte range at or below its flushed watermark is immutable and a pread against it is safe while the executor keeps appending; the memtable therefore serves chain rows under the READ lock, and the write buffer is flushed ON THE WRITE SIDE at every block boundary (one `write(2)`, no fsync) so a landed block is readable that way the instant it lands. Only a row still sitting in the buffer falls back to the write lock. Above that, `txCeiling` (the height -> TxNum conversion every account and slot read starts with) is memoized in one slot and needs no invalidation, because a block's tx range is immutable once the block has landed: the whole tip workload collapses to one atomic load instead of a `blk/` row read per state read.

READ-THROUGH IS THE MAIN INSTRUMENT (user ruling 2026-08-11: the target machine cannot hold 700GB, "that is practically impossible financially right now"). A node declares a local budget; blooms, SST index blocks and the manifest are ALWAYS RESIDENT LOCALLY (a few GB at mainnet), data blocks read through the windowed chunk cache from S3. A cold state read costs local bloom probes plus exactly ONE remote GET; the second touch is free. Contract clustering makes the cache converge on the operator's actual working set with zero configuration.

RESIDENCY IS AN EXPLICIT OVERLAY, not a cache policy: at open, a run reads its filter, index, top-index, properties and metaindex blocks into a per-section overlay that serves those byte ranges from RAM forever after, so pebble's own reads of them never reach the artifact. A block cache would have made residency probabilistic, and one evicted index block turns every cold read into two GETs.

getLogs: intersect `topic/` and `logaddr/` posting rows, tx-granular, read the named `rcpt/` rows, exact-filter. The memtable serves the unflushed window, so sealed-plus-tail is seamless by construction, not by a special index. Aggregate and time-dimension queries are out of scope for the node; serious analytics is an external system fed by exports, said plainly (ruling carried from 2026-08-09).

## Verification: three layers, no self-trust [layers 1 and 2 DONE on numine, layer 3 TODO]

NEVER VERIFY AGAINST OUR OWN PRIOR BINARY (user ruling 2026-08-12). (1) CRYPTOGRAPHIC SELF-VERIFICATION, the strongest oracle: every run recomputes header hash chain, txRoot, receiptsRoot, logsBloom from stored bytes, checks TxNum contiguity block to block, checks the `itx/` family is present and decodes, and checks THE STATE ROWS the only way that costs one pass: a block whose header Root differs from its parent's changed the state, which is consensus math, so it must own at least one state row inside its own slots. A check that cannot run is a FAILURE, never a pass; the anchor is mandatory. (2) AN INDEPENDENT ARCHIVAL RPC, diffed on eth_* including historical state (the method the flat-history avalanchego PR proved: 5,685 queries, 0 mismatches). HOSTED FIRST: Glacier serves per-L1 RPCs at `https://glacier-api.avax.network/v1/ext/bc/<evmChainId>/rpc`, and numine's (8021) answers archive queries (verified 2026-08-12); throttle the diff, rate limits unknown. THE DIFF IS `epochdb dev rpcdiff --peer <url>`: it starts the local server on its real wire path, samples one height per band across the whole range so no era is missed, and compares the whole JSON document structurally WITH NO IGNORE LIST. A method the peer does not implement (-32601) is a fact about the oracle and counts as a skip, never as our mismatch. NUMINE RESULT 2026-08-12: 1,820 queries over three runs, 0 mismatches, at 5 req/s with no rate limiting observed; Glacier serves no `eth_getBlockReceipts` and no `ots_` namespace, which is where every skip came from. A self-run archival avalanchego/subnet-evm node is the fallback ONLY where no hosted archive exists: it costs ~18h of P-chain re-execution before the L1 syncs a single block (user, 2026-08-12). (3) PUBLIC RPC SPOT CHECKS where one exists (mainnet C bodies/receipts/logs; its public endpoint has no archive state, so state rides on layers 1 and 2).

## The windowed shared chunk cache [DONE, unchanged]

Plain 4MB chunk files under 20-minute UTC window dirs; the window IS the LRU, recency in the filesystem, shared across processes, eviction is `unlink` of the oldest non-current window under a statfs watermark, admission control never eviction, fsync-then-rename fills, ranged GETs checked against Content-Range, promote-on-read once per window, singleflight per chunk. Full rationale in git history of this section; nothing about the new engine changes it, it caches run chunks exactly as it cached epoch chunks.

## Distribution and casfs [DONE, byproduct]

Torrent alignment notes and R2 economics stand as recorded (4MiB pieces map 1:1 to chunks; a 700GB sync is ~6.5 cents of R2 reads). ## Sizing inputs

- IN-PROCESS CALLS, MEASURED 2026-08-12 on the dev box (i7-10700K, 8 cores / 16 threads) against numine at tip, an ERC20 `totalSupply()` through `Node.CallAt`, all four runs back to back on an otherwise idle box:

  | | single-core | all-core (16 threads) | scaling |
  |---|---|---|---|
  | baseline, the descent as built | 7,314/s (137us) | 13,586/s | 1.86x |
  | reads off the write lock (chainGet RLock + the txCeiling memo) | 7,483/s (134us) | 50,779/s | 6.79x |
  | plus the flat latest-state cache, warm | 15,544/s (64us) | 91,381/s | 5.88x |
  | plus the contract-code cache, warm | 40,271/s (25us) | 198,520/s | 4.93x |

  THE SAME FOUR RUNS ON A CODE-HEAVY SHAPE, measured 2026-08-13: a PROXY's `totalSupply()` at the same tip, which loads its own code and its implementation's, so it is two code reads per call rather than one. Without the code cache 6,123/s single-core and 43,675/s all-core; with it 19,679/s (163us -> 51us) and 124,694/s. A proxy call was paying MORE in code descent than in state, which is the whole reason the tier exists.

  THE SCALING WAS THE WHOLE GAP AND IT IS CLOSED: 6.7x more all-core throughput for a per-call cost that got cheaper rather than more expensive, and 91,381/s on 8 physical cores extrapolates past the 200-400k goal on the target 96-core box by any reading of it (5,711/s per hardware thread x 96 = 548k/s; 11,422/s per physical core x 96 = 1.1M/s). The flat cache halves the per-call cost on top, which is where the single-core doubling comes from. gRPC over loopback with the cache on: 3,194/s serial (313us, i.e. ~250us of round-trip latency) and 32,184/s parallel, which is why the library exists. WHAT IS LEFT: a state read the flat cache misses still decompresses a whole zstd-9 data block, so the cold and historical path is unchanged.

- FRAMES (measured 2026-08-09): 10.4 frames/tx, 209 B/frame raw on the C-chain's DeFi-dense era (upper bound); 4.77 frames/tx, 138 B/frame on a real L1; capture free on wall clock (66.7s with vs 67.6s without over the same corpus); mainnet compressed upper bound ~285GB, S3-resident.

- MAINNET SCALE: ~0.95-1.1B distinct state keys, ~1.6-1.8B total writes, 92.1M blocks, ~1.5B txs. PER-TX STATE ROWS add the within-block write-collision rate over per-block: low single-digit percent expected on Avalanche (fees are burned, so no per-tx coinbase write; measure at rebuild).
- STATE VS TRIE: Firewood is ~86% merkle overhead over flat state; current state 130-157GB; flat history was 175GB per-block at mainnet-43M, per-tx somewhat above.
- RUN COUNT: flush at 500k SLOTS (transactions plus one per block) = ~3,200 L0 runs over mainnet history, merged sixteen at a time into ~200 terminal runs; the live set is those plus at most sixteen L0 runs, and blooms and SST indexes are resident at a few GB. A chain under 8M txs has L0 runs and nothing else: numine ends at twenty.
- SECTION SPLIT AND CORPUS SIZE, MEASURED ON NUMINE 2026-08-12 over blocks 1..1,000,000 (1,030,022 txs), the same rows written both ways. Snappy at the old block sizes, 20 L0 runs: chain 630.3MB, state 157.2MB, lookup 135.6MB, 923.1MB, ~896 B/tx. THE PINNED ZSTD-9 CONSTANTS, 6 live runs (measured before the terminal ruling, when a fan-in-8 merge fired twice over this range; the same rows under the 8M boundary stay 20 unmerged L0 runs, which moves the state and lookup shares a little and nothing else): chain 455.0MB (68.1%), state 107.3MB (16.1%), lookup 106.0MB (15.9%), 668.3MB, ~649 B/tx. That is 27.6% off the corpus; the codec is the dominant term and the merge takes some of the state and lookup share with it. The chain section's 128KB block is what the rest of that 2% costs: at 512KB the same rows are 435.1MB and the corpus 648.4MB, i.e. 20MB (3.1%) cheaper, and the sections whose block size did not move come out byte-for-byte the same size. Frames cost ~64MB of the chain section and ~2.5MB of lookup at 4.77 frames/tx. Chain dominating by 4x is why it takes the biggest block.
- SINGLE-ROW READ COST IS THE CODEC, NOT THE BLOCK SIZE (measured on numine 2026-08-12, same box, same binary). Layer 1 verify over blocks 1..1,000,000 is the tx-by-hash shape a few million times over, and as a pass of point Gets it costs 17m31s at the pinned constants, 19m10s with the chain block at 512KB, and 6m44s under the old snappy pin. So the block size moves that clock by under a tenth and the codec moves it by 2.6x: zstd-9 decode per Get is what a point read pays, which is why there is a block size below which shrinking further buys nothing. The corpus is 29% smaller for it and every read that matters is served out of the chunk cache, so the trade stands.

- A WHOLE-RANGE READER MUST NOT PAY THE CODEC PER ROW (measured 2026-08-12, same corpus, same box). The fix for the clock above is not a smaller block, it is A SEQUENTIAL SECTION ITERATOR: `DB.ChainRows(fam, from, to)` streams one chain family over a number range in one pass (the runs covering it oldest-first, then the window), and because each family is a contiguous key range of the chain section, a data block is decoded exactly ONCE for the whole pass instead of once per row. It returns `iter.Seq2`, and a reader that needs several families in lockstep wraps each in `iter.Pull2`, which is what layer 1 verify now does with five cursors. THE SAME 1,000,000-BLOCK PASS: 17m24.5s as point Gets, 48.3s as iterators, 21.6x, and 8.4x below even the snappy era. Point Gets are still correct for what they are (`eth_getTransactionByHash` reads one row); only readers that touch a whole range use the iterator.
- THE BLOCK-HASH FAMILY is one lookup row per block, keyed by a hash that lives in exactly one run. At mainnet's 92.1M blocks it is a few GB of point-lookup rows inside the lookup section's share above.
- READ-THROUGH, MEASURED ON NUMINE 2026-08-12 (6 runs, 668.3MB, MinIO through a counting proxy): 11.4MB resident = 1.71% of the corpus, i.e. a mainnet-scale corpus's blooms and indexes land near the few-GB estimate. Cold open of the 6 runs: 19 chunk fetches, 656ms. Every cold point read (state slot, tx by hash, tx body, receipt, header, absent hash) cost AT MOST ONE 4MB chunk, and the second touch cost nothing.
- JOIN AND FRONTIER, MEASURED ON NUMINE 2026-08-12, when every run was published: a fresh dir resolved the pointer and walked 20 run footers backward to the chain root in 17s over MinIO, built the frontier (1,656,231 rows -> 56,769 accounts, 664,305 slots, 935,021 deletes, 9 batches) in 8s at 215k rows/s, and was serving 28s after start; it then executed forward from 1,000,001 to the live tip at ~2,950 blk/s with zero root mismatches, having asked p2p for nothing below 1,000,000.
- REPLAY WALL CLOCK, measured i7i.2xlarge: mainnet from genesis ~2 weeks serial at 1,100-1,300 tx/s; first 500M txs 3.3 days; numine (1.03M blocks) 7m30s to tip on the dev box.

## Operations

- BUILD/RUN: `go run ./cmd/epochdb serve [--data <dir>] [--network mainnet] [--chain C|<blockchainID>] [--port] [--grpc-port] [--node <uri,uri>] [--vdr-sources <uri,uri>] [--tip-override <containerID>] [--pprof ...]`. `--tip-override` now names WHERE FORWARD FETCH STOPS TRUSTING THE NETWORK: the fetch climbs to that container's height and stops there, and no consensus follower runs, which is the fixed reproducible corpus the flag always existed for. `--walks` is gone with the walks. ALWAYS PASS `--network mainnet`; the default is fuji. One process listens on two ports: `--port` carries JSON-RPC (`/`, `/ext/bc/<id>/rpc`, `/ext/bc/<id>/ws`), plain HTTP (`/v0/`) and `/status`; `--grpc-port` carries gRPC. The dead `--verify` and `--cook-every` flags are gone, they had no effect after the epoch cook died.
- UPSTREAM PUBLIC API, THE WHOLE POLICY (2026-08-14, written the day a 429 took mainnet C down). A node asks a public Avalanche endpoint for THREE things and nothing else: the validator set (once at dial, then a cross-checked refresh every 4h JITTERED), the bootstrap peer list, and, on an L1's FIRST start only, the CreateChainTx that `chain.json` then caches forever. THE NETWORK ID AND THE C-CHAIN BLOCKCHAIN ID ARE NOT ASKED AT ALL: they are constants of the chain descriptor the data dir was built with, and asking a public node for them cost two requests per container per restart. `--node` and `--vdr-sources` take COMMA-SEPARATED LISTS and every upstream call rotates over them. A TRANSIENT UPSTREAM CONDITION IS NEVER A FATAL STARTUP ERROR (`dist.Try`): 429, 5xx, timeouts and resets are retried over every source with exponential backoff and jitter for ~2 minutes, and only then does the node give up LOUDLY, naming every source and what each answered. THE FAILURE THIS REPLACES: a 429 killed the process, the orchestrator restarted it into the same 429, and dozens of containers restarting into one rate-limited endpoint is how a chain stays down for hours. THE CROSS-CHECK RULE IS UNCHANGED (L1 exact, primary network 95%): the retry unit is the WHOLE PASS over the sources, never one source at a time, so failover can never silently reduce a cross-check to whoever answered first, and a source that fails is skipped exactly as it always was. MEASURED on a fake endpoint that counts: a C-chain container's dial went from 4 requests to 2, and the validator refresh from 1/h to 0.25/h.
- A NODE THAT CANNOT MAKE PROGRESS MUST NOT LOOK IDLE (2026-08-14, after step, dexalot and gunz). When every peer answers a height poll with the PRUNED FALLBACK (its own last accepted block, because it no longer holds the height), `seedSpan` cannot terminate, and it used to spin in silence: gunz polled 4,070 times and fetched zero containers for 20 minutes with nothing in the log. It now names the height, the pruned-answer count and the connected archival peers after 10s and every minute after that, and `serve`'s status line and `/status` carry `pruned_seeds`/`bad_links` (omitted while zero, so a healthy node's output is unchanged). IT KEEPS TRYING RATHER THAN DYING: the height is unavailable from THESE peers, a restart comes back to the same peers, and the fail-stop we do want is the operator reading the line.
- CONFIG IS ENVIRONMENT ONLY: `EPOCHDB_S3_*`, `EPOCHDB_CACHE_*`, `EPOCHDB_FETCH_CONCURRENCY`, `EPOCHDB_FIREWOOD_CACHE`, `EPOCHDB_FLAT_CACHE`, `EPOCHDB_CODE_CACHE`, `EPOCHDB_HEAVY_SLOTS`, `EPOCHDB_NEW_CHAIN`, `GOMEMLIMIT`, `GOGC`. Credentials: static keys win, else the AWS SDK default chain; HTTP client and SigV4 signer stay hand-rolled.
- MEMORY DEFAULTS: GOGC=50, GODEBUG=madvdontneed=1 baked into the image (docker replaces GODEBUG wholesale; the binary warns when missing).
- PACKAGING: per-commit images ARE the release channel; vet+test then `ghcr.io/containerman17/epochdb` as `latest` and `sha-<short>`; cgo mandatory (firewood, and the zstd byte-identity pin); runtime `distroless/cc-debian13`. There is no zstd CLI layer: block compression is the library's.
- SOLE WRITER: flock on `<data>/.epochdb.lock`; read-only openers cohabit freely.
- NEVER MINT CLOUD CREDENTIALS FOR A TEST; reuse what exists; MinIO for S3 tests.
