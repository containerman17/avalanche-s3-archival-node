## Principle [BUILT]
Bodies + headers + proposervm extras are the only ground truth. State history, receipts, logs, all indexes are caches rebuildable by re-execution (~5-6k blk/s). Re-executing one block was the universal primitive; after the 2026-07-20 ruling logs/receipts are STORED, and re-execution remains only for traces, createAccessList, and verification.

## Architecture [BUILT]
- Immutable per-epoch files, self-described by filename: `epoch_<startblock>_<blockcount>.epoch`. No catalogue; startup = readdir + read footers. Height->epoch = binary search over the readdir table.
- Epoch boundary rule: FIXED TX COUNT per epoch. An epoch seals at the first block whose cumulative tx count reaches the threshold. Uniform file weight by construction, immune to throughput growth (SAE ~10x). Deterministic and bit-identical: cumulative tx count is chain content.
- Staging during sync is separate and disposable: height-bucketed arrival segments (100k blocks per bucket, `arrival_NNNNN.log` + `index_NNNNN.log` sidecar). The cooker consumes staging forward behind the executor, cuts epochs by tx count, and deletes a staging bucket once all its blocks are cooked. Buckets and epochs do NOT align 1:1; staging exists only on the machine doing the initial sync. Buckets are height-bounded (not tx-bounded) because blocks arrive out of order, so a file must be addressable by height alone; the constant is local-only tuning, never canonical. Mainnet at 10M blocks measured ~1.2GB per bucket all families combined (writelog ~450MB avg, 1-2GB dense-era). For a much denser chain (subnet EVM later), lower BucketBlocks per deployment: cook RAM scales with per-bucket writelog size (user reviewed 2026-07-29: fine as is).
- Epoch sections: bodies (zstd frames of 16 containers + published 512KB dict; measured 2026-07-17 on 112k real containers: 2.24x blended, 34us random-access decode; frame-256 buys +5% for 14x slower access, rejected), headers, proposervm extras, state write-log SST of (account,key,^block)->NEW value rows, EF fp48 tx index, log posting lists (position-agnostic addr/topic -> EF block lists), per-epoch key bloom, stored-logs sections, footer (offsets, version; NO embedded signature: signing is manifest-level so independent syncs stay bit-identical, decided 2026-07-20).
- Tx index: Elias-Fano over sorted 48-bit hash fingerprints + bit-packed block numbers. Verify by decoding the candidate block. No MPHF (EF matches its size, simpler). Validated on 12M real Fuji txs 2026-07-17: 288ns lookups, 0 false positives. EF cost is density-dependent (log2(U/N)+2), so PER-EPOCH sections run ~27-28 bits/tx; duplicate fp48s are real (~2,600 pairs at 1.2B txs), so the lookup API returns a candidate LIST. Atomic txs live in extdata, not the eth tx list, so they are outside this index.
- Compression: per-epoch zstd dict trained AT SEAL TIME on that epoch's raw containers (user directive 2026-07-18, supersedes one-global-dict; the dict ships inside the epoch file so distribution stays self-contained). Trainer is the zstd CLI (pinned v1.5.7) with a start-block-derived `--dictID`: klauspost's `dict.BuildZstdDict` is map-iteration nondeterministic (measured) and would break bit-identical files. Encode/decode is klauspost zstd, SpeedBestCompression.
- Sealing parameters (constants in `state/epoch.go`): PRODUCTION EPOCH_TXS=10,000,000 (user-confirmed 2026-07-20: ~120 epochs of ~4GB for full mainnet, ~10-day seal cadence, hot tail 1-4GB; 25,000 was corpus-stress only), frame-16 bodies/headers, 512KB dict target, 64KB SST blocks, bloom 10 bits/key x 7 hashes.
- WHY EPOCHS STAY SMALL, the argument re-derived and re-confirmed 2026-07-30: the UNSEALED tail costs ~1.8GB per million txs on every node (measured: 128GB of ancillary families for 70M txs), and the sealed form is ~4.5x denser. Epoch size therefore sets everyone's raw window: 10M txs bounds it at ~18GB, while the 50-100M-tx epochs proposed that day would make it 90-180GB. Seal itself is cheap and streaming either way (a k-way merge, a few GB of RAM, ~2h of single-threaded zstd CPU per 10M-tx epoch), so nothing pulls the other direction. EPOCH_TXS stays 10M.
- ONE NODE TYPE (ruling 2026-07-30). There are no archival/pruned/indexer personas and no second binary: "how much history do I keep locally" is a config knob (a floor, plus a chunk-cache size over the bucket), and the indexes are inside the epoch format. The serving core does decompose into two roles, which is what makes that true: the follower/executor/publisher role, which owns the writable data dir and is the only writer, and a STATELESS IMMUTABLE-HISTORY role, which needs nothing but hashes and a chunk cache. A future `serve --history-only` worker (pin a hash or chunk range, serve reads out of it) therefore falls out of the seal boundary with no architecture change; not built, nothing blocks it.
- Epoch format v3 (2026-07-28 user decision): contract code ships INSIDE the epoch as `'c' | hash | zeros` rows in the SST keyspace ('a' < 'c' < 's'), so it rides the existing sparse index and key bloom and needs no new section. An epoch carries the code of every account row it writes (placement rule, see Torrent distribution). Blob rows are not state diffs: verification and the base fold skip them.
- Epoch format v2 (2026-07-20 user ruling), folded into v3: stored-logs sections are MANDATORY, not a flag. Per log-bearing block: addr/topics/data/txIndex records (logIndex positional, txHash+blockHash derived from bodies at read time), frame-16 with a DEDICATED 128KB logs-trained dict (measured better than the container dict). Per tx-bearing block: uvarint gasUsed + status byte (cumulative gas by prefix sum; bloom/contractAddress/effectiveGasPrice derived). eth_getProof stays impossible; getLogs posting lists still provide candidates, the stored sections replace only the response construction.
- NO UPGRADE PATH (user ruling 2026-07-28). v3 is the only format the code can read: `OpenEpoch` refuses a v1 or v2 file by name ("format v2, unsupported: delete the corpus and resync") and there is no re-seal, no section surgery, no migration. The corpus is disposable, so a format change is paid for by a from-scratch sync, not by rewriting files.
- No database anywhere. Hot period = append-only logs + RAM maps; sealing = rewriting those logs into sorted compressed sections. Everything mmap'd; recent blooms pinned, old ones page-cached.
- Historical state read at block N: LRU, then hot RAM map, then per-epoch blooms newest-to-oldest from epoch(N), one SST seek on first hit, then the floor (genesis alloc today). DESCENT COST, verified 2026-07-30 and the reason no snapshot ladder is needed: ALL mainnet epoch blooms together are ~1.5-1.8GB resident, so a full-depth miss walk (which is what every touch of a fresh address costs) is bounded by ~1.5GB of RAM for the whole chain and a few hundred bloom probes. Snapshot-less serving is affordable at mainnet scale. See Measured numbers for the derivation.
- getLogs: intersect posting lists -> candidate blocks -> read stored logs sections -> exact filter. Range capped at 10k blocks. No re-execution.
- DISK EMERGENCY LEVERS, recorded 2026-07-29, deliberately NOT pulled because getLogs is a primary workload on this node: (1) delete the posting lists and range-scan the stored-logs section instead (block-ordered and contiguous, so a 10k-block query is one ~5-10MB sequential read + ~600 frame decodes = 20-40ms CPU, near-zero IOPS): saves ~10-13% of every epoch. (2) delete the stored logs+receipt sections and bring back re-execution for getLogs/receipts: saves another ~20% but makes every log/receipt read cost ~ms per candidate block, which is the wrong trade for a log-heavy serving node. Together ~30% of the corpus if disk ever truly forces it.
- RECEIPTS AND FULL LOGS ARE CAPTURED LIVE INTO THE TAIL [BUILT 2026-07-29, user ruling: a node must serve recent receipts/blocks/txs/logs like a normal node]. Found by the fold dry run: receipts existed ONLY in sealed epoch sections, so the unsealed tail (up to ~10 days at EPOCH_TXS=10M) and any pruning node (which never seals) served zero receipts; proven pre-existing with a control full node, 100% identical mismatches. AS BUILT: a new bucketed tail family `rcpt_NNNNN.log` + `rcpt_idx_NNNNN.log` (same 100k-block bucketing, same bucketLog machinery, same fsync group as writelog/headers/logs, missing files = empty store), one record per tx-bearing block: `uvarint len(logsRec) | logsRec | rcptRec`, both halves being the EPOCH stored-section encodings VERBATIM (full-logs record; per-tx uvarint gasUsed + status byte). The codecs moved from `rpc` to `state/storedlogs.go`, because the executor is the producer now and `exec` cannot import `rpc`. Both execution paths append: the coreth path (`runEVM` returns receipts instead of logs, appended in `executeSingle` and in `flushBatch` via the batch item) and the SAE path (`res.Receipts`, beside the existing logs-tuple append). The raw logs-tuples family (`logs_NNNNN.log`, getLogs candidates) is untouched and stays separate. Readers: `storedBlockReceipts` resolves epoch-or-tail through one `storedSections` helper, so eth_getTransactionReceipt and eth_getBlockReceipts serve the whole tail, and the tail branch of getLogs builds responses from the captured full-logs records; the filter API inherits both through `runGetLogs`. SEAL NOW COPIES BYTES: `gatherEpoch` fills FullLogs/RcptRecs from the captured records and the `DeriveStored` re-execution stage is DELETED, with `rpc.NewDeriveStored`, `state.DeriveStored` and seal's `--network`/`--workers` flags (seal needs no genesis, no overlay and no EVM at all any more). BYTE-IDENTITY, proven before the derive path died: mainnet blocks 1..50,000 re-executed with capture into a scratch dir, sealed at `--epoch-txs 40000`; the derive-path seal (code at HEAD, in a worktree) and the capture-path seal of the SAME corpus both emit `epoch_1_42961.epoch` with sha256 `1b9f45193f863a964e6ac40dad49792bfe2cb333abf121563faa3368213ded38`, which is also the sha256 of the independently built `data-v3` epoch: three separate runs, one file. NO-RECORDS RULE: seal REFUSES a tx-bearing block that has no captured record ("resync it, there is no backfill"); there is deliberately no backfill-by-re-execution crutch, because corpora are disposable, so a pre-capture corpus is paid for by a fresh sync. A pruning node's fold retires rcpt buckets below B exactly like the other families. MEASURED cost on that corpus: 9.05MB of records for 42,961 blocks / 40,000 txs = 211 B/block, 8.5% of all raw tail bytes and 15.0% of the capture families (headers+writelog+logs+rcpt); sealed epochs are byte-identical, so this is purely tail disk. SAE-proof by construction: receipts are per-block deterministic at execution regardless of when a header settles them. GATE: against api.avax.network on pure-tail heights, eth_getTransactionReceipt byte-identical and eth_getLogs over blocks 45,000..47,000 identical (628 logs, same sha256); before this change both were a "not sealed into an epoch yet" error.
- Tip following: REAL snowman consensus (ported from flatstate), validator set from 2+ cross-checked P-chain RPCs (>=95% stake agreement). Ingest: naked p2p GetAncestors racing peers (deforestationdb-proven), no full node.

## RPC surface [BUILT]
Full parity with a coreth v1.14.2 node across eth, web3, net, txpool, debug, minus the exceptions below. Filters and WS subscribe exist; personal/admin are N/A by design (no keystore, no node-ops surface). Notable entries:
- `debug_getModifiedAccountsByNumber/ByHash` at ANY height straight from the per-block write capture (the differentiator; a normal node needs both boundary states live). Caveats: union-of-writes counts a value rewritten to its original; capture order, not hash order; needs the raw writelogs, so epoch-only nodes get a clean error; range capped at 10k blocks.
- `eth_getProof`: NOT SERVED, ever (user ruling 2026-07-29, superseding the same-day build-it ruling). Historically impossible by construction (no per-block tries); at the tip it was buildable via ffi EthGetProof, but it would have been the only Firewood reader and was ditched with the Firewood-is-verify-only ruling. Firewood has ZERO readers.
- `eth_sendRawTransaction` / `sendTransaction` / `fillTransaction` / `resend`: documented errors, no mempool or relay yet.
- `debug_dumpBlock` / `accountRange` / `storageRangeAt`: NOT SERVED. The ffi could range-read the frontier, but Firewood is verify-only with ZERO readers (ruling 2026-07-29), so these stay unsupported like eth_getProof.
- `avax_*` atomic tx/UTXO methods: unindexed, out of scope.
- Tolerances vs the public archive RPC: it refuses the whole debug namespace, createAccessList, getProof, and the internal-eth methods (-32601), so those gates are self-consistency or cryptographic rather than A/B.

## Verification without re-execution [BUILT]
Third parties verify downloaded epochs with NO EVM execution: (1) state: stream SST post-image diffs from genesis into a throwaway Firewood, commit per block, root must equal `header.Root` every block; (2) bodies: recompute txRoot per block from verbatim containers; (3) logs/receipts: v2 sections reconstruct full receipts (cumGas prefix sum, bloom from logs) and recompute receiptsRoot; (4) headers: parent-hash chain to a trusted anchor. Estimated 5-10x cheaper than replay (~1 day for full mainnet vs ~9 days); (2)+(3) are embarrassingly parallel.
Two bootstrap modes: plain (download-only, exit when the manifest is complete) and `--verify` (download + PIPELINED sequential verification: a cursor and one throwaway Firewood chase the contiguous prefix as epochs complete out of order). Failure names the epoch and exits nonzero. Slab-parallel verification (self-anchoring constructed frontiers) is a future many-machines option, not built.

## Distribution: S3-first and content-addressed [library BUILT as casfs, epochdb integration PLANNED]
User ruling 2026-07-29: "normal centralized epoch + latest snapshot publishing works for me." Distribution is one publisher and many read-only consumers, exactly the case where a swarm is a worse HTTP server, so the ENTIRE torrent stack is GONE: `dist/` (471 lines), the anacrolix dependency tree (17 modules out of go.mod, 458 lines out of go.mod+go.sum), `epochdb seed`, DHT/trackers, `serve --fetch-epochs` (redundant once bootstrap is a plain GET pass), and the manifest's infohash column. Object storage is R2/B2-class with zero egress; raw S3 egress would be ~$60 per full archival bootstrap. Epochs stay deterministic and bit-identical across builders, so sha256s remain stable facts anyone can independently reproduce.

RULING 2026-07-30 (supersedes the 07-29 "lazy loading, fuck that" ruling): S3 offloading with lazy chunk loading IS core, 100%. Publishing an epoch means putting it in a bucket, and a node's local disk is a CACHE of that bucket sized by config. This is the only structural addition that came out of the 2026-07-30 design day; every other candidate was parked or rejected, see "Parked and rejected".

THE LIBRARY [BUILT: github.com/containerman17/casfs, its own public repo, deliberately isolated from epochdb because nothing in it is chain-specific]. A content-addressed file store over any S3-compatible bucket.
- WHOLE FILES, NAMED BY HEX SHA256. The name IS the integrity check, so Put is idempotent and any number of nodes can share one bucket with zero coordination and dedupe for free.
- SPOOL-DIRECTORY DURABILITY: the library holds NO state outside the filesystem, and its spool directory IS the registration. A caller atomically renames a hash-named file into the spool, so there is no ack to lose and it is kill-safe by construction; the library scans the spool at startup and on demand, uploads anything not already in the bucket, and verifies the sha256 WHILE uploading (loud failure on a name/content mismatch, no separate pre-verify pass). `Release` confirms the upload and unlinks the spool file.
- ONE READ PATH: reads ALWAYS go through the local chunk cache. Chunks are ~4MB and each is one file (`cache/<2-hex>/<hash>.<offset>`); a miss is filled by pread from the spool file while that file is still local, otherwise by a ranged GET, and that source choice is the ONLY difference between the two states. Chunks are never durability (the spool file or the bucket is), so eviction is unlink of whole cold chunks: no rewriting, no compaction, the filesystem is the database. Recency is an in-memory LRU seeded from mtime at startup, with touch-on-read throttled (default 1h) so serving does not become an mtime write storm. A 200GB cache at 4MB chunks is 50k files, trivial.
- REJECTED same day: a Release-time full-chunkification pre-warm (user: cache pollution; ranges that are cold by definition falling through to S3 on demand IS the design). Only organic traffic warms the cache, which also makes the spool-to-bucket transition invisible: whatever was being read is already cached when the spool file goes away.

NODE SIDE: S3 credentials are OPTIONAL. With them, sealed epochs and snapshots offload to the bucket and deep history lazy-loads on demand, so a ~200GB node serves FULL archive semantics and is merely slower on cold history. Without them, the node holds everything locally and nothing about the read path changes.

MIRRORS FEDERATE TRIVIALLY: the config takes a LIST of backend URLs, and any HTTP endpoint serving the same hashes is interchangeable, an IPFS gateway included. No registry, no coordination, no official mirror; the hash space is the namespace.

BOOTSTRAP FLOW [PLANNED]. The bucket carries exactly ONE mutable, non-content-addressed object: the `latest` pointer, naming the newest snapshot hash and the newest epoch hash. Boot from an empty disk is then: config (a list of bucket or mirror URLs, plus which network) -> GET `latest` -> walk the hash-chained epoch footers BACKWARD to learn every name in history -> fetch the snapshot eagerly and the history lazily -> start the consensus follower and execute the still-unpublished tail. THE POINTER IS A HINT, NEVER AN AUTHORITY: all content self-verifies by hash, the chain roots at sha256 of the chain's own genesis config, and the first executed block's Firewood root check against consensus-verified headers catches a lying snapshot. S3 is untrusted infrastructure; the only attack it enables is withholding bytes, which is what mirrors answer.

FORMAT COMMITMENTS, to land BEFORE mainnet is sealed [PLANNED]. There is no reseal (see the no-migration rule), so these are cheap now and impossible later.
- HASH-CHAIN FOOTERS: epoch K's footer embeds sha256(epoch K-1), plus the associated snapshot hash at boundaries where one applies. Prev-hash is deterministic, so files stay bit-identical across builders, and ONE head hash authenticates all of history. Bootstrap walks the footers backward with range GETs (effectively free, the bodies download anyway). This KILLS the JSON manifest entirely.
- PER-CHUNK HASH LISTS: one hash list per artifact, ~600KB per epoch, itself content-addressed and referenced from that artifact's footer. It moves verification from whole-file to chunk granularity, which is what makes untrusted mirrors safe and is the prerequisite for peer-to-peer chunk serving later.
- NAMING STANDARD: plain hex sha256. Deliberately NOT IPFS CIDs (a CID of any multi-chunk file is a chunker-dependent DAG root, forcing UnixFS on us) and NOT torrent infohashes (a hash of a bencoded dict, piece-length dependent). Everything stays verifiable with stock `sha256sum`; CIDs remain computable later if interop is ever wanted.

AS BUILT TODAY, and transitional: the manifest is JSON at a fixed path (`epochs.manifest`), `{"epochs":[{"name","size","sha256"},...],"snapshot":{"name","size","sha256"}|null}`, emitted by `epochdb manifest` (which hashes every local epoch plus the local `base_<B>` if there is one) and carrying all epochs plus the ONE newest snapshot, paired at the same boundary (epochs 1..K with snapshot(K), the assembler takes the min when one producer lags). `epochdb bootstrap --url <base> [--data <dir>]` reads it, GETs `<base>/<name>` for every missing file (snapshot first, then epochs, fan-out 4, 3 attempts each), streams straight into a temp file while hashing, checks size + sha256, renames, exits 0 when the local set matches the manifest. `--verify` is unchanged and transport-independent: the pipelined verification cursor is fed by the same completion callback the fetcher already had. All of it is ~230 lines in `cmd/epochdb/dist.go`; there is no `dist` package any more. The hash chain plus `latest` replaces the manifest half of this; the fetch-and-verify half becomes casfs.

Contiguous-prefix rule after an incomplete fetch: coverage is the contiguous epoch range from genesis (`EpochSet.CoveredEnd`). State, receipt, and log queries above the first gap return a clean "missing epoch epoch_X" error (`RequireCovered`). ASYMMETRY, deliberate: bodies and tx-by-hash above the gap still serve (epoch-local reads) while state correctness requires full descent to genesis. `SealedEnd`/head still reports the highest local epoch.

CODE IN THE EPOCH FILE, format v3 [BUILT 2026-07-28, user decision 2026-07-28]. The gap: contract code is NOT in the epoch format and NOT in the manifest, it lives only in the standalone `code.log` (`state/codestore.go`, read at `state/overlay.go:433`), which the executor writes as a side effect of replaying blocks. So a node bootstrapped purely from downloaded epochs holds every block, state value, log, and account code HASH, but not the code, and the first `eth_getCode` or contract-touching `eth_call` fails. Never caught because every gate ran on a box that had built its own corpus and therefore had `code.log` locally.

Decision: code belongs IN the epoch, as `'c' | hash` rows in that epoch's SST keyspace, exactly the trick `state/base.go` already uses ('a' < 'c' < 's' share one sorted keyspace). Code lookup then rides the existing per-epoch bloom and descent with no new machinery, and an epoch file becomes genuinely self-contained, which is what the distribution contract always claimed. `code.log` stays as the hot-tail store for code deployed above the sealed end. Limited-history nodes are unaffected either way: the snapshot carries the blobs as 'c' rows.

PLACEMENT RULE, decided by measurement on the real 0-10M corpus (2026-07-28): an epoch carries the code of EVERY account row it writes, not only of the code first deployed inside it. Measured on the 7 production epochs: first-deploying-epoch would cost 288MB of blobs, every-referencing-epoch costs 478MB, i.e. +190MB (+0.6%) on a 32.6GB corpus, 57-87MB per epoch before compression. That price buys the invariant that WHICHEVER epoch answers the account read also carries that account's code, derived from the epoch's own account rows: no earlier epoch and no raw writelog, only code.log for the blob bytes. DETERMINISM: the set is a pure function of the epoch's own post-image rows (chain content), blobs are content-addressed, and `buildSST` sorts them, so map iteration order, wall time and local file layout cannot reach the bytes. Sanity check on the corpus: every code hash referenced by an account row over all 10M blocks is present in code.log, zero misses, and 34,711 of code.log's 35,011 blobs are referenced at all.

AS BUILT: footer version 3, same 16 sections and same layout as v2 (code rows live inside the SST, so nothing new is indexed). Read path is code.log, then epochs newest-to-oldest bloom-gated, then the base file, then the genesis alloc (alloc code is never deployed by a block, so no epoch carries it). There is NO in-place upgrade: the v1 -> v2 append path and the v2 -> v3 section surgery were written, proven on a real production epoch, and then DELETED 2026-07-28 per the no-migration ruling. `OpenEpoch` reads the footer version, refuses anything but v3 by name, and that is the whole of the compatibility story, so `serve` needs no version check of its own. Two absent-file rules relaxed so a download-bootstrapped node can start at all: a missing `code.log` and a missing `misc.log` are now empty stores rather than open errors (nothing ever executed there); `OpenHistory` still refuses a dir with no buckets, epochs or base file. `epochdb manifest` regenerates cleanly; every sha256 changes, which is expected (a v3 epoch is a different file). Per the 2026-07-28 ruling there is no re-seal of the existing mainnet corpus: data-fresh stays v2 and frozen, and the v3 corpus comes from the from-scratch sync at the end of the work order.

## Parked and rejected (design day 2026-07-30)
A full day of alternatives was walked. The outcome, in the user's words: the current architecture was defended 100%, and the only addition is S3 offloading. Concretely, what STANDS: epochs cut at EPOCH_TXS=10M, ONE latest snapshot artifact for bootstrap, and state reads by descent with per-epoch blooms. What follows is recorded so nobody re-derives it from scratch.

PARKED, viable and deliberately not built: FAT EPOCHS. A snapshot welded to every Nth epoch boundary, with lookups walking the light epochs back to the nearest fat one instead of all the way to genesis. It buys real things: multiple bootstrap entry points, range nodes ("hold epochs 38-42 only"), misses that cost O(1) independent of chain age, and bloom residency bounded by the cadence rather than by chain length. It costs compounding snapshot rent (every fat epoch carries a state-sized payload that grows with the chain) and a cadence constant to pick and defend forever. PARKED because the verified bloom numbers removed its main argument (all mainnet blooms together are ~1.5-1.8GB, so RAM survival was never at risk) and because bootstrap has exactly one entry point today anyway. REVISIT IF: bloom residency or full-depth miss latency actually starts hurting at 5-10x mainnet, or range nodes become a product requirement. The door stays open at zero cost: hash-chain footers plus snapshots stamped with their boundary make turning this on a publishing-cadence decision, not a format change.
RELATED, also parked: a node can fold its OWN floor locally at any boundary from epochs it already downloaded, because fold is deterministic. So read-path self-sufficiency never depends on the publisher's cadence, whatever cadence the publisher picks.

PARKED: peer-to-peer chunk serving between nodes that are already connected for consensus, one RTT to a peer instead of a ranged GET to a bucket. The per-chunk hash lists above are the whole enabling piece; nothing else is needed and nothing is built.

REJECTED, each with the reason:
- EMBEDDING SNAPSHOT BYTES INSIDE EPOCH FILES: a hash reference from the footer gives identical capability, and separate files let several epochs share one snapshot and keep seal and fold independent of each other.
- 50-100M-TX EPOCHS: the unsealed tail costs ~1.8GB per million txs, so this makes every node's raw window 90-180GB. Epoch size is a tax on all consumers, not just on the publisher.
- RESEALING OR INCREMENTALLY UPDATING PUBLISHED EPOCHS: every reseal is a new hash, which breaks the economics of content addressing (every mirror and every cache re-downloads) and makes compression O(n^2) over the life of the chain.
- IPFS AS THE TRANSPORT: cold DHT resolution is seconds against ~30ms for a ranged GET, and private or permissioned chains need access control, which swarms leak by design. IPFS gateways stay usable as ordinary mirrors, since the naming is plain sha256.
- TORRENTS: buried 2026-07-29, stays buried. Webseeds add nothing over HTTP mirrors.
- SHIPPING FIREWOOD'S OWN FILES instead of our snapshot format: the layout is non-deterministic, so two honest producers emit different bytes and nothing is verifiable across builders.
- A SECOND "INDEXER" SOFTWARE CATEGORY beside the node: the epoch format's internal indexes ARE the indexer (tx index, log posting lists, stored logs and receipts). One binary, one artifact set.

## Multi-chain, Avalanche L1s [PLANNED]
One binary and one format, with trust anchored PER CHAIN: the hash chain roots at sha256 of that chain's genesis config, which the client already has, so there is no global registry and no cross-chain authority anywhere. Every chain operator runs their own publisher and their own bucket. A private or permissioned chain uses a private bucket and inherits access control from S3 natively, which is precisely what a swarm cannot offer. Per-chain constants (EPOCH_TXS, bucket URL list, network id) live next to the genesis.
CONSIDERED AND YAGNI: an OR-bound on the epoch cut (seal at N txs OR M blocks) so a nearly idle chain does not take years to fill an epoch. Avalanche chains build blocks on demand, so few txs means few blocks: an idle chain's epoch simply stays small and cheap, and nothing is waiting on it. The tx-count cut alone stays canonical.

This deletes the Firewood.Revision latest path AND unpins CommitEvery (it was 1 only so the served frontier was a committed revision). No exceptions: `eth_getProof` was the one candidate Firewood reader and was ditched same day; Firewood has ZERO readers. GOROUTINES AND OWNERSHIP (`cmd/epochdb/follow.go`, ~270 lines; the rest of the work was making pinned values dynamic):
- `fetch.Fetcher` runs `Follow` (real snowman) and is the SOLE writer of staging. Its in-RAM `fetch.Store` IS the executor's `BlockSource`, so an accepted container is executable the instant it is durable, with no reader-sidecar lag. `--tip-override N` swaps the follower for a bounded backfill walk in the same slot (fixed-corpus builds and integration runs).
- `exec.Executor` runs one goroutine, holds the exclusive Firewood handle (verification only, nothing reads it), and is the sole writer of the state layer AND of the tail overlay, which it feeds through the one choke point every execution path already uses, `Store.AppendWrites`. serve now runs `CommitEvery=64`: the pin to 1 existed only so the served frontier was a committed Firewood revision, and with no Firewood readers it buys nothing. Freshness is unaffected because head, block-hash index and overlay all advance together in `flushBatch`, per block, right after each block's appends land (publishing only at the batch boundary left `latest` naming an older height than the overlay already served, and left 63 of every 64 block hashes out of the index; both were caught by the A/B probe). ROOT VERIFICATION: per block below the boundary, per batch above it, with an automatic per-block bisect on a boundary mismatch. At the tip that distinction disappears, because `Run` closes the open batch the moment staging runs dry, which at chain pace is after every single block: a following node commits and root-verifies per block exactly as before. Batching only ever engages while catching up. After each published block `OnBlock` advances the serving head and the block-hash index ON THE EXECUTOR GOROUTINE, which is what makes `eth_blockNumber` and the served state agree: a 200ms advance ticker (the first build) let them drift by ~70 blocks during catch-up, which the A/B probe caught as real mismatches.
- `rpc.Server` serves N request goroutines throughout. `latest`/`pending` state is the UNCOOKED-TAIL OVERLAY over the descent (`state/tail.go`), and there is no second read path: `Executor.LiveState`, the `readDB` and the whole `Firewood.Revision` frontier read are DELETED. The overlay is a map of 53-byte sorted key -> newest post-image, fed by the executor's own write frames (nothing re-derived), carrying each entry's block so the cook can prune by height; SELFDESTRUCT is tracked per address so a destructed account's storage reads as gone exactly like the descent's delete rule, recreation included. A miss falls through to `AccountAt`/`StorageAt` at the cooked watermark, and the watermark is read AFTER the miss, which is what makes the prune safe (see below). eth_call/getBalance/getCode/getStorageAt/getTransactionCount at latest stay sub-millisecond, now with zero FFI crossings on the read path.
- cook loop: `CookIndex` + `CookTxIndex` + `History.Refresh` + `PruneTail`, every `--cook-every` (default 60s) and ONCE AT STARTUP (so the node begins serving with the smallest possible overlay, and so the residue it then backfills from the raw writelog is bounded; a gap wider than two raw buckets is refused at open with "run epochdb cook-index first"). Async and fail-loud: a failure logs `COOK FAILED ... chain unaffected` and the chain keeps moving; the visible consequence is the historical window freezing plus an overlay that keeps growing, both of which the status line prints. THE PRUNE RACE, and why no double buffer is needed: the prune drops entries at or below the watermark Refresh has just published, Refresh publishes that watermark only after the new sorted buckets are readable, and a reader probes the overlay BEFORE loading the watermark. So an entry pruned between a reader's miss and its descent is covered by the watermark that reader then reads: a write is always in at least one of the two layers. Prune rebuilds the map rather than deleting in place, because a Go map never returns its buckets and this one grows to catch-up size.

STATE READ BANDS, and the one new refusal: `n > executed` is "not executed yet" (error), `n in [head, executed]` is the executed head (overlay then descent), `n < head` is the historical descent alone. The descent now REFUSES anything above the cooked watermark (`History.stateHead`) instead of silently descending past uncooked writes and answering with a pre-gap value: that was the one place where a moving head could have been quietly wrong. Cook cadence is therefore the historical window's lag (60s chosen; measured 1.2-4.6s of work per run at 1000 blk/s catch-up, far less at chain pace).

PINNED-AT-OPEN VALUES MADE DYNAMIC (the whole point of the change): `History.head` (atomic, advanced per executed block) and the new `History.stateHead`; the sorted-bucket mmaps and the account-delete index (`History.Refresh` re-opens only buckets whose `cookedThrough` grew, merging their deletes into a copied map, and unmaps the replaced ones after the write lock drains readers); the block-hash index (locked, grown per block); the raw tx index (`txIndexHolder` swaps the whole `CombinedTxIndex` after each cook; it is heap-only, so the old one is just garbage); and the state layer itself, which in follow mode is the executor's WRITER store rather than a snapshot taken by `OpenReadOnly`. STILL PINNED, deliberately: the `EpochSet` and the base-file floor, because neither seal nor fold runs in-process (below).

SHARING THE WRITER STORE forced the concurrency work that had never been needed: `bucketLog.idx`, `codeStore.idx` and `miscStore.m` were read outside their locks, which beside a live appender is a fatal concurrent map access, not a stale read (`state/store_test.go:TestLiveStoreConcurrentReadWrite`, run with -race). `EthDB()` returns a NEW `ethKV` per call, so its own mutex never guarded anything across instances; the locks now live in the stores themselves, where every caller routes through.

RPC LABELS (SAE, closes the "rpc labels" follow-up): `pending` = last accepted, `latest` = last executed, `safe`/`finalized` = last settled (`Executor.SettledHeight()`, which is the executed head below the Helicon boundary, so all three coincide there). `pending` resolves to the last EXECUTED height for state reads (no mempool: pending state is latest state); `eth_getBlockByNumber("pending")` is the exception and returns the last accepted container, which the tail already serves. `eth_syncing` now reports the geth-shaped object whenever accepted runs ahead of executed.

SEAL AND FOLD STAY OUT OF THE PROCESS (decision, with the evidence). Against the live APPENDER both are safe: seal only deletes buckets entirely at or below `sealedEnd <= exechead` and the appender only ever writes at `exechead+1` in a higher bucket; fold additionally waits for `exechead >= B + BucketBlocks` so the crash walk-back can never land on a retired container. Against the live READER they were NOT safe, and that is new because the reader is now in the same process: a reader keeps `bucketLog.idx` entries for retired blocks, and `pair()` opened with `O_RDWR|O_CREATE`, so the next read RESURRECTED an empty data file where the retirement had just removed one, turned every later read of that range into an EOF error instead of an epoch fallback, and left a zero-length file for the next cook to trip over. Fixed: the read path never creates, and a missing bucket returns "not here" so the descent falls through to the epochs or the base. With that, running seal or fold as the documented external sibling degrades correctly; they still must not run beside a cook, and with EPOCH_TXS at 10M a boundary is ~10 days away, so nothing is lost by keeping them out of the tip loop.

## Dev/prod cohabitation on one box [half BUILT, half DROPPED 2026-07-29]
The point (user clarification 2026-07-29): develop bots against live captured state, one writer capturing the tip while bot processes start and stop freely against the same files. That half is BUILT and production-proven: read-only openers (`state.OpenReadOnly`, `fetch.Reader`) beside a live writer, files are the API. The flock failover-pool half (standby WRITERS queuing on an exclusive lock for instant takeover on writer death) is DROPPED: bots never write, a crashed writer just restarts, and the machinery bought nothing for a one-box deployment. Block delivery to reader processes must be sub-5ms: split visibility from durability (writer `write()`s per block so bytes are visible via page cache instantly, fsync stays batched), wake slaves via inotify on the sidecar (sub-ms) or a tipbus-style mmap seq counter (~100us, flatstate-measured). The bleeding tail is visible-but-provisional: a writer crash may truncate behind what a slave saw, so the lockfile carries a generation counter and slaves re-validate their last blocks on writer change.

## Limited-history mode [step 1 BUILT; step 3 built then DELETED (superseded by snapshot download); fold producer and step 4 PLANNED]
Disk-bounded deployment for a validator host that needs current state and fast tip, not deep history: two validators share a 2TB disk with ~600-700GB free, and full-mainnet epochdb is ~590-690GB of epochs plus ~130-157GB of Firewood. Target ~200GB.

THE ONE STRUCTURAL CHANGE: state reads descend epochs newest-to-oldest and fall through to a floor (`History.search`), and that floor is the genesis alloc. That is the only reason coverage must reach genesis. Replace it with a flat live-state base file at block B: every read at N >= B is answered by (raw tail, epochs above B, base file) and nothing below B exists. Deleting epochs WITHOUT swapping the floor is silently wrong, not an error (the descent misses and reports "account does not exist"), so the floor check is the safety property of the whole feature.

Decisions, REWRITTEN 2026-07-29 (the original 07-28 rulings assumed network state sync; superseded by the snapshot design, see "Our own state sync"): the bottom is a SNAPSHOT from the manifest, preimage-keyed, produced by a pruning node. B is the snapshot's boundary (canonical, cumTx in the footer), so sealing above B cuts canonical epochs. Firewood and its per-block root check stay, so ~130-157GB is a fixed cost and not a lever. Gate: A/B vs the public network RPC at tip.

Base file (`base_<block>`): a new file kind, not an epoch, because its rows are live state with no block numbers (the file IS state at B). Reuses the epoch machinery (zstd-framed sorted blocks, sparse index, keybloom, mmap, versioned footer) with the SAME 53-byte preimage keyspace as an epoch SST, code blobs as `'c' | hash | zeros` rows in it, and the headers of [B-256, B] so eth_call BLOCKHASH works in [B, B+256). The footer records B, the state root and cumTx at B.

Call sites that change: floor check plus base lookup in `History.search` (`state/overlay.go`); `EpochSet` coverage anchors at the floor and `RequireCovered` reports "pruned below block B" (`state/epochread.go`); the delete map only needs epochs above B (the base file is a post-image, so no pre-B deletion or resurrected slot can exist); `OpenHistory` must open with a base file and no buckets; `serveMain`'s block-hash scan starts at the floor, not 0; `rpc/{tx,block,logs}.go` coverage errors become pruned errors, and below-floor tx-by-hash returns a typed pruned error rather than null (a bot silently seeing null for a real tx is the bad failure mode).

Contract: full archive semantics from B forward, nothing below B, B printed at startup. Budget ~175-205GB full mainnet (base ~20 + code ~5 + 0-3 epochs + raw tail ~18 + Firewood ~130-157), plus whatever chunk cache is configured when S3 credentials are present. Epochs above B accumulate ~4GB per 10 days on a snapshot+pruning-off node; the disk-bounded answer is the pruning MODE (fold snapshots, never seal), not a fold-down conversion, which does not exist. Lazy-attach of old epochs on query stays rejected: fine for epoch-local reads, useless for state, since a tip read can hit a key last written years ago.

AS BUILT (format v2, 2026-07-29, `state/base.go` + floor-aware read path): file `base_<block>`, footer-last with magic at both ends, four sections (sst rows `key53|uvarint vlen|value` in ~64KB zstd blocks, 61B sparse index, keybloom identical to the epoch bloom, and one zstd frame of the headers in [B-256, B] decoded at open). Footer: magic, version, B, hdrFrom, cumTx, state root, 4x(offset,len), magic = 132 bytes. Code blobs are ROWS, not a section: kind 'c' | hash | zeros, and since 'a' < 'c' < 's' they share the one sorted keyspace, index and bloom. No zstd dict (short values are not worth training one). NO UPGRADE PATH, same policy as epochs: a v1 file is refused by name ("format v1, unsupported"), and it could not be migrated anyway since it stored hashes and threw the preimages away.

Reads: `Account(addr)` / `Storage(addr, slot)` build the same 53-byte key the epochs and buckets use and probe once, with NO keccak on the read path at all. `WalkRows` is the only place hashing happens: it streams `kind | keccak(addr) | keccak(slot)` (65B) so `exec.startFromBase` can bulk-load Firewood, whose own keyspace is hashed. Rows therefore arrive at Firewood in PREIMAGE order, not hash order, so the near-linear trie-order bulk load measured on the v1 file no longer applies; profile the load if it matters. HISTORICAL, v1: hash-keyed 65B rows built by a k-way merge over bucket and epoch cursors (`BuildBase` + `epochdb snapshot`), measured 24.5MB / 586,687 rows at `--at 1000000` and 0.37GB / 8.8M rows at F=4,904,340. That builder, its StackTrie/`--verify` root pass and the `snapshot` command are all DELETED: the producer is now the pruning node's fold, and verification is the Firewood load itself. There is NO producer in the tree today; `state.WriteBase` exists so the tests exercise the format, and the fold producer takes it over. The "base ~20GB" budget line is a FULL-MAINNET estimate: at 10M blocks the base is ~2GB.

Read path as built: `History` gained a floor from `OpenBase`; `search` rejects below-floor with a typed `state.PrunedError` before any descent and consults the base after epochs miss; the genesis-alloc fallthrough survives only when floor == 0; code and the BLOCKHASH headers fall back to the base; `EpochSet` coverage anchors at the floor; the deletes map skips everything below it; `serve` prints `LIMITED HISTORY: floor=N`. RULINGS: an unknown tx hash on a pruned node returns an ERROR, not null (a hash carries no height, so "below the floor" is undecidable, and null would let a bot conclude a real tx never existed); the JSON-RPC code is the generic -32000 that geth-family pruned nodes use, with the floor in the message. THE ROOT GUARANTEE, precisely. Two independent checks, and the file only reaches disk if both pass. (1) Wire-level: every leaf response is verified by the reused coreth sync client as a merkle RANGE PROOF against the root we asked for, and every code blob against its hash, so no peer can insert a row that is not in the trie of that root, and the client's verified `More` flag plus contiguous `lastKey+1` continuation means a peer cannot silently skip a range either. That is a guarantee about ROWS. (2) File-level, which is the one that matters, because (1) says nothing about whether OUR walk covered the keyspace: `BaseBuilder.Finish` streams the finished row set through `trie.StackTrie` and recomputes every storage root (compared to the root each account row claims) and then the state root (compared to `header(B).Root`), refusing to leave a file behind on mismatch and also refusing an account that claims a storage root whose slots never arrived. So a `base_<B>` on disk is proof-carrying: its rows rebuild `header(B).Root` exactly, and the only remaining trust is that header(B) is the real block B, which comes from the peer-majority accepted frontier plus a verified parent-hash chain down to B (real snowman consensus on the frontier is the obvious upgrade and is not wired here).

CONCURRENCY IS THE ONLY LEVER THAT MATTERS (measured 2026-07-29, both runs on the same pivot minutes apart). A peer takes ~2s to serve one 1024-leaf range, so throughput is purely outstanding-requests, not bandwidth. `--workers 32` (flatstate's default) gave 14k rows/s; `--workers 384 --inflight 1536 --per-peer 6` gave 125-135k rows/s, a 9.5x speedup, with the failure rate staying negligible (771 failed requests over 90.9M accounts). The global in-flight semaphore is what makes this safe to turn up: workers can exceed it freely and simply queue locally, so the cap, not the worker count, is what peers ever see. Do NOT raise inflight to flatstate's measured collapse point (~4000 outstanding degenerated to <20 req/s). 32 workers is the wrong default at 580 connected mainnet peers.

HASHED KEYS ARE NOT A WALL, for the base file OR for the Firewood frontier (settled 2026-07-29 with a runnable proof, `verify/hashedfrontier_test.go`; supersedes the step-1 belief that a hash-keyed file can never be re-verified). Two independent facts. (1) A merkle-patricia root needs hashed keys in ascending order and nothing else, so `trie.StackTrie` recomputes `header(B).Root` from the base file's own rows, in one streaming pass, no Firewood and no preimages: that is what `BaseBuilder.Finish` does, and it also checks every contract's storage root against the root its account row claims. (2) Firewood's key space is ALREADY HASHED. `graft/evm/firewood/base_trie.go` hashes on the way in and stores `keccak(addr)` -> account leaf RLP and `keccak(addr)||keccak(slot)` -> `rlp(trimmed value)`, which is byte-for-byte what a state sync yields and what the base file stores; the preimage-keyed `UpdateAccount(addr, ...)` surface is a convenience layer, and `TrieDB.Firewood` is an exported `*ffi.Database` whose `Propose([]ffi.BatchOp{ffi.Put(hashedKey, val)})` + `Commit` reproduces the canonical MPT root exactly (proven against a stack trie in that test). So a limited-history node builds its Firewood frontier at B directly from the base file's rows, with no preimages, no execution and no replay, and the executor above B keeps its per-block root check unchanged. The frontier does NOT have to come out of the sync in merkle form.

Known gaps: genesis-alloc STORAGE was unsupported in the deleted folder and will need handling in the fold producer (dead code on both networks today, whose single alloc account has code but no storage). Two more from the gate run: "nothing below F exists" is exact for STATE but bucket-granular for BODIES (a raw bucket straddling F still serves bodies below it, and the floor check lives in the descent, not in the file set); and the base's CODE section is still effectively untested, because code.log is a single global file that has to be carried whole, so eth_getCode resolves from it rather than from the base on any node built by folding an existing corpus.

Work order: (1) DONE, floor plumbing against the existing mainnet 10M corpus with a synthetic floor, gated on "a node pruned to floor F answers byte-identically to the full node for every block >= F"; (2) Helicon bump, the long pole and bigger than this feature; (3) DONE then DELETED, the `follower/sync` port, superseded by snapshot download; (3b) the pruning-node fold producer, the one remaining piece; (4) follow and seal above B on Fuji, A/B gated. Former open questions, both CLOSED: SAE deletes the state-sync protocol outright (see the SAE section), and EPOCH_TXS stays 10M everywhere (ruling 2026-07-28).

## Our own state sync: publish a flattened snapshot [PLANNED] (user design 2026-07-29)
Upstream has no C-chain state sync under SAE and will not soon: `vms/saevm/cchain/sync.go` is a stub returning StateSyncEnabled=false with `// TODO(#5513)`, the SAE VM registers only three p2p handlers (warp/acp118, atomic tx gossip, tx gossip), and ava-labs#5513 "Epic: SAE State Sync" is open with "register the server side" still on its list. Verified against both the v1.15.0-fuji tag and master HEAD c5d3c8aa (2026-07-28). So every new Fuji C-chain node today bootstraps by executing from genesis, and porting flatstate's v1.14.2 leaf-sync client is dead work for Fuji.

We route around it: SNAPSHOTS. A pruning node's normal output IS the state-sync artifact, and clients download it instead of syncing state from the network. One sync mode, one rule, no special cases (user rulings 2026-07-29):

- ONE SYNC MODE: every node starts from a snapshot. "Genesis sync" is just starting from snapshot(0), which is the genesis alloc and is HARDCODED IN THE CLIENT (it already ships there: `exec.NetworkGenesis`); no snapshot-zero file exists. The first pruned node on a network executes from genesis ONCE, ever; every later client starts from a published snapshot. THE TRUST ANCHOR IS THE GENESIS CONFIG (ruling 2026-07-30, supersedes the 07-29 source-committed snapshot hash): the hash chain roots at sha256 of the chain's genesis config, which the client already ships, so no per-network snapshot constant has to be committed or bumped when a newer snapshot is published. A downloaded snapshot needs no pinned hash of its own either: loading it into Firewood computes its root, and the first executed block's root check against consensus-verified headers rejects a lying one. A node given a later snapshot downloads it, dumps it into Firewood, and replays the gap to tip; every key not found in local data falls back to the snapshot, which is the descent floor.
- ONE PRODUCTION RULE: at every canonical boundary (cumulative-tx-count, same for everyone), a PRUNING node emits snapshot(K) = snapshot(K-1) folded with the period's own captured writes, and a NON-PRUNING node emits epoch K. Each is a pure function of chain content plus the previous artifact of its kind, hence bit-identical across nodes within its kind. Pruning nodes never seal epochs; archival nodes never emit snapshots. No producer flags, no conversions, no folding epochs into snapshots anywhere, ever.
- ONE PUBLICATION PATH: the operator runs two real nodes, one archival and one pruned, and both simply rename their finished artifacts into the casfs spool, which uploads them. Publication carries the NEWEST snapshot only, no ladder. The only mutable thing anywhere is the `latest` pointer, updated to the new epoch and snapshot hashes once they are in the bucket (until the hash chain lands, it is the manifest JSON assembled from each node's reported hashes: see Distribution, AS BUILT TODAY).
- ONE ROW FORMAT [BUILT 2026-07-29, base format v2]: the snapshot is PREIMAGE-KEYED with the same 53-byte keys as epochs and buckets, because its producer (the pruning node's own capture) has the preimages. The hash-keyed 65-byte base keyspace existed only for network leaf-sync, which is deleted (below). Firewood load hashes keys on the way OUT, in `Base.WalkRows`, so an account or storage read costs no keccak at all and only the once-per-node bulk load pays for hashing.
- VERIFICATION IS THE LOAD, not a pass: dumping the snapshot into Firewood computes the root as a side effect of the commit, so the check is one free comparison against `header(B).Root` (kept only for a clear early error), and the next executed block re-verifies the inherited state transitively anyway. The StackTrie verify pass and `snapshot --verify` machinery are deleted. Same ruling applied to the FOLD's pre-publish gate (built 2026-07-29, DELETED same day, user: "extra validation of already-validated data no one asked for"): the producer executed every block root-verified and every client's load re-checks the root, so the throwaway-Firewood gate (which transiently doubled the merkle store on the disk-bounded node) is gone; a bad snapshot is impossible to publish silently because every client refuses it at load. GONE with it: `verify.CheckBase` and its whole file, its teeth test, `FoldSnapshots`' gate callback parameter and the cmd wiring; the fold goes Finish -> Commit directly. What SURVIVES is the zero-root premise test (moved to `verify/zeroroot_test.go`, reworded: it is a library-behaviour pin, not gate infrastructure), because `exec.startFromBase` genuinely depends on zero-rooted rows loading to the canonical root, and the CLIENT-side root check in `startFromBase`, which is load-bearing and untouched.
- Cadence does not matter for clients: catching up from B to tip is p2p block fetch plus replay at 3-6k blk/s, so even a 10-day-old snapshot costs a couple of minutes of replay.
- BYTE-IDENTITY REQUIREMENT [BUILT]: all producers cut at the same canonical heights, and a snapshot-synced node cannot compute cumulative tx count from history it does not have, so the SNAPSHOT FOOTER carries cumTx at B (`Base.CumTx()`). It is the one footer field `header(B).Root` does not cover; a lie there breaks manifest agreement loudly at the node's first boundary.
- Measured basis (2026-07-29): base_200000 loads into a frontier in 1.04s with the root matching the header; 8.8M rows rebuild in 11s; full mainnet extrapolates to about a minute. Rows stored sorted in trie order make the bulk load near-linear despite a 7-9 level trie.

DELETED BY THIS DESIGN (Occam pass, user-confirmed 2026-07-29, DONE 2026-07-29): the network state-sync port (`statesync/`, `state/basebuild.go`, `fetch/apprequest.go`, the second base-writer and its encoding conflict): snapshots travel over HTTP, nobody leaf-syncs, and post-Helicon peers cannot serve leaves anyway; the one-shot fold-epochs `epochdb snapshot` command (a pruning node produces snapshots as its normal output; the manifest asks it, not a tool); the hash-keyed base keyspace; the StackTrie/`--verify` snapshot verification machinery. The mode-matrix legality rules from earlier today collapse too: with genesis = snapshot(0) there is no genesis-vs-snapshot switch and nothing is illegal, the only switches are pruning on/off and which snapshot you start from.

ONE NODE TYPE, THREE CONFIGURATIONS, one artifact set (reframed 2026-07-30: these are knob settings, not personas or builds): (1) FULL ARCHIVAL, take the epochs, do indexing and historical work; (2) TIP-FAST, take the newest snapshot and replay the gap, serving the tip within about the download time; (3) TIP-FAST BUT KEEP EVERYTHING FROM NOW ON, the same snapshot with pruning off, for rerunning algorithm benchmarks against identical data as development proceeds. That third one is exactly the floor node built on 2026-07-28. With S3 credentials the first and second collapse into each other: local disk size stops deciding what a node can answer and only decides how fast it answers cold history.

Distribution [BUILT]: the snapshot travels exactly like an epoch file, named and checked by sha256. The two checks stay independent: the sha256 proves the bytes are the ones named, and the root check against header(B).Root proves those bytes are real state. S3-as-truth for epochs is no longer a speculative mode, it is the design (see Distribution), and the format was already shaped for it: every section is offset-addressed, so a read is a range GET and only footers, blooms and indexes (a few GB) want to be resident.

PARKED, not rejected (2026-07-29): rewriting Firewood in Go. Read-side FFI crossings were already worked around by the capture cache, and replay runs 2,900-6,000 blk/s, so FFI is not obviously the bottleneck; profile before touching it. If we ever did own the merkle store, the measured shape says NOT to bother dropping leaf values (flat state is 2.82GB of a 20.7GB Firewood at 10M blocks, so at most ~14%); the 86% is interior nodes, so the only real lever is storing interior hashes down to a depth cut and recomputing deeper subtrees from flat state on demand, which our trie-order row layout makes cheap. Disk down, per-block CPU up, root checks intact.

## Helicon / ACP-194 SAE [PLANNED] (researched 2026-07-22 at avalanchego v1.15.0-fuji)
SAE is not a coreth change, it is a whole new VM (`vms/saevm`). The C-chain registers `transitionvm.Factory{PreFactory: coreth, PostFactory: saevm/cchain}`, runs coreth until HeliconTime - 10s, then boots the SAE VM on the same database. Coreth actively rejects blocks carrying SAE settled markers, so coreth-as-library can never process post-Helicon blocks.

What changes semantically: `header.Root` of block N is the post-execution state root of the last block SETTLED by N, not N's own state (settlement lag tau = 5s of gas time, a handful of blocks). Headers gain `SettledHeight`, `SettledGasUnix`, `SettledGasNumerator`, `SettledExcess`, plus ACP-283's `MinPriceExponent` and ACP-176's `TargetExponent`. Receipts are computed and stored per block at execution time but committed only at settlement: the settling block's receiptsRoot/bloom cover the CONCATENATED receipts of every block it settles. `header.GasUsed` becomes worst-case charged gas of the block's own body (statically checkable), per-tx gas charging floors at limit/2, and base fee for execution comes from the deterministic gas clock, never `header.BaseFee`. RPC labels shift: pending = last accepted, latest = last executed, safe/finalized = last settled.

Wire format is otherwise unchanged (one RLP block-with-extData, proposervm and GetAncestors untouched), but the new RLP tail fields mean a v1.14.2 decoder CANNOT parse any post-Helicon header, and v1.15 peers drop sub-v1.15 handshakes at activation. Fuji activates 2026-07-29 00:00 JST; mainnet is unscheduled in the tag, expect roughly 3 weeks after the mainnet release lands (Granite precedent), and our mainnet v1.14.2 pin is safe until then.

SAE DELETES C-CHAIN STATE SYNC (measured + read 2026-07-29, decisive for limited-history mode). `vms/saevm/cchain/sync.go` is a stub: `StateSyncEnabled` returns false, every summary getter returns ErrNotFound, `AcceptSummary` returns ErrStateSyncableVMNotImplemented, and the file carries `TODO(#5513): Implement C-Chain state sync`. The SERVING side went with it: `vms/saevm/sae/vm.go` registers exactly one p2p handler, `p2p.TxGossipHandlerID`, and there is no coreth leafs/code/block handler anywhere in saevm. `transitionvm` routes every AppRequest to `vm.current.chain`, which after HeliconTime is the SAE VM, so coreth's legacy even-request-ID sync server stops existing on that chain at activation. `p2p.FirewoodProofHandlerID` is RESERVED in `network/p2p/handler.go` and has zero implementations and zero references in the tag, so the Firewood-proof replacement is planned, not shipped. MEASURED on live Fuji 2026-07-29 09:43 JST: 36 peers connected, the header walk and container parse both fine (v1.15 handshakes and post-Helicon containers decode), then 24,881 leaf requests, 100% AppError, ZERO accounts in 4 minutes. Same binary, same minute, mainnet: 121 failures and 5.5M accounts. Consequence: a limited-history Fuji node cannot be built from the network at all until #5513 lands, and any Fuji plan that assumed state sync needs re-planning. Mainnet is unaffected (coreth peers, HeliconTime unscheduled).

Ranked epochdb work: (1) small and urgent, do not crash at the boundary (park fetch at HeliconTime on Fuji); (2) small, dep bump to v1.15.0-fuji so parsing and handshake work; (3) medium, verifier re-point: keep a ring of computed roots and assert `header.Root == root(SettledHeight)` with marker monotonicity, plus the body statics (`GasUsed == sum tx gas + op gas`, receiptsRoot over the merged settled range); (4) large, execution engine swap for post-Helicon heights to `saexec.Execute` + `vms/saevm/cchain` hooks. Firewood stays, and SAE ships native Firewood support to crib from. Scale note: max block gas becomes R*tau*lambda = 20x target (double the old cap), so EPOCH_TXS assumptions should be sized on charged gas. Risk: SAE Go APIs are explicitly unstable, so pin exact release tags.

## Operations
- Build/run: `go run ./cmd/epochdb <cmd>`. Commands: fetch (`--network mainnet --tip-override N` | `--follow --vdr-sources ...`), exec (`--stop N --state-cache 3 --commit-every 1000`), cook-index, cook-txindex, seal (`--out DIR --epoch-txs N`), manifest, bootstrap (`--url <base> --verify`), verify, serve (`--port --vdr-sources ... | --tip-override N`, follows by default), ab-bench / ab-bench-tx / ab-bench-rpc / ab-bench-logs / rpc-bench.
- SEAL ALWAYS DELETES fully sealed raw buckets (2026-07-29: `--delete-raw` was the only sane setting, so the flag is gone). NEVER run seal beside a live fetch or exec, they own those files. Buckets are 100k blocks and epochs cut on tx count, so the bucket straddling the sealed end survives and still overlaps the newest epoch: the delete-map and tx-index dedup stay necessary.
- New node today: copy `epochs.manifest` (JSON) into the data dir, `epochdb bootstrap --url <base-url> --data <dir>` (exits 0 when complete), then `epochdb serve --data <dir> --network mainnet` (follows the chain by default; pass `--vdr-sources <2+ P-chain RPCs>` for a cross-checked validator set).
- Memory: replay wants `GOMEMLIMIT=10GiB --state-cache 3 --commit-every 1000` on a 25GB box (the 6GiB default state-cache thrashes in dense eras, incident 2026-07-19). Seal at 10M-tx epochs gathers a whole epoch in RAM (~20GB anon live): run it ALONE with `GOMEMLIMIT=20GiB`, it OOMs beside a replay.
- Long stages MUST be setsid-detached (harness background tasks get reaped; learned twice).
- Multi-process: writers truncate torn tails on open, so NEVER open a live writer's dir with the writing opener. `state.OpenReadOnly` / `fetch.Reader` exist for cohabitation (production-proven). Two cook/seal processes must not share a dir (tmp+rename races).
- `du` lies on WSL2 and page-cache-heavy dirs; footers and manifests are truth.
- `epochdb serve` is the node: follower + executor + RPC in one process, no restarts, following by default (`--vdr-sources <2+ P-chain RPCs>` cross-checks the validator set, otherwise the --node URI with a warning); `--tip-override N` runs a bounded backfill in the same slot instead. It OWNS the data dir (state writer + Firewood), so nothing else may write there, and seal/fold/cook must not run beside it.
- ALWAYS pass `--network mainnet`: the default is fuji and the chain-id mismatch fails late.
