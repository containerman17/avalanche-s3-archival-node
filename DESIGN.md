## Principles and standing rules [DONE]

- BODIES + HEADERS + PROPOSERVM EXTRAS ARE THE ONLY GROUND TRUTH. Re-execution rebuilds everything else: state history, receipts, logs, frames, every index. We STORE logs and receipts rather than re-derive them (user ruling 2026-07-20). Frames will be too.
- MIGRATIONS EXIST ONLY FROM V2 ONWARD (this amends the 2026-07-29 no-migrations rule; user direction 2026-08-09). During active development we destroy and rebuild the data. There is never a compat shim. From the V2 bump on, SEALED epochs migrate by the deterministic per-epoch conversion below. Unsealed data never migrates: dump it and recook, "an extra three or four hours" (user, 2026-08-06).
- BYTE-IDENTITY ACROSS INDEPENDENT BUILDERS IS THE CORE PROMISE. Every artifact is a pure function of chain content. This rejects adaptive epoch boundaries, configured thresholds, randomized index construction, and embedded signatures, everywhere and forever.
- NO EXTRA VALIDATION OF ALREADY-VALIDATED DATA (user ruling 2026-07-29).
- NO DATABASE ANYWHERE. The hot period is append-only logs plus RAM maps. Sealing rewrites them into sorted compressed sections. Everything is mmap'd or pread. The kernel tiers RAM to SSD; casfs tiers SSD to S3. The /sql door is an ENGINE over these files, not a store.
- FIREWOOD IS VERIFY-ONLY WITH ZERO READERS (user ruling 2026-07-29: "Firewood is just a dumb hash verifying machine"). No read path touches it. This deletes `eth_getProof` and the state-range debug methods permanently, and unpins `CommitEvery`.
- ONE CHAIN PER PROCESS (user ruling 2026-08-04). One node type, no personas (user ruling 2026-07-30): local disk decides only how FAST cold history answers, never WHAT a node can answer.
- SEAL ALWAYS DELETES fully sealed raw buckets (user ruling 2026-07-29; there is no flag).
- AGENT POLICY (user ruling 2026-07-29): subagents on this project run OPUS, pinned per dispatch, never fable.

## Chain identity [DONE]

A CHAIN IS NAMED BY ITS BLOCKCHAIN ID (user ruling 2026-07-31): `--chain C|<blockchainID>` beside `--network fuji|mainnet`. Everything a descriptor carried is ON-CHAIN. The blockchainID is its CreateChainTx txID, so one `platform.getTx` returns `genesisData` and `subnetID`. `C` is coreth; everything else is subnet-evm. The data dir's vmkind stamp (`epochdb.vmkind` in misc.log) refuses the other kind forever. First resolution caches to `<data>/chain.json`. The cache is a cache: it wins over flags, and a cache naming another chain is refused.

THE CHAIN ROOT IS THE TRUST ANCHOR: `root = sha256(genesisData)`, the P-chain bytes VERBATIM, no separator, no normalization (user rulings 2026-07-31 and 2026-08-05). UPGRADE BYTES ARE NOT IN IT. The STATE ROOT enforces correctness, because upgrades apply inside blocks, never to genesis (subnet-evm `Genesis.toBlock` runs only `ApplyPrecompileActivations`; `ApplyUpgrades` takes a parent timestamp). A wrong upgrade.json diverges at its activation height and hard-stops, so a corpus built with a wrong one cannot exist. upgrade.json is the ONE off-chain input: `<data>/upgrade.json`, read verbatim every start, never cached. The C-chain genesis bytes are byte-identical to avalanchego's embedded copy; a test pins both network hashes.

MULTI-CHAIN: one binary, one format, trust anchored per chain. Every operator runs their own publisher and bucket; a private chain inherits S3 access control natively.

## Epoch format [DONE for V1; V2 is the frames bump]

An epoch is an IMMUTABLE artifact NAMED BY ITS OWN HASH (see casfs naming). The local index is one marker file per epoch, `epoch_<startblock>_<blockcount>.cas`, holding the artifact hash. No catalogue, no manifest.

V1 SECTIONS (17, format v6): bodies (zstd frames of 16 containers plus a per-epoch 512KB dict), headers, proposervm extras, the state write-log SST of `(account,key,^block)->NEW value` rows, the Elias-Fano fp48 tx index, the tx bloom in front of it, log posting lists, the key bloom, stored-logs sections, stored-receipt sections, footer (offsets, version, prev-epoch hash). V2 ADDS FOUR (21, format v7): `frames` and `framesIdx` (stored call frames), `addridx` (the address index) and `txcum` (the cumulative tx count). They are written AFTER every v6 section, so the first 17 sections of a v7 file lie exactly where a v6 build put them.

- NO EMBEDDED SIGNATURE: nothing may depend on WHO built the file.
- CODE SHIPS INSIDE THE EPOCH (user decision 2026-07-28) as `'c'` rows in the SST keyspace. An epoch carries the code of EVERY account row it writes (measured +190MB, +0.6% on a 32.6GB corpus). This buys the invariant: whichever epoch answers an account read also carries its code.
- STORED LOGS AND RECEIPTS ARE MANDATORY (user ruling 2026-07-20). Logs: addr/topics/data/txIndex, frame-16 with a dedicated 128KB logs dict. Receipts: uvarint gasUsed plus a status byte; the rest derives.
- BLOCK HASHES LIVE IN THE TX INDEX (user ruling 2026-07-30: "instead of 1.2 billion there is 1.3 billion, who cares"). It deleted the biggest resident map (4.6-5.8GB heap at 57.4M blocks) for +180MB of evictable bloom and +520MB of lazy on-disk index at mainnet. Only a bounded 128Ki-entry FIFO ring survives on the heap, 12.6MB flat.
- COMPRESSION: the zstd CLI trains a per-epoch dict AT SEAL TIME on that epoch's own containers (klauspost's trainer is map-iteration nondeterministic). The dict ships inside the epoch. Encode/decode is klauspost, SpeedBestCompression, one encoder state per seal. Body framing is 16 containers per frame (2.24x at 34us random access). Frame-256 rejected: +5% for 14x slower access.
- THE zstd CLI AT AN EXACT PINNED VERSION IS A HARD SYSTEM REQUIREMENT: `state/epoch.go`'s `ZstdPinnedVersion` (1.5.7), read by the Dockerfile from that one place. `serve` REFUSES TO START on a missing or wrong version. User ruling 2026-08-05, verbatim: *"you can absolutely check the zstd version in the binary, and in case if it's different from what you expect to have in the Docker image or whatever, you can just crash immediately. It's okay. We can afford this requirement."* WHY: a dict-less fallback once made the same epoch seal to two different artifacts. The fallback is DELETED, not configurable. The one dict-less case is a corpus below the trainer's sample floor (7), checked in Go so every builder skips the same corpora.

STAGING DURING SYNC is separate and disposable: height-bucketed arrival segments (100k blocks per bucket, `arrival_NNNNN.log` + `index_NNNNN.log`) plus the capture families `writelog`, `headers`, `logs`, `rcpt`, `itx` (frames), same bucketing, same fsync group. The cooker consumes buckets forward behind the executor, and deletes each once cooked.

RECEIPTS AND FULL LOGS ARE CAPTURED LIVE INTO THE TAIL (user ruling 2026-07-29): `rcpt_NNNNN.log` holds the EPOCH encodings VERBATIM, so seal copies bytes and needs no EVM, no genesis, no overlay. NO-RECORDS RULE: seal refuses a tx-bearing block with no captured record ("resync it, there is no backfill"). Cost 211 B/block of tail disk. Frames follow the identical pattern.

## Epoch size: the doubling schedule [DONE]

`EpochTxsAt(i) = min(8,000,000, 250,000 << i)`: 250k, 500k, 1M, 2M, 4M, then 8M forever. Cumulative boundaries are 0.25M, 0.75M, 1.75M, 3.75M, 7.75M, then +8M (user ruling 2026-07-31). No flag, no config: every node must cut byte-identical boundaries independently, which is why we reject adaptive and configured thresholds. The small start exists because never sealing is not free: an unsealed tail is heap-backed (~250 B/tx), ~4.2x bigger than sealed, with no S3 offload and no bloom. The giants converge to the flat 8M (~152 epochs at mainnet's ~1.2B txs, the shape the residency numbers are sized against). The 8M ceiling (user lowered from 16M, 2026-07-31) bounds every node's raw window at ~14.5GB. Going below 1M would multiply miss cost by 10, because miss cost scales with epoch COUNT. An OR-bound on blocks is YAGNI: Avalanche builds blocks on demand, so an idle chain's epoch stays small.

## The read path [DONE]

STATE AT BLOCK N: uncooked-tail overlay, hot RAM map, then per-epoch key blooms newest-to-oldest, one SST seek on the first hit, then THE GENESIS TRIE STATE. No floor, no snapshot ladder. Coverage must reach genesis. The descent's bottom is what genesis MATERIALISED, not the alloc. On subnet-evm, `Genesis.Commit` also runs precompile activations, so `exec.Genesis` carries `TrieAlloc`, computed once by running the VM's own activation code against a throwaway statedb.

CODE BY HASH: `code.log`, then epochs newest-to-oldest (bloom-gated 'c' row), then genesis. ONE function, `state.Store.Code`; the RPC descent, the sealer and the executor all call it.

MISS COST is the model that sizes the residency design. A key never written probes EVERY epoch, because keys are unhashed `kind|addr|slot` with no range pruning. A wasted SST read can be a cold 4MB chunk GET. THE BLOOM IS 20 BITS PER KEY x 14 HASHES (user-driven ruling 2026-07-30). Measured at 40M probes on a 120-epoch mainnet: 0.0069% per-epoch FP, 0.0083 wasted reads per miss, 3.30GB resident, against 0.98 wasted reads at the original 10 bits. 118x fewer wasted reads for 1.65GB. Readers take m and k from the file.

SECTION RESIDENCY: blooms load ONCE into the Go heap (immutable files; a filter page changed underneath is a wrong answer, not a slow one). Dict, sstIdx, headersIdx, bodiesIdx, deletes, logsDict, fullLogsIdx, rcptIdx hold per-chunk mmaps for the process's life. The tx index view is LAZY, mapped on first query past the tx bloom, so a pending-tx poll touches no EF page. Query-path reads go through pread and copy. THE STRADDLE RULE is generic: `View.Slice` aliases within one 4MB chunk and COPIES across a boundary, once, for everything.

RESIDENT INDEX BUDGET at mainnet shape: ~7.7GB (5.70GB bloom, ~2GB other indexes); resident sections are 4.7-7.2% of an epoch.

THE ACCOUNT-DELETE MAP STAYS A HEAP MAP, on measurement. Real corpora show a couple of distinct deleted accounts (EIP-158 precompile touches); block count bounds the rows (~50MB at mainnet). REVISIT TRIGGER at `state/overlay.go`: delete rows approach one per block AND distinct accounts become many.

getLogs: intersect posting lists, read stored-logs sections, exact filter, 10k-block cap, no re-execution. Disk emergency levers (drop posting lists, or drop stored logs entirely, ~30% of corpus together) are recorded and deliberately NOT pulled: getLogs is a primary workload.

CONTIGUOUS-PREFIX RULE: state, receipt and log queries above the first epoch gap error cleanly; bodies and tx-by-hash still serve above it (epoch-local reads).

## The tx index [DONE]

Elias-Fano over sorted 48-bit fingerprints plus bit-packed block numbers, verified by decoding the candidate block. Lookups 288ns, ~27-28 bits/tx, candidate LIST (duplicate fp48s are real). Atomic txs live in extdata, outside this index.

SEPARATE REJECT FROM LOOKUP: this took 7.10GB off the resident set. `secTxBloom` covers exactly the fp48s the index encodes: 16 bits/tx, zero-copy mmap-backed views, 2.00 B/tx, 0.046% per-epoch FP. The polling-wallet unknown-hash query is the HOT path; a tip-only node would otherwise pay full-history residency. The index is read in place (16-byte header parse, five slices). `WalkCandidates(hash, fn)` is the one traversal: raw tail, then epochs newest to oldest, verification inside the callback. fp48 MUST NOT SHRINK: 40 bits would cost ~1.1 false body reads per query. We analysed MPHF (2026-07-30) and did NOT adopt it: ~18% size saving, but seed-search construction is a hazard on the byte-identity promise. If ever adopted, it must land before a format is final.

## The windowed shared chunk cache [DONE]

A shared tree of PLAIN 4MB CHUNK FILES at `<cache root>/<window>/<chain>/<artifacthash>.<index>`. It replaced a byte budget + pin contract + hole-punch eviction, for four reasons: a byte budget is a number nobody can set (the operator knows a WATERMARK, "do not fill my disk"); a hole punch under a live mapping silently zeroes bloom pages (false negatives); one process per cache dir wiped siblings' warm cache; un-fsynced fills made every crash a cold start. Eviction is `unlink`, which cannot change what a mapped reader sees.

- THE WINDOW IS A 20-MINUTE UTC BUCKET named `2026-08-03T12-40`: alphabetical order IS chronological order, and a name that does not re-format to itself is not ours. The chain directory under it makes ownership visible (`du`/`rm` per chain) with the data dir's own name as identity.
- THE WINDOW IS THE LRU: recency lives in the filesystem, survives restarts, shared across processes with zero coordination. Reads are open+pread; a read of a chunk in any non-current window renames it into the current one, at most once per chunk per window (promote-only-if-old degraded to FIFO under pressure and was killed). In-process singleflight per chunk.
- LONG-LIVED MMAPS ONLY FOR THE RESIDENT SET, one mapping per chunk, copy-at-boundary. Accepted: unlinked-but-mapped chunks ghost roughly the resident set's size.
- RANGED GETS ARE CHECKED before becoming chunks: Content-Range must parse, start must equal the ask, total must equal the derived size. Anything else is never cached.
- WRITES ARE ADMISSION CONTROL, NEVER EVICTION: a statfs absolute-bytes watermark (default 5% free floor). Over it, serve from memory and forget; under it, tmp + FSYNC + rename (a torn chunk under a correct name is a silent wrong answer). A failed statfs skips the fill AND the eviction worker (a flapping mount once ate the cache window by window).
- EVICTION IS ONE WORKER dropping THE OLDEST NON-CURRENT WINDOW whole while over the watermark, ~60s settle between drops, never the current window: a saturated cache freezes full, because an evicted-and-refetched chunk is a GET that bought nothing. TTL (`EPOCHDB_CACHE_MAX_AGE`, default 30 days) is the same drop gated on the window NAME.
- METRICS: windows dropped, refusals, fill/evict/cached-read errors with last text (a node that cannot cache is an S3 passthrough and otherwise looks merely cold), free bytes, watermark, VICTIM AGE (the honest horizon a byte cap could never report). `/status` carries it.
- Containers sharing a cache bind-mount one host dir and MUST agree on UID. Deletion races are harmless (ENOENT tolerance). One cost: object sizes are no longer free at startup, one HEAD per artifact.

## Seal [DONE]

SEALING IS AUTOMATIC AND IN-PROCESS (user ruling 2026-08-01): serve seals at the end of every cook pass. Safe in one process because THE ORDER IS THE MECHANISM: (1) CUT the epoch, deleting nothing; (2) PUBLISH it into the live epoch set by atomic snapshot swap, folding its deletes into the descent; (3) ONLY THEN unlink raw buckets, drop handles, raise the fetch floor, retire staging. The read path never creates: a retired height reads "not here" everywhere.

PER EPOCH AND INTERRUPTIBLE BETWEEN EPOCHS (ruling 2026-08-01): the cycle above runs once per epoch, with ctx checked between epochs. Shutdown costs at most the epoch in flight, and resume needs no machinery (seal always starts at the next unsealed block; an interrupted crunch produces byte-identical epochs).

COST IS GATED, NOT CADENCED: the sealer extrapolates the boundary from the last measured tx-per-block rate HALVED and opens nothing below it. The gate dates a MEASUREMENT, never a failure (a gate pushed on error once bought a night of silence). Failures log and are never fatal.

THE SEAL'S CEILING IS ITS READABLE HEAD (ruling 2026-08-05): a read-only open takes the exec head BEFORE it scans, so the snapshot never carries a head it cannot serve.

SEALING DOES NOT KNOW S3 EXISTS (ruling 2026-08-02): publishing sets local-first spooled pointers; the head epoch comes from local markers alone. A fully offline node and one with expired credentials behave identically; only uploads stall, loudly, on the sync ticker.

PEAK MEMORY IS BOUNDED AND INDEPENDENT OF BLOCKS PER EPOCH (ruling 2026-08-02, after OOM kills on sparse-L1 shapes): stream sections straight into a spool file hashing as it goes; re-read raw rather than gather (bandwidth, not memory); external-sort spills to a scratch dir IN THE DATA DIR; one encoder state. Peak is ~1084 B/block, same hash as the gathering path (pinned by test). The scratch sweep is UNCONDITIONAL AT STARTUP (user ruling 2026-08-06) as well as before each seal. Safe because the flock below makes single-writer provable.

## Distribution and casfs [DONE]

ONE PUBLISHER, MANY READ-ONLY CONSUMERS (user ruling 2026-07-29: "normal centralized epoch + latest snapshot publishing works for me"). Object storage is R2/B2-class with zero egress. S3 OFFLOADING WITH LAZY CHUNK LOADING IS CORE (user ruling 2026-07-30): a node's local disk is a CACHE of the bucket.

casfs (own repo, chain-agnostic): whole files named by sha256 OF THEIR OWN PER-CHUNK HASH LIST. Spool-directory durability: rename in = registration, kill-safe, scanned at startup. Every chunk is verified on fill against `list[i]`; cache hits not re-verified. Cold chunks fetch as PARALLEL 1MB SUB-RANGES (S3 TTFB ~20ms flat, so 4 sub-ranges make a 4MB chunk ~31ms instead of ~63ms), tiled exactly, each checked against its Content-Range, any failure failing the whole chunk; one store-wide semaphore (default 16, `EPOCHDB_FETCH_CONCURRENCY`). Multipart above 5GiB in 128MiB parts, completion PARSED (S3 answers errors under 200 OK). Pointers are spooled files too, written with or without credentials, uploaded AFTER content, so a bucket reader following a pointer never lands on a missing object. Rejected: Release-time pre-warm (user: cache pollution; cold ranges falling through to S3 IS the design).

NAMING STANDARD [DONE, user-specified 2026-08-05]: `[content: L][hash list: 32*N][trailer: 16]`, chunk i = `content[4MB*i:...]`, last chunk short and never padded, name = `sha256(hash list)`. Stored size admits exactly one L, so one tail read self-verifies. Ceiling 131072 chunks = 512GB; larger REFUSED. Not CIDs, not infohashes: those force someone else's container for interop nobody asked for. Cost stated plainly: a name is four lines of any language rather than stock sha256sum; the trade is incremental verifiability.

FORMAT COMMITMENTS: epoch K's footer embeds K-1's NAME; the first epoch embeds the CHAIN ROOT. One head hash authenticates all of history; there is no manifest to sync. The snapshot hash is NOT in the footer (bytes must not depend on which kind of node built them). THE POINTER IS A HINT, NEVER AN AUTHORITY: one mutable object per chain, `latest-<chain root>`, root-qualified so chains sharing a prefix cannot overwrite each other. S3 IS UNTRUSTED: the only attack it enables is withholding bytes, which mirrors answer: the name commits to every 4MB range, so the bucket cannot substitute, truncate or edit anything.

V1/V2 PREFIX POLICY (user direction 2026-08-09): existing V1 corpora stay under their current prefixes, frozen, kept. V2 publishes under NEW prefixes. Nothing is moved.

TORRENT DISTRIBUTION (designed 2026-08-08, not built): piece length 4MiB aligned 1:1 with casfs chunks, v2/hybrid torrents (per-file alignment), seeder reads through the chunk cache, so a cold piece costs exactly one 4MB GET. Piece size does not change the 16KiB wire request unit, so alignment protects the READ LAYER, not the wire. Hashes are not interchangeable (flat sha256 vs SHA-1/merkle-16KiB). Economics: R2 read ops make a 700GB sync ~6.5 cents (free under the 10M/month tier); storage $0.015/GB-month dominates; egress is the murder weapon only on AWS-class providers.

## Joining a chain [DONE]

ONE start sequence, no separate bootstrap story (ruling 2026-08-03). Decision tree: (1) resolve `latest`, local-first; (2) no pointer AND empty prefix = fresh chain, sync from genesis; no pointer over a NON-empty prefix is a HARD ERROR (a broken publish, not a fresh chain; `EPOCHDB_NEW_CHAIN=1` is the deliberate escape); (3) pointer exists: walk the epoch chain backward by prev-hash, existence and linkage only, contiguity at every step, and the first epoch's prev-hash must equal the chain root; anything broken REFUSES TO START naming the artifact; (4) chain intact, no local state: frontier build, then serve; (5) both: warm start. NEVER silently fall back to from-scratch: hard error over silent re-replay, always (a typo'd prefix must not re-execute weeks of history).

VALIDATION IS CHEAP AT EVERY START: warm dirs pay the filesystem only (markers must cover 1..N and name the pointer's epoch). Cold dirs pay one pointer GET plus per epoch a HEAD and ONE tail read (footer + metadata together). Nothing rehashes content; `serve --verify` is the full pass.

THE FRONTIER BUILD replaces downloading a snapshot: a k-way merge over every epoch's SST section (one 64KB block per cursor, measured 71MB heap at 100 cursors), streaming winners into Firewood in 200k-op batches ONTO THE VM'S OWN COMMITTED GENESIS (subnet-evm activations included; alloc-gated tombstones once merged a wrong root on Beam). Deletes emit unconditionally; account keys sort before storage keys. The build opens Firewood with 2 REVISIONS (the serving 128 retains every batch and OOM-killed a 63.9GB join; pinned by test). A TORN BUILD HEALS ITSELF: exec head 0 with non-genesis Firewood IS the torn signature, so the join wipes and rebuilds; a dir with exec head above 0 is never wiped.

THE MERGE TARGETS THE HEIGHT THE SEALED END'S HEADER COMMITS TO (ruling 2026-08-01). Below SAE that is H, checked against `header(H).Root`. Above it, the settled height S, because settlement points are the only heights any header attests AND the only place the gas clock is published. The build seeds `ring[S]` and stamps a FRONTIER FLOOR (headers settling below it skip the root check; the floor itself is checked). Cost: the follower re-executes the settlement lag (1..10 blocks); the fetcher floors at min(sealed end, exec head).

## serve: one process, one chain [DONE]

`epochdb serve` runs follower, executor, RPC, cook, seal, publish and upload in ONE process; nothing restarts to surface a block (user rulings 2026-07-29). The five-part operator surface (ruling 2026-08-03): (1) `serve` is the product and the only name an operator types; (2) `serve --verify` verifies the SEALED epochs (the local raw tail's verification story is from-scratch reprocessing, deliberately); (3) the resilience contract: organize-and-reprocess or refuse-to-start with a readable reason; runtime failures flush writers FIRST then exit 1; no library `os.Exit`; (4) `/status` reports this process's one chain from the moment the listener binds (the bind precedes the startup work, so a port collision cannot be a fatal an hour in), an aggregate endpoint is the orchestrator's job, not ours; (5) dev stages and benches live behind `dev`; retired top-level names exit 2 with a pointer.

SOLE WRITER IS ENFORCED (ruling 2026-08-06): `flock(LOCK_EX|LOCK_NB)` on `<data>/.epochdb.lock`, held for life, kernel-dropped on death; a second writer fails at startup by name. Read-only openers (`state.OpenReadOnly`, the SDK, `dev probe`) take no lock, on purpose; that cohabitation is production-proven.

GOROUTINES AND OWNERSHIP. THE FETCHER runs real snowman consensus (validator set from 2+ cross-checked P-chain RPCs) and is the sole writer of staging; its RAM store IS the executor's block source. THE EXECUTOR holds the exclusive Firewood handle at `CommitEvery=64` (1.84x catch-up; per-block commits return at the tip because the batch closes when staging runs dry), publishes head and block hash PER BLOCK, appends to the state layer BEFORE committing Firewood (the other orders each shipped a real bug). THE RPC SERVER reads through the uncooked-tail overlay, one read path; ordering alone resolves the prune race. THE COOK LOOP runs every `--cook-every` (60s) and once at startup; fail-loud, never fatal. THE SYNC LOOP uploads spooled artifacts every `--sync-every`.

STATE READ BANDS: `n > executed` errors; `[head, executed]` is the overlay; `n < head` is the descent, which REFUSES anything above the cooked watermark rather than descending past uncooked writes. Nothing is pinned at open. Every structure moves under live readers by atomic swap or reopen-then-drain.

RPC LABELS (SAE-aware): `pending` = last accepted, `latest` = last executed, `safe`/`finalized` = last settled. `pending` resolves to executed state for state reads (no mempool means pending state IS latest). `eth_syncing` reports the syncing-toward goal as a separate number from the labels.

THE SEALED END IS A FETCH FLOOR: live, monotonic, pushed in from the command layer: no walk descends to sealed history. Without it a restarted follower re-downloads everything, since walks short-circuit on staging alone.

RETAINED STAGING IS UNBOUNDED, BY DIRECTIVE (2026-08-08). A staged-bytes ceiling that paused walks shipped 2026-08-06 and was REMOVED whole two days later. Walks stage freely, sealing retires raw behind the executed point, and the disk is the budget. THE USER'S REASONING IS THE DESIGN: a machine that cannot hold a chain's staging is an undersized machine ("we are not expecting a small machine with 100 gigs of disk to cook a 300-million-transaction chain from genesis, that is fine"), and the from-genesis fetch is a PRODUCER-SIDE job; consumers receive sealed epochs. WHAT KILLED IT was a liveness hole: the pause counted TOTAL staged bytes while drain only follows the contiguous-from-floor run, so a walk paused on disconnected spans deadlocks the chain (an L1's single FollowTip walk is exactly the wedging shape; mainnet escaped by span-ordering luck). A correct bound needs contiguous-runway accounting plus a free-space floor, not worth its weight on a producer-only path. `stagingBytes` stays visible in `/status`; disk-full fails the walk loudly, as intended.

TIP OVERRIDE IS A PHYSICAL CONTAINER ID (ruling 2026-08-01), cb58 or pre-ProposerVM eth hash. A height is refused by name. Checkpoint resolution skips anything at or below the fetch floor (their containers are legitimately retired).

## Verification without re-execution [DONE]

Third parties verify downloaded epochs with NO EVM: (1) stream SST diffs from genesis into a throwaway Firewood, root per block against headers; (2) recompute txRoot from verbatim containers; (3) reconstruct receipts from stored sections and recompute receiptsRoot; (4) chain parent-hash to a trusted anchor. ~5-10x cheaper than replay; (2) and (3) are embarrassingly parallel. A CHECK THAT CANNOT RUN IS A FAILURE, NEVER A PASS: both halves count the blocks they actually checked against the epoch's claim, framed walkers refuse short frames, and the anchor is mandatory (an anchorless verifier passes any internally consistent forgery). Both VM kinds route through the same seam; epoch 1's prev-hash is checked against the chain root before a byte is verified. SLAB-PARALLEL VERIFICATION: **TODO**.

## Execution: the VM seam, SAE, fetch on L1s [DONE]

ONE INTERFACE, TWO PER-KIND STRUCTS, both linked always; `--chain` picks at runtime. libevm's extras registry is process-global and panics on re-registration, which one-chain-per-process makes free. Registration is a one-shot switch; the precompile registry import is LOAD-BEARING (without it a genesis precompile config unmarshals to zero precompiles with no error). The genesis type is VM-neutral; snow.Context fields are execution inputs (the Warp precompile reads them).

THE FIREWOOD CACHE CLAMP: the node cache holds DECODED nodes and is sized AGAINST THE CONTAINER, an eighth of this container's `memory.max`, floored at 64MB, same rule as the exec state cache (a dir-size formula under-provisioned exactly during catch-up: measured 262 -> 48 mgas/s with 13GiB idle). The 3%-of-dir formula survives only with no cgroup, capped at 4GB. `EPOCHDB_FIREWOOD_CACHE` wins; below the floor refuses to start. THE ANON BUDGET: malloc is unevictable and page cache is not, so NO dynamic memory control loop. a fixed anon budget of ~30-40% of the box, and the majority of RAM deliberately unallocated, because on a serving box the page cache IS the read cache.

KNOWN UPSTREAM ISSUE (measured 2026-08-08, ffi v0.8.0): Firewood's Rust side grows ~2GB/h linear under heavy replay. Its 4GB node cache and RevisionsInMemory=2 do not explain it (verified applied, zero slope change); Go stays flat at GOMEMLIMIT. 12-point dataset in the wiki, upstream-issue grade. Operational mitigation while replaying: a guarded restart on measured fw starvation (>2.5s of the 10s exec window averaged over 10m, uptime >3h, serving, not mid-seal).

SAE (Helicon / ACP-194) is a whole new VM, not a coreth change. `header.Root` of N is the post-execution root of the last block N SETTLES; receipts commit at settlement; `GasUsed` is worst-case; the base fee comes from the deterministic gas clock, never the header. The cchain hooks are forked in (unexported upstream), metrics/warp dropped, the gas-target parse fallback hardened to a hard stop. The gas clock and per-height roots persist in a ring of 8192 crc'd slots fsynced with the exec head; crash walk-back matches OUR roots. Verifier: GasUsed identity per block, ring root + marker clock per settling header, monotonic markers, hard stop. Subnet-evm neutralization is structural (reports the transition never scheduled). WHY OUR JOIN EXISTS: upstream has NO C-chain state sync under SAE (measured: 24,881 leaf requests, 100% AppError). THE POST-HELICON BASE FEE IS DERIVED FROM EPOCH CONTENT: markers republish the clock at settlement points, per-tx gas comes from stored receipts, and op gas by subtraction from the worst-case identity, behind the `rpcVM` seam (`baseFees`/`baseFeeOf`), verified bit-for-bit against Fuji's public RPC at nine post-boundary heights. Every executing read path stamps the derived fee onto its header COPY (NoBaseFee disables checks, not the BASEFEE opcode). RISK: SAE Go APIs are unstable; pin exact tags.

FETCH ON A NON-PRIMARY SUBNET (ACP-77): TrackedSubnets is the L1's subnetID, never primary. Subnet validators enter the manager AFTER network construction (that is what makes PeerList gossip dial them). Zero matching peers at `info.peers` is normal; dial budget 90s. THE 95% CROSS-CHECK IS SUBNET-AWARE: ACP-77 weights are static registrations, so an L1 requires EXACT agreement between sources; the primary keeps 95%. The accepted frontier is the anchor (no checkpoints exist for subnets); the walk terminator is height 1 everywhere. THE BOOTSTRAP ANCHOR TALLY COUNTS SAMPLE DRAWS, NOT DISTINCT NODES: weighted sampling with replacement collapses onto few nodes on a stake-skewed L1 (mean 8.7 distinct of K=20 on a real 25-validator set), so chits credit draw counts, as live polls already do.

## Stored call frames [DONE: captured always, stored in the epoch]

CAPTURE EVERY CALL FRAME AT EXECUTION, not only value-bearing ones (user direction 2026-08-08: full frames roughly double the corpus and "it's not a big deal whatsoever, because we are offloading everything to S3"). A frame records kind, from, to/created, value, gas, gasUsed, input, output, error, depth, in execution order. The top-level frame is excluded: it IS the transaction. WITH ALL FRAMES STORED, "what counts as an internal transaction" becomes a READ-TIME FILTER, call-tracer debug methods become section reads (~40ms of re-execution vs tens of microseconds, ~1000x for sequential crawls), and every future index over call data becomes a byte transform. Frames are the one thing not derivable from stored bytes: net per-block write results do not decompose into calls.

- MECHANISM, BUILT: a tracer through the exec seam's two ApplyTransaction sites into the bucketed tail family `itx_NNNNN.log`, records in the epoch encoding VERBATIM (seal copies bytes, no EVM). Same NO-RECORDS rule as receipts: a tx-bearing block with no frames record is REFUSED at seal. THE TRACER IS ALWAYS ON, with no env var, because a corpus captured without frames has to be re-executed. Frames are stored in ENTER order with their depth, which is a pre-order DFS and therefore exactly what a call tracer replays.
- THE `itx` RECORD HAS TWO HALVES, like the receipts record. The FRAMES half is stored. The PARTICIPANTS half is one address group per transaction, positional, and it is the ADDRESS INDEX's input; it is dropped once the epoch is sealed (98 B/tx of tail, measured).
- SEAL DOES NO ECDSA RECOVERY, and this amends the address index's cost line below. `CaptureStart` hands over the top-level (from, to), where `to` is the CREATED CONTRACT ADDRESS for a creation, so the sender, the recipient, the created address and every frame participant are all in hand at execution, where the EVM has already recovered the sender. The ~90s per 8M-tx epoch is not spent.
- SAE IS THE ONE BLOCKING HOLE: `saexec.Execute` hardcodes `vm.Config{}` at this pin, so there is no tracer seam and a post-Helicon C-chain block captures nothing. The seal's no-records rule makes that LOUD rather than silent, which is the point; a forked seam is owed before mainnet C rebuilds to V2.
- MEASURED ON A REAL L1 WITH THE PRODUCTION CAPTURE (2026-08-09, 147,511 blocks / 230,589 txs replayed twice): 4.77 frames/tx, 138 B/frame, 656 B/tx of frames plus 98 B/tx of participants, and 24.2x at the ruled 4MB grouping. AND THE CAPTURE IS FREE ON WALL CLOCK: 66.7s with the tracer against 67.6s without, over the same corpus, i.e. inside run-to-run noise. An L1 is lighter than the C-chain's DeFi era, so both sets of numbers stand as the range.
- MEASURED ON THE C-CHAIN (2026-08-09, count tracer + a 768MB byte sample on the live mainnet replay at height ~43M, DeFi-dense era): 10.4 frames/tx sustained (49% STATICCALL, 30% CALL, 21% DELEGATECALL), 0.48 value-bearing frames/tx, 209 B/frame raw (input 55% of bytes, output 20%, fixed 25%). Tracer overhead invisible inside era noise, consistent with the 1.3-4% bench (the pinned libevm has only the legacy per-opcode EVMLogger; if hook-shaped tracing ships the cost collapses, and that upgrade is a format bump).
- COMPRESSION, zstd-19 on the sample, stable from 100MB to 768MB: 7.4x at 128KB raw groups, 8.7x at 512KB, 11.5x at 4MB, 13.9x whole-file bound. Mainnet upper bound ~3.3TB raw (this era is dense) -> ~285GB at 4MB grouping.
- THE RULED GROUPING IS 4MB RAW (user ruling 2026-08-09): ~370KB compressed, ~11 groups per casfs chunk, so a frame SELECT through /sql pays one chunk GET plus one ~4MB decode (~5-10ms). The ~45MB-raw variant approaching the whole-file bound was REJECTED because frames must stay query-adequate: archive-only access is not the contract. A dict retest is owed if small groups are ever chosen (the first test trained on slices of the same file and hurt).
- DETERMINISM PINS, all format commitments: the capture rule is frozen like the zstd version; DELEGATECALL frames carry the parent's value (excluded by read-time transfer filters, never by capture); documented holes are SELFDESTRUCT (no hook at this pin), coreth atomic txs, and subnet-evm's nativeMinter. Frames follow execution exactly, so a config that would change them diverges the state root first.

## The index set and the SQL door [IN PROGRESS: the door is BUILT, and the first TWO index families are in the format]

TWO API SURFACES AND NO MORE (user ruling 2026-08-09, verbatim): "instead of like having this zoo of methods, we're like, hey, there're two API methods: one /rpc, one /sql. Everything you ever need is in there." The SQL door replaces the REST indexing API that was on the table; it does NOT replace the indexes, which make point queries fast. DELIBERATELY NOT AN ANALYTICS SYSTEM (user ruling 2026-08-09): no columnar sections, no duplication. Serious analytics is an external ClickHouse fed by exports; our sections are row-shaped; a whole-history column scan is minutes, said plainly.

THE BUILD ORDER (user direction 2026-08-09): expose /sql in the MOST PRIMITIVE form over the existing indexes, run real filters against it, and let what is missing drive the index set and the frame fields before the V2 format commits.

THE PRIMITIVE DOOR IS BUILT (`rpc/sql.go`): `POST /sql` and `GET /sql/schema` inside serve, three read-only tables (`blocks`, `txs`, `logs`) over the header section, the fp48 tx index and the log posting lists, no new bytes on disk. The engine parses, plans and filters; the door takes the narrowing conjuncts and the ORDER BY off the analyzed plan and hands the narrowing to the tables as a HINT, so the engine's own Filter node still decides what a row means (the safe side of the PreciseMatch trap). Row budget, deadline, keyset-only pagination and index-order-or-refuse are enforced there.

PARAMETERS AND THE PLAN CACHE ARE BUILT (user-approved 2026-08-09). The body is sniffed: a JSON object is `{"query": "... ? ...", "params": [...]}`, anything else is the raw SQL string the door always took. Values go through the engine's own BINDVAR path (`plan.ApplyBindings`), never string substitution. A query then splits in two, and the split is the whole safety argument: the ANALYZED PLAN plus the ORDER BY rewrite depend only on the placeholder TEXT and are cached in a 64-entry LRU keyed on it; the NARROWING reads the bound literals and is redone on every execution. Caching the narrowing too would be a silent wrong answer, the same shape reading the previous call's address. The cached plan is immutable and shared; binding returns a private tree, so concurrent requests never touch one another.

THE HOT-TAIL LOG INDEX IS BUILT (`state/taillogidx.go`), and it is the first hot-tail counterpart of any index family. It is an in-memory posting list of the SAME SHAPE as the epoch sections (log address or topic value -> ascending block numbers, a candidate superset), over the UNSEALED blocks only. It catches itself up from the raw `logs` family on first use and on every later query, folding in only the blocks captured since; the seal drops everything at or below the sealed end, because from that moment the epoch answers it and the raw records are unlinked. Both readers use it: `eth_getLogs` and the `/sql` logs table now answer over sealed plus tail seamlessly, and a NARROWED `/sql` log query no longer carries the 10,000-block unsealed cap (an unnarrowed range still does, having nothing to narrow with). Its ceiling is the logs family's own max block, never the serving head, because a header is appended before its logs record; above that ceiling the caller falls back to the per-block walk, so no block is ever silently skipped. MEMORY: (key, block) pairs, measured 2.39 pairs and 21 bytes per transaction on a mainnet L1 tail, and the tail is at most ONE EPOCH, so ~5MB at the 250k-tx first epoch and ~170MB at the 8M-tx ceiling.

ALL DATA MUST ALWAYS BE SAFE (user ruling 2026-08-09), as it applies here: the hot-tail index is PURELY DERIVED STATE. It opens nothing for writing, deletes nothing, truncates nothing, and never reads below the retirement floor. Its invariant is that it is EXACT over (floor, through]. Any inconsistency (an unreadable record, a decode failure) stops the catch-up and REFUSES THE QUERY LOUDLY; it never serves a tail with a hole in it, and the blocks it could not fold in are answered by the per-block walk, which fails on the same damage rather than skipping it. The master copy of the ruling lives with the migration work.

WHAT THE FIRST REAL QUERIES MEASURED (2026-08-09, a mainnet L1 corpus of 147,511 blocks, 120k txs sealed into two epochs plus a raw tail; full log in the devlog). These are the design inputs for the V2 index set:
- WHAT ALREADY WORKS, at 25-50ms for ten rows anywhere in the sealed range: newest-first and oldest-first event lists narrowed by log address, by topic0, by a topic VALUE at any position, or by all three; tx-by-hash and block-by-hash point lookups (9-28ms); keyset pagination flat at ~53ms/page over ten pages.
- THE ADDRESS INDEX IS THE FIRST THING EVERY QUERY WANTED. `WHERE from_addr = X` has no index at all: it decodes every container and recovers every sender, measured 12,700 rows/s, so wallet history is not answerable at any budget. This is family 1 in the list below and the measurement confirms its place.
- THE POSTING LISTS NAME BLOCKS, NOT LOG POSITIONS. Counting one token's 4,929 transfers in a 10,000-block window scanned ~25,000 log rows, because every log of every candidate block is read: 5.1x amplification on a chain where the token is in most blocks. A posting list at (block, log ordinal) granularity, or a per-block log fence, is worth its bytes.
- THE UNSEALED TAIL HAD NO LOG INDEX, and now it does (above). "The latest N events of X" is the main use case (user, 2026-08-09: "mostly ones that just happened", historical queries are rare), and it was the one the sealed-only posting lists could not answer. Every OTHER index family still needs its own hot-tail counterpart.
- WHERE THE TIME ACTUALLY GOES, measured 2026-08-10 on the grotto corpus (147,511 blocks, 85,996 sealed into two epochs, a 61,515-block / 110,555-tx tail), medians of 21 runs, warm: for "latest 10 events of an address" over the whole chain, 20.3ms total of which parse+analyze is 160us, section read plus decompress for the ten rows that matter is 364us, and **20.95ms is CANDIDATE GATHERING**: 47,075 candidate blocks materialised to answer a LIMIT 10. Tx-by-hash is 162us total (62us analyze, 99us read). The plan cache takes analyze to 600ns, so it removes 1-40% of a query depending on shape and all of it on the cheap ones. DECOMPRESS DOES NOT DOMINATE (1.8% of the hot query), so a decompressed-section LRU was measured and NOT built. The gather is the whole cost, and it is exactly what family 1 and tx-granular postings are for; bounding the range to the tail (`block_number > sealedEnd`) already cuts the same query to 2.2ms. Against the pre-index path the tail alone went from a 24.6ms per-block scan of 61,515 blocks to a 1.87ms index lookup.
- NO TIME DIMENSION ANYWHERE: `WHERE timestamp > ...` is a header scan. The metrics family's per-hour rows are what answers it.
- AGGREGATES ARE SCANS BY CONSTRUCTION: COUNT over a narrowed range costs the scan it counts. Cumulative counters (family 4) are the only thing that makes a count cheap.
- JOINS DEGENERATE: joining `logs` to `blocks` on the height blew a 20,000-row budget, because with no declared index the engine cannot do a point lookup on the join key. Declaring `sql.IndexAddressable` on the height column is the fix, and it is engine wiring, not new bytes.
- TWO ENGINE TRAPS, RECORDED: every column reference in an analyzed plan carries the query's ALIAS, not the table name, so anything keyed on the table name must resolve aliases first; and `LEFT`/`SUBSTRING`/`LENGTH` over a binary column go through a character set and return mangled bytes (`HEX` is correct under binary collation). Method-selector filtering therefore cannot be done in SQL today.

THE INVESTIGATION BASIS (2026-08-05, Glacier usage CSV + OpenAPI + a measured epoch): most of Glacier's EVM surface is RPC in a costume; existing log posting lists already serve ERC20/721/1155 transfer lists and ICM messageId lookups with zero new bytes. What remains needs FIVE index families, each a deterministic epoch section plus a cook-maintained hot-tail counterpart:
1. THE ADDRESS INDEX **BUILT** (`addridx`): address -> EF posting lists over epoch-relative TX ORDINALS. Wallet history, the single biggest workload (528M req/6mo on Glacier), ~+1.2-1.4% of corpus. Population is tx from/to plus created addresses plus FRAME PARTICIPANTS: without frames, an address only ever paid by a contract is invisible, a silent false negative, which is one reason frames precede this index. It reuses the log index's section layout with an empty topic table, so ONE reader searches both. Sender recovery at seal is NOT needed after all (see frames above). STILL OWED: the 16-bit-per-key bloom in front of it, so a miss costs a binary search rather than one heap probe; and the cook-maintained hot-tail counterpart.
2. HOLDINGS: holder -> token set, THE LIST ONLY, no amounts, no time dimension (user ruling 2026-08-06: balances reconstruct via eth_call, and zero balances drop out at read time). +0.36% measured. Cross-epoch dedup rejected (seal reads only local raw and markers).
3. NFT OWNER: (collection, tokenId) -> (owner, block), last-write-wins descent. +0.12%.
4. CUMULATIVE TX COUNT **BUILT** (`txcum`): one u32 per block, epoch-relative, resident. +0.05%. It is what turns a tx ordinal back into (block, index), and therefore what lets the address index be tx-granular instead of paying the log index's measured 5.1x block-granular amplification.
5. THE METRICS FAMILY: per-hour aggregate rows (~4MB corpus-wide, resident), per-hour address-id bitmaps, and a GLOBAL ADDRESS -> u32 REGISTRY in first-appearance order (2.18GB, +0.29%). KNOWN DIVERGENCE: Glacier's activeAddresses sums per-source distincts; we implement the documented union and say so. THE REGISTRY IS THE WEAKEST JOINT AND ITS FALLBACK IS PART OF THE DESIGN (user concurrence 2026-08-09): first-appearance ordering is the ONE cross-epoch dependency in an otherwise per-epoch-pure format. It serializes migration of that section; a registry bug in epoch K poisons every later epoch's compressed keys. If it fights back: full 20-byte keys everywhere plus per-epoch metrics summed at read, losing only O(1) cumulativeAddresses and none of the queries.

Plus one retrofit: a RESIDENT FENCE over every searchable table (~64KB/epoch), which turns a cold binary search over S3 into one resident lookup plus one ranged read.

THE ENGINE IS go-mysql-server, EMBEDDED, PURE GO (source-verified 2026-08-09 with measured probes):
- The two gates pass: ordered index scans deliver 5 row pulls from a 1M-entry posting list PROVIDED the ORDER BY is a positional prefix of the index expressions, so THE DOOR REWRITES THE ORDER BY (~40 LOC, semantics-preserving under the pinned equality). Snapshot capture is table resolution, once per query, composing with the epoch set's atomic snapshots lock-free.
- PAGINATION IS KEYSET ONLY: OFFSET is O(n) and heap-drains, so the door caps or rejects it.
- TYPES: u256 as VARBINARY(32) big-endian (byte order IS numeric order; DECIMAL tops out at 65 digits), addresses VARBINARY(20), never BINARY(n) (NUL padding breaks equality). Custom aggregates require overwriting the exported `planbuilder.IsAggregateFunc` var, the engine's declared extension point and its most fragile joint: PIN THE ENGINE VERSION like the zstd CLI.
- CORRECTNESS TRAP, recorded: `PreciseMatch() == true` makes the engine delete its own Filter node; a backend that fudges range bounds returns wrong rows silently.
- WIRE: the HTTP `/sql` handler is what ships. The MySQL protocol server is four statements (DBeaver, Grafana, every client) and stays unbuilt until someone asks. No build tag is needed: v0.20.0 is pure Go.
- ONE PROCESS, ONE CHAIN, /sql INSIDE serve (user ruling 2026-08-09). `--no-follow`/`--no-sql` split the roles over the same files when isolation is wanted. RPC never routes through SQL.
- THE SCHEMA IS NOT A VERSIONED EXTERNAL CONTRACT (user ruling 2026-08-09): table and column names are an internal data contract. External discovery is a PUBLISHED SCHEMA FILE served by the node (llms.txt or whatever the standard settles to). A schema change updates the file; a client that starts getting errors re-reads it. No deprecation cycle, no compatibility machinery, deliberately: the consumers are agents and scripts that can re-read a description.
- EVERY QUERY RUNS UNDER A ROW-SCAN BUDGET (user ruling 2026-08-09): ~100 rows scanned unless the query says otherwise, plus a per-query timeout. The budget bounds the hostile or accidental query, which keyset pagination alone does not: a whole-history scan competes for exactly the page cache the memory design defends.

## Epoch versioning: V1 to V2 [IN PROGRESS: this is the current work]

V1 IS FORMAT v6 (17 sections). V2 IS FORMAT v7 (21 sections): the frames sections plus the address index and the cumulative tx count. A v7 reader STILL READS v6 (the footer's size follows its section count, so `OpenEpoch` probes v7 then v6, and `Epoch.Version` carries the result); writers only ever write v7. It is also the bump at which migrations START EXISTING (user direction 2026-08-09; the earlier "no migrations until adoption" rule is amended by the same authority that set it).

- A MIGRATION IS A DETERMINISTIC PER-EPOCH TRANSFORM v(N) -> v(N+1); chained migrations compose. SEALED EPOCHS ONLY: the unsealed tail is dumped and recooked, never migrated.
- ON STARTUP, A V2 NODE OPENING A V1 CORPUS CONVERTS IT IN PLACE, walking the epochs FROM GENESIS UPWARD (user direction 2026-08-09). The format forces the order: epoch K's footer embeds K-1's NAME, and conversion changes the name, so K cannot be finalized until K-1's new name exists. Section recompute can parallelize per epoch. The footer re-link is the sequential last step per epoch, genesis-first.
- TWO COST CLASSES, and the split is the whole point of storing frames. IO-CLASS: anything derivable from stored bytes; stream, recompute, rewrite, hours of sequential IO. EXECUTION-CLASS: exactly one ever, the V1->V2 frames backfill itself, which replays each epoch's blocks from its own bodies with state streamed forward from the SST sections, no network, no full Firewood, slab-parallel by epoch range ACROSS MACHINES if wall clock demands it. After frames exist, every migration is IO-class.
- BYTE-IDENTITY SURVIVES MIGRATION: two independent migrators emit identical artifacts, so a consumer migrates locally and verifies against the publisher's new head hash without re-downloading. The corpus gets new hashes and a new chain of names; old artifacts become garbage-collectable. The migration tool's version is pinned exactly like the zstd CLI.
- THE PROVING GROUND IS A SMALL CHAIN FIRST (user direction 2026-08-09): a mainnet L1 with over ~250k txs (one sealed epoch) and preferably over 750k (two epochs, which is what actually exercises the genesis-first re-link). Define one or two indexes, bump to V2, prove capture, seal, startup conversion and /sql on it end to end. Then the bigger chains, mainnet last, freshly synced with capture on (~2 weeks serial at the measured pace) or backfilled from its V1 epochs, whichever the test chain proves cheaper.
- THE V1 CORPORA ARE VALIDATION, NOT PRODUCT (user, 2026-08-09): they proved fetch, exec, seal, join, serve and verify at scale ("good confirmation that everything is good, but for us it's kind of trash because we have to re-execute everything anyway"). They stay frozen under their S3 prefixes and on the stopped fleet's disks.

## RPC surface [DONE]

Full parity with a coreth node across eth/web3/net/txpool/debug minus the refusal classes (user ruling 2026-08-01: "whatever API methods are not implemented, implement them"). 78 methods served, filters exist, WS subscriptions FIRE (newHeads/logs/newAcceptedTransactions off the serving head; newPendingTransactions installs and never fires, correctly, since no mempool means nothing is pending).

Notable rules, each the product of a found bug. `debug_getModifiedAccountsBy*` at any height straight from the write capture (THE DIFFERENTIATOR; epoch-only ranges get a clean error). Override objects on call/estimate/traceCall honoured field-for-field (silently ignoring them looks like it worked). `BlockNumberOrHash` handled once in the shared resolver. JSON-RPC BATCHING with the spec's semantics and geth's caps (1000 requests, 10MiB body, both refused BY NAME); elements run sequentially in one goroutine. `eth_getLogs` takes the `blockHash` form; an unknown hash is an ERROR naming it, never `[]`. Block marshalling through each VM's own `PostRPCMarshal` (a hand-copied subset silently dropped later-fork fields); subnet-evm's empty extData fields are OMITTED rather than emitted empty. Fee answers are real numbers on both kinds: `eth_maxPriorityFeePerGas` is price MINUS base fee floored at zero; `eth_feeHistory`'s trailing entry below the head is read off block newest+1 exactly; only a head-ending range is projected, through each VM's own estimator, assuming the unbuilt block lands at the head's own timestamp (elapsed time only lowers the fee, so the answer is an upper bound, the safe direction). RE-EXECUTION MUST NOT SWALLOW STATEDB READ ERRORS: geth's `getDeleteStateObject` hands back an empty account; the fix returns the statedb error in preference to the tx error, and the tracers take the same band selection, so a trace of the uncooked tail is a cook-lag refusal, not a plausible fiction over zeroed state. NULL MEANS "NOT ON THIS CHAIN", NEVER "I COULD NOT READ IT" (2026-08-05 audit): a broken tx index, an unreadable candidate container, an unrecoverable sender, a nil header are all ERRORS now, on every path that marshals them, and subscriptions end the connection rather than skip a promised notification.

THE REFUSAL CLASSES, named -32000/-32601 with a reason, never a bare not-found: (1) NO TRIES (`eth_getProof`, dump/range/intermediateRoots): genuinely unimplementable, Firewood is verify-only; (2) NO PREIMAGE TABLE; (3) NO MEMPOOL / KEYSTORE / MINER / NODE-OPS, refused by namespace; (4) NO RETAINED BAD BLOCKS (a bad block halts the executor); (5) `debug_traceChain`, a wire shape we will not half-match, pointed at traceBlockByNumber. `avax_*` atomic methods are unindexed and out of scope.

THE READ SERVER EXECUTES, so it has its own per-VM seam (four execution entry points plus the fee answers): calling coreth's core on a subnet-evm chain is a segfault, not a wrong answer. `applyUpgrades` takes the parent timestamp BY VALUE (a nil parent reads as "never forked" and re-activates every precompile). subnet-evm's fee window in `header.Extra` is parsed by its own estimator now (feeHistory needed it). Every executing read path stamps the derived base fee onto its header copy; a caller's `blockOverrides.baseFee` still wins.

- SEALED SIZES: 409-592 B/tx by era; whole-epoch compression 3.1-4.2x; full mainnet V1 projects 0.59-0.69TB; V2 adds ~285GB of frames at the ruled grouping plus ~2-3% of index families.
- FRAMES: 10.4 frames/tx and 209 B/frame raw at 7.4-13.9x by grouping on the C-chain's DeFi-dense era (upper bound); 4.77 frames/tx and 138 B/frame at 24.2x on a real L1, plus 98 B/tx of participants that never leave the tail. Both measured 2026-08-09.
- STATE VS TRIE: Firewood is ~86% merkle overhead over flat state. Full-mainnet local budget: Firewood 130-157GB + tail + ~7.7GB warm indexes + chunk cache.
- SEAL PEAK: ~1084 B/block. Bucket-log open: ~182 B/block RAM, paid by every opener. fetch.Store: ~250 B/block resident (byID is unbounded within a process; known, deferred).
- COOK WRITE AMPLIFICATION, accepted (user 2026-07-31: "that's fine"): the 60s cook rewrites the current bucket's sorted file wholesale, ~100-150GB/day of SSD at C-chain tip pace, a decade inside NVMe endurance. LSM-style deltas deliberately unbuilt.
- REPLAY WALL CLOCK, measured on the i7i.2xlarge: mainnet from genesis is ~2 weeks serial at cycle-average ~1,100-1,300 tx/s beside six co-tenant chains; the first 500M txs took 3.3 days.

## The fleet memory budget [DONE, dormant while the fleet is stopped]

A BOX HAS ONE MEMORY BUDGET AND IT IS NOT THE SUM OF THE CONTAINERS' (ruling 2026-08-05, forced by two outages in one day; the requirement is SSHD ALWAYS RUNS). Three parts, no accounting system. THE BOX: a systemd slice (`ops/epochdb.slice`, docker `cgroup-parent`) with `MemoryHigh` ~70% of RAM as the working-set target (the kernel reclaims the slice's own file pages first, so the fleet degrades by slowing) and `MemoryMax` ~85% as the backstop whose failure is one container's, not the box's. THE BIGGEST EVENT: a frontier build (21.54GiB peak measured) is gated by a cross-process flock queue on `EPOCHDB_HEAVY_SLOTS` slot files (default 1) in the shared cache dir; the kernel frees a dead holder's slot. THE MEMBER: each process derives its grants from its own container ceiling: GOMEMLIMIT = 7/10 (a third of the container is invisible to Go: cgo cache, mappings, zstd), exec state cache = 1/8, Firewood node cache = 1/8. 82.5% declared; the residue covers what nobody sizes. Explicit env always wins. What the operator watches: `memory.current` vs `high`, `memory.events`, PSI `some avg60`, and `free -g` available as the sshd reserve.

## Operations

- BUILD/RUN: `go run ./cmd/epochdb serve [--data <dir>] [--network mainnet] [--chain C|<blockchainID>] [--port] [--verify] [--tip-override <containerID>] [--pprof ...]`. ALWAYS PASS `--network mainnet`; the default is fuji.
- A NEW NODE: export `EPOCHDB_S3_*` for the publisher's bucket and run serve on an empty dir. It joins, frontier-builds and follows by itself. `--verify` re-verifies everything first.
- CONFIG IS ENVIRONMENT ONLY: `EPOCHDB_S3_{ENDPOINT,BUCKET,ACCESS_KEY,SECRET_KEY,PREFIX,REGION}`, `EPOCHDB_CACHE_{MIN_FREE,MAX_AGE,DIR}`, `EPOCHDB_FETCH_CONCURRENCY`, `EPOCHDB_FIREWOOD_CACHE`, `EPOCHDB_HEAVY_SLOTS`, `EPOCHDB_NEW_CHAIN`, `GOMEMLIMIT`, `GOGC`. The measurement-only `EPOCHDB_COUNT_FRAMES` and `EPOCHDB_FRAME_SAMPLE_MB` are GONE with the tracers that read them. Credentials: static keys win; unset keys mean the AWS SDK default chain (SSO, instance role), resolved per request; the HTTP client and SigV4 signer stay hand-rolled.
- MEMORY DEFAULTS IN THE BINARY: GOGC=50 (the pacer optimises the wrong resource on a page-cache workload; 40 is set explicitly on the biggest chain), GODEBUG=madvdontneed=1 baked into the image (MADV_FREE ratchets RSS to the high-water mark; docker REPLACES GODEBUG wholesale, so the binary warns when it is missing).
- PACKAGING: per-commit images ARE the release channel (user ruling 2026-08-01). Every push to main runs vet+test, builds and pushes `ghcr.io/containerman17/epochdb` as `latest` and `sha-<short>`. cgo is mandatory (firewood static lib), runtime layer `distroless/cc-debian13`, the pinned zstd CLI built statically into the image with its version sed'd out of `state/epoch.go`.
- OWNERSHIP: serve owns its data dir (flock-enforced); read-only openers cohabit freely. Long stages must be setsid-detached. `du` lies on WSL2.
- NEVER MINT CLOUD CREDENTIALS FOR A TEST; reuse what exists. MinIO for S3 tests.
- THE TOKYO BOX (i7i.2xlarge, 61.78GiB, 1.8TB): fleet STOPPED 2026-08-09, data dirs intact, crons paused; see the wiki for access and the deployment shape.
